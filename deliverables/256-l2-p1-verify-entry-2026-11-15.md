## 1. 为什么必须是这个结构

### 1.1 `prepare` 的 REFRESH 不是判决

`rbfeatctl l2 enable`（`src/ctl/rbfeatctl.c:252-272`）在写 `Flags|=4` 之后**无条件**发一次 `RB2_IOCTL_REFRESH`（`:271`）。REFRESH 是控制面开路（`rbL2.c:850`），它会把容器打开。所以 prepare 结束时 `state=1` **不能**归因于 P1 的数据路径放行 —— 只有跨一次新引导（`s_VolId` 归零、容器关闭）后的**首个纯数据面读**才是干净判据。

### 1.2 `verify` 的顺序就是判据

`RbL2IdxUnseal` 在打开容器时会写 `.idx` 的 Magic=0。因此 verify 的**第 0 段必须在读 `D:\rbc-l2-load.bin` 之前**完成：

```
0) baseline / 重启证据 / .idx 大小+mtime+Count+前 32 B hex / pwr: 行 / LastCleanShutdown / pre stats
1) 唯一一次数据读：FILE_FLAG_NO_BUFFERING 读 D:\rbc-l2-load.bin
2) post stats + 五个增量
3) 四判决 + 证据 JSON 落盘
```

第 0 段读的都是 `C:\ProgramData` 与 `C:\` 上的小文件（C 是 bypass 卷），以及 `rbfeatctl stats` 的 IOCTL —— **都不会触发被加速卷 D 的数据路径**。

### 1.3 严格只读边界

verify 全程**不发 refresh、不调 `l2 enable/disable`、不写注册表、不删文件、不重启、不回滚**。只写两样自己的产物：日志 `l2-p1-verify-<utc>.log` 和证据 `l2-p1-verdict-<utc>.json`（后者含 `.idx` 前 32 B 的 hex，因此随后跑 rollback 删掉 `.idx` 也不会消灭证据）。

**刻意不自动回滚**：容器/索引是核心取证对象，自动删除会剥夺复核机会，且 `RB-l2-p0c-rollback.cmd` 末尾有 `pause`，从子进程调用会挂住。收尾保留为独立一步（第三次 UAC）。

## 2. 前置闸（fail-closed，空匹配集一律不 PASS）

`l2_p1_prepare.py::preflight()` 任一不符即 `exit 2`，**不改任何状态**：

1. 提权断言（`--check` 只读模式下降为 WARN，便于非提权预检）
2. 仓库根定位（逐级上溯找 `AGENTS.md`）
3. **四源同哈希**：`dist/*.sha256` sidecar + `deploy.ps1` + `verify_deploy_signature.ps1` 各取首个 64-hex，三者必须相等；文件缺失/无 64-hex ⇒ FAIL
4. `dist` 与 `live` 的真实 SHA256 必须等于上述基线
5. `Get-AuthenticodeSignature(dist) == Valid`（pwsh 子进程，失败原因打印）
6. `Features\Flags == 0`（否则先跑 rollback）
7. 容器 `C:\RAMBoostL2c.bin`、索引 `C:\RAMBoostL2c.idx`、负载 `D:\rbc-l2-load.bin` **三者必须不存在**（夹具 preflight 语义）
8. `C:` 剩余 ≥ 3 GiB（2 GiB 容器）
9. `rbfeatctl vols` 输出必须含 `D: accelerated`（`--check` 非提权时跳过并标 WARN）
10. 本地时间必须早于 **2026-11-16 09:30**（否则拒绝打开 `Flags=4` 窗口，避免与观察期巡检冲突）

`l2_p1_verify.py` 的前置：baseline 必须存在且 `phase=prepared`；`uptime_ms` 相对 prepare 显著变小 **或** `LastBootUpTime` 晚于 prepare ⇒ 判定「确实重启过」；否则四个判决一律 **INCONCLUSIVE**（R7：没有触发证据不算验证）。

## 3. 四判决口径

| 判决 | PASS / 结论 | 关键陷阱 |
|---|---|---|
| **P1** 数据路径首次开容器 | `pre.state==0` ∧ `dCoreMiss>0` ∧ `post.state==1` ∧ `dL2Miss>0` | `pre.state!=0` 或 `dCoreMiss==0` ⇒ INCONCLUSIVE，不写成驱动缺陷 |
| **P2** 电源 IRP 可见性 | DEVICE-only ⇒ **证实** `250` §3 的「SystemPowerState 分支是死代码」；出现 SYSTEM ⇒ **推翻**该推断需另查；零 `pwr:` 行 ⇒ `IRP_MJ_POWER` 根本没到本设备对象 | 本次 20:05 关机时内核仍是旧映像，零行属预期；这次窗口的关机才有新驱动 |
| **B2** 关机索引定稿 | `.idx` ≥32 B ⇒ H5 执行过（B2-a 不再复现）；仍 4 B ⇒ B2-a 复现 | 必须在读 D: 之前取；读会改 `.idx` |
| **J6** 跨引导命中 | `dL2Hits>0` 只是**命中证据**，不是逐字节正确性证明；0 时写 NOT ESTABLISHED（空索引结构性不可满足） | 不得为拿 PASS 放宽判据 |

`pwr:` 打点解码（`rbmsg.c` 的 `pack` 编码）：

```
pack = (MinorFunction & 0xF)<<28 | (ShutdownType & 0xFFF)<<16 | State & 0xFFFF
minor: 0 QUERY_POWER / 1 WAIT_WAKE / 2 SET_POWER / 3 POWER_SEQUENCE
ShutdownType: 2 Sleep / 3 Hibernate / 4 Shutdown / 5 ShutdownReset / 6 ShutdownOff
```

日志中 `SYSTEM power irp` / `DEVICE power irp` 字样区分 `Type`。扫描范围为所有 `driver-*.log` 中时间 ≥ `utc_prepare − 120 s` 的行（跨日重启也能覆盖）。

`LastCleanShutdown` 只作 INFO，不进判据 —— 它每次开机被 `rbdriver.c:295` 清零（`250` 已作废过这条证据）。
