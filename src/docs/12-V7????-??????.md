# 12 · V7 架构定稿：稳定性、可配置颗粒度与一键部署

> 本章为 V7 的**权威定稿**。若早期章节（如 `00-总览.md`、`10-竞品对比与优化.md`）中关于
> “分页/缓存 I/O 默认参与加速、普通缓冲应用可命中”的表述与本章冲突，**以本章为准**。

## 1. 为什么 V7 改为“仅非缓冲 I/O 加速”

V7 在真机（Win11 Pro 26H2，多轮 diskspd + 内存压力）反复出现内核崩溃，主线为
`KERNEL_SECURITY_CHECK_FAILURE (0x139)` 与 `IRQL_NOT_LESS_OR_EQUAL (0xA)`。通过多份完整内核转储
（含特殊池）逐条定位，确认了**结构性根因**：

- 旧设计在文件系统层（minifilter，位于缓存管理器 Cc 之上）**自完成 I/O**，并对同一文件
  另开一个 `FILE_NO_INTERMEDIATE_BUFFERING`（非缓存）句柄做回写/补读。
- 对同一个文件由此出现**两个不一致的写者/视图**：系统缓存管理器（Cc）的缓存视图，与我方
  经第二句柄的非缓存视图。Cc 在延迟写（`CcWriteBehind`）、卷检查点（`NtfsCheckpointAllVolumes`）
  释放/复用 BCB 时，其内嵌 `ERESOURCE` 与系统资源链表已被这种非一致双写污染，触发
  `FAST_FAIL_CORRUPT_LIST_ENTRY`（0x139 arg1=3）。
- 这类损坏发生在 **Cc 内部状态**，并非我方缓冲区越界，因此**特殊池不会在越界点拦截**，
  且总是延迟到系统后台线程才爆发——这正是“跑一会儿才蓝屏、日志来不及写”的原因。

**结论**：在文件系统层用“自完成 + 第二句柄”去加速**缓存方式（cached）I/O**，无法与 Cc 保持
单一一致视图，本质不安全。PrimoCache 工作在更靠下的**块/存储层**（Cc 与文件系统之下），天然只有
单一视图，不会自完成 Cc 的分页 I/O。

因此 V7 定稿做了清晰的边界切分：

| I/O 类型 | V7 是否加速 | 说明 |
|---|---|---|
| **非缓冲 I/O**（`FILE_NO_INTERMEDIATE_BUFFERING` / `FILE_FLAG_NO_BUFFERING`） | ✅ 读+写 | 大型游戏/流式加载、专业拷贝与备份工具、diskspd `-h` 等；不经 Cc，安全 |
| 缓存方式（cached）普通应用 I/O | ❌（本版透明旁路） | 需块/存储层方案，列入 V8 路线图 |
| 分页 I/O（`IRP_PAGING_IO` / `IRP_SYNCHRONOUS_PAGING_IO`） | ❌ 透明旁路 | Cc 自身的回写/回读，绝不自完成、不吸收 |
| NTFS 元数据、系统卷关键路径 | ❌ 透明旁路 | 避免污染元数据 BCB |
| 压缩 / 稀疏 / EFS 加密文件 | ❌ 透明旁路 | NTFS 非缓存 I/O 不支持这些属性，且涉及密文一致性 |

> 收益：**彻底消除与 Cc 的双写冲突**，真机稳定性显著提升；非缓冲工作负载（正是大块顺序/高带宽
> 场景）可获得内存级读命中。代价：普通走系统缓存的软件在 V7 不加速，待 V8 块层版本补齐。

## 2. 三道门控（一致性保证）

“仅非缓冲”由同一判定 `FileObject->Flags & FO_NO_INTERMEDIATE_BUFFERING` 在三处统一把关：

1. **PostCreate `RBStreamSetup`（`driver/flt_io.c`）**：在任何 `FltCreateFileEx`（第二句柄）、
   `rb_stream_create`（引擎流，内含 64 个 `ERESOURCE`）、`FltSetStreamContext` **之前**判定；
   非非缓冲打开直接 `FLT_POSTOP_FINISHED_PROCESSING`。
2. **PreRead `RBPreRead`**：非非缓冲、分页 I/O 一律 `FLT_PREOP_SUCCESS_NO_CALLBACK`。
3. **PreWrite `RBPreWrite`**：同上，并删除旧的“吸收分页/缓冲写”分支。

由此，缓存方式打开的文件做到**零第二句柄、零引擎流、零 ERESOURCE**，从源头不与 Cc 产生交集。

## 3. 可配置“加速颗粒度”（缓存块大小）

对标 PrimoCache，V7 支持运行时选择缓存块大小：**4K / 8K / 16K / 32K / 64K / 128K**。

- **几何映射**：`chunk = block × 16`（每 chunk 16 个子块、uint16 位图保持不变）：

  | 块大小 | chunk 大小 | | 块大小 | chunk 大小 |
  |---|---|---|---|---|
  | 4K | 64K | | 32K | 512K |
  | 8K | 128K | | 64K | 1M |
  | 16K | 256K | | 128K | 2M |

- 缓存核心的几何（block/chunk、位移、掩码、字节计数、锁分片）已**全部运行时化**（原先为编译期
  宏），并新增 `test_geom` 对 4/8/32/128K 做“写后读命中一致、脏=0”回归，全部通过。
- **设置方式**：
  - WPF：内存设置页「加速颗粒度」下拉；
  - CLI：`ramboostctl set block=<KB>`（4/8/16/32/64/128），`ramboostctl get-config` 查看；
  - Web：控制台「缓存块大小」下拉。
- **生效时机（务必注意）**：块大小在**引擎创建时确定**。修改后**随下次驱动加载生效**
  （`fltmc unload` → `fltmc load`，或重启）。本版**不做**运行时热切换——热切换需
  “回写脏=0 → 分离卷 → 销毁/重建引擎”，引擎被在途流与线程引用，强重建易产生释放后使用（UAF），
  故不冒险。切换前请确保脏数据已回写。
- 协议：`RB_CONFIG` 尾部追加 `uint32 BlockSize`（字节，默认 4096），不改动既有字段偏移；
  注册表持久化包含 `BlockSize`，非法值回退 4096。

**颗粒度选择建议**：小块随机为主（游戏素材、大量小文件）选 4K/8K，命中率高；大块顺序、
高带宽流传输选 64K/128K，元数据开销小、吞吐高。

## 4. 一键部署（硬件自适应）

`v6work/deploy.ps1` 串起完整流程，硬件自适应、不硬编码路径，支持重启后幂等续跑：

```
# 运行已编译好的产物（run-only）
powershell -NoProfile -ExecutionPolicy Bypass -File deploy.ps1
# 从源码编译后再部署（需 VS Build Tools + WDK + dotnet）
powershell -NoProfile -ExecutionPolicy Bypass -File deploy.ps1 -Build
# 开启测试签名重启后续跑
powershell -NoProfile -ExecutionPolicy Bypass -File deploy.ps1 -Resume
```

流程：单次 UAC 提权 →（`-Build`：用 vswhere/常见路径自动探测 MSVC，设置 WDK NuGet 包路径，
编译驱动/控制/WPF）→ 自签（100 年 RSA4096，导入 Root/TrustedPublisher）+ 开启测试签名
（首次需重启，状态写入 `STATE.json`，`-Resume` 续跑）→ 复制驱动、建服务、写 minifilter 实例
注册表、`fltmc load`（默认不附加任何卷）→ 启动 WPF 控制台由用户运行时选盘（免重启）。

换机时：自动按本机物理内存与卷布局适配，无需改配置；系统卷默认不自动附加，更安全。

## 5. 已证实的崩溃 → 修复台账

下列问题均有 dump / 转储头 / 反汇编证据（详见 `BUILD_TEST_REPORT.md` §9 起、`analyze*.log`）：

| 现象 | 根因 | 修复 |
|---|---|---|
| ctl 一连端口即 0x139 arg1=10（kCFG） | `FltCreateCommunicationPort` 的 Connect/DisconnectNotify 为**必需**回调却传 NULL | 补 `RBConnectNotify/RBDisconnectNotify` 桩 |
| attach 回读仍 attached=0 | 消息8处理器漏设 `g_RB.CtlMsg=ATTACH_VOLUME`，控制线程沿用消息7枚举 | 补设消息号 |
| `fltmc load` 即 0x3B (0xC0000005) | WDK26100 `FltAllocateContext` 仅 **5 参**，两处误把标签传到 PoolType 槽，破坏池跟踪 | 改 `NonPagedPoolNx`、正确 5 参 |
| 0x139 arg1=3（流上下文） | `FltSetStreamContext` 失败路径 `RemoveEntryList` 后未置 NULL，Cleanup 双删 | 摘链后 Flink/Blink 双 NULL |
| 0xA（`ExDeleteResourceLite` 读 0x8） | 失败路径手动 teardown 未置 NULL，Cleanup 二次销毁 ERESOURCE | 统一单一 teardown 入口 |
| `fltmc unload` 挂死 | 注销后销毁引擎仍在发 FltWriteFile；泄漏流致 while 反复 flush | teardown 期不发盘 I/O；先整体摘流链表再销毁 |
| 0xC4（注册表容错，故障注入） | `ZwCreateKey/SetValueKey` 失败未逐个处理 | 逐值检查 NTSTATUS、失败即返回，调用方容忍 |
| 0x139（rb_stream_create，系统资源链表） | 锁数组 stripes 分配后未清零，回收池残留旧 ERESOURCE 被双挂入系统链表 | 初始化前 memset 清零 |
| **Cc BCB 0x139（本主线）** | **cached 文件也建第二句柄/引擎流，与 Cc 双写非一致** | **PostCreate/PreRead/PreWrite 三道非缓冲门控** |

## 6. 已知限制与后续（如实说明）

1. **缓存方式普通应用 V7 不加速**：需 V8 块/存储层方案（Cc 之下、单一一致视图）。
2. **miss 读采用 read-through 预热（不再塌队列）**：未命中时 pre-op 不做同步 `FltReadFile`、
   不阻塞，返回 `FLT_PREOP_SUCCESS_WITH_CALLBACK` 让原 IRP 正常下盘（天然异步、保留设备 QD），
   在 `RBPostRead`（DISPATCH 时经 `FltDoCompletionProcessingWhenSafe` 降到 PASSIVE）按实际
   读取字节回填缓存；回填有脏保护、不覆盖并发写的更新数据。首遍≈裸盘速度，第二遍命中内存。
   后续可选优化：在途合并（single-flight）去重、顺序预读。
3. 块大小需随驱动重载生效，无运行时热切换。
4. 控制线程在同步 `Flt*` 阻塞时，停止超时（5s）后继续卸载存在窄窗口（循环顶已补退出检查）。
5. detach 的 flush 刷整引擎所有卷（保守正确，多卷时略慢）。
6. Windows 无内核态 TSan，竞态靠并发压力与代码审查，不宣称已用 TSan 验证。

## 7. 单次真机验收清单（部署后）

按顺序，确认每一步结果：

1. `fltmc load RAMBoostFS` 干净返回；`ramboostctl volumes` 列出全部卷、Attached=0，**不蓝屏**。
2. `ramboostctl attach F` 回读 F: attached=1 read=1 write=1，免重启立即生效。
3. 非缓冲读写小文件正常；随后 `diskspd -h`（或 `perf_verify.ps1`）全程**不蓝屏**。
4. 完整预热后，第二遍 cached 段**磁盘活动近空闲、带宽明显超过 F: 基线**（顺序读基线约
   302 MiB/s、随机读约 346 MiB/s）。
5. `ramboostctl detach F` 快速返回、脏=0；`fltmc unload RAMBoostFS` 秒级完成。
6. （可选）设置块大小后重载驱动，`get-config` 回读一致。

任一步蓝屏：记录停止代码与四参数，恢复后用 `read_bugcheck.ps1` 读取、必要时 cdb 深度分析，
不再盲目改动。
