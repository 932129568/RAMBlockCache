## 1. P0-A · `s_Halt` 中途被清零导致 UAF 窗口重开

### 1.1 175 的判定（直接引用，不重新论证）

> Close 在 `:701` 观测到 0 之后、`:715 Rb2Free` 之前的窗口里，另一线程可以经
> `RbL2LazyOpenInt` 的 `:548 if (s_File)` 分支把 `s_Halt` 清回 0 并返回（此时 `s_File`
> 尚未在 `:711` 置 NULL），随后任何 probe/store/drop 的判据都为假 ⇒ 正常进入并解引用
> `s_Idx`，而 `:714-715` 随即 free。

我逐行核过源码，**成立**。174 声称的"构造上排除"缺一个它自己没写出来的前提：
`从 :698 到 :715，s_Halt 不得被清 0`——而代码里没有任何机制维持这个不变量。

### 1.2 改法（零新状态，不引入 spinlock / 不引入初始化时机）

**思路**：不去"阻止清零"，而是让清零与"摘指针"这两件事通过 `s_Closing` 建立先后，
并在 Close 侧做一次幂等重置 + 复查。三段代码：

**(a) 打开路径的两个清零点加 `s_Closing` 判据**（`rbL2.c` 两处）

```c
    if (s_File) {                                    /* 已开且通过复检：无需重开（解除停机闸） */
        /* [176/P0-A] 解除停机闸前必须确认没有 Close 在跑。... */
        if (InterlockedOr(&s_Closing, 0) == 0) {
            s_Halt = 0;
            s_State = 1;
            return;
        }
        /* 关闭进行中：本次不解除停机、也不打开。... */
        return;
    }
```

```c
    s_State = 1;                                   /* [D7] 已打开 */
    if (InterlockedOr(&s_Closing, 0) == 0)
        s_Halt = 0;                                /* [F1] 开机闸解除 */
    InterlockedExchange(&s_Opening, 0);
```

**(b) Close 在 drain 通过后再置一次停机闸，并复查计数**（`RbL2CloseIntEx`，drain 之后、`RbL2IdxSave` 之前）

```c
    s_Halt = 1;
    if (InterlockedCompareExchange(&s_Ops, 0, 0) != 0) {
        RbLog(1, __LINE__, 0, L"l2: close aborted (ops entered after drain; container kept open)");
        InterlockedExchange(&s_Closing, 0);
        return;
    }
```

### 1.3 为什么这样没有 TOCTOU（逐条穷举交错）

记 O = 打开线程，C = 关闭线程。C 的临界段是「CAS `s_Closing`→1 → `s_Halt=1` → drain → **`s_Halt=1`（第二次）** → 复查 `s_Ops` → 摘 `s_Idx` → free → `s_Closing=0`」。O 的清零写作 `读 s_Closing == 0` 然后 `s_Halt = 0`。

| # | 交错 | 结果 |
|---|---|---|
| 1 | O 读 `s_Closing==0`，C 尚未 CAS | O 清 0 → C CAS 成功 → C 的**第一次** `s_Halt=1` 覆盖 → drain → 第二次 `s_Halt=1` → 复查 `s_Ops`：O 不持计数，为 0 → C 继续 free。O 此时已 return，认为可用；但它后续任何 probe/drop 读到的 `s_Halt` 是 **1**（C 覆写过），直接 MISS/拒绝。**安全**（代价：这一次打开白做） |
| 2 | O 读 `s_Closing` 得 1 | 不清，保持停机。**安全** |
| 3 | O 读 `s_Closing==0` 且 C 已 CAS（即 O 读到的是"上一个 Close"留下的 0） | O 可能清 0。但 C 的两次 `s_Halt=1` 都在其后 ⇒ 覆盖。若 O 的清零发生在 C 的**第二次** `s_Halt=1` 之后，则 O 必然读到 `s_Closing==1`（C 全程持 1）⇒ 不清。**矛盾，该交错不存在** |
| 4 | O 清 0 之后、C 复查 `s_Ops` 之前，有第三个线程 T 持计数进入 | C 的复查看到非零 ⇒ **放弃关闭**（不关句柄、不摘指针、不 free），容器原样保持可用。T 的使用完全合法。**安全**（代价：这次关闭没做成，下次 tick/REFRESH 重试） |
| 5 | C 复查 `s_Ops==0` 通过后、free 之前，T 进入 | 不可能：T 要进入必须先读到 `s_Halt==0`，而 C 已置 1 且此后只有 O 能清，O 又需 `s_Closing==0`，此时为 1。**不存在** |

**关键点**：`s_Closing` 是**单调闸**——C 从 CAS 成功到 free 完成全程持 1，`RbL2CloseIntEx` 的每一条出口（drain 超时、复查放弃、正常完成）都清回 0，不会悬挂。O 的判据读的是同一个变量，因此"O 能在 C 期间清零"这件事在构造上被排除，除非 C 已经清了自己的闸（那时 C 的临界段已结束）。

### 1.4 与 174 的差别（为什么要多这一步）

174 只做了「drain 之后立刻 free」，没有第二次置位、也没有复查。175 指出 `s_Halt` 可被中途清零后，单靠 drain 不足以挡住"drain 读之后才采集的计数"——drain 已经退出，不会再观察。本轮补的正是这个缝。

### 1.5 自查发现的第二个 bug：放弃关闭会制造新的单向闩

第一版写完 §1.2(b) 后我自查"放弃分支要不要恢复 `s_Halt`"，查出**必须恢复**：

- `RbL2ProbeFill` / `RbL2Store` 在 `s_Halt` 非零时是 **`goto cleanup` 直接 MISS**（`rbL2.c:901` / `:974`），
  **不会**调用 `RbL2LazyOpenInt`。
- 而 `s_Halt` 的清零点只有打开路径的两处（`:631` / `:778`）。
- ⇒ 一旦 `s_Halt` 停在 1，数据路径永远进不了打开路径 ⇒ **`s_Halt` 是单向闩**，
  L2 静默永久失效，直到用户手工 REFRESH（`RbL2LazyOpen(TRUE)` 控制面）。
  文件头 `:85` 那句"5s 停摆 + `s_Halt` 闩死 + 句柄泄漏不关"记的正是这个形态。

所以 §1.2(b) 的 `s_Halt = 1`（第二次置位）必须配套"放弃时还原"。**还原成 `haltPrev` 而不是 0**：

```c
    ULONG spin; PVOID old; LONG haltPrev;
    if (InterlockedCompareExchange(&s_Closing, 1, 0) != 0) return;
    haltPrev = s_Halt;               /* 记住进入时的停机态 */
    s_Halt = 1;
    ...
    s_Halt = 1;                      /* drain 后二次置位 */
    if (InterlockedCompareExchange(&s_Ops, 0, 0) != 0) {
        RbLog(1, __LINE__, 0, L"l2: close aborted (ops entered after drain; container kept open)");
        s_Halt = haltPrev;           /* 还原，不是清 0 */
        InterlockedExchange(&s_Closing, 0);
        return;
    }
```

**为什么不还原成 0**：进入前 `s_Halt` 可能已经是 1（数据路径因卷身份变更设的延迟闩 `:580`/`:603`）。
那种情况容器本来就不该服务，清 0 会放行跨卷/换卷后的陈旧服务。还原 `haltPrev` 才是"当作没关闭过"。

**这一条同样是自查改出来的**（不是 173/175 提出的）。两处自查（本条 + §2.2(c) 的 `h == s`）
说明本轮"作者=验证者"确实有盲区，见 §8.3。

## 2. P0-B · 跨引导陈旧命中（`KNOWN_ISSUES.md` J11）

### 2.1 问题（一句话）

172/174 用 `s_Gen != 0` 判断"本次引导打开 L2 之前是否写过盘"，而 `s_Gen` 是**进程内 static**，驱动重载即归零，**看不到"上一次引导写过盘"**。`RbL2IdxLoad` 的五重校验（Magic/Build/SlotCount/Count/VolId/CRC）跨引导全部不变，记录本身也自洽 ⇒ 陈旧索引被完整加载。

### 2.2 改法：引导序号世代

**(a) 索引头加字段 + 换 magic**（`rbL2.c:50` 一带）

```c
typedef struct _RB2_L2IDX_H {
    ULONG Magic, Build, SlotCount, Count, Crc, BootSeq;
    ULONG64 VolId;
} RB2_L2IDX_H;
...
#define RB2_IDX_MAGIC   0x32494258u            /* 'RB2I' v2：加 BootSeq 字段后换值，老索引作废 */
```

**为什么必须同时换 magic**：原结构 5×ULONG + ULONG64 实际占 32 字节（20 + 4 padding + 8）；
插入一个 ULONG 后仍是 32 字节，但 `VolId` 的偏移从 20 挪到 24。如果不换 magic，
老文件会被"按新布局读旧字节"，`BootSeq` 读到的是 `VolId` 的低 4 字节、`VolId` 读到垃圾——
`ib.Information != sizeof(h)` 判据也挡不住（长度相同）。换 magic 让老索引在
`h.Magic != RB2_IDX_MAGIC` 上整份拒绝，退化成冷启动（安全方向）。
**代价**：一次性格式迁移，盘上现存索引全部作废。可接受——L2 从未在任何真机启用过。

**(b) 引导序号的生命周期**

```c
static ULONG   s_BootSeq;
static VOID    RbL2BootSeqInit(VOID);

static VOID RbL2BootSeqInit(VOID)
{
    ULONG prev = 0, next;
    if (KeGetCurrentIrql() != PASSIVE_LEVEL) return;
    Rb2GetDW(L"Parameters", L"BootSeq", 0, &prev);     /* 与 RbRegSetDW 同一键 */
    next = prev + 1;
    if (next == 0) next = 1;                           /* ULONG 回绕：跳过 0 这个哨兵值 */
    RbRegSetDW(L"BootSeq", next);
    s_BootSeq = next;
}
```

- 读：`Rb2GetDW(L"Parameters", …)`（`rbfeat.c:114`，内部拼 `RB2_SVC\Parameters`）
- 写：`RbRegSetDW`（`rbdriver.c:76`，内部用 `RB_REG_PARAMS` = `…\RAMBlockCache\Parameters`）
  ⇒ **同一个键**，无需手工拼路径。声明用 `extern VOID RbRegSetDW(PCWSTR, ULONG);`，与 `rbctl.c:20` 同款（该函数是文件级非 static 复用）。
- 三处调用，均带 `== 0` 幂等判据：`RbL2Periodic` 首行、`RbL2IdxLoad` 开头、`RbL2IdxSave` 开头。
  为什么不能只放 tick：`RbL2Periodic` 只在 `Flags & RB2F_L2` 时被调（`rbfeat.c:517`），
  而首次读 miss 触发的 LazyOpen 可能在开机数秒内发生，远早于第一个 60s tick。

**(c) Load 判据（接受两种，其余整份拒绝）**

```c
        (h.BootSeq != s_BootSeq && h.BootSeq + 1 != s_BootSeq))
        return;                                    /* 任何不符 -> 空索引，安全 */
```

**为什么不是单纯的 `h.BootSeq + 1 != s_BootSeq`**：我第一版就写成那样，随后自查发现
**同一次引导内会永久冷启动**——`RbL2CloseIntEx(Persist=TRUE)` 的显式关闭（卸载 / REFRESH /
flags-off）会把 `h.BootSeq` 写成**当前**值，之后重开会再走一遍本函数，此时
`h.BootSeq+1 == cur+1 != cur` ⇒ 拒绝。而 `s_BootSeq` 在同一次引导里不会再递增，
等于每个显式关闭周期都白丢一次热数据、L2 基本不可用。
所以必须同时接受 `h.BootSeq == s_BootSeq`（本次引导自己刚保存的索引，内容就是本次会话生成的，可信）。
**这一条是本轮自查改出来的，不是 175 或 173 提出的**——记在这里是因为它属于"自己写的 bug 自己发现"，
比"别人发现"少一层保障，§9 的口径相应保守。

### 2.3 三条路径的推演

| 路径 | `h.BootSeq` | 本次 `s_BootSeq` | 判据 | 结果 |
|---|---|---|---|---|
| ① 正常：引导 N 干净关机定稿 → 本次 N+1 | N | N+1 | `N+1 == N+1` | **加载**（热索引保留，这是功能底线） |
| ② **本次缺口**：引导 N 定稿 → 引导 N+1 未启用 L2 但写过盘（不 Load 不 Save）→ 本次 N+2 | N | N+2 | `N+1 != N+2` | **整份拒绝**（冷启动） |
| ③ 崩溃：上次引导打开时就 unseal 过 | — | — | `h.Magic != RB2_IDX_MAGIC` | **先被 Magic 判据拒绝** |
| ④ 初始化失败（非 PASSIVE / 注册表读失败） | 任意 | 0 | `h != 0` 且 `h+1 != 0` | **拒绝**（fail-closed） |
| ⑤ 同一次引导内显式关闭后重开（`Persist=TRUE` → Save → 再 Load） | N（=本次） | N | `h == s` ⇒ 接受 | **加载**（否则每个关闭周期都冷启动，见 §2.2(c)） |

**为什么 ② 恰好被挡住**：引导 N+1 虽然不 Load 也不 Save，但它在 `RbL2Periodic` 或
（若 Flags 无 L2 则不会跑 tick）——**关键点是序号只在 Save 时写进索引头**。
所以序列号在注册表里确实递增了（N→N+1→N+2），而索引头里的 `BootSeq` 停在 N。
判据 `h+1 == cur` 于是只在"定稿引导的**紧邻下一次**引导"成立，中间隔了任何一次引导都不成立。
**这正是要的语义**：索引只对"紧接着的那一次开机"有效。

**若中间那次引导连 `RbL2BootSeqInit` 都没跑**（Flags 无 L2 且从未 LazyOpen/IdxSave）：
序号没递增，本次读到 N ⇒ `h+1 == cur` 成立 ⇒ 加载。但这意味着中间那次引导**从未打开过 L2、
也从未保存过索引**，它对卷的写没有任何观测者——这是**残余窗口**，见 §8.2，不是本轮引入的，
需"写即持久化标记"才能闭合。

### 2.4 溢出

`ULONG` 回绕（42.9 亿次加载）：`next == 0` 时强制为 1。跳过 0 是因为 0 是"不可信"哨兵。
回绕瞬间会误判一次（`h=1, cur=1` → 拒绝，冷启动一次），之后恢复正常。无安全影响。

## 3. P1-C · 32GB 配置下索引保存后永远无法加载

`RB2_L2IDX_MAX = 262144`（`:45`），而 32GB 配置下 `s_Slots = (32<<30)/4096 = 524096`。
`RbL2IdxSave` 的 `used` 由遍历 `s_Slots` 得出，可超上限；而 `RbL2IdxLoad` 的
`h.Count > RB2_L2IDX_MAX` 会**整份**拒绝 ⇒ 默认 32GB 配置下 L2 持久化静默失效。

```c
    if (used > RB2_L2IDX_MAX) {
        RbLog(2, __LINE__, 0, L"l2: idx save truncated to RB2_L2IDX_MAX (entries beyond cap dropped)");
        used = RB2_L2IDX_MAX;
    }
```

截断按 slot 顺序（不是按 Stamp 新鲜度），代价是被丢掉的条目下次探针 MISS —— 安全方向。
**没有**改 `RB2_L2IDX_MAX` 常量：那个常量同时是磁盘格式的一部分，而格式兼容面已被 §2 的 magic 变更占用。

### 8.2 本轮修法**自己**留下的残余（必须写清，否则又变成 174 那种过度声明）

- **J11 的残余窗口**：如果"中间那次引导"连 `RbL2BootSeqInit` 都没跑（`Flags` 无 L2 **且**
  从未 LazyOpen/IdxSave），序号不递增，本次 `h+1 == cur` 成立 ⇒ 仍会加载那份陈旧索引。
  闭合它需要"写即留下持久痕迹"（注册表一个 DWORD，任何 drop 时置位），
  但那要处理 drop 侧 IRQL 与"崩溃关机无法落盘"两个新问题，属独立设计项。
  **当前修法把最常见的路径（引导 N+1 打开过 L2 / 或跑过 tick）封住了，不是全覆盖。**
- **P0-A 的"放弃关闭"路径**：`s_Ops` 复查非零时整体放弃关闭。若该情形反复出现（例如
  `RbL2Io` 长期卡住导致 probe 一直持计数），会表现为"关不掉"，容器句柄与 8.4MB 索引
  长期占着。功能上安全（仍在服务），但会拖住 `l2 disable` 的生效。**未做实测**。
- **P0-A 未覆盖 `s_Reopen` 时序**：`RbL2HandleReopen` 里 `RbL2CloseIntEx(FALSE)` 之后
  无条件清 `s_Reopen`。若那次 Close 走了"放弃"分支，`s_Reopen` 已被清而容器仍开着 ⇒
  该次延迟重开丢失，要等下一次卷身份变化才重试。**安全方向（多服务了一段时间），
  但语义上是个缺口**，本轮未改（改它要引入返回值传播，超出"只改三条"的约定）。

### 8.3 方法论弱点与补偿建议

本轮**改动者与主线程验证者是同一个主体**（子代理被 429 中断后由主线程接手），
比 173→174 那轮的"作者≠验证者"弱。而且本轮**已经出现过一次"自己写的 bug 自己发现"**：
`BootSeq` 判据第一版只认 `h+1 == s`，会因 `Persist=TRUE` 的显式关闭导致同引导内永久冷启动
（§2.2(c) ⑤），是自查时才补上的。这说明同一主体自评确实容易漏。

**因此提权前建议再挂一个只读代理，只核一条**：`s_Halt` 在 Close 的**每条出口**上是否最终落回"正确值"——
`RbL2CloseIntEx` 现在有 4 条出口（CAS 失败提前 return、drain 超时 return、本轮新增的"复查 `s_Ops`
非零放弃"return、正常完成），其中：
- CAS 失败：不持闸，不碰 `s_Halt` ✓
- drain 超时：保持 `s_Halt=1`（leak-by-design，容器不释放，本就不该服务）
- **复查放弃：必须 `s_Halt = haltPrev`**（§1.5，第一版漏了，自查补上）
- 正常完成：`s_Halt` 保持 1，容器已释放，正确

**为什么这条比 UAF 更值得核**：`s_Halt` 停在 1 是**单向闩**——数据路径在 `s_Halt` 非零时根本
不会调用打开路径（`:901`），所以 L2 会**静默永久失效**且不崩不报错，直到用户手工 REFRESH。
UAF 会蓝屏（有事件日志），这个不会。
