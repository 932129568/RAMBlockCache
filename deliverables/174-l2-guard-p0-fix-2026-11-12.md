## 1. P0-1 · `RbL2DropRange` / `RbL2DropAll` / H5 的 `RbL2IdxSave` 没有生命周期保护

### 1.1 改前（`sed -n '139,168p' src/driver/rbL2.c`，改动前原文）

```
VOID RbL2DropRange(ULONG64 off, ULONG64 len)
{
    ULONG64 b, b0, b1, end; ULONG i, slots;
    if (len == 0) return;
    InterlockedIncrement64(&s_Gen);                /* ① 先 bump：在飞 Store 的写前快照据此失效 */
    slots = s_Slots;
    if (!s_Idx || !slots) return;
    ...
}
VOID RbL2DropAll(VOID)
{
    InterlockedIncrement64(&s_Gen);
    if (s_Idx && s_Slots) RtlZeroMemory(s_Idx, (SIZE_T)s_Slots * sizeof(RB2_L2E));
}
```

问题：两处都不持 `s_Ops`，而 `RbL2CloseIntEx`（`rbL2.c:575/588-590`）在排空 `s_Ops` 之后
`InterlockedExchangePointer(&s_Idx,NULL)` + `Rb2Free(old)` + `s_Slots=0`。排空对不持计数的 drop
毫无保护 ⇒ free 之后继续遍历/清零 8.4MB 非分页池 = UAF；若期间已重开且 `L2SizeGB` 变小，
本地 `slots` 快照大于新缓冲 ⇒ 越界写。

### 1.2 改后（`rbL2.c:144-183`）

```c
VOID RbL2DropRange(ULONG64 off, ULONG64 len)
{
    ULONG64 b, b0, b1, end; ULONG i, slots;
    if (len == 0) return;
    /* [174/P0-1] 在飞计数：与 RbL2ProbeFill(:662)/RbL2Store(:735) 同款。… 单一出口 :cleanup 严格配对。 */
    InterlockedIncrement(&s_Ops);
    /* [174/P0-1] 停机态直接跳过 drop：容器即将关闭、索引即将整体释放，不存在
     * "陈旧条目幸存"。此处也不 bump 世代——停机期间没有任何 Store 能落进
     * 索引（RbL2Store 的 s_Halt 判据在计数之后，同样直接退出）。 */
    if (s_Halt) goto cleanup;
    InterlockedIncrement64(&s_Gen);                /* ① 先 bump：在飞 Store 的写前快照据此失效 */
    slots = s_Slots;
    if (!s_Idx || !slots) goto cleanup;
    ...
cleanup:
    InterlockedDecrement(&s_Ops);
}

VOID RbL2DropAll(VOID)
{
    InterlockedIncrement(&s_Ops);
    if (s_Halt) goto cleanup;
    InterlockedIncrement64(&s_Gen);
    if (s_Idx && s_Slots) RtlZeroMemory(s_Idx, (SIZE_T)s_Slots * sizeof(RB2_L2E));
cleanup:
    InterlockedDecrement(&s_Ops);
}
```

**为什么这样就消除了风险**：drop 触碰 `s_Idx/s_Slots` 的整个窗口现在落在 `s_Ops` 里，而
`RbL2CloseIntEx:575` 的 5s 有界排空就是这个计数唯一的消费者——free 必然发生在计数归零之后，
"读到非空指针 → 被 free → 解引用"的序列在构造上不再成立；`s_Halt` 判据同时保证停机态下
不再有任何 drop 进入已开始收摊的索引。

> 关于 `s_Halt` 时**不** bump 世代：停机期间 `RbL2Store` 也在 `s_Halt` 判据处直接退出
> （`rbL2.c:737`），没有任何 Store 能落进索引，所以不存在"漏 bump 导致写前内容被放行"；
> 而重新打开走的是"释放旧索引 + 新分配全零索引"的完整路径，也不存在陈旧条目幸存。

### 1.3 H5 侧（`rbmsg.c`）改走 `RbL2IdxSaveGuarded()`（`rbL2.c:352-386`）

```c
BOOLEAN RbL2IdxSaveGuarded(VOID)
{
    BOOLEAN ok;
    InterlockedIncrement(&s_Ops);
    if (s_Halt) { InterlockedDecrement(&s_Ops); return FALSE; }
    ok = RbL2IdxSave();
    InterlockedDecrement(&s_Ops);
    return ok;
}
```

**为什么不会自持死锁**（这是本轮最容易写错的一处，单独展开）：

1. **计数不放进 `RbL2IdxSave` 内部，是因为该函数有两个调用方，语义不同。**
   - `RbL2CloseIntEx:583` 调它时，Close 自己就是"排空 `s_Ops` → 落盘 → 摘指针 free → `s_Slots=0`"
     的所有者，且已置 `s_Halt=1` / `s_Closing=1`。在那里 increment 得到的计数**没有任何 drain 会观察**
     （Close 的 drain 已跑完）→ 悬挂计数。
   - 更危险的是现状已有一条"**持计数进入 Close**"的路径：`RbL2ProbeFill` 持 `s_Ops`
     → `RbL2LazyOpenInt(FALSE)` → flags-off 分支 `RbL2CloseInt()`（`rbL2.c:441`）。
     一旦该帧走到 `:583`，drain 就在等它自己持有的计数 → 5s 超时 → lease 路径
     （与文件头 `:68-72` 记录的 S7-02 同一类）。
   ⇒ 计数只加在**外部调用方一侧**：H5 的 `RbDispatchPower` 既不持 `s_Ops`、也不持
   `s_Closing`、也不在 worker 池里，从构造上排除了"自己等自己"。
2. **increment 之后立刻检 `s_Halt`**（同 Probe `:664` / Store `:737`）：为 1 说明容器正在/已经收摊，
   直接放弃落盘并归还计数——此时索引即将或已经释放，落盘本来就没有意义；且一旦收摊成功，
   下次引导因头部未定稿必然冷启动（安全方向）。
3. **`s_Halt` 与 drain 的先后序**（`rbL2.c:572` 置 halt，`:575` 才开始 drain）保证：
   本函数"读到 `s_Halt==0`"蕴含"drain 尚未开始"，随后 Close 的 drain **必然看到**这个计数并等待；
   不存在"drain 已越过、本线程仍持计数去解引用 `s_Idx`"的窗口。
4. 计数窗口内只调 `RbL2IdxSave`（叶子：只有 `Zw*File`，不等待 `s_Ops`、不进入 Close）⇒ 无嵌套等待。

### 1.4 `rb_common2.h` 新增原型

```c
BOOLEAN  RbL2IdxSaveGuarded(VOID);
```
（原 `RbL2IdxSave` 原型与注释保留；其"调用方仅在 TRUE 时置 Clean"的语义已由 P1-1 作废，
在该处追加了指向本轮改动的说明。）

## 2. P0-2 · A.2 覆盖不到"本次开机根本没打开 L2"

### 2.1 改前（`sed -n '531,538p' src/driver/rbL2.c`，改动前原文）

```
    RbL2IdxOpen();
    RbL2IdxLoad();                                 /* 重建内存索引（安全校验在探测时） */
    /* [172/A.2] 载入后立刻把磁盘头 Magic 写 0 … */
    RbL2IdxUnseal();
```
unseal **只在打开路径**里。L2 是懒开 ⇒ "卷被写但一次 64KB 读都没发生 / 卷未 attach / `l2 disable`"
的那次引导既不 unseal，关机时 `RbL2IdxSave` 又因 `s_IdxFile==NULL` 直接 `return TRUE` ⇒ 盘上
上次封好的索引原样留着 ⇒ 再下一次开机完整加载 ⇒ 静默陈旧命中（记录自体自洽，三重校验挡不住）。

### 2.2 改后：新增开机期一次性 unseal（`rbL2.c:313-352`）

```c
static VOID RbL2BootUnsealInt(VOID)
{
    ULONG v = 0, gb = 0, magic = 0, zero = 0;
    WCHAR path[96]; UNICODE_STRING u; OBJECT_ATTRIBUTES oa;
    IO_STATUS_BLOCK ib; LARGE_INTEGER z; HANDLE h = NULL; NTSTATUS st;

    s_BootUnsealed = 1;                            /* 一次性闸：先置位，任何结局都不再重试 */
    Rb2GetDW(L"Features", L"L2Letter", 0, &v);
    Rb2GetDW(L"Features", L"L2SizeGB", 32, &gb);
    if (!v || v < L'A' || v > L'Z') return;
    s_Letter = (WCHAR)v;                           /* 与 RbL2IdxOpen 同一路径构造口径 */
    RbL2Path(path, RTL_NUMBER_OF(path), L"RAMBoostL2.idx");
    RtlInitUnicodeString(&u, path);
    InitializeObjectAttributes(&oa, &u, OBJ_KERNEL_HANDLE | OBJ_CASE_INSENSITIVE, NULL, NULL);
    st = ZwCreateFile(&h, FILE_READ_DATA | FILE_WRITE_DATA, &oa, &ib, NULL,
                      FILE_ATTRIBUTE_NORMAL, FILE_SHARE_READ, FILE_OPEN,
                      FILE_SYNCHRONOUS_IO_NONALERT | FILE_NON_DIRECTORY_FILE |
                      FILE_WRITE_THROUGH, NULL, 0);       /* [P0-4] */
    if (!NT_SUCCESS(st)) return;                   /* 不存在/卷未挂载/不可写：无需作废，静默 */
    z.QuadPart = 0;
    st = ZwReadFile(h, NULL, NULL, NULL, &ib, &magic, sizeof(magic), &z, NULL);
    if (NT_SUCCESS(st) && ib.Information == sizeof(magic) && magic == RB2_IDX_MAGIC) {
        st = ZwWriteFile(h, NULL, NULL, NULL, &ib, &zero, sizeof(zero), &z, NULL);
        if (!NT_SUCCESS(st) || ib.Information != sizeof(zero))
            RbLog(2, __LINE__, st, L"l2: boot unseal failed (stale idx may survive this boot)");
    }
    ZwClose(h);
}
```

调用点（`rbL2.c:377-383`，`RbL2Periodic` 首行）：

```c
    if (!s_BootUnsealed) RbL2BootUnsealInt();
```

**为什么这样就消除风险（这条上我偏离了 173/任务的建议一步，理由如下）**：
`RbL2Periodic` 只由 `rbfeat.c:508` 的 `if ((g_Rb2Flags & RB2F_L2) && (n % 60 == 0))` 调用，
两个纯逻辑后果：

- **`l2 disable` 的那次引导根本不会跑 tick**（Flags 不含 `RB2F_L2`）⇒ 单靠 tick 覆盖不到
  任务点名的"用户 disable"场景；
- **首次打开通常远早于第一个 tick（60s）**：若那次引导在打开前已经写过盘，单靠 tick 也不能
  把"已经装进内存索引的陈旧条目"拿掉（tick 只清磁盘头）。

所以除 tick 之外，在**打开路径的加载之前**加了一道兜底闸（`rbL2.c:645-655`）：

```c
    RbL2IdxOpen();
    /* [174/P0-2] 打开前的兜底作废：本次引导若在打开 L2 **之前**已经发生过写
     * （每次写都经 H1–H5 命中 RbL2DropRange/DropAll，表现为 s_Gen != 0）… */
    if (InterlockedOr64(&s_Gen, 0) != 0) RbL2IdxUnseal();
    RbL2IdxLoad();
```

**为什么这样就消除了风险**：`s_Gen` 是"本次引导发生过 drop"的充分观测（H1–H5 的每一次写都会
在落盘前 drop）。首次打开时 `s_Gen != 0` ⇒ 打开前已有写 ⇒ 盘上那份旧索引对相关块必陈旧 ⇒
先把头写 0，`RbL2IdxLoad` 的 `h.Magic != RB2_IDX_MAGIC` 判据整份拒绝 ⇒ 冷启动。
`s_Gen == 0` ⇒ 打开前没有任何写 ⇒ 旧索引仍是本次引导起点的真实内容，照常加载（热索引保留）。

**代价（明确接受）**：打开前有过写的引导拿不到热索引，属于"一次冷启动"。这是本特性的固有
权衡（要既热又安全，需要"每条记录与当前盘面一致"的证明，本驱动没有），本报告选择正确性。

**仍未覆盖的残余（新引入以外的已知口径，见 §10.3）**：驱动加载之前发生的写（boot loader /
其他 OS）、以及"该卷本次引导从未 attach 且被外部写入"的那一类。

**(c) 排除进程直写分支**（`rbio_worker.c:636-642`）

```c

            rb_engine_note_direct_write(g_Rb.Engine, len);
        /* [174/P0-3] 排除进程直写同样"写已落盘后再推一次 L2 世代"… */

```

L2→盘的回写通道。若 drop 之后又有读把它按新内容存回来，这次 drop 只是让它变 MISS——
代价是性能，不是正确性。

## 4. P0-4 · unseal 是不落盘的写

### 4.1 改前（`sed -n '249,255p' src/driver/rbL2.c`，改动前原文）

```c
    st = ZwCreateFile(&s_IdxFile, FILE_READ_DATA | FILE_WRITE_DATA, &oa, &ib, NULL,
                      FILE_ATTRIBUTE_NORMAL, FILE_SHARE_READ, FILE_OPEN_IF,
                      FILE_SYNCHRONOUS_IO_NONALERT | FILE_NON_DIRECTORY_FILE, NULL, 0);
```

### 4.2 改后（`rbL2.c:249-260`）

```c
    st = ZwCreateFile(&s_IdxFile, FILE_READ_DATA | FILE_WRITE_DATA, &oa, &ib, NULL,
                      FILE_ATTRIBUTE_NORMAL, FILE_SHARE_READ, FILE_OPEN_IF,
                      /* [174/P0-4] FILE_WRITE_THROUGH：… */
                      FILE_SYNCHRONOUS_IO_NONALERT | FILE_NON_DIRECTORY_FILE |
                      FILE_WRITE_THROUGH, NULL, 0);
```

**为什么这样就消除了风险**：`s_IdxFile` 是 unseal 与 IdxSave 共用的**同一个句柄**，
`FILE_WRITE_THROUGH` 让那 4 字节在 `ZwWriteFile` 返回前就下发到存储栈（绕过 lazy writer 的
延迟刷盘），"崩溃即作废"不再依赖"几秒后才会发生的后台刷盘"。代价是索引写变成 write-through，
但索引只在关机/显式关闭各写一次，可忽略。
（§2.2 的开机 unseal 用的是另一个独立句柄，也带了同一标志。）

## 5. P1-1 · H5 用 L2 索引保存失败去否决 `LastCleanShutdown`

### 5.1 改前（`sed -n '240,258p' src/driver/rbmsg.c`，改动前原文）

```c
            if (RbL2IdxSave()) {
                if (g_Rb.Engine && rb_engine_has_dirty(g_Rb.Engine) == 0)
                    RbRegSetClean(1);
            } else {
                RbLog(2, __LINE__, STATUS_IO_DEVICE_ERROR,
                      L"shutdown: L2 index save failed - clean flag withheld (next boot cold)");
            }
```

### 5.2 改后（`rbmsg.c:241-256`）

```c
            if (!RbL2IdxSaveGuarded())
                RbLog(2, __LINE__, STATUS_IO_DEVICE_ERROR,
                      L"shutdown: L2 index save failed (log only; clean flag not gated by L2)");
            /* FIX[P2-2]: 全部落盘且脏数据归零 → 记录“干净关机”，下次启动不进安全模式 */
            if (g_Rb.Engine && rb_engine_has_dirty(g_Rb.Engine) == 0)
                RbRegSetClean(1);
```

**为什么解耦不会让 P0-2 的语义变松**：P0-2 之后，磁盘索引的可信度**完全**由 `.idx` 自己的
Magic 决定（开机 unseal 把它写 0；只有成功的 `RbL2IdxSave` 才会重新写下 `RB2_IDX_MAGIC`），
全驱动没有任何代码读 `LastCleanShutdown` 来判断 L2 索引是否可用（173 §4 P1-1 已 grep 确认）。
所以 Clean 标记对 L2 是**零信息量**的，把它与 L2 的磁盘写失败绑在一起只剩副作用：
`BootFailCount` → SafeMode / self-disable（`rbdriver.c:302-331`）。
解耦后 L2 侧只剩两件事：定稿成功 → 头部 Magic 存在 → 下次可加载；失败 → 头部仍是 0 →
下次冷启动。两者都不依赖 Clean。
