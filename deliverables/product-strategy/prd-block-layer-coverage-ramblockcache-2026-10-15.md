## 📌 TL;DR（执行摘要）

- **一句话**：V10.4.3 的驱动在代码中**已完成向 WDM 卷块上层过滤的迁移**（`rbattach.c` 运行时定向挂载 + `rbio.c` 数据通路）——即路线图原"V8 块层预研"的架构目标已成形；本 PRD 的使命是**把"看起来到位"变成"验证过、可声明、可产品化"**：全 I/O 覆盖矩阵验证、分页 I/O 一致性证据链、准入策略产品化、系统卷 opt-in、以及修订已过时的架构文档口径。
- **为什么重要**：覆盖是本品与 PrimoCache 的**最大结构差距**（竞品矩阵结论 1）。V7 定稿为消除与缓存管理器（Cc）双写冲突，主动把加速范围收缩到"仅非缓冲 I/O"，代价是普通应用（浏览器/Office/缓存方式加载的游戏）不加速——这是用户可感知差异点，也必须在销售话术中诚实管理。迁移到卷块层后，该收缩的**结构性理由已消失**，但"消失的理由"需要证据链来兑现。
- **范围**：不写新驱动、不重构数据通路；做验证、产品化、口径修订三件事。
- **硬门禁**：Driver Verifier 全绿；分页/缓存 I/O 数据一致性 100%（A/B 字节级对账）；attach/detach 数百次无泄漏；覆盖矩阵逐类冻结；文档口径修订合并。
- **最大风险**：验证债（本机无 WDK/MSVC/.NET SDK，编译与真机验收均为零，两次 No-Go 共识）——本 PRD 全部排在 Phase 0 验证基建（Gate 0）之后启动。

## 1. 功能背景与目标

### 1.1 背景：一次"以覆盖换稳定"的取舍，及其偿还

**V7 的历史取舍（文档事实，`src/docs/12-V7架构定稿`）**：旧设计在文件系统层（minifilter）自完成 I/O，并对同一文件另开非缓存句柄做回写/补读，形成与缓存管理器（Cc）的**双写非一致视图**，真机反复爆发 `KERNEL_SECURITY_CHECK_FAILURE (0x139)` / `IRQL_NOT_LESS_OR_EQUAL (0xA)`。定稿将加速范围切分为：仅非缓冲 I/O 加速，缓存方式/分页 I/O 透明旁路。

**V9–V10 的架构迁移（代码事实，2026-10-15 核验）**：

| 证据 | 内容 |
|---|---|
| `deliverables/architecture-and-work-breakdown-2026-10-15.md` §2.1 | 驱动定性为「**WDM 卷块上层过滤**」：`rbdriver`（全局态/卸载/僵尸）、`rbattach`（PnP 挂载）、`rbio`（数据通路）、`rbctl`（IOCTL 控制面）+ 特性钩子层 |
| `rbattach.c` 头注释 | V9 起「**不再使用 Volume 类类级 UpperFilters**；仅当用户在 UI/CLI 显式 attach 时，运行时打开卷、构造过滤设备并挂栈」；引导关键卷双闸门硬排除（设备节点 + DOS 盘符 + 注册表事实：页面文件/转储/休眠；不可判定一律按引导关键处理） |
| `rbio.c` 数据通路 | `IoMarkIrpPending` + 投递系统 worker（PASSIVE）处理，DISPATCH 级绝不取缓存锁——块层标准 pending 模式 |
| 准入门 `RbFeatAdmit`（`rbfeat.c:153`） | 按**进程镜像名排除名单** + panic 门——不是按 I/O 类型（非缓冲/分页/缓存）区分，即附加卷上的 I/O 统一进缓存通路 |

**结构性论证（设计层面，待实证）**：卷块过滤驱动位于文件系统与 Cc **之下**，看到的是文件系统下发的块 I/O 单一视图；不在文件系统层自完成缓存方式 I/O，即不产生 V7 的"双写者"问题。PrimoCache 15 年实践证明该位置可行。**但"结构上应该安全"不等于"验证过安全"**——分页 I/O 一致性、元数据写、快照/卷影（volsnap）、BitLocker、动态磁盘、4Kn/512e、电源循环的交互，必须逐类实证并冻结为覆盖矩阵。

### 1.2 目标（可衡量）

| # | 目标 | 目标值 |
|---|---|---|
| G1 | 覆盖矩阵冻结并全绿 | I/O 类型（分页/缓存/非缓冲/元数据/TRIM/IOCTL）× 卷类型（HDD/SATA SSD/NVMe/4Kn/512e；NTFS/动态磁盘）× 场景（读/写/冲刷/快照/睡眠/热插拔）逐类有结论 |
| G2 | 分页 I/O 数据一致性 | A/B（缓存开/关）字节级对账 **100% 一致**（含延迟写开启组合） |
| G3 | 归因本品的新增内核崩溃 | **0**（Driver Verifier + T1–T6 真机验收） |
| G4 | 普通应用可感知加速 | 缓存方式加载的典型负载（浏览器/Office/游戏二次加载）第二遍读命中可量化（与 V7 边界期的 0% 命中对照） |
| G5 | 准入策略可运营 | 进程排除名单可配置、默认名单覆盖已知冲突类（碎片整理/备份/镜像工具——PrimoCache 已知问题 #005/#014 的同题教训） |
| G6 | 文档口径修订合并 | `00-总览 §12`、`10-竞品对比` 架构表述、竞品矩阵行 1–3 更新为 WDM 卷块过滤事实 |

### 1.3 Non-goals

1. **不重开 minifilter 路线**——V7 根因（Cc 双写）已定性，不回退。
2. **不新写驱动、不重构数据通路**——本 PRD 是验证与产品化，不是重建。
3. **不做 TRIM/删除语义透传**——独立路线图项（P1-02），另有规格。
4. **不做 DirectStorage/BypassIO 写路径兼容**——读路径共存（只读卷）为配置模板建议；"开回写即阻止 BypassIO"的行业共识（PrimoCache KB 同款取舍）保持。
5. **不承诺文件系统全覆盖**——NTFS 为首验目标；exFAT/ReFS 附加与否以验证矩阵结论为准，未验证前不声明。
6. **不承诺 Server 版/NUMA**——远期评估项。

## 2. 目标用户与使用场景

### 2.1 目标用户

| 用户层 | 画像 | 本功能价值 |
|---|---|---|
| **S1 普通个人用户（主）** | 浏览器/Office/IM 日常负载，游戏缓存方式加载 | V7 边界期"装完没效果"的主体人群；覆盖兑现后获得可感知加速 |
| **S2 游戏玩家** | 游戏素材二次加载（非 DirectStorage 直读部分） | 命中率从 0 到可量化；与游戏模式/只读卷配置模板联动 |
| **S3 技术用户** | 关注"到底加速了什么" | 覆盖矩阵 + 每卷加速/旁路状态可观测 = 可信度 |
| **运维/批量部署者** | 需要确定行为可预期 | 准入策略统一下发 + 系统卷默认排除 = 批量安全 |

### 2.2 使用场景与用户故事

**场景 A：普通应用真的被加速了**
> 作为普通用户，我希望浏览器、Office 等日常软件的重复读写也能命中缓存，以便不用关心"I/O 类型"就获得速度提升。

**场景 B：游戏二次加载**
> 作为玩家，我希望游戏（缓存方式加载部分）二次进入场景接近内存速度，以便减少重复等待；同时 DirectStorage 直读游戏不受影响、不被破坏。

**场景 C：我知道它没加速什么**
> 作为技术用户，我希望控制台明示每个卷"已加速/旁路"及原因（如系统卷默认排除、备份进程排除），以便我能判断是否符合我的预期，而不是猜。

**场景 D：批量机器的确定行为**
> 作为网吧运维，我希望排除名单和系统卷策略可经注册表/CLI 统一下发，以便 100 台机器行为一致、不与还原/备份软件打架。

### FR-BL-02 分页 I/O 一致性证据链（P0）

- **描述**：针对 V7 根因（Cc 双写）的正面证据建设——证明卷块位置的分页 I/O 处理不与 Cc/文件系统产生不一致视图。
- **详细要求**：
  1. **A/B 字节级对账**：同一工作集（含大量缓存方式 I/O：文件拷贝、Office 保存、浏览器缓存、编译输出），缓存开/关两轮，事后全盘/全文件哈希对账 100% 一致；
  2. **失败注入**：冲刷失败穿透、panic 注入、在途 I/O 中断（复用审计 §8.7 三类失败注入用例扩展）；
  3. **快照/卷影交互**：VSS 创建/删除/回滚期间缓存行为验证（volsnap 为当前系统安全态 UpperFilters，交互必测）；
  4. **元数据安全**：$MFT/位图等元数据路径的数据结构校验（chkdsk 干净）+ 卷检查点（NtfsCheckpointAllVolumes）期间无异常。

### FR-BL-03 准入策略产品化（P0）

- **描述**：将 `RbFeatAdmit` 的进程镜像排除名单（`s_Excl`）从内部机制产品化为可配置面，并沉淀默认名单。
- **详细要求**：
  1. **默认排除名单**（基于 PrimoCache 已知问题 #005/#014 的同题教训——碎片整理/备份/镜像工具运行期缓存会互相干扰）：碎片整理类、备份/镜像类、杀毒扫描类（可配置关）；
  2. **配置面**：WPF 设置页 + CLI + 注册表（`Policies\<X>` 既有每卷策略结构扩展）；支持通配进程名；
  3. **每卷读/写独立开关**保持（只读卷配置模板 = DirectStorage 共存前提，竞品分析 8.3）；
  4. **可观测**：被排除进程的 I/O 计数（让用户知道"为什么没加速"）。

### FR-BL-04 系统卷 opt-in（P1）

- **描述**：系统卷默认不附加（现状保持，更安全）；提供显式 opt-in 路径——开启前明确确认 + 引导关键卷双闸门硬排除保持（设备节点/盘符/注册表事实，不可判定按引导关键处理）。
- **验收**：opt-in 后 Win11 26H2 干净安装机 50 次重启循环无 0x7B/启动失败（复用 T 系列真机用例）。

### FR-BL-05 真机验收矩阵执行（P0）

- **描述**：在验证基建环境（WDK 26100 + VS2022 + .NET 8 SDK + 3–5 台异构真机：HDD 老机/SATA SSD/NVMe/4Kn/Win10+Win11 26H2）执行并全绿：Driver Verifier（PnP/电源循环）、panic 数据完整性、FLUSH 失败穿透、attach/detach 数百次无泄漏、干净 Win11 单路径安装、UI 安全入口四态（对齐路线图 T1–T6）。
- **依赖**：Phase 0 验证基建（Gate 0）。**本 PRD不前置**——无 Verifier 证据不合并相关改动（写入工程 Definition of Done）。

### FR-BL-06 覆盖状态可观测（P1）

- **描述**：WPF 磁盘页每卷展示「已加速/旁路 + 原因码」（系统卷默认排除/进程排除/特征文件类型/用户关闭），把 V7 时代"猜有没有效果"变为"看得见"。原因码进 `RB_STATS` 遥测集（最小遥测集 v1 依赖）。

### FR-BL-07 文档口径修订（P0）

- **描述**：修订已过时的架构表述，消除研发/销售/用户三方的口径分裂：
  1. `src/docs/00-总览.md` §V7 定稿说明及对比表（minifilter、仅非缓冲 I/O、分页 IO 表述）；
  2. `src/docs/10-竞品对比与优化.md` §1.1 架构层表（工作层级/分页 IO 两行）；
  3. 竞品分析矩阵行 1–3（工作层级/普通缓冲应用 I/O/分页 I/O）；
  4. 修订后口径：**WDM 卷块上层过滤驱动，运行时定向挂载，I/O 分类经准入门统一进缓存通路，系统卷默认排除，引导关键卷硬排除**；未验证类（exFAT/ReFS 等）标注"验证中"，不预先声明。

## 4. 竞品对比分析（重点对标 PrimoCache）

### 4.1 PrimoCache 的卷级位置（本品对标基准）

| 维度 | PrimoCache（事实） |
|---|---|
| 工作层级 | **卷级扇区过滤驱动**，位于文件系统与缓存管理器之下——所有 I/O 均经过（含分页 I/O、页面文件、任意文件系统） |
| 覆盖 | 不依赖文件系统（含专有 FS、junction）；基本/动态磁盘、RAID、Storage Spaces、iSCSI（映射网络盘不支持） |
| 已知冲突史 | #005 碎片整理/备份软件运行变慢（无解，建议暂停缓存）；#014 SmartDefrag 兼容（关其"智能磁盘加速"）；#006 延时写致 Windows 体验指数不过；#013 MMC/TF/SD 弹出丢数据；#016 4Kn 数据损坏（4.1.0 起支持） |
| 安装门槛 | 商业签名常规安装；历史 HVCI 冲突（v3.0.9 要求关闭内存完整性，4.2.0 支持 Core Isolation） |
| 分层佐证 | 15 年实机验证 = 该位置可行性的最强行业证据 |

### 4.2 正面对标（覆盖维度）

| 维度 | PrimoCache | RAMBlockCache 现状 | M1/M2 目标态 |
|---|---|---|---|
| 驱动位置 | 卷级扇区过滤 | **WDM 卷块上层过滤（代码已就位）** | 对齐 |
| 普通缓冲应用 I/O | ✅ | 架构已具备，**待验证冻结** | 验证后声明 |
| 分页 I/O | ✅（含系统卷） | 架构已具备，**待验证冻结**；系统卷默认排除（安全取向差异） | 验证后声明；系统卷 opt-in |
| 文件系统依赖 | 不依赖 FS | NTFS 首验；其他待验 | 验证矩阵结论驱动 |
| 进程级排除 | ❌（未见） | ✅ 进程镜像名单（内部已实现） | 产品化 + 默认名单 |
| 冲突软件应对 | 用户自行暂停缓存（KB 建议） | **默认排除名单自动让行** | 领先 |
| 4Kn | 4.1.0 起支持（曾数据损坏） | 验证矩阵必测项 | 验证后声明 |
| DirectStorage | 只读卷可共存；开回写阻止 BypassIO | 每卷读/写独立开关已具备 | 配置模板化 |
| 稳定性履历 | 15 年 | 新建，硬门禁自证 | 以证据链追赶 |

| **Open CAS / OCF**（块缓存框架） | ① cache/core 显式配对模型——本品"附加卷 = core、缓存引擎 = cache"映射固化进覆盖矩阵文档；② 设备无响应 fail all IO 的 fail-closed 纪律——本品宿主设备异常时的降级路径设计输入（FR-BL-02 失败注入）；③ 逻辑块大小兼容约束（cache 块 ≤ core 块）——4Kn/512e 矩阵的判据来源 |
| **bcache / dm-cache / flashcache**（Linux 块缓存） | ① miss 旁路不塌队列（本品 pending+worker 模式同构）；② 策略与机制分离（dm-cache 策略插件）——准入/排除策略产品化的架构输入；③ 顺序检测——与 PRD-03 预取共用 |
| **mhtvsSFrPHdE/prefetch**（用户态预取） | 反向证据：用户态方案受 OS 缓存机制制约、依赖手工配置——佐证驱动级透明覆盖的价值主张 |
| **Arsenal Image Mounter**（ImDisk 的 Win11 接棒者，2025-10 活跃） | 老牌开源驱动在 Win11 新版的适配维护模式——本品 Win11 26H2 适配的工程参照 |

**调研结论**：覆盖维度没有"可抄的 Windows 开源块缓存驱动"，但 **ImDisk 证明了"开源/免测试模式/存储栈驱动"在 Windows 上的可行工程路径**，Linux 三件套（OCF/bcache/dm-cache）提供位置模型与失败语义的参照系。本品的覆盖差异化 = **PrimoCache 的位置 + 准入策略产品化 + 覆盖状态透明化**。

## 5. 差异化亮点

1. **覆盖状态全透明**：每卷「已加速/旁路 + 原因码」可观测——PrimoCache 用户只能自行暂停缓存来应对冲突软件（KB 原话），本品把"为什么没加速"变成界面上的确定答案（用户研究 M1：信任显性化）。
2. **准入策略默认开箱安全**：碎片整理/备份/镜像/扫描类进程默认排除——直接消化 PrimoCache 已知问题 #005/#014 的同题冲突，且可运营（名单可配、计数可见）。
3. **系统卷默认排除 + opt-in 双闸门**：比 PrimoCache（可缓存系统卷）更保守的默认姿态，契合"信任/数据安全"的社区第一决策因素；引导关键卷不可判定按引导关键处理，从设计上杜绝 0x7B 类启动事故。
4. **位置对齐 + 安全工程链叠加**：架构位置追平 PrimoCache 后，本品差异回到既有长板——防蓝屏 IRQL 规范、崩溃修复台账、SHA256 fail-closed 门禁、安全模式自愈、正式签名/HVCI 路线（竞品分析机会 1）。
5. **诚实边界作为卖点**：覆盖矩阵三态（已验证加速/待验证/明确旁路附理由）对外公开——在内核驱动品类，"知道它不做什么"本身就是信任资产。

## 6. 技术可行性初步评估

### 6.1 现状盘点（代码已验证）

- **架构位置就位**：WDM 卷块上层过滤 + 运行时定向挂载（无类级 UpperFilters，引导卷不被 PnP 自动挂入）+ 惰性引擎（首次 attach 前不建引擎不起线程，DriverEntry 快进快出）。
- **数据通路模式正确**：pending + PASSIVE worker，DISPATCH 级不取缓存锁；拆除铁律（停流入→快照→等在途排空→销毁）已有引用计数模型 5/5 场景 17/17 断言。
- **准入门已存在**：进程镜像排除名单 + panic 门；引导关键卷双闸门硬排除；系统卷默认不附加。
- **核心引擎双栖**：`core/cache.c` 平台无关，64 分片条纹锁多核并行。

## 附录 B · 术语

- **WDM 卷块上层过滤**：挂在卷设备栈上的过滤驱动，位于文件系统之下；区别于 minifilter（文件系统之上）。
- **引导关键卷硬排除**：设备节点 + DOS 盘符 + 注册表事实（页面文件/转储/休眠）三重判定，不可判定按引导关键处理。
- **双闸门**：上述三重判定的俗称（设备节点级 PDO + DOS 盘符 + 注册表事实）。
- **覆盖矩阵三态**：已验证加速 / 已加速待验证 / 明确旁路（附理由）。
