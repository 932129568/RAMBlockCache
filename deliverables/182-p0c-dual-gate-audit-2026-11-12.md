被审对象：`src/driver/rbL2.c`（1082 行）、`src/driver/rb_common2.h`、`src/driver/rbfeat.c`
立场：找漏洞。只读，未改任何源码，未跑构建/门禁/git。

## §0 一句话结论

**条件放行**：无 UAF/内存安全阻塞项，"两边都让路"的时序**代码上存在**（§2-E），但后果是延迟与状态滞留、不是内存不安全；放行条件 = ①把 `:836-837` 那段"后到者必被先到者挡住、先到者继续"的互斥论证改掉（它与代码行为不符，是错误的设计声明）；②`l2 disable` 的 flags-off 分支（`:560-574`）在"关不成"时没有任何自动重试者，需明确接受"直到下一次 REFRESH/卸载才真正关闭"。

## §2 Q1/Q3 完整时序枚举（T1=开，T2=关）

记号：`a1`=T1 CAS `:676`；`a2`=T2 CAS `:825`；`r1`=T1 读 `s_Closing` `:684`；`r2`=T2 读 `s_Opening` `:838`；`w1`=T1 清 `s_Opening` `:685`；`w2`=T2 清 `s_Closing` `:839`。

| # | 顺序 | 结果 | 是否安全 |
|---|---|---|---|
| A | `a1 < r1(=0) < a2 < r2(=1)` | T1 继续打开；T2 让路 `FALSE` | 单方胜，安全 |
| B | `a2 < r2(=0) < a1 < r1(=1)` | T2 继续关闭；T1 让路，清 `s_Opening` | 单方胜，安全 |
| C | `a1 < a2 < r1(=1) < w1 < r2(=0)` | T1 先让路并清门；T2 随后读到 0，继续关闭 | 单方胜，安全 |
| D | `a1 < a2 < r2(=1) < w2 < r1(=0)` | T2 先让路并清门；T1 随后读到 0，继续打开 | 单方胜，安全 |
| **E** | `a1 < a2 < r1(=1) < r2(=1) < w1 < w2` | **T1 放弃、T2 也放弃**，两门均被释放，容器原样 | **双放弃存在**（安全方向，但谁也不干活） |
| F | `a2 < a1 < r2(=1) < r1(=1) < w2 < w1` | E 的镜像，同样双放弃 | 同上 |

**E/F 为什么能成立**：两个检查各自读的是"对方的门"，而不是"双门联合状态"。`a1`/`a2` 都成功之后，只要两次读（`r1`、`r2`）都落在对方清零（`w1`、`w2`）之前，双方就都看到 1。`InterlockedOr` 只保证"读不回卷到本线程 CAS 之前"，不保证"读到对方读到之后的状态"。因此 `:836-837` 的断言"后到者必被先到者挡住并释放自己的门，先到者继续"**与代码行为不符**——它描述的是 C/D 两个分支，漏了 E/F。

**后果**：
- 开侧 T1 放弃：下一次 probe/REFRESH 自然重试，无状态损伤。
- 关侧 T2 放弃：`s_Halt` 未动（`:838` < `:847`），`s_State`/`s_File` 未动，容器保持原样——这正是"放弃"的设计意图，方向安全。
- 若 T2 是 tick 的 `s_Reopen` 清偿（`:535`）：`s_Reopen` 保留，下一个 tick 重试，最坏多 60s。
- 若 T2 是 `l2 disable` 的 flags-off 分支（`:570`）：**该分支失败时既不设 `s_Reopen` 也无自动重试者**（见 §3），容器会一直开着直到 REFRESH/卸载。
- 若 T2 是卷身份变更的控制面分支（`:599`）：`s_Halt=1` 已在 `:594` 置位，`s_Reopen=1` 已在 `:595` 置位 ⇒ 探针全 MISS、按 tick 重试，安全但多等一个周期。

**没有"永久不开/永久不关"的代码路径**：E/F 不改变任何持久状态，所有状态位保持进入前值，因此不存在"卡在非法中间态"。

### 3.2 "flags 已关但容器未关"时 `l2 status` 报什么、持续多久

- 报**旧状态**：`:570` 的 else-if 落空时不写 `s_State`，所以 `RbL2State()`（`:901`）返回 1/2/3/4 中进入前的值；若原为 1 就是 `opened`，而 flags 已无 L2 位。这是本轮修改**有意**保留的（`:564-566` 注释），但用户可见面是"`l2 disable` 之后 `l2 status` 仍显示 opened"。
- 持续多久：**没有上界**。`Rb2Tick` 只在 `g_Rb2Flags & RB2F_L2` 时才调 `RbL2Periodic`（`rbfeat.c:517`）；`RbL2ProbeFill` 在 `:955` 就按 flags 返回 `STATUS_NOT_FOUND`，不再进 `:967` 的 `RbL2LazyOpenInt`。所以自动清偿链条在 flags-off 后**整体断开**。
- 仍能到达 `RbL2CloseIntEx` 的回收者只有两个：
  1. REFRESH IOCTL（`rbfeat.c:718 RbL2LazyOpen()` → `rbL2.c:560` flags-off 分支 → `:570`）；
  2. 卸载/关机（`rbfeat.c:625`）。
  两者都不是周期性的 ⇒ 用户不主动 REFRESH 就一直滞留到重启。

### 3.3 `rbfeat.c:625`："池已停，不会有 open" 的推理不成立

- 池/worker/tick 确实停了（`rbfeat.c:616` `Rb2PoolShutdown()`、`:600` tick join）。
- **但 REFRESH IOCTL 没有卸载闸**：`rbctl.c:301` 的 `Unloading` 门只覆盖 `SET_CONFIG` 一类入队路径，`RbFeatDispatch` 的 `RB2_IOCTL_REFRESH` 分支（`rbfeat.c:717-718`）无门；而 `RbFeatShutdown()`（`rbdriver.c:932`）发生在 `IoDeleteDevice(g_Rb.ControlDevice)`（`rbdriver.c:1030`）**之前**，控制设备此刻仍在收 IRP。
- 因此存在：用户态线程正在 `RbL2LazyOpen()` → 持 `s_Opening` 装索引；卸载线程在 `:625` 调 `RbL2Close()` → `:838` 看到 `s_Opening!=0` → 让路 `FALSE` → 被 `(void)` 丢弃。结果：`s_File`/`s_IdxFile`/`s_EvH` 三个内核句柄与 8.4MB 非分页池**在卸载时泄漏**（每次卸载累积），`s_Halt` 保持 1。
- 方向安全（不会 UAF：卸载后没有代码再引用这些），所以是 P2 资源泄漏，不是 P0。
- 附带（超出本单范围，见 §5）：同一窗口里若卸载线程推进到代码页卸载，而 REFRESH 线程仍在 `LazyOpenInt` 内执行 → 0xC4/0xC5。这是既有缺口，与本轮改动无关，但"Shutdown 时一定没有 open"这个前提不能作为设计依据。

### 3.4 与 175 / 176 的分歧点

- **与 176 P0-A 不冲突（成立）**：T2 让路路径的唯一写是 `:839` 清 `s_Closing`，且在 `haltPrev`（`:847`）**之前**；T1 在 `:684` 读 `s_Closing`，若读到 1 则自己让路、不继续装索引；若 T2 已让路清 0，T1 读到 0 继续，而 T2 全程未碰 `s_Halt`/`s_Idx`。`:810-811` 的第二处 176 检查同理：T2 让路后 `s_Closing==0` ⇒ T1 清 halt 正确，因为确实没有 Close 在收摊。
- **不存在"T2 清 `s_Closing` 晚于 T1 读"的有害序**：那种序就是 §2 的 E/F，两边都退，T1 不会带着"已打开"的假象继续持有索引。
- **与 175 §4.3 的分歧**：175 指出的那条"Close 在 drain 后 free 前被清 halt"的窗口，本轮改动没有闭合它，闭合它的仍是 176 的 `:869-878` 二次置位+复查。本轮新增的门只解决"打开与关闭并发"，不解决"halt 被清"。两者不重叠、也不互斥。

### 3.5 长期饥饿量化（Q3 原问）

- 只有在"每次 tick 重试都撞上 open 窗口"时才连续让路。open 窗口 = `ZwCreateFile` + 8.4MB 分配清零 + `IdxLoad`（可能读盘）+ `ZwCreateEvent`，几十 ms 到秒级；tick 周期 60s。随机碰撞的概率极低。
- **没有公平性机制**（无 aging、无"让路计数"），所以严格说是**无上界饥饿**：若某调用方以 < 60s 的周期持续触发 REFRESH（用户脚本循环 `l2 enable`），tick 的关闭可以无限期让路。工程上不构成 P0，写在这里是为了不让"最多等一个周期"的说法被当成定理。

## §5 顺带发现

1. **`rbL2.c:829` 的 UAF 触发源描述与代码不符（P3，文档级）**：注释说"worker 的 probe 同时在 LazyOpenInt 里装索引"。但 `RbL2ProbeFill` 在 `:965` 先 `InterlockedIncrement(&s_Ops)`，再在 `:967` 调 `LazyOpenInt`；Close 的 drain（`:851`）会看到非 0 → 5s 超时 → `:855` 返回 FALSE，**不会走 free**。因此 probe 帧不持 `s_Ops` 的说法不成立，probe 路径原本就被 drain 挡住。真正无 `s_Ops` 保护、能与 Close 并发的 open 是**控制面 `RbL2LazyOpen`**（`rbfeat.c:718` REFRESH、`rbrebuild.c:590/620`）。两个并发 REFRESH 即可构成原始 UAF（T1 在 `:760` 装索引，T2 在 `:560` flags-off 或 `:599` 卷变更里关）。修法仍然必要，但根因定位应改成"控制面 open 不计数"，否则下一个复审会照着错误的触发源去验证而验不出来。
2. **`rbL2.c:671` 在 CAS 之前就写 `s_VolId`**：任何一次 open 尝试（哪怕随后在 `:684`/`:699`/`:710` 让路或失败）都会把容器身份改写成当前卷。§2 的双放弃时序 E 下，容器仍是旧卷，`s_VolId` 已是新卷。现有两道下游检查（`:957` 探针入口比 `Extp->VolId`、`:993` 记录头比 `rec->VolId`）使它退化为"全 MISS"而非跨卷命中，故不是新洞；但"身份在拿门之前就被改写"这一点与 `:586-601` 的复检设计意图相悖，值得记一笔。
3. **`RbL2CloseIntEx` 的 `s_Reopen` 与 `s_State` 没有任何写入**：让路是纯"放手"。这意味着所有"让路后状态自洽"的论证都依赖调用方，而 `:570` 的调用方没有重试者（§3.2）。这是本轮修改引入的唯一功能性倒退面：**改前** `l2 disable` 一定能关（哪怕撞车也只是双 free 风险），**改后**能关不成且不报错。方向比 UAF 安全，但用户可见行为变了，需要产品侧知情。
4. **`:936` `RbL2AttachBlocked` 用 `s_Opening` 作"正在开"判据**：让路后该值立即归 0，因此"正在开但已让路"的帧不会阻塞 attach —— 行为正确，无需改。
5. **`:848` 与 `:869` 两次 `s_Halt = 1` 之间无 `KeMemoryBarrier`**：两次都是普通 volatile 写，依赖 `:851`/`:870` 的 `InterlockedCompareExchange` 提供屏障。x64 上成立；ARM64 上 `InterlockedCompareExchange` 自带全屏障，也成立。属"能工作但靠隐式屏障"的写法，非缺陷。
6. 报告口径：本文件所有"正确/安全"仅指"按代码路径推演未发现内存不安全"，**未经真机或 Verifier 验证**。

## §6 只有真机 / Driver Verifier 能定的

- `s_Reopen` / `s_Halt` 的最终收敛性：源码上只能证明"不永久为 1"，不能证明"实际会在有限时间内关一次"。
- 卸载期 REFRESH 竞态（§3.3）：需要 Driver Verifier（special pool + handle tracing）+ 并发 `l2 disable`/REFRESH 压测，观察卸载后是否残留 `\??\X:\RAMBoostL2.bin` 句柄与 8.4MB 池。
- 双放弃（§2-E）的实测发生率：需要通过 ETW/`l2 status` 观察"`l2 disable` 后仍报 opened"的实际出现频次，决定是否值得给 flags-off 分支补一个 `s_Reopen=1` 让 tick 有机会重试（但 tick 本身被 flags 门挡住，真要修得改 `rbfeat.c:517` 的门条件，属于设计决策，不在本单范围）。
