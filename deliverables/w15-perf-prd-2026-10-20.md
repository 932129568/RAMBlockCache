## 二、现状基线与症状归因（实测定局，采信主理人代码级取证）

**基准数据**（AS SSD Benchmark 2.0.7316，D: Crucial MX500 1TB SATA SSD，卷已挂载、直写模式）：

| 指标 | 实测 | MX500 物理能力参照 | 判定 |
|---|---|---|---|
| Seq 读 | 504.92 MB/s | ~530–560 | 盘速，零加速 |
| Seq 写 | 409.58 MB/s | ~455–510 | 盘速，零加速 |
| 4K 读 QD1 | 61.55 MB/s | ~40–90 | 盘速附近（冷缓存） |
| 4K 写 QD1 | 41.50 MB/s | ~110–136 | **低于盘速，疑似负优化** |
| 4K-64Thrd 读 | **3132.89 MB/s** | ~388（~97K IOPS） | 内存级＝缓存命中，**唯一生效项** |
| 4K-64Thrd 写 | 91.91 MB/s | ~341（~85K IOPS） | 盘速档 |

**症状 → 根因链**（全部有代码实证，行号已核）：

| 症状 | 根因 | 证据 | 后果 |
|---|---|---|---|
| ① 顺序读写「没加速」 | **B1** 8MB 透传门：`len > (8UL << 20)` 直接 passthrough | `rbio.c:773` | AS SSD Seq 的 16MB 块 100% 旁路缓存，顺序读写零加速 |
| ② 「仅一项优化生效」 | **B2** 预取默认关：RbPrefStream 经数据路径钩子调用，但部署默认 `Features\Flags=0` 全关（红线）→ 预读空转、顺序流无预热；**B4** 写模式默认直写（红线） | `rbio.c:324` 钩子 + `rbfeat.c` Flags 门；`rb_proto.h:85 RB_DEFAULT_WRITEBACK=0` | 唯一生效的 4K-64Thrd 读靠同 run 前置测试把工作集预热进缓存；顺序流无预热、写永远盘速 |
| ③ 「4K 随机慢」 | **B3** 直写路径同步+拷贝：整段 RbSyncIo 同步下盘→成功后 `rb_read_commit` 再拷进缓存；每 IO 还有 RB_SYNCCTX 分配+同步 IRP 构建+事件等待；QD1 串行读同吃每 IO 机制开销 | `rbio.c:481-488`、`127-175` | 写延迟=盘写+机制开销；4K QD1 写低于盘能力 |
| （诚实项） | **B5** 物理下限：冷缓存首次读（顺序或 4K）不可能超过盘物理速度 | 4K-64Thrd 读 3132 MB/s 反证热数据已内存级 | 冷读提升空间有限，热读/写提升巨大——必须管理用户预期 |

## 三、产品定义

### 3.1 产品目标（3 个，正交）

- **G1 顺序读写进入加速面**：拆 8MB 透传门 + 逐卷回写配置引导，使 Seq 从「100% 盘速」变为「第二遍内存级、第一遍有预热」。
  - 量化预期（**预估**）：Seq 写 409→**900+ MB/s**（回写标脏即 ack，受内存预算约束见 R5）；Seq 读二次扫描 504→**2000+ MB/s**（memcpy 带宽档，4K-64Thrd 读 3132 MB/s 已实证缓存数据面可达内存级）。
- **G2 4K 随机写进入加速面并消除负优化**：回写让写标脏即返回；直写路径轻量化消除每 IO 机制开销。
  - 量化预期（**预估**）：4K 写 QD1 41.50→**300+ MB/s**（回写，内存吸收速度）；直写模式下回到盘能力档 **110+ MB/s**（消除负优化，不依赖回写）。
- **G3 4K 随机读削减机制开销 + 冷读预期管理**：命中路径去冗余跳转/双拷；对用户明示「冷读首遍=盘速是物理下限，不是缺陷」。
  - 量化预期（**预估/部分已证实**）：冷 QD1 读 ≥61.55 不劣化、向盘能力上限收敛（65–75 MB/s 量级，若盘 QD1 读能力即 ~65 则空间有限——B5 诚实项）；热读保持 **3000+ MB/s**（已证实，验收只要求不回归）。

### 3.2 User Stories

1. 作为视频剪辑师，我希望 >8MB 大块的顺序读写能被缓存加速，这样二次剪辑/导出不必重复等盘。
2. 作为游戏玩家，我希望 4K 随机写（存档/着色器编译）不再卡顿，这样回写开启后写延迟从毫秒级降到微秒级。
3. 作为新装机用户，我希望首次向导用一句话讲清「回写=写加速的唯一入口」并引导我开启，这样我能知情决策，而不是对着没变化的跑分困惑。
4. 作为技术用户，我希望顺序读第一遍就有预读加速，这样影视/扫描/拷贝的冷启动体感改善（依赖拍板项 Q1）。
5. 作为 QA，我希望有固定的 AS SSD 复测矩阵与判据 + 计数器曲线，这样每项改动可归因、可回归，终结「看不出变化」争议。

## 七、给架构师的关键约束（改动正确性的隐藏地雷，必答）

### 7.1 pre_dirty 掩码 8MB 覆盖约束（L1-1 的正确性前提）

- `rbio.c` 写回路径的「写前脏掩码快照」`pre_dirty[256]` = 2048 位 × 4K 子块 = **仅覆盖 ≤8MB 的写入**（注释 line 416-418 明示 "len<=8MB → 2048 子块 = 256B"）。
- 现状安全性依赖：8MB 透传门保证进入写回路径的 `len` 恒 ≤8MB，故 line 432 的掩码溢出分支标称「理论不可达」，走保守记账（`pre_bits=0`、`pre_dseq=NULL`，无证据当有早期脏）。
- **门一提高到 64MB，>8MB 的回写写入会真实触发溢出**→保守记账：语义安全但丢回滚精度（失败回滚时「早期已 ack 脏」被多丢）。
- **必答项（二选一或组合，禁止「放任溢出走保守记账」作为交付形态）**：
  - (a) **按 8MB 分块**：>8MB 回写写入按 8MB 切块逐块走现有快照逻辑（推荐，语义不变；切块点 4K 对齐）；
  - (b) **掩码扩容**：DseqBuf 2048→16384 项 + pre_dirty 同步扩容，须评估每 worker 非分页常驻（64KB×worker 数）代价。
- 关联约束：写路径 `rb_write` 的 direct 区间上限 `RB_MAX_RANGES=32`（`dcnt` 超限已有整段直写兜底 `rbio.c:435`）；门限抬高后大 IO 的 direct 区间数变化需评估。

### 7.2 同步 IO 机制（L1-2/L1-3 的评估底座）

- `RbSyncIo`（`rbio.c:127-175`）每 IO = `ExAllocatePool2(RB_SYNCCTX)` + `IoBuildSynchronousFsdRequest` + `KeWaitForSingleObject`（15s 步进超时+`IoCancelIrp` 取消逻辑）+ 完成例程收尾。观测 QD1 写 ~198µs/IO vs 盘能力 ~36µs。
- 池化/复用必须保持：取消语义（取消已请求仍继续等、**绝不弃缓冲**）、完成例程 `STATUS_MORE_PROCESSING_REQUIRED` 的 IRP 所有权约定、PASSIVE 级完成收尾。
- 异步化（L1-3）还须论证：写穿/回写失败路径的错误传播与 `RbNoteIoResult` 熔断语义（连续失败 ≥32 全局透传）不破坏。

### 7.3 透传门与 staging 峰值（L1-1 的内存评估）

- 8MB 门同时是 worker staging 尺寸假设的安全阀，不只是缓存策略。
- 读路径 `RbReadMissRange`（`rbio.c:277`）按 miss 区间长度向 **per-worker staging**（`RbStageGet`）取缓冲：门限→64MB 意味着单 worker staging 峰值同步放大，**最坏非分页峰值 = 64MB × 并发 worker 数**。抬门前必须给出 staging 策略结论（按需扩容上限/分片/大 IO 直读 IRP 缓冲免 staging），否则抬门=抬内存峰值（R2）。
- 写路径 `tgt` 缓冲来源（IRP 映射 vs staging）须架构核验；写穿双拷的「去拷贝」方案依赖此结论。
