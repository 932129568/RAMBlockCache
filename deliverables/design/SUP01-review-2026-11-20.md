## 2. 三问直答

### 2.1 问一：`seq=7` 的「①`Engine==NULL` 可证」这个结论，证据链有没有洞？

**答：结论可证、成立；但 `J11` 这条判据的写法有 2 个洞（1 个必须补，1 个应当换）。**

报告给的链条是三条同向证据（`SUP01:662-675`）：

```
① :84  ERROR [440] self-disable: armed boot failed, not attaching any volume
② :88-95 WARN [432] self-disable: not attaching (armed boot failed)   ×8
③ :79-96 该会话 "engine + worker pools lazily started" 零命中
④ :96 01:19:11.292Z 之后到 :97（02:18:35Z）无任何行
```

我逐条重数过，**四条全部与日志逐字吻合**（`:84` 单条、`:88-95` 正好 8 条、
`:79-96` 无 `engine` 行、`:96`→`:97` 之间零行）。且 `[1254]/[1425]/[1430]` 属 S4/S5，
`[1392]/[1397]` 属 S1/S2/S3 —— 行号指纹作为**一次性旁证**用在这里是对的（不能作判据，见 §2.3-③）。

**洞 1（必须补）：③ 这一条 leg 在一般情形下不成立。**
"该会话零次 `engine + worker pools lazily started`" **不等于** "该会话全程 `Engine==NULL`"，
因为**引擎有第二个创建点**，且它不打这句话：

```c
/* src/driver/rbquiesce.c:18-38  RbCreateEngineOnly（重建专用） */
g_Rb.Engine = rb_engine_create(&cfg);          /* :34  ← 第二个创建点 */
RbLog(0, __LINE__, (LONG)newBs, L"rebuild: engine created (pools kept running)");  /* :37 ← 另一句话 */
```

`RbCreateEngineOnly` 只在 `rbrebuild.c:583/591/603` 被调（重建事务）。**它建引擎但不打
`engine + worker pools lazily started`** ⇒ 一个"发生过重建、后来引擎又被销毁"的会话，
会同时满足 ③（零 `engine` 行）与"关机时 `Engine==NULL`"，而中间**真的有过引擎**。
这不推翻 `seq=7` 的结论，但 `J11` 作为**可复用判据**必须补一句：
**"且该段内零次 `rebuild: engine created`（`rbquiesce.c:37`）"**。

对 S4 这一条我实测是**闭合的**：`grep -c 'rebuild:' driver-20261120.log` = **0**。
所以 S4 不存在"重建过又销毁"这条路 ⇒ 结论不受影响。**洞在判据的可复用性上，不在本次结论上。**

**洞 2（应当换）：② 这一条 leg 用的是跨会话推理，同会话有更硬的证据没用上。**
"8 次 `not attaching` 恰等于其它会话的 8 条 `[524] AddDevice`" —— 这个"恰好等于"是
**拿别的会话的卷栈数比出来的**。S4 自己没有任何卷枚举行。更直接、同会话、零推理的证据是：

```
S4 段（:79-96）内 "AddDevice: filter on volume stack"（[524]）出现次数 = 0
```

因为 `rbmsg.c:431-434` 是 `RbAddDevice` 的**首句**：`if (RbSelfDisabled()) { RbLog(1,...[432]...); return STATUS_SUCCESS; }`
⇒ 一个过滤设备都没建。**没有过滤设备 ⇒ 没有卷 ⇒ 没有任何 attach 入口 ⇒
`RbEnsureEngine`（全树只有 `rbattach.c:1193` 与 `:1579` 两个调用点）零调用 ⇒ `Engine==NULL`。**
这条链比"数 8 条日志"强一档，而且**不需要跨会话比较**。建议 `J11` 的 leg ② 换成这一条。

**不是洞、且我确认成立的三处地基**（这几条报告写对了，我逐行核过）：
- **`qst=0` ⇒ 持久化体被真正到达。** `RBD4` 落盘在 `if/else` **之外**（`rbmsg.c:393-402`），
  所以"有 RBD4 记录"并不能证明走了成功分支；能证明的是 `rec2[5] = qst`（`:400`），
  `qst = RbFeatStopTick()`（`:263`）为 0 ⇒ `NT_SUCCESS` ⇒ 走 `:272` 的 `if` ⇒ `:285` 调
  `RbShutdownPersist()`。**`qst=0` 是这条链上不可替代的一环**，报告 §5 结论 2 用对了。
  （反向也成立：`RbFeatStopTick` 的 CAS 认领失败会返回 `STATUS_DEVICE_BUSY`（`rbfeat.c:611-616`），
  qst 就不会是 0 ⇒ 走 `else` ⇒ `whyOut` 留 `0xFF`。所以 `qst=0` 还顺带排除了"并发认领失败"。）
- **`cleanNow` 首项为假是唯一的。** `rbmsg.c:725-726` 是合取式，
  `Engine==NULL` ⇒ 首项假 ⇒ `cleanNow==FALSE` **与脏页多少无关** ⇒ `:743` 是**唯一**可能的出口。
  报告说的"不是两种可能之一，是唯一可能"，字面成立。
- **`:732` 不可达 ⇒ A4-d 结构性不可达。** 不是"没触发"，是"到不了"。报告这一处措辞准确。

**结论**：`seq=7` 是可证的。补 1 条 leg、换 1 条 leg 之后，`J11` 才配得上"可确证"这个等级。
在补之前，`J11` 是"对本例可确证、作为判据不完备"。

### 2.2 问二：把 `(1,7)` 当作「A4-d 首证」这个用法，对不对？该用什么代替？

**答：不对。代替物是 `(7,9)`，而且它有一条可写出来的触发路径。**

**为什么 `(1,7)` 一定不能当 A4-d 首证**（理由已不再是"件旧"，那条理由报告已自行撤回、我复核认可）：

A4-d 的签名是 `WHY_WITHHELD(7) → SKIP_CLEAN_WITHHELD(9)`（`rbmsg.c:89`）。
这两个值只能在 `RbRegSetClean(1)` **返回 FALSE** 之后产生（`:732-734`）。
而 `RbRegSetClean`（`rbdriver.c:216-254`）的卷数门在 `:231-242`：
`nVol = RbCountAttachedVolumes(); if (nVol == 0 && !RbBootAttachedAny()) { 写 LastCleanWithheld=1; return FALSE; }`。
⇒ **`(7,9)` 的必要条件是"执行到了 `:732`"**。
`Engine==NULL` 时 `cleanNow` 先假，`:727` 的 `if (cleanNow)` 整块不执行 ⇒ `:732` 到不了。
所以 **`Engine==NULL` 这一整类情形，A4-d 的覆盖面是 0**，而且它被**错误编码**成 `why=1 DIRTY`。
这不是"更窄的路径"，**这是本机实际走过的那条路径**（§4）。

**代替物 `(7,9)` 的可达路径（我推导，含代码链，供 299 批次验证）**：

`(7,9)` 要求同时满足：`Engine != NULL` ∧ `total_dirty == 0`（否则 `cleanNow` 假）
∧ `RbCountAttachedVolumes() == 0` ∧ `RbBootAttachedAny() == FALSE`（票没置）。

**先把"引擎从哪来"钉死**（枚举不全，后面就会漏掉一整条路）：`g_Rb.Engine` 全树 **5 个赋值点**
= **2 个创建点** + **3 个置 NULL 点**。
创建：`rbattach.c:486`（`RbEnsureEngine` 内）、`rbquiesce.c:34`（`RbCreateEngineOnly` 内，不启池）。
置 NULL：`rbattach.c:504`（flush 线程启动失败的回滚）、`rbdriver.c:1186`（销毁）、`rbrebuild.c:574`（换出后锁外销毁）。
⇒ **`Engine != NULL` 有 2 个来源，其中只有 `RbEnsureEngine` 能在票未置时造出引擎。**
`RbCreateEngineOnly` **进不去**这个状态（`rbrebuild.c:467 if (!g_Rb.Engine) { st = STATUS_DEVICE_NOT_READY; goto out_clear_gate; }`
—— 它要求引擎**已经存在**），但它**能把这个状态保下来**：重建事务 `:574` 把引擎换出置 NULL、`:583 RbCreateEngineOnly`
按新几何回建，全程不碰票，而 `RbRebuildSnapshotVolumes`（`:141` 要求 `IsAttached && Stream`）零卷时 `volCount==0`
不阻断重建（`volCount==0` 全程没有非零断言）⇒ **该窗口可以跨若干次几何重建长期存在**，不是"一关机就过去"。
**证据等级：代码上可达、本机未观测**（S4 是 `self-disable` 态，`RbAddDevice` 全早退，连控制面都没有，不会触发重建）。
写在这里的用处只有一个：**别把"`(7,9)` 需要一次导入"想成"只能靠改代码才能出现"** ——
`rb_stream_create` 的 `STATUS_INSUFFICIENT_RESOURCES` 在低内存机器上是真实可能发生的运行期事件。

**这条路径与 `rbquiesce.c:126` 那个窗口共用同一个构造条件 —— 这一条值得单独写出来，它把两条看起来无关的路收在一个触发点上。**

先说清"零卷重建"这个前提（我逐行核过，不是推测）：
`RbRequestGeometryRebuild` 的前置门（`:785-790`）只有 `Unloading` 与 `s_RebuildInFlight`，**没有"至少挂过一个卷"的门**；
`RbRebuildSnapshotVolumes` 零卷时返回 `0` ⇒ `RbRebuildDetachAll(vols, 0)` 的 `for (k = 0; k < count; k++)`
（`rbrebuild.c:227-244`）**一次都不进循环体** ⇒ **`RbDetachStreamForRebuild` 压根不被调用**，
空循环返回 `TRUE` ⇒ 一路走到 `:583 RbCreateEngineOnly`。`volCount` 全部 11 处使用（`:276/:438/:463/:486/:506/:551/:555/:618/:627/:648/:667`）
**没有一处断言其非零**。

于是两条路共用同一个触发点 `rb_stream_create` 失败：
- **要 `(7,9)`**：`rb_stream_create` 失败 ⇒ 引擎在、票未置、零卷 ⇒ 关机 `cleanNow==TRUE` ⇒ 卷数门扣留。
- **要"跨重建存活"**：**同一个**失败态之上的那次 `set block=` ⇒ 零卷重建放行 ⇒ `:574` 换出、`:583` 回建 ⇒ **票仍未置**。

⇒ **一次分配失败同时产出了"可观测的 `(7,9)`"和"一个能跨任意次重建存活的窗口"** ——
这也是为什么 §2.2 与 §2.3 那条注释建议必须一起读：**注释里那句"重建只对已 attach 的卷跑"在零卷情形下是空指**（说的是一件没发生的事），
准确写法是「**进 `vols[]` 的卷**必须 `IsAttached && Stream`；**零卷重建不调本函数**」。

三个"卷/票"条件里，**票只会被 `rbattach.c:1203` / `:1587` 两处置 1**（`s_BootAttachedOnce` 全树只有 3 处引用：
`:1615` 静态初值、`:1619` 置 1、`:1624` 读 —— **无复位点**，本引导内一旦置 1 永不复原），
而这两行都在 `RbEnsureEngine()` 成功**之后**、且都在 `ext->IsAttached = TRUE`（`:1202` / `:1586`）之后。
于是唯一能同时满足"引擎在、票没置、卷数 0"的路径是：

```c
/* rbattach.c:1193-1198（自动挂载路径；:1579-1584 运行期挂载同款） */
st = RbEnsureEngine();                      /* :1193  引擎建成功 */
if (!NT_SUCCESS(st)) break;
if (!ext->Stream) {
    ext->Stream = rb_stream_create(g_Rb.Engine, ...);   /* :1196 */
    if (!ext->Stream) { st = STATUS_INSUFFICIENT_RESOURCES; break; }  /* :1197  ← 中断点 */
}
...                                         /* :1202 ext->IsAttached = TRUE 到不了 */
RbBootMarkAttachedOnce();                   /* :1203 票置不了 */
```

`rb_stream_create` 会因三次分配失败返回 `NULL`（`cache.c:343-353`：`s` / `s->buckets` / `s->stripes`）。
⇒ **引擎已建、票未置、零卷、`total_dirty==0`（新引擎必然 0）** ⇒ 关机时
`cleanNow == TRUE` ⇒ `:732` 执行 ⇒ 卷数门命中 ⇒ `why=7` ⇒ `skip=9`。

⇒ **这就是 A4-d 首证的唯一可制造路径**：一次"引擎建成功但流创建失败"的挂载
（两个站点：`:1193-1198` 自动挂载、`:1579-1584` 运行期挂载；两者结构同构，
都在 `:1202/:1586` 之前被 `rb_stream_create` 的失败出口截断）。
**它是运行期事件，不是只能靠改代码制造** —— 三次分配任一失败即可（低内存/高碎片机器上真实存在）；
**要把它变成"可复现的证"才需要受控注入**（改代码或加测试钩子），那一步**不在本冻结批**。在此之前，
**唯一不改代码就能拿到同等判别力的办法是 Path 1**（把 `Engine!=NULL` 与 `total_dirty` 写进 `RBD4`，§9）。

**这条推导最脆弱的一根支柱（必须写进注释，否则等着被"补对称"补掉）**：
`ext->IsAttached = TRUE` 全树 **3 处**（`rbattach.c:1202` / `:1586` / **`rbquiesce.c:126`**），
而置票 **2 处**（`rbattach.c:1203` / `:1587`）。第三处是重建事务的"刷不下去、就地复原"分支
（`rbquiesce.c:96-131`：`:108 IsAttached=FALSE` → `:115` 取流 → `:117/:119` 两趟 flush + `:118` drain
→ `:123 if (rb_stream_dirty_bytes(st) != 0)` → `:126 IsAttached=TRUE` → `:128 return FALSE`）。
**`rbquiesce.c:126` 不得补 `RbBootMarkAttachedOnce()`。**

**但理由要说准，不能写成"补了就毁掉 `(7,9)`"** —— 那个说法在本文件里被我核过，**不成立**：
`RbDetachStreamForRebuild` 的唯一调用者是 `rbrebuild.c:238`（`RbRebuildDetachAll` 逐卷，`:506` 是唯一调用点），
而**进 `vols[]` 的卷**必须 `IsAttached && Stream`（`rbrebuild.c:141` 的快照判据）——
**注意：不能说成"重建只对已 attach 的卷跑"**：零卷重建时 `volCount==0`，`RbRebuildDetachAll(vols, 0)`
的 `for (k = 0; k < count; k++)` 一次都不进循环体，**`RbDetachStreamForRebuild` 压根不被调用**，
那句在零卷情形下是**空指**（说的是没发生的事）。准确写法是"进 `vols[]` 的卷"这个前提条件。
⇒ 凡是**走到** `:126` 的卷，其 attach 早就走完了 `:1202/:1203` ⇒ **票在本引导内已是 1（且无复位点，见上）**
⇒ 在 `:126` 补票是**幂等冗余**，写不写都不改变票的值。正确理由是**语义**：

**顺带把 `ext->Stream` 的写入点枚举补齐**（我上一封只报了 2 处赋值，那是"建流"的点，不是全部写点）：
**非 NULL 写 2 处** —— `rbattach.c:1196`（自动挂载）、`:1582`（运行期挂载），都是 `rb_stream_create` 的返回值；
**置 NULL 写 3 处** —— `rbattach.c:858`（`RbVolumeRemove` 销毁流）、`rbdriver.c:561`（僵尸回收）、`rbrebuild.c:267`（重建摘流），
全是 `InterlockedExchangePointer(&ext->Stream, NULL)`；`rbquiesce.c:115` 是 `InterlockedCompareExchangePointer(..., NULL, NULL)`，
**比较值与交换值同为 NULL ⇒ 纯读**，不是写。外加 `rbdriver.c:597 e->Stream = Stream` 是**诊断环记录字段**（`RB_DIAG_EVENT`），不是 `RB_DEV_EXT`。
⇒ 结论不变：**"stream 非 NULL 而票为 0" 无路径** —— 2 处建流点之后紧接 `:1202/:1203`（或 `:1586/:1587`），中间无早退；
3 处置 NULL 只做减法，不会造出"有流无票"。

- 该分支是**撤销本函数刚做的 `:108 IsAttached=FALSE`**，不是"一次新的挂载成功"。
  票的语义是"本引导 attach 真的成功过"（`rbattach.c:1608-1613` 的注释自述），而这里既没有新建流
  （`:115` 取的是原流）、也没有让卷进入可用态（`:128` 返回 FALSE 后调用方回滚几何重建）。
  在此置票 = 让"复原动作"冒充"成功动作"。
- 真正的危险不是毁掉 `(7,9)`，而是**把这条不对称一直留在没有解释的状态**：
  下一个人（或下一次 AI 扫代码）看到"3 处置 TRUE、2 处置票"，标准反应就是补齐第三处。
  补的那一次**恰好无害**，但它会把这条不对称**洗完**，于是"置票点必须紧跟成功的 attach"这条纪律
  在代码里就再也找不到反例 —— **下一次真正会破坏语义的补票（比如加在 `:108` 之后、或加在 detach 路径上）就不会被任何人看出不对**。

⇒ 建议的注释文本（`rbattach.c:1613` 那一行改为，**不改 `src/**`，仅给文本**）：

```
 * 只在两处 ext->IsAttached = TRUE 之后置 1（rbattach.c:1202 / :1586 两站），
 * 即"attach 真的成功过"。第三处 ext->IsAttached = TRUE 在 rbquiesce.c:126
 * （重建事务刷脏失败的就地复原分支）：那是**撤销** :108 的关 inflow、不是新的
 * 挂载成功，故**故意不给票**。且该路径上票必已为 1 —— 进 vols[] 的卷必须
 * IsAttached && Stream（rbrebuild.c:141），而这两态的达成必然已经过
 * :1202/:1203 或 :1586/:1587。零卷重建不调本函数。
 * 补票是幂等冗余，但会洗掉"置票紧跟成功 attach"这条不对称的唯一反例 ——
 * 请不要为了对称而补。
```

**顺带一条必须写进 299 的话**：`(1,7)` 不是 A4-d 首证，但它**是**主张 4 的证
（"持久化函数体进入过、并以 DIRTY 退出"）—— 两者**不能互相借力**。报告 §6 结论 1 与结论 2
分开写，是对的，我认可。

## 3. `why=1` 的四路优先级：排序对不对、有没有第五路、哪一路代价判错了

报告 `§8.3`（`SUP01:317-347`）给的是：

```
why=1 不唯一，按序排除（先排除的代价最低、最可能是真因）：
  ① Engine==NULL（本引导一个卷都没挂上）
  ② flush_acquire 2s 超时 ⇒ 整轮 flush 被跳过
  ③ flush 与 has_dirty 之间的并发写者（rbmsg.c:694 返回后、:726 读取前）
  ④ 真残留脏页 —— 前三条全部排除后，才轮到它
why=1 单独出现，不构成"有脏页"的证据。
```

**裁决：方向对、① 的排序对、② 的"排除代价"判错了、③/④ 在产物上不可分、缺第五路。**

### 3.1 ① 放第一：正确，而且是"零成本可排除"

`driver-<date>.log` 里 `[440]` + `[432]×N` + 零 `engine` 行三条一 grep 就能定，且**本次实测就是 ①**。
排除代价 = 读一个日志文件。**这条排序没有争议。**

### 3.2 ② 放第二：**代价判错了，而且注解给的排查动作是空的**

注解写「② `flush_acquire` 2s 超时 ⇒ 整轮 flush 被跳过 … → **日志里有对应的 flush 跳过行**」。
**没有那条日志。** 我核过三层：

- `src/core/cache_flush.c` **全文零 `RbLog`**（`grep -n "RbLog\|LOG("` → 无命中）。
- core 层**根本没有日志能力**：`cache_internal.h` 的 include 列表里没有 `rblog`/`rb_logq`
  （`grep -n include cache_internal.h` 只有 `fltkernel.h` / `cache.h` / `rb_wiring.h` / `rb_percpu.h` / libc 头）。
- `flush_acquire` 失败唯一的痕迹是 `s->flush_exec_seq` **不递增**（`cache_flush.c:446`），
  而 `rb_stream_flush_exec_seq` 的唯一读者是 **FLUSH IRP 路径**（`rbio_worker.c:1305-1308`，
  按"某一条流的第几次"做前后差分），**关机路径上没有读者**。
  `RB_FLUSH_STAT_INC(sflush)`（`:425`）也只进 `g_flush_pcpu` 计数器，**全树没有任何对外出口**
  （`grep -rn "g_flush_stat\|g_flush_pcpu"`：只有定义点 `cache.c:14/15/17`，无读者）。

⇒ **② 是四条里最难排除的一条，而不是第二便宜的。** 现存产物**无法**把它与 ③/④ 分开。
注解应改为「② 当前**不可**从产物排除（core 层无日志、`flush_exec_seq` 无关机侧读者）」。

### 3.3 ③ 与 ④ 在产物上不可分（所以"③→④"不是排查顺序，是猜测顺序）

③ 与 ④ 是**同一个合取项**（`Engine != NULL && total_dirty > 0`）的两个子情形，
区分它们需要 `total_dirty` 的数值 —— **`RBD4` 里没有这个字段**（`rbmsg.c:394-400` 六元素：
`magic/seq/why/skip/epoch/qst`）。所以"先排除 ③ 再看 ④"在现有产物上是**做不到的**，
只能靠"量级应与写负载同阶"这种口径判断，而那个口径本身不可证伪。

### 3.4 缺第五路：**计数器过报**（不是没刷完、也不是并发写，而是 `total_dirty>0` 本身不可信）

`cache_flush.c` 自己的注释承认计数器会漂：

```
/* :411-412 */ the running dirty counter still drifts transiently (observed as
               dirty underflow in test_counter)
/* :438-441 */ The running mark/clean counters are exact under the per-stripe WLOCKs
               (verified: fixed-seed 1..200 + ASan). No concurrent reconciliation here:
               a stripe-by-stripe bitmap walk is racy in both directions and corrupts
               the exact counter (caused the historic dirty underflow).
```

`rb_engine_has_dirty()` 是 `RB_ALOAD64(&eng->total_dirty) > 0`（`cache_stats.c:49-50`），
**一个纯计数器判断，不做盘面核对**。`total_dirty` 的加减点我 grep 全树，**7 处**
（`cache.c:104 / :186 / :213 / :232 / :461`、`cache_write.c:516 / :577`），全部是
`RB_AADD64` 无符号加减，**没有任何钳位或反向对账**（`grep -rn "define RB_AADD64" src/` 三处定义全是裸 `InterlockedExchangeAdd64`）。
⇒ **`total_dirty > 0` 可以在"盘上零脏数据"的情况下成立** ⇒ `why=1` 而实际零丢失。

这条与 ③ 的区别很关键：**③ 需要并发写者，⑤ 不需要**；③ 是一次性的，⑤ **可能持久存在**。
这条既不在 `RB-postreboot-verify.ps1:510-527` 的三条里，也不在
`read_shutdown_sentinel.py:238-250` 的三条里。**这是我要求补的第五路。**

**（可达性声明：⑤ 是"代码上可达、本机未观测"，不是"已经发生"。§8.8 的教训在这里适用 ——
不许把"可达"写成"发生了"。）**

### 3.5 修正后的写法（建议替换 `§8.3` 那段注解，**不改判据、不改 rc**）

```

     ① Engine==NULL —— 可确证：self-disable + [432]×N + 该段零 [524] + 零 engine 行 + 零 rebuild 行
  B. 当前产物上不可排除（四条并列，不排序）：
     ② flush_acquire 2s 超时整轮跳过   ← 无日志、核心层无日志能力，不可从产物排除
     ③ flush 与 has_dirty 之间的并发写者 ← 需要 total_dirty，RBD4 里没有
     ④ 真残留脏页                      ← 同上，与 ③ 不可分
     ⑤ total_dirty 计数器过报           ← cache_flush.c:411-412 / :438-441 自述会漂；同样需要 total_dirty
why=1 单独出现，不构成"有脏页"的证据。要分开 B 组，必须把 Engine!=NULL 与 total_dirty 写进 RBD4（299 / Path 1）。
```

**为什么这样改**：现有写法给运维一个**假的排查路径**（"去看那条 flush 日志"），
走到第二步就断头，断头之后人会**默认落到 ④「真残留脏页」**——正是 §8.3 自己想避免的那个错误动作。
**排不掉的三条必须明说排不掉，否则"按序排除"就是把 ④ 变成默认答案。**

## 5. 一次关机可派发两次 ⇒ `(1,7)` 只代表「最后一次派发」

**硬事实（我独立解出，与报告一致）**：

```

off=384  RBD4 seq=5  why=0 skip=0xFFFFFFFF epoch=1 qst=0   ← CLEAN（真的写成功过）
off=480  RBD3 seq=6  irql=0 isCtl=1  t=2026-11-20T01:17:53.077524Z   ← 隔 110.0 s
off=504  RBD4 seq=6  why=1 skip=0x00000007 epoch=1 qst=0   ← DIRTY
off=600  RBD3 seq=7  irql=0 isCtl=1  t=2026-11-20T02:17:46.599342Z   ← S4 的关机
off=624  RBD4 seq=7  why=1 skip=0x00000007 epoch=1 qst=0
```

⇒ **`(1,7)` 的语义是「该关机（或该会话）最后一次控制设备派发的判词」，不是整体判词。**
这条直接影响"R7 没触发证据不算验证"怎么用：**只读注册表的人永远看不到那条 CLEAN；
只有 `RBD4` 这条追加文件通道留住了它。**

**并且这条解释了"为什么日志里没有 `seq=6` 对应行"**：`RbLog` 只写内存环（`rblog.c:35-61`，
无 `ZwWriteFile`），关机末刻会丢；`RbDiagWriteSentinel` 是 `FILE_WRITE_THROUGH` 同步写
（`rbmsg.c:171-194`，`FILE_APPEND_DATA | SYNCHRONOUS_IO_NONALERT | FILE_WRITE_THROUGH`）
⇒ **记录留住了、日志没留住**。⇒ **`RBD4` 是这条链上唯一没丢的证据通道**，这也再次说明
不能靠日志判关机结果。这一条我复核认可，无保留。

**但叙事要降一级**：「同一次关机的第二次派发」是**推理**（§2.3-①）。改成
「同一会话内的第二次控制设备派发」，**结论不变**。

### 11.2 关于「四个点」/「五个点」这两个说法 —— 口径必须写清

不写「`why` 的 4 个 return 点」。**一个词之差，就是"全清单"与"某一段"之差。**

### 11.3 一条与基线同级的补充事实：`WHY` 值本身还有生产点，`return` 不是唯一形式

`RbShutdownPersist` 返回的是 `RB_PERSIST_WHY_*`；但落到 `WhyPrev` 上的值经过两道：
`rbmsg.c:285 ULONG why = RbShutdownPersist();` → `rbmsg.c:314 whyOut = why;` → `:397 rec2[2] = whyOut`，
且成功分支另有 `rbmsg.c:307 RbRegSetDW(L"ShutdownPersistWhy", why)`。
**而 `whyOut` 的初值是 `0xFFu`（`:264`）**，两条分支都往 `RBD4` 落盘（`:393-402` 在 `if/else` 之外）。

⇒ **基线必须包含这一条**：`RBD4` 里读到 `why=0xFF` **不代表** `RbShutdownPersist` 返回了 `WHY_NONE`

## 12. 块 2：裁决 —— 「四路缺一不可」**是排查顺序，不是判定条件**

### 12.1 原文与两种读法

`SUP01:345-347`：

> **为什么③必须进注解**：它**良性但不好看** —— 刷盘成功、一个字节都没丢，却记成"不干净"。
> 若注解只写"刷完仍有脏页"，运维会把一次完全正常的关机当成数据事故去查；
> 反过来，若把 `why=1` 一律当良性，④ 这个真问题会被放过。**四路缺一不可。**

**读法 P（判定条件）**：四路同时成立，才算对 `why=1` 归因成功。
**读法 Q（排查顺序）**：按序逐路排除，全部排除则归因失败。

### 12.2 裁决：**只能是读法 Q。读法 P 是一个不可满足的判据。**

**理由三条，从硬到软：**

1. **读法 P 在本轮的真机数据上自证不可满足。**
   ① 与 ④ 是**互斥**的：① 要求 `Engine==NULL`，④ 要求 `Engine!=NULL && total_dirty>0`
   （`rbmsg.c:725-726` 的 `cleanNow` 合取式）。二者不可能同时成立。
   ⇒ 若把「缺一不可」当判定条件，**`seq=7` 这条已确证的记录反而"归因失败"** ——
   而报告 §8.9 明确说它是 ①。**读法 P 直接否掉报告自己的结论。**
2. **`why=1` 是单值单记录，一个值只能有一个成因。**
   `RbShutdownPersist` 是直线代码，`why` 是**一次** `return` 的结果（`:285` 单次调用）。
   四路不是四个并发条件，是**四个互斥候选**。对互斥候选说「缺一不可」，
   等同于说「必须有四个成因才叫一个成因」。
3. **报告自己的用法就是读法 Q。** `§8.9(3)` 写「前三条全部排除后，才轮到它」——
   这是顺序，不是合取。**错误只出在 `:347` 那四个字上，不在整段的设计上。**

### 12.3 但这个裁决**不推翻任何已有结论** —— 它只推翻一句话

**这是本次评审里唯一一次「一句话的字面含义决定判据是否可满足」的裁定**（§3.5 也是措辞改写，

## 13. 块 3：`why=1` 与 A4 `BootFailCount` 的因果边界

### 13.1 结论先说

**`why=1`（`RB_PERSIST_WHY_DIRTY`）出现在关机路径上，与 A4 的 `BootFailCount`
计数逻辑之间没有任何因果通道。两者走的是不同字段、不同函数、不同时间点。
`why=1` 既不证明也不否证 `BootFailCount` 是否算错。**

### 13.2 字段与函数分离（逐项核过）

| | `why` / `skip` 这条线 | A4 `BootFailCount` 这条线 |
|---|---|---|
| 注册表键 | `ShutdownPersistWhy` / `ShutdownPersistWhyPrev`<br>`PersistSkipReason` / `PersistSkipReasonPrev` | `BootFailCount` / `LastCleanShutdown` / `LastCleanWithheld`<br>`LastBootHealthy` / `BootReachedUser` / `FilterArmed` / `DeploySeq`-`DeployAck` |
| 生产点 | `rbmsg.c:307/:313`（写 Why/Skip）、`rbdriver.c:354-355`（翻 `*Prev`） | `rbdriver.c:427 RbRegSetDW(L"BootFailCount", fails)`（**唯一写点**） |
| 生产时机 | **关机**（`IRP_MJ_SHUTDOWN` → `RbDispatchShutdownDiag` → `RbShutdownPersist`） | **下一次开机**（`RbBootFailLoad`，`DriverEntry` 内 `rbdriver.c:1369` 调） |
| 消费函数 | `RbDiagWriteSentinel`（`rbmsg.c:171-194`）、`rbctl.c:1010-1015`、`rbfeatctl.c:493-503` | `RbBootFailLoad`（`rbdriver.c:326-441`）、`RbSafeModeLoad`（`:266-285`） |
| 判据位 | `RB-postreboot-verify.ps1:500-501` 的 `DIRTY` 行 | `check_a4_clean_gate.py`（A4 门禁） |

**`whyOut`/`skipOut` 的唯一消费者是 `RBD4` 落盘**（`rbmsg.c:397/:398`，我 grep 过
`whyOut|skipOut`：定义 `:264/:265`、赋值 `:314/:315/:367/:372/:377`、消费 `:397/:398`，
**没有第三个读者**）。而 `BootFailCount` 的判定输入里**没有任何一项来自 `why`**：

```c
/* rbdriver.c:416-427  A4 计数的全部输入 */
if (healthy == 1 || (ticket == 1 && clean == 1)) { fails = 0; }        /* :416-417 */
else if (depSeq != 0 && depSeq != depAck)        { grace = TRUE; }     /* :418-421 不计失败 */
else { if (fails < 1000) fails += 1; else fails = 1000; }              /* :423-426 */
RbRegSetDW(L"BootFailCount", fails);                                   /* :427 */
```

`healthy` = `LastBootHealthy`（`logon_disarm.ps1` 写）、`ticket` = `BootReachedUser`（`boot_guard.ps1` 写）、
`clean` = `LastCleanShutdown`、`depSeq/depAck` = `DeploySeq/DeployAck`。
**`why` 不在这个列表里。**

### 13.3 唯一的"相邻点"是 `LastCleanShutdown`，而它**不由 `why` 决定**

两者确实共享一个字段：`RbRegSetClean(1)` 写的是 `LastCleanShutdown`（`rbdriver.c:245`），
而 `RbShutdownPersist` 在 `:732` 调它。**但方向是单向且不可逆的**：

```
why=CLEAN(0)  ⇔  走到了 :732 且 RbRegSetClean 返回 TRUE   ⇒ LastCleanShutdown := 1
why=WITHHELD(7) ⇒ 走到了 :732 但返回 FALSE（卷数门/IRQL 门） ⇒ LastCleanShutdown 不变（仍是 0）
why=DIRTY(1)   ⇒ cleanNow==FALSE，:732 **压根没执行**      ⇒ LastCleanShutdown 不变（仍是 0）
why=DISABLED(6)/FROZEN(2)/BUSY(3) ⇒ 更早 return            ⇒ LastCleanShutdown 不变（仍是 0）
why=ALREADY(5) ⇒ **本条是例外，见下**                      ⇒ 取决于更早那次派发
```

**为什么 `ALREADY(5)` 必须单独说（我上一版这里写错了，改正）**：
`:687` 的条件是闩 `prev == RB_PERSIST_DONE`，而 `DONE` 由**三条**出口置位：
`:736`（CLEAN，`LastCleanShutdown:=1`）、`:733`（WITHHELD，不置）、`:711`（`mode!=FULL`，不置）。
⇒ **`why=5` 时 `LastCleanShutdown` 可能是 1 也可能是 0，取决于更早那次派发走到哪个出口。**
我上一版把 `ALREADY` 一并写成"仍是 0"，**那是错的** —— 这一条恰好证明 §2.3 的教训也适用于本文件。
**正确写法**：`why=5` 本身**不携带** `LastCleanShutdown` 的信息，必须回看同一次关机的**前一次派发**。
（这也和 §5 那条"一次关机可派发多次"扣在一起：**读 `why=5` 时必须先按 `seq` 找到前一条记录**。）

⇒ **`why != 0` 一律意味着 `LastCleanShutdown` 没被本次关机置 1** ⇒ 下一次引导
`RbBootFailLoad` 的 `clean` 读到 0 ⇒ 若 `healthy==0 && ticket!=1` ⇒ **算一次失败**。

**所以正确的因果句是**（这句话可以写进任何注解）：
**`why=1` 不是"`BootFailCount` 算错了"，而是"这一次关机没给下一次开机留下 clean 票"。
前者是指控 A4 逻辑，后者是 A4 的**正常输入**。**

### 13.4 但本轮 `seq=7` 这条 `why=1` **连这个相邻效应也没发生**（关键，别混）

`seq=7` 属 S4，而 S4 的开机侧（`01:18:41.035Z`，`:84`）已经
`RbLog(2, __LINE__, 0, L"self-disable: armed boot failed, not attaching any volume")`
⇒ `RbSelfDisabled()==TRUE` ⇒ **本引导一个卷都没挂**。
于是 `why=1` 与 `BootFailCount` 的关系在 S4 上是这样断掉的：

- `why=1` 的成因是 ①（`Engine==NULL`），**与脏页多少无关**（§4.1）；
- `LastCleanShutdown` 确实没被置 1（`:732` 不可达），**但**它下一轮要不要算失败，
  取决于 `healthy`/`ticket`/`armed`/`grace` —— **`armed == 1` 且 `fails >= 1` 才会 self-disable**，
  而 S4 **已经** self-disable 了 ⇒ 这个 FAIL 是上一轮就算出来的，**不是 `why=1` 造成的**；
- 更直接：S4 的失败已经被 `RbBootFailLoad` 用 `LastCleanShutdown==0` **独立**判出来了，
  `why=1` 只是同一事实的**另一份记录**，不是它的原因。

⇒ **一句话边界**：
**`why=1` 与 `BootFailCount` 是"同一批证据里的两条记录"，不是"一条导致另一条"。
把 `why=1` 读成"`BootFailCount` 有问题"，等于把体温计读成病因。**

**而且这一次连"相邻效应"都被实证挡掉了 —— 我找到一条直接证据（比推理硬）：**

⇒ **`seq=7` 那次关机之后的下一次引导走的是 grace 分支 ⇒ `fails` 一个都不加、`BootFailCount` 不被这一次触碰。**

**这是 §13.1–13.3 那条"无因果通道"的实证，不是推理：**
`why=1` 写在 `02:17:46`，`BootFailCount` 的那次判定发生在 `02:18:35`，而它**根本没走到 `:423-426` 的 `fails += 1`**。
⇒ **这一轮里 `why=1` 与 `BootFailCount` 之间连"间接影响"都没有发生。**

（附带一条对 §2.1-洞 2 的补强：S5 的 `[524]` 实测 **8 条**，与 S4 的 `[432]` **8 条**逐条对齐 ——
这是"8 个卷"的**同机、相邻、可对照**证据，比我上一版"拿别的会话比"强一档。

### 15.3 问 3：要不要加交叉引用指向 D-01 两件？

2. **它会扩大复核面，而复核面是有成本的。** D-01 两件合计 **~90 KB**

   额外验算一套与本主题无关的数学 ⇒ **复核成本上升，而结论强度一点不涨。**
3. **它会让"隔离"这个优点变成"耦合"这个负债。** §15.2 末尾我实测：D-01 的整个数轴
   在 SUP-01 里全缺席。**这是有意为之的好设计。** 一旦加上指针，

**⇒ 唯一允许的例外形态（如果将来非加不可）**：写成**单向的、否证式的**一句话，
放在**文末"不覆盖什么"一节**（即本文件 §14），形如

**要点是：说"无关"，不说"相关"。** 这仍然是"不加交叉引用"，只是把"不加"这个决定**留痕**。

**最后一条与方法论有关的话**：你给的这句话 ——
**「插一行指针会让复核者以为两者相关，进而扩大复核面」** —— 是本轮我见到的、
