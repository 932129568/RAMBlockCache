## 1. 改动清单

### 1.1 core：`rb_stream_discard_clean`（cache.c / cache.h）

```c
void rb_stream_discard_clean(rb_stream *s)
{
    /* view_gen++；逐桶：dirty==0 的 chunk 整块销毁（可从盘重建），
       含脏 chunk 只做 loaded &= dirty —— 干净子块失效、脏子块原样留驻 */
}
```

与 `rb_stream_discard_all` 的区别：**不销毁任何脏数据、不计
`lost_dirty_bytes`**，同时满足 DATA-13（离场期被外部改写的干净块必须作废，
不能读旧视图）与数据安全（已 ack 脏块不可丢）。

### 1.2 rbctl.c：四个站点

| 站点 | 位置 | 旧行为 | 新行为 |
|---|---|---|---|
| I48c 热开启 attach | `RbMsgAttachVolume` | flush 后无条件 `discard_all` | `dirty==0 ? discard_all : discard_clean` + `attach: cache view KEPT …` |
| I48d SET_VOLUME 切直写 | `RbMsgSetVolume` THROUGH 分支 | 同上 | 同上 + `write-through switch: cache view KEPT …` |
| I48e FSCTL 簇重排 | `RbDispatchFileSystemControl` | 同上 | flush 后仍有脏 → 清 view_mutating、`STATUS_DEVICE_BUSY` 拒绝、`fsctl: refused …` |
| I48f DeviceIoControl 簇重排 | 同上（IOCTL 分支） | 同上 | 同上 + `ioctl: refused …` |

fail-closed 语义（用户选定）：簇重排期间若脏无法落盘，宁可让该 FSCTL/IOCTL
失败（应用可见错误），也不能继续回写旧 LBA 造成「重排后以旧盖新」的静默腐坏。

### 1.3 rbio.c：P4 取证（`RbWritebackCb`）

此前失败路径完全静默（疑似 `RbGetExt` 返回 NULL 早退）。新增：

- `writeback cb: first invocation (path live)` —— 仅首次，证明回调被调用；
- `writeback cb: ext lookup failed - no disk IO attempted (dirty retained)`
  —— 首次 + 每 256 次限流，计数存于 Status；
- `writeback cb: oversize len rejected (contract guard)`；
- 原有 `writeback sync io failed (dirty retained)` 保留（记录真实 NTSTATUS）。

三条新日志可一次性判别 P4：ext-NULL（路径根本没到磁盘 IO）vs
`RbSyncIo` 5 s 首超时取消（会走 sync io failed 日志）vs 回调从未进入
（first invocation 不出现）。

## 5. 已知影响与风险

- **I48e/f 的 fail-closed 是行为变化**：回写态 + 杀软在位导致脏无法落盘时，
  簇重排类 FSCTL/IOCTL（如卷影/碎片整理/某些 antivirus 的簇级操作）会收到
  `STATUS_DEVICE_BUSY`。这是刻意的（宁可报错不可腐坏），但需要被记录为
  用户可见行为。
- e5 的 attach 步骤现在会保留脏视图，后续 detach/降档仍可能被拒——
  属预期，探针脚本不要再把「拒绝」判为失败（137 号已确认 e5 判据按
  `LostDirtyBytes` 而非 RPC status）。
- 本轮未提交 git；dist 仍是上一代签名件，部署脚本才会切换并同步 anchors。
- ASan 全绿仅覆盖 core 引擎；驱动侧只有静态门禁 + 变异验证，
  真机行为必须由第 4 节触发证据闭环。
