### 1.2 真根因（三层，缺一不可）

这不是一个单点缺陷，是**三个条件相乘**：

#### 层一：驱动单帧 1,480 B 吃掉 12 KB 栈的 12%

`RbDispatchDeviceControl`（`src/driver/rbctl.c`）入口 prolog：

```
push rbp / rbx / rdi / r12 / r13 / r14 / r15      = 7 push = 56 B
lea  rbp, [rsp-0x490]
sub  rsp, 0x590                                    = 1,424 B   ← ALLOC_LARGE 1424
```

**帧总 = 56 + 1,424 = 1,480 B。**

其中 **1,304 B 只属于一个变量**：`RbMsgGetStats` 里的栈上 `RB_STATS local`
（`rbctl.c:228`，全仓唯一一处栈实例；`sizeof(RB_STATS) = 1304` 实编确认）。

```
1,304 / 1,424 = 91.6%
```

> **这不是「14 条 IOCTL 路径并集」**——那说法字面成立但工程含义误导。
> 实际是**一个对象绑架了其余 13 条路径**：剩下 13 个 handler 加起来只用 104 B。
> 这个区分决定了修法：不需要拆 14 个函数，只需要让那一个大对象不出现在分发器帧里。

#### 层二：崩溃走的是**透传分支**，那 1,424 B 一个字节都不需要

栈方向（SP 越大 = 帧越老 = 越外层）：

```
RAMBlockCache+0xe00a      SP=dd0eb600   ← 本驱动，最外层（最先进入）
  nt!IofCallDriver        SP=dd0eb5c0   ← 由驱动 call 出来
    volsnap!VolSnapDeviceControl  SP=dd0eb480
      volume!VolumePassThrough    SP=dd0eb350
        fvevol!FveFilterDeviceControl  SP=dd0eb100
          volmgr!VmDeviceControl       SP=dd0eafa0   ← 最深
```

驱动帧的返回地址 `+0xe00a` 正是 `call nt!IofCallDriver` 的下一条指令
⇒ **是驱动自己下传的**。而 `RbDispatchDeviceControl` 里唯一走 `IofCallDriver` 的路径是
`RbForward`（`:1129` / `:1161` / `:1168`），它**只在 `dev != ControlDevice` 分支可达**。

⇒ 崩溃的 IRP 是**卷设备上的 `IRP_MJ_DEVICE_CONTROL`，走了透传**。
透传分支不需要任何局部变量，**却因为 prolog 一次性分配而全额付了 1,424 B**。

**这是税，不是用量。**

> 未能确定：走的是 `:1129` / `:1161` / `:1168` 哪一条（三者对结论无影响）。
> **不得**据此宣称「是 TRIM 触发的」。

#### 层三：Driver Verifier 是放大器（关掉它等于拆报警器）

栈里这五层全部是验证器的堆栈抓取机制：

```
nt!VfPtFreePoolNotification      ← VRF 池释放钩子
  → nt!ViPtCaptureStackTrace
    → nt!RtlCaptureStackBackTrace
      → nt!RtlWalkFrameChain
        → nt!RtlpxVirtualUnwind
          → nt!RtlpUnwindPrologue   ← 展开驱动帧
```

纯粹的诊断消费者，**偏偏在栈只剩 2.5 KB 时执行**。

#### 算术闭合（这是全篇最硬的一条，纯减法）

```
入口 RSP  R = 0xffffc688'dd0ebbc8
栈界限    L = 0xffffc688'dd0e9000      (页对齐)
入口预算  B = R − L = 0x2bc8 = 11,208 B

驱动帧 F = 1,480 B
下游实测 D = 9,760 B
  = 卷栈 1,632 + 完成路径 960 + VRF 释放钩子 576
  + VRF 抓栈 2,832 + 时钟/DPC 1,712 + ETW 1,600

slack = B − F − D = 11,208 − 1,480 − 9,760 = −32 B
```

**崩溃时 RSP = `0xdd0e8fe0`，比栈界限 `0xdd0e9000` 低 32 字节** ⇒ 已踩进守护页。
守护页一碰就以 `STATUS_STACK_OVERFLOW`（`0xC00000FD`）抛异常，
而该异常自身又要在同一张已经见底的栈上派发 ⇒ **二次异常 ⇒ DOUBLE_FAULT ⇒ 0x7F**。

**这一条不依赖符号、不依赖 `.pdata`、不依赖任何函数归属推断。**

### 1.3 误判记录（六次改方向，这是本文最重要的部分）

按发生顺序，每一次都写清「当时凭什么这么想」和「什么推翻了它」。

#### 误判 1：把 6,304 B 帧判成 `RbRwWorker`（296 号）

**当时的推理**：`.pdata` 里 `0xb0c0` 是 `RbRwWorker` 起点，`0xb0ee` 离它只有 `0x2e`，
所以那段 `mov eax,0x18a0 / call __chkstk / sub rsp,rax`（单帧 6,304 B）属于它。

**错在哪**：这是**相邻推断**，把「离谁近」当成「属于谁」。
x64 编译器会把大函数折成「主函数 + CHAININFO 续块 + 冷热分区」，函数边界不连续，
两个独立函数之间还有 `cc` 填充。

**推翻它的三条反证**（任一条足够）：

| # | 反证 | 结果 |
|---|---|---|
| 1 | `RbRwWorker` 在 `0xb0c0` 的**完整字节** | `sub rsp,0x28 / xor edx,edx / call / lock dec / add rsp,0x28 / ret / cc` = **23 字节，帧 40 B**，与 6,304 B 毫无关系；源码印证 `rbio_worker.c:1332` 只有 4 行 |
| 2 | `0xb0e0` 是另一函数起点，且**有唯一源码指纹** | `mov ecx,0xFFFF` + `call KeQueryActiveProcessorCountEx` ⟺ `rbio_worker.c:1049`，即 `RbStartIoWorkers`（`:1044`）第二行；紧接 `:1069` 的 `RB_AFFIN_TARGET auxT[RB_PCPU_MAX]`，`256 × 24 = 6,144 B` ⇒ 加局部与影子空间 = 6,304 B，**来源闭合** |
| 3 | **栈上没有它** | 全文搜 `RAMBlockCache+` 只 1 处命中（`+0xe00a`）；若 `RbStartIoWorkers` 在链上，必有 `+0xb0xx` 帧 |

**教训**：`0xb0c0` 之后 23 字节就是 `ret` + `int3` 填充，`0xb0e0` 是另一个函数起点。
**C 语言允许你把 `a=1; b=2;` 写成一行，但汇编里 `0x0e` 字节的间隔不蕴含任何从属关系。**

#### 误判 2：把 6 个 CHAININFO 续块当成「6 份 6.3 KB 副本」

**当时的推理**：`.pdata` 里 6 个连续区间都是 6,328 B ⇒ 「`RbDispatchCtx` 被内联进多个调用点，各复制一份」。

**错在哪**：那 6 个区间的 `flags = 4`，即 `UNW_FLAG_CHAININFO` = **本区间是前一个函数的续块**：

```
0xb0e0..0xb158  flags=3 (EHANDLER|UHANDLER)  ALLOC_LARGE 6304  ← 真正的 head
0xb158..0xb164  flags=4  → chain 0xb0e0
0xb164..0xb497  flags=4  → chain 0xb158
0xb497..0xb540  flags=4  → chain 0xb164
0xb540..0xb5d7  flags=4  → chain 0xb497
0xb5d7..0xb5fe  flags=4  → chain 0xb540
```

**6 段串成一条链 = 1 个函数被拆成 6 段**，不是 6 份副本。
这也解释了「每段算出的 RSP 分配都一样」——算的是同一条链。

**教训**：按 `flags=4` 去重后，全镜像真实 head 只有 **278 个**（648 − 370 个是 chain/epilog 块）。
用未去重的口径数「危险函数个数」会直接放大 2.3 倍。

#### 误判 3：帧大小算成 1,488 B（差 8 B）

**当时的推理**：把 `SAVE_NONVOL` 也算成栈分配。

**实际**：`SAVE_NONVOL` 是保存非易失寄存器，**不分配栈**。真值 1,480 B。
差额 8 B 看着小，但它会顺着余量公式把 `slack` 从 `−32` 变成 `−40`，
**进而让人以为缺口更大、需要更激进的方案**。

**教训**：**小误差沿着公式传播会改变方向判断**。

#### 误判 4：把崩溃归因成「大批量文件操作走回写路径」

**当时的推理**：用户在删 901 MB 文件、跑 `npm install`，所以是回写路径。

**实际**：崩溃在 **DPC 里的 ETW 写入**（`nt!EtwpGetLoggerTimeStamp`），
`RbStartIoWorkers` 根本不在栈上，回写线程也未见。

**教训**：**「用户在做什么」不是证据，「栈上有什么」才是。**
用户操作只能给概率，不能给归因。

#### 误判 5：把调用方向写反（297 §3.2）

**当时的推理**：`volmgr → fvevol → volume → volsnap → RAMBlockCache`，即「驱动在卷过滤最底层」。

**实际反过来**：栈**向下长**，SP 越大 = 帧越老 = 越外层：

```
RAMBlockCache SP=dd0eb600  (最高 = 最外层)
volmgr        SP=dd0eafa0  (最低 = 最深)
```

⇒ 本驱动在卷栈**顶部**（与 `UpperFilters` 把本驱动挂在卷栈上面的部署事实一致），
它 **call 了 `IofCallDriver`** 把 IRP 下传。

**教训**：**方向搞反会让整个因果链反向**——如果驱动在底层，那它是受害者；
如果在顶层，那它是施害者。「谁 call 谁」在栈上就是「谁的 SP 更大」。

#### 误判 6：以为「只差 32 B ⇒ 消掉一个小局部变量就够」

**当时想**：缺口只有 32 B，删个 `ULONG` 就完了。

**为什么错**（四条）：

1. **32 B 是这一次的欠账**。`D` 里的 VRF 抓栈、ETW 写入都是**随机量**，下次可能多 200 B。
2. **F 是常量，D 是变量**。买余量的唯一稳定手段是压 `F`，因为 `D` 是别人的代码。
3. **余量公式**：`slack(F) = 1,448 − F`

   | F | slack | 判读 |
   |---|---|---|
   | 1,480（现状） | **−32 B** | 必然崩 |
   | 1,448 | 0 | 恰在页边界，一次中断就翻 |
   | 1,416 | +32 | 「刚好够过一次」——**不可接受** |
   | 1,160 | +288 | 仍薄于任意一次额外 VRF 抓栈帧 |
   | **230（候选 1+2 目标）** | **+1,218** | 可接受 |

4. **目标是买余量，不是凑 32 B**。所以修法不是「删一个小变量」，
   而是「让 1,304 B 那个对象根本不出现在分发器帧里」，把 F 从 1,480 压到 230 量级。

## 三、当前「缓存收益为零」的事实（不是缺陷，是未启用）

这一条容易误解成 bug，必须写清：

| 指标 | 实测 | 含义 |
|---|---|---|
| `Features\Flags` | `0x0` | **L2 / HOT / ETW 全部关闭** |
| `L2state` | `0` | L2 未启用 |
| `.idx` 文件 | **仅 4 B 头** | 索引未定稿 ⇒ **跨引导命中不可能** |
| 读命中（次数） | **47.78%** | 只有 L1 |
| 读命中（字节） | **42.23%** | 请求级与字节级**有落差**，这本身是 D-01 的指纹 |
| 缓存吸收 | **0.00%** | 直写模式，不吸收写 |
| 回写字节 | **0.00 GB** | `WriteBack=0` |
| 脏数据 | **0.00 MB** | 直写不留脏页 |

**「命中 47.78%」不等于「加速 47.78%」**——这是命中率，不是收益。
且 `ReadHit` 是请求级、`ReadHitBytes` 是字节级，两者落差说明**碎片化**，
只报前者会系统性高估收益。

**J6（跨引导命中）从未验证过**，`.idx` 停在 4 B 就是证据。

## 四、工具链自身出过的事故（这一节最容易被忽略，但坑最多）

### 4.1 唯一的真机日志被自己的清理逻辑删掉

**发生了什么**：`RB-write-load.ps1` 的旧版把日志写进 `%TEMP%`，
而桩测的清理 glob 也扫 `%TEMP%` ⇒ **唯一一次真机跑的日志（487 行）被删**。
从会话转录抢救回 67 行，**420 行永久丢失**（含 P2 的 4 行 VDL 值、P3 的 2 行回收值）。
不可重跑——那次 UAC 机会已用掉。

**已做的处置**：
- 日志目录改为 `$PSScriptRoot/design/logs`（进仓库、不易丢）
- 同款地雷在两个桩测件里拆除：`$env:TEMP` 改道私有 sandbox，只删自建绝对路径
- 抢救集落在 `deliverables/tests/_SALVAGED-151840-fragments.txt`

**教训**：**清理逻辑的作用域必须显式限定到自建路径**，
「干净的临时目录」是最危险的假设。

### 4.2 `grep -c $'\r'` 的因果归因错了，而且错因被写成了规则

**现象**：`grep -c $'\r'` 对纯 LF 文件报 10（不可能的结果）。

**第一次归因（错）**：「因为放进了 `for` 循环，`$'\r'` 被重新展开成空模式」。
还写成了规则：「必须单条跑、不能放进循环」。

**真因**：**字面量 `$'\r'` 出现在 `$( )` 命令替换内部时被 shell 展开成空串**，
空模式匹配每一行 ⇒ 无论文件形态一律返回行数。**与 `for`、与 `$f` 都无关。**

**决定性反例（E 组）**：`x="$(grep -U -c $'\r' f)"` ——
**无 `for`、无 `$f`、完全单条跑，照样 10/10/10 全错**。
⇒「不能进 for 循环」这条规则**挡不住 E**，而 `x=$(...)` 恰是最常见写法。

**字节级证据**：

```
printf '%s' $'\r' | od -An -tx1               → 0d   (1 字节)
CR=$(printf '\015'); printf '%s' "$CR" | wc -c → 1
y="$(printf '%s' $'\r')"; printf '%s' "$y" | wc -c → 0   ← 进 $() 归零
```

**正确规则**：`$'\r'` 永不直接写进 `$( )`；先在 `$()`**外**存
`CR=$(printf '\015')`，`od -An -tx1` 验得 ` 0d` 再用。

**最该记住的不是这条 shell 知识，而是它的传播路径**：
这个错误归因是 QA 给 team-lead 的，team-lead **没复核就升格成了台账规则**。
⇒ **台账里每条规则必须由维护者自己跑出反例或正例才能写入。**

### 4.3 台账自我登记哈希必然滞后

`FROZEN-BASELINE.md` 里有一行是它自己的哈希。**这一行一定过期**，
因为写它的动作本身改变文件字节。已显式标注「故意滞后，引用前必须重算」，
并保留一个过期值当实物例子——**让「自我登记不可能自洽」这件事可被看见**。

### 4.4 评审期间给被评审文件登记哈希，必然产生假锚

`SUP01-review-2026-11-20.md` 一天内出现**五个**真实值：

| 时刻 | 字节 | 行 | sha256(前8) |
|---|---|---|---|
| 20:21:13 | 40,744 | 518 | `3936B381`（**全仓无实物**） |
| 20:42:04 | 73,745 | 1,002 | `7F98D23C` |
| 21:01:08 | 76,879 | 1,033 | `6DC0F501` |
| 21:45:27 | 85,488 | 1,120 | `40826F24` |
| 22:02:09 | 88,884 | 1,154 | `84CBCB09`（终值） |

**五次变更全部由评审动稿造成，无一例外。**
⇒ 台账对该件改为「**不登记**」：8 格全写 `—`。
**留空比填一个会过期的值诚实。**

### 4.5 哨兵 `—` 不显式声明会让核对器假报 FAIL

同一核对器、同一文件，只改「哨兵是否声明」：

| 处理方式 | 实核格数 | mismatches | 结论 |
|---|---|---|---|
| 跳过哨兵 | 70 | **0** | PASS |
| 不声明哨兵 | 75 | **5** | **假 FAIL**（5 条无一真错） |

**教训**：判据不允许用「这格长得不像预期值」去推断「这格有问题」。
**跳过必须有显式依据。**

### 4.6 校验器自身漏检格式（`^\|` vs `^\s*\|`）

台账里有 4 空格缩进的表格。首版校验器只认行首 `|`（`^\|`），
于是**报了「13 张表 bad=0」，其实只检查了 10 张**，新加的表根本没被看过。
改成 `^\s*\|` 后才是真的 13 张。

**教训**：**校验器「通过」的说服力，不超过它实际覆盖的范围。**

## 五、这份文档怎么用

1. **遇到新问题，先在这里搜有没有同型的**。本项目六次误判里，至少三次是同一个模式：
   **把「离谁近 / 看起来像 / 用户正在做什么」当成证据**。
2. **看误判段，不只看看结论段**。结论对、理由错的情况这里至少有两处。
3. **想引用某个数字前，先确认它对应哪个时刻**。本项目的哈希、字节数、行号都在动。
4. **不要从这份文档里得出「已修复」的结论**。它记录的是「做过什么、证到什么程度」。
