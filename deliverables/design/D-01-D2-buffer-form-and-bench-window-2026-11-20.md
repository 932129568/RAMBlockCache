## 1. 撤回：我上一轮的"直读 `tgt`"是同一个错

### 1.1 team-lead 的更正成立

```
rbio.c:17-22   PVOID RbMapIrpBuffer(PIRP irp)
               {
                   if (irp->MdlAddress) return MmGetSystemAddressForMdlSafe(irp->MdlAddress, NormalPagePriority);
                   return irp->AssociatedIrp.SystemBuffer;
               }
rbio_worker.c:412   PVOID tgt = RbMapIrpBuffer(irp);
rbio_worker.c:488   tgt = (PUCHAR)tgt + chunk;      /* 纯指针位移 */
```

⇒ `tgt` 是**发起方 IRP 的 MDL 系统映射**（或 `SystemBuffer`）。它的所有权在 IRP，不在我们。

### 1.2 我上一轮 §4.3 的错在哪

我写的是：

> full-cover 区间 → `RbSyncIoIssue(off=ms, buf = tgt + (ms-rs), len = mr->len)` —— **直读 `tgt`**

`RbSyncIo` 内部会把 `buf` 直接交给 `IoBuildSynchronousFsdRequest`（`rbdev.c:216` 传的是 `ctx->PoolBuf`，但在"直读"设想里我等于让 `PoolBuf == buf == tgt`）。那样一旦超时 ORPHAN，`RbSyncComplete`（`:177-182`）在 late IRP 完成时仍会**释放 `PoolBuf`**，而那个 `PoolBuf` 就是 `tgt` —— **等于释放调用方 IRP 的 MDL 映射缓冲**。更糟的是如果走 `:262` 之前就放手，late IRP 直接**写进已归还给上层的缓冲**。

team-lead 的判断（「D2 如果把 IRP 直接建在 `tgt` 上，等于把这条保护拆掉」）**完全正确**。我上一轮的 §4.3 犯的是同一个错，只是包装在"省一次 memcpy"的收益论证里。

**⇒ 我的 §4.3（混合式：full-cover 直读 `tgt` + 边缘 2 槽）整段作废。**
**⇒ X14（`full_cover` 保真）依然成立且必须遵守** —— 它与 buffer 形态无关，是 commit 语义问题。
**⇒ X13（`RbStageGet` 单槽）在 §2 的新形态下自动解除** —— 但 X13 的禁令（并行路径不得调 `RbReadMissRange`）仍然保留，理由变了（见 §2.3）。

### 1.3 一条技术澄清（免得后面又混）

`rbdev.c:207` 的注释是准的：「数据缓冲池化：IRP 全程只看见 PoolBuf，**超时后调用者 buf 可立即失效**」。

`PoolBuf` 隔离提供的是**单向保护**：调用方 `buf` 可以随时失效，因为数据先落 `PoolBuf`、成功后才回拷。它**不**提供「`PoolBuf` 自己可以随便释放」的保护 —— `PoolBuf` 的所有权仍必须由 `Refs=2` 那套状态机裁决。这两件事不能混。

⇒ **`buf` 必须是「我们自己的、生命周期独立的」内存，不能是 `tgt`。** 这就是全部结论。

## 2. 定稿：D2 的 buffer 形态 —— 一字节不改

### 2.1 关键洞察：「发」可以并行，「收」必须串行

| 阶段 | 是否需要 staging | 能否并行 |
|---|---|---|
| **发（Issue）** | **完全不需要**。`RbSyncIoIssue` 内部自建 `ctx->PoolBuf`（`rbdev.c:208`），IRP 只看见它 | ✅ 可并行 8 路（各有独立 ctx + PoolBuf + KEVENT + iosb） |
| **收（Wait + commit）** | **需要，且只在收的时候**：`RbSyncIoWait` 的 `:262` `RtlCopyMemory(buf, ctx->PoolBuf, len)` 就是「PoolBuf → 我们的缓冲」那一次拷贝 | ❌ **串行**（因为 `commit` 要在同一处做完） |

⇒ 收阶段串行 ⇒ 我们可以把 `w->Stage` 那**唯一一个槽**当"收件缓冲"，**一笔一笔地** 收 → commit → 下一笔。槽在整个过程里始终只有一个使用者。

**这就是解。** 不需要 2 槽、不需要 8 槽、不需要混合式、不需要扩 ctx。

### 2.2 逐笔时序（一条切片，`mcnt = 5`，在飞上限 8）

```
[发阶段]  i = 0..4（可扩到 min(mcnt, 8)）
          ctx[i] = RbSyncIoIssue(ext, FALSE, &off[i], /*buf*/ NULL, miss[i].len, NULL)
                   └─ 内部：ctx 分配 → PoolBuf 分配(:208) → 建 IRP(:216, buf=PoolBuf)
                            → IoCallDriver(:228) → 立即返回 ctx（不等）
          ⇒ 此时 5 条 IRP 同时在下层飞行，5 个独立 PoolBuf

[收阶段]  i = 0..4（严格串行）
          s = RbSyncIoWait(ctx[i], /*buf*/ w->Stage)     ← 复用唯一槽
                   └─ 内部：KeWaitForSingleObject 剩余预算 → IoCompleteRequest
                            → 短传归一(:260) → RtlCopyMemory(w->Stage, PoolBuf, len)(:262)
                            → 释放 PoolBuf(:264) → 归还 ctx(:267)
          若 !NT_SUCCESS(s)：记 s，**仍继续把余下 in-flight 全收完**（I4），然后 return
          若 NT_SUCCESS(s)：
              rb_read_commit_gen(ext->Stream, miss[i].offset, w->Stage, clen, vgen)   ← 整块 commit（X14）
              memcpy(tgt + (lo-rs), w->Stage + (lo-ms), hi-lo)                        ← 切出交集给调用方
          ⇒ 槽 w->Stage 在本轮收完后即可被下一笔复用（串行独占，无竞争）
```

### 2.3 为什么 X13 在这个形态下自动解除

X13 的风险是「同一 worker 的 N 条区间**同时**持有 `w->Stage`」。§2.2 的收阶段**严格串行** ⇒ 任意时刻只有一笔在用槽 ⇒ `RbStageGet` 的 `w->Stage` 不被共享，`:113-118` 的放大分支不可能被他人在读时触发，`RbStagePut` 的 `p != w->Stage` 也不会变成双重释放开关。

**但 X13 的禁令要保留，理由改写为**：

> 并行路径**仍然不得调用 `RbReadMissRange`**，原因不再是 staging 竞争，而是 **`RbReadMissRange` 是「发+收+commit」一体的同步函数**。调它一次就会阻塞到该笔完成，等于把 N 路并行退化成串行 —— 收益归零。**它必须被拆成两趟，而不是被并发调用。**

这个改写很重要：它把 X13 从"内存安全禁令"降级为"结构禁令"，更容易被工程师接受（不需要理解 0x9F）。

### 2.4 卷尾钳位与边缘区间

- **卷尾**：`me_io = min(me, DiskSize)`（沿用 `:276-277`），下盘长度用 `me_io - cur`，commit 长度同。**不能**用 `me`。
- **边缘**（`ms < rs` 或 `me > re`）：**不需要特殊处理** —— 因为它们读进的是 `w->Stage`（不是 `tgt`），整块 commit 天然成立；只要 `memcpy` 时用交集 `[lo,hi)` 就对了。**这比 §4.3 的混合式简单一个数量级。**
- **`RbFeatOnMiss`**：每笔一次，传 `w->Stage` 作为 `Dst`（与现状 `:289` 一致）。注意它是**收阶段之前**要判的 —— 若 L2 命中（返回 SUCCESS），可以**跳过下盘**，那就变成：先判 `RbFeatOnMiss` → 命中则不进 issue 队列，直接 commit + memcpy。这条要保持，否则 L2 失效。

### 2.5 `ctx->CallerBuf` 从死字段变成 I8-b 的承载体

I8-b 要求「`Issue` 返回 ctx 所有权，`Wait` 接收 ctx 数组」。`Wait` 要往哪写？**就是 `ctx->CallerBuf`**：

```
rbdev.c:148   PVOID CallerBuf;        /* 当前全仓零读取（死字段） */
rbdev.c:205   ctx->CallerBuf = buf;   /* Issue 时记下 */
rbdev.c:262   改为 RtlCopyMemory(ctx->CallerBuf, ctx->PoolBuf, len)
```

- 对合成的 `RbSyncIo`（`Issue` 立即 `Wait`）**字节级等价**（因为 `:205` 与 `:262` 用的是同一个 `buf`）⇒ **I8-a 的"零 diff"验收成立**；
- 对 D2 路径，`Wait(ctx[], ...)` 可以每笔传不同 `CallerBuf`（甚至 8 笔全传同一个 `w->Stage`，靠串行保证安全）。

⇒ **L7 的处置要改**：不是"删除死字段"，而是「**保留并激活**，它是 I8-b 的天然载体」。这一点我在 `D-01-I7c` 里写成了「建议删除」，**此处更正**。

## 3. 内存账：team-lead 的 20 MB 高估了 7.53×

### 3.1 关键约束：同一切片内的在飞区间共享同一个 128 KiB 窗口

`miss[]` 来自**一次** `rb_read(ext->Stream, cur, tgt, chunk, miss, &mcnt, RB_MAX_RANGES)`（`rbio_worker.c:472`），而 `chunk = rb_read_plan_chunk(...) ≤ RB_READ_PLAN_MAX_BYTES = 131,072`（`read_plan.h:18` 定义、`:29` 的 `window_128k` 断言）。

`rb_read` 的 miss 区间**互不重叠且都在 `[rs, rs+chunk)` 内**（两端各可越出一个子块，`cache_read.c:65-66`）。所以：

```
Σ_{i ∈ 在飞} miss[i].len  ≤  chunk + 2 × 4096  ≤  131,072 + 8,192  =  139,264 B   （每个 worker）
```

（`139,264` 也是单条区间的绝对上界，与上一轮 O1 的推导同一个数。）

### 3.2 三档对照（本机 20 worker / 上限 32 worker）

| 口径 | 20 worker | 32 worker |
|---|---|---|
| team-lead 的算法（每笔按满 128 KiB × 8） | `8 × 131,072 × 20` = **20.00 MiB** | `8 × 131,072 × 32` = **32.00 MiB** |
| **正确上界**（Σlen ≤ 139,264 / worker） | `139,264 × 20` = **2.66 MiB** | `139,264 × 32` = **4.25 MiB** |
| **倍数** | **7.53× 高估** | **7.53× 高估** |
| 现状对照（1 笔在飞 + 1 staging 槽） | `139,264 × 20` = 2.66 MiB | 4.25 MiB |

⇒ **D2 的 `PoolBuf` 峰值与"现状 1 笔在飞但按上界算"是同一个数（2.66 MiB）** —— 因为同切片内的总长被窗口钳死，**并发度不改变字节总量**，只改变"这笔内存是被 1 个 ctx 占还是被 8 个 ctx 分占"。

### 3.3 所以「每切片一个 1 MB 池块按笔切分」不该做

- 1 MB 是 `8 × 131072` 的算法产物，**没有对应的真实需求**（真实需求 ≤ 139 KiB）；
- 20 worker × 1 MiB = **20 MB 常驻**（若按 `RbStageGet` 懒涨不缩语义），**比正确上界高 7.5 倍**，纯浪费；
- 而且池块切分要引入「块内偏移分配器」，多一层所有权纪律 —— 与 X12 的「三套纪律必须原子地待在同一处」相冲突。

⇒ **否决。一个 ctx 一个 `PoolBuf` 就是最优形态。**

### 3.4 顺带更正：`rbdev.c:151-158` 讲的不是 `PoolBuf`

team-lead 引用它来论证「必须池化复用，否则回到 QD1 机制开销主项」。原文：

```
rbdev.c:151   /* [W1.5] RB_SYNCCTX 非分页旁视池（CTX-1 IoCtxLa 先例，见本文件 :76-77）。
rbdev.c:152    * 消除 RbSyncIo 每 IO 的 ExAllocatePool2+ExFreePoolWithTag 固定机制开销
rbdev.c:153    * （QD1 串行路径每 IO 成本主项，PRD §7.2 / L1-2）。
```

**主语是 `RB_SYNCCTX`（ctx 结构体，`sizeof ≈ 80 B`），不是 `PoolBuf`（数据缓冲）。** 而 `PoolBuf` **至今仍是每笔一次 `ExAllocatePool2`**（`rbdev.c:208`），已在线上跑过、已被 `firstMbps=145.8` 那次 bench 覆盖。

⇒ 「`PoolBuf` 必须池化」**不是 D2 的新增准入条件** —— 现状就没有池化，且已验收。D2 只是把"同时在飞 1 笔"变成"8 笔"，**每笔的分配次数不变**。

**但建议做**（列 P2 可选）：8 路并发下 `ExAllocatePool2` 的 pool 锁争用会被放大，把 `PoolBuf` 也挂 lookaside（按 4 KiB 与 128 KiB 两档）能把这段开销压掉。理由与 `:151-155` 对 ctx 做的完全同构。**成本低、收益可测（QD1 单笔路径就会受益，与 D2 无关）** ⇒ 可以**独立于 D2 先做**。

## 4. 收益重估：1.63× 不变

### 4.1 逐项对照 team-lead 的三条

| team-lead 的项 | 判定 | 理由 |
|---|---|---|
| 读放大仍 1.00× | ✅ **不变** | D2 一个字节不多读，与 buffer 形态无关 |
| 多一次 memcpy（`PoolBuf → tgt`） | ✅ **不是新增** | 现状 ② 就是 `PoolBuf→st`（`rbdev.c:262`）+ `st→tgt`（`:297`）= **2 次**；D2 定稿形态也是 2 次（`PoolBuf→w->Stage` + `w->Stage→tgt`）。**次数完全一样** |
| 新增成本 = 池内存 ≤ 20 MB | ❌ **实际 2.66 MiB** | §3.2：同切片 Σlen ≤ 139,264/worker，并发度不改字节总量 |
| 必须池化复用 | 🟡 **建议但不必须** | §3.4：现状每笔就是一次 `ExAllocatePool2`，已上线 |

### 4.2 收益模型不依赖 buffer 形态

```
情形①  T_slice = ceil(k/QD) × L + k × transmit
```

- `L = 31.8 µs` 是**每笔 IO 的固定延迟**（盘 + 卷栈），与数据落哪块内存无关；
- `transmit = 26.8 µs` 是**每笔传输时间**，与地址无关；
- `QD` 由在飞上限（8）与真实并发度（P1 定）决定，与 buffer 形态无关。

⇒ **`k=5, QD=5` ⇒ 每切片 293 µs → 166 µs，`secondSec` 48.27 s → 29.6 s = 1.63×**。数值**一字不改**。

### 4.3 但有一个**新增的串行项**要交代（诚实）

定稿形态的「收」是串行的，串行段包含：

| 串行工作 | 量（k=5, 4 KiB 区间） | 对 293 µs 占比 |
|---|---|---|
| 5 × `RtlCopyMemory(w->Stage, PoolBuf, 4 KiB→26 KB)` | 5 × ~26 KB = 130 KB @ ~10 GB/s ≈ **13 µs** | 4.4% |
| 5 × `rb_read_commit_gen`（含 lock_stripes + memcpy 到 chunk） | 5 × (锁 ~0.1 µs + memcpy 4 KB) ≈ **2 µs** | 0.7% |
| 5 × 交集 `memcpy` 到 `tgt` | 同 13 µs 量级（4 KB 内） | 已含上 |
| **合计** | **≈ 15–28 µs** | **5–10%** |

现状也是串行做这些（`for` 循环里一笔一笔来），**所以这不是 D2 的新增**。但要注意：D2 把 293 µs 压到 166 µs 后，这 15–28 µs 的**占比从 5–10% 升到 9–17%**。等价表述：**1.63× 里的 `transmit` 项省不掉，串行收省不掉，能压的只有 `k·L`** —— 这与 §1.4 的"天花板 2.18×"结论一致，不影响 1.63× 这个下限。

### 4.4 一句话

> **1.63×（下限、带宽串行），上界待 P1 实测。** buffer 形态改动不改变这个数（X15 合规，未出现任何 >1.63× 的预测）。

## 5. `bm` / `dBytesMiss` 外层窗口污染：判定与量级

### 5.1 先把两个窗口说清（代码逐行）


### 5.2 污染的三段拆解（能扣的两段 + 不能扣的一段）

设 `B = 20,707.6 MB`（bench 自己打印的 `bytes=`），`S = ceil(B/131072) = 165,661` 切片，`h = 0.8445`。

| 段 | `dMisses` 贡献 | `dBytesMiss` 贡献 | 能否扣除 |
|---|---|---|---|
| **首遍（全 miss）** | `S = 165,661`（相邻子块合并 ⇒ 1 条/切片） | `B = 20,707.6 MB`（Σlen = 整片） | ✅ **可精确扣**：用 bench 打印的 `bytes=` 与 `S=ceil(B/131072)` |
| **热读段**（我们要的） | `S × k` | `B × (1−h) = 3,220.0 MB` | ← **目标量** |
| **flush + 背景盘活动** | `R_m` | `R_b` | ❌ **不可扣**（同窗口混入） |

扣完之后：

```
dMisses_hot    = dMisses_outer    − S            ≈ S·k
dBytesMiss_hot = dBytesMiss_outer − B            ≈ B(1−h) = 3,220 MB
```

**扣除后的占比（`k = 4.976`，即 `k_bytes` 真值；`-passes 2`）**：

| 量 | 外层总量 | hot 部分 | **hot 占比** |
|---|---|---|---|
| `dMisses` | 989,990 | 824,329 | **83.3%** |
| `dBytesMiss` | 23,927.6 MB | 3,220.0 MB | **13.5%** |

⇒ **`dMisses` 路径健康（hot 占 83%）；`dBytesMiss` 路径病态（hot 只占 13.5%）。** 这就是 team-lead 的直觉说的那件事，量化出来了。

### 5.3 误差放大：为什么 `dBytesMiss` 只能当参考

设外层测量有相对误差 `ε`（= `R_b / 总量`），扣完首遍后传递到目标量：

```
dMisses    路径：Δk/k = ε × (1 + k)/k = ε × 1.20     （k=5）
dBytesMiss 路径：ΔBM/BM = ε × 23,927.6/(23,927.6−20,707.6) = ε × 7.43
```

| k | `dMisses` 放大 | `dBytesMiss` 放大 |
|---|---|---|
| 1（全合并） | **2.00 ε** | 7.43 ε |
| **5（D-01 假设）** | **1.20 ε** | **7.43 ε** |
| 32（完全碎片） | 1.03 ε | 7.43 ε |

**换算成现场预算**（外层窗口 `T ≈ 142 s`（首遍）+ `48 s`（热读）+ `10 s`（flush/启动）≈ **200 s**）：

| 判据容差 | 允许背景读（`dBytesMiss` 路径） | 相当于 |
|---|---|---|
| 2% | 64.4 MB / 200 s | **329 KB/s** |
| 3% | 101 MB | 494 KB/s |
| 5% | 169 MB | 823 KB/s |

**329 KB/s 的背景读 miss 预算，在现场（NTFS 元数据 + Defender + 浏览器/索引器）是不可控的。** 我不断言它一定超，但**它不可控** —— 一个不可控的输入不该进发版门禁。

⇒ **判定：`dBytesMiss = B(2−h)` 那条改判为「一致性参考」，不作门。team-lead 的判断正确，我确认。**

**另附一条硬上限自检**（不依赖任何假设）：

```
dBytesMiss_outer ≤ 2B = 41,415.2 MB
```

若超过，说明除了"首遍 + 热读"还有别的读大块数据进来了 —— 最可能是 **flush 触发的 readback**（`rbctl.c:661` 注释：「core 契约 …… 恢复路径锁外 readback」）。⚠️ **这是我要提醒的一个真实风险**：如果 bench 文件此前被**写**过（缓存里存的是脏块），`RB_MSG_INVALIDATE_RANGE` 的 `superseded=1` 语义可能触发 **readback 下盘读**，即把整个文件的脏块重新读一遍 —— 那是 **+20 GB 的 miss**，会让整个窗口报废。

- bench 用 `GENERIC_READ` + `OPEN_EXISTING`（`ctl_bench.c:326-330`）打开，**自己不写**；
- 但如果 QA 生成 bench 文件时走过缓存且未刷干净，脏块就在。
- **防御**：`dBytesMiss_outer > 2B ⇒ 判 FLUSH_READBACK，判 INVALID 并重跑**（明确区分"污染"与"结论错"）。

### 5.4 `hitRate` 的 2% 容差：担心反了

`h = 1 − dBytesMiss_hot/B`。`h` 的容差换算到 `dBytesMiss_hot`：

```
Δh = 2% × 0.8445 = 0.0169   ⇒   ΔdBytesMiss_hot = B × 0.0169 = ±350.0 MB
                              相当于 dBytesMiss_hot 的 ±10.9%
```

⇒ **`h` 的门极宽（容忍 `dBytesMiss_hot` ±11%），不是极紧。** team-lead 担心的"2% 不够"不成立；**真正的问题是它太宽 —— `h` 几乎测不出任何变化**。

所以 `h` 的正确用法：

| 用法 | 判定 |
|---|---|
| 当**模型绝对门**（`dBytesMiss = B(2−h)`） | ❌ 错误：窗口含 86.5% 首遍，放大 7.43ε |
| 当**改前/改后对照量**（`|h_after − h_before| < 0.01` 绝对） | ✅ **正确**：D2 零放大 ⇒ `h` 必须不变；两次 run 的共模污染在这个差里抵消 |
| 当**`k` 的双路校验**（§5.5） | ✅ 辅助 |

### 5.5 定稿判据：双路 `k` 一致性（替代 `dBytesMiss = B(2−h)`）

**核心思路**：`k`（每切片 miss 区间数）能从**两条独立的路**算出来，两条路吃**同一个窗口的同一污染** ⇒ 共模相消。

> **【2026-11-20 深夜修订 · 裁决 11/12 落实】** 本节原先把门 2 写成**双侧窄带** `|k_count − k_bytes|/k_count < 5%`，且 `k_bytes` 写成 `4.745`。**两处都错，且后者不是笔误问题、是判据形式问题。** 见 5.5.0。

```
路 A（只用计数）  k_count = (dMisses_outer − S) / (S × hot_passes)
路 B（只用字节）  k_bytes = (dBytesMiss_outer − B) / (4096 × S × hot_passes)
                            ↑ 4096 是因为 k=5 时每笔 ≈ 一个 4 KiB 子块
                            ↑ hot_passes = passes − 1（默认 2 ⇒ 1）

闸 0（量级闸，裁决 12）：  S < dMisses_outer < 2 × 989,988          ← 超出 ⇒ INVALID
                            （抓"灾难性错配"，**不是**污染闸：上界只是 CONFIRMED 翻带点的 1.865×，
                              污染防护由 N2 字节侧承担。归因见 §5.5.1-补）
门 1（D-01 前提验证）：    k_count ∈ [4, 6]   （即 dMisses_outer 的 4% 精度带）
门 2（模型自洽下限）：     k_count >= 4.0                             ← 单侧，裁决 11
门 3（零放大验证）：       |k_after − k_before| / k_before < 2%       ← 最有价值，见下
参考（不判 FAIL）：        |k_count − k_bytes| / k_count   （打印，不判定）
硬断言：                   dBytesMiss_outer ≤ 2B（否则 flush readback ⇒ INVALID）
必须打印：                 k_count 与 k_bytes 两个数（裁决 11 硬要求）
```

#### 5.5.0 为什么门 2 必须是单侧下限（裁决 11）

先纠数：`k_bytes = m2 / (4096 × S)`，`m2 = B(1−h) = 20,707.6 MB × (1−0.8445) = 3,376,448,065 B`：

```
k_bytes = 3,376,448,065 / (4096 × 165,661) = 4.975994  ≈ 4.976
```

**我上一版写的 `4.745` 无来源**（同一节里我自己的算式却写着 `S*4.976 = 824,329`，自相矛盾）。正确值是 **4.976**。

但改常数**修不好**这个门。`k_count` 的物理值域是 `[1, 32]`（`read_plan.h:17` `RB_READ_PLAN_MAX_SUBS 32` 是硬上界），而 D-01 是**单侧假设**（"miss 区间 ≥4 条/片"）。用双侧窄带卡一个单侧假设，**必然在某个分支上失效**：

| 真值分支 | `k_count` | 双侧带 `4.745±5%` | 双侧带 `4.976±5%` | **单侧 `>= 4.0`** |
|---|---|---|---|---|
| CONFIRMED（D-01 成立） | 4.976 | 偏差 4.6% ⇒ PASS | 偏差 0.0% ⇒ PASS | **PASS ✓** |
| **REFUTED（热读全合并）** | **1.000** | 偏差 **374.5%** ⇒ FAIL ✗ | 偏差 **397.6%** ⇒ FAIL ✗ | **FAIL = 否证，正确采信 ✓** |
| PARTIAL（轻度碎片） | 3.000 | 58.2% ⇒ FAIL ✗ | 65.9% ⇒ FAIL ✗ | FAIL = 否证 ✓ |

⇒ **双侧形式在 REFUTED 分支上把"有效的否证结论"判成 INVALID —— 那是把最有价值的一次实验废掉。** 问题不在常数取值，在判据形式本身。

单侧下限 `4.0` 的可复算性（留 19.6% 余量，且对 `h` 的估计误差不敏感）：

```
当前 h=0.8445 ⇒ k_bytes = 4.976  ⇒ 4.0 留 19.6% 余量
h=0.80 ⇒ k_bytes = 6.400  ✓        h=0.82 ⇒ 5.760  ✓
h=0.86 ⇒ k_bytes = 4.480  ✓        h=0.88 ⇒ 3.840  ✗（唯一跌破点，需 h 与实测同量级）
```

⇒ **`h ≤ 0.86` 时 `4.0` 安全**；若实测 `h` 明显高于 0.86，`k_bytes` 本身就是「每笔不足 4 KiB」，此时门 2 的 FAIL 是**正确**的否证信号，不是误判。**上界不设**：`MAX_SUBS = 32` 已由 `read_plan.h:17` 编译期保证。

#### 5.5.1 门 1 的量级闸（裁决 12）

精度容差维持 4%，但**前面加一道量级闸**（量级错 ≠ 精度不够，两者要分开判）：

```
B = Get-Item(<bench 目标文件>).Length                  ← 运行时取，不得写死
S = ceil(B / 131072)                                  ← 定义，不是常数
闸 0：S < dMisses_outer < 2 × (S + m2/4096)
      ↑ 下界 = S（首遍全 miss 是物理下限，低于它说明首遍有 OS 缓存命中 ⇒ 前提不成立）
      ↑ 上界 = 2 × 期望中心（= team-lead 裁决 12 的 `2×989,988` = 1,979,976）
门 1 精度带：989,988 × (1 ± 4%) = 950,388 … 1,029,588
门 2 下限：  dMisses_outer >= S × (1 + 4.0) = 828,305
期望中心：  S + m2/4096 = 165,661 + 824,327 = 989,988     （本机本次 B 的代入值，仅举例）
```

> ⚠️ **`S` 必须写成定义 `ceil(B/131072)`，不能写成 `165,661`。** 换目标文件（`B` 变）时，
> 写死的常数会**静默失效并仍然判 PASS** —— 这是本项目反复踩的那一类洞。
> `deliverables/RB-bench-miss-coalescing.ps1:229-231` 已经是运行时算的
> （`$B = (Get-Item -LiteralPath $canon -Force).Length`；`$S = [math]::Ceiling($B / 131072)`），
> **这一点是对的，不要改回常数。** 上表的 `165,661 / 989,988` 只是本机本次的代入值，
> 用来让人能一眼复算，不是判据常量。
>
> ⚠️ **`989,990` 与 `989,988` 的 2 笔差**：`S × (1 + 4.976) = 989,990` 是**按 `k_bytes` 反算**的近似；
> 按字节链 `S + m2/4096 = 989,988.02` 截断是 `989,988`。两者差 2 笔（0.0002%），
> **精度带取整数即可**，但同一份文件里不要混用两个中心值。

##### 5.5.1-补 闸 0 的**归因**修正（2026-11-20 第二轮，team-lead 复算）

**闸 0 上界不承担污染防护。** 上界的作用是抓**灾难性错配**（统计窗口串进了别的负载 / 两次跑混算 /
单位错 / 计数器翻倍），它与污染灵敏度**只差 1.865 倍**，宽不到一个数量级：

```
CONFIRMED 漂到 MORE-FRAGMENTED（r2 < 3768）：
    denom = dMisses − S ≥ m2/3768 = 896,084  ⇒ dMisses ≥ 1,061,745  ⇒ 只需 +71,757 次 stray
闸 0 上界                                                     = 1,979,976
                                                              1,979,976 / 1,061,745 = 1.865×
```

⇒ **污染只要让 `dMisses` 涨 8.70%（denom 的 `+71,757`），判据就翻带，而闸 0 不响。**
（`237,419 = S + 71,758` 是**废数**：把"denom 增量"当成了"dMisses 绝对量"，已撤回，不得再引用。）

**三个漂移方向各由谁挡**（这一张表替代"闸 0 是污染闸"的说法）：

| 漂移方向 | 需要的 stray | N2 字节闸（容差 `2% × 25,089,642,496 B ÷ 4096 = 122,508` 笔） | 危险吗 |
|---|---|---|---|
| **REFUTED → 假 CONFIRMED**（`r2` 从 131,072 涨进 `4096` 带，`r2 ≤ 4424`） | **737,451**（denom `25,760 → 763,211`） | **拦得住**（737k > 122k，差 6 倍） | **这是唯一真危险的方向**：把"被否证"说成"成立" |
| CONFIRMED → MORE-FRAGMENTED（`r2` 跌破 3,768） | 71,757 | **拦不住**（71k < 122k） | 不危险：结论变成**更强的前提**，不是错结论 |
| REFUTED → INCONCLUSIVE（丢掉否证，`r2 < 117,965`） | **2,861**（11.1% of denom） | **拦不住**（2.8k ≪ 122k） | 不危险：**拒绝下结论** ≠ 错结论 |

⇒ **精确表述（可直接引用）**：

> N2 字节闸拦住的是**假 CONFIRMED** —— 唯一会把「D-01 被否证」说成「D-01 成立」的方向；
> 伪造它需 `737,451` 次 stray，N2 只容 `122,508`，**差 6 倍，拦得住**。
> 另两个方向的漂移 N2 拦不住，但它们都不是错结论：一个让结论更强，一个是拒绝下结论。
> 闸 0 是**灾难性错配闸**，上界仅 `1.865×` 于 CONFIRMED 翻带点，**不足以当污染闸**。

> **口径不能混**：`737,451` 是从 REFUTED **基线**爬到 CONFIRMED **判据边界**（`r2 = 4424`）所需的 denom 增量；
> `798,567` 是从同一基线爬到**本次实测中心** `dMisses = 989,988`（`r2 = 4096`）所需的增量。
> 前者是判据边界、后者是观测值。**说"伪造 CONFIRMED 需要多少次 stray"时用 `737,451`**（边界更严谨），
> 说"本次测量离 REFUTED 有多远"时用 `798,567`。两个数都对，但**不能互相替代**。
>
> **同样不能混的两个倍数**：`824,327 / 25,760 = 32.0x` 是 **denom 之比**；
> `71,757 / 2,861 = 25.08x` 是**可容忍 stray 次数之比**。两者都对，含义不同，引用时必须说明是哪一个。

##### 5.5.1-补2 `S + m2/4096 = 989,988` 是**自洽核对**，不是"模型被实测证实"

`165,661 + 824,327 = 989,988` 与实测 `dMisses = 989,988` 逐位相同——**这个吻合不能当独立验证用**：

1. **它只是自洽核对，不是模型被证实。** 参与该式的三个量（`B`、`h`、`dMisses`）**来自同一次测量**，
   同源数字当然能对上；对上只说明"这组数没有自相矛盾"，**不说明 D-01 的合并假设成立**。
   D-01 是否成立，仍然只能由门 2（`k_count >= 4.0`）与门 3（两跑 `k` 不变 ±2%）回答。
2. **量级上也不支持"精确到个位"这种说法。** `h` 只给到 4 位小数（`0.8445`），半步 `±0.00005`
   ⇒ `±0.00005 × B = ±1,085,673 B` ⇒ `m2/4096` 的不确定度 **±265 笔**（相对 824,327 为 ±0.032%）。
   也就是说，把 `h` 的真实值取在任何落在 `0.84445…0.84455` 的数上，`m2/4096` 都能在 `±265` 内变动。
3. **若 `h` 本身是由本次 `dMisses` 反解出来的**（`h = 1 − (dMisses−S)×4096/B`），则本式是**恒等式**，
   对本模型**不构成任何证据**——它必然成立，与模型对不对无关。
   **要把它变成证据，唯一的办法是 `h` 与 `dMisses` 来自两次独立测量**（不同轮次 / 不同文件 / 不同负载），
   并在记录里写清是哪两次。当前记录不满足这一点。

> **口径**：引用时写「**自洽核对通过**」，**不要**写「模型被实测证实」「逐位吻合证明模型正确」。
> 本项目已经因为"看起来像证据的论断"返工过数次，这是其中最隐蔽的一种：**一个恒等式被当成了一次验证**。

**为什么门 3 是最有价值的一条**：

- **D2 一个字节不多读、不合并、不改 commit 语义 ⇒ `k` 必须严格不变**；
- 它是**两次 run 的差**，`S` 与 `B` 在两个 run 里是同一个常量 ⇒ 首遍常量完全消掉；
- 背景污染在两跑里同向、同量级 ⇒ 在差里只剩差分项（若两次都 200 s、都同一台机器，共模抑制很强）；
- 它同时是 team-lead 说的 **"若 `dMisses` 跌到 1/5 说明做的是合并不是并行，方向错了"** 这条判据的精确化形式：**合并会让 `k` 掉 5 倍（k=5→k=1），并行不会动它。**

| **5** | **3,220.0 MB** | **4,076 B** |

⇒ 注意 `dBytesMiss_hot` **与 `k` 无关**（它只由 `h` 决定）。所以

```
k_bytes = 3,376,448,065 / (4096 × 165,661) = 4.975994 ≈ 4.976
```

**`k_bytes` 是常量 4.976，`k_count` 才是变量。**（⚠️ 上一版此处写 `4.745` —— 无来源的笔误，已按裁决 11 更正为 `4.976`。）

这个事实把门 2 变成一句很干净的话（**单侧，裁决 11**）：

> **`k_count` 必须 `>= 4.0`，否则「每片 ≥4 条 miss 区间」这个 D-01 前提不成立 ⇒ 采信 REFUTED，D2 不必做。**

配平数值：

```
闸 0 量级闸：  S < dMisses_outer < 1,979,976            （S = ceil(B/131072)，本次代入 165,661）
门 1 精度带：  950,388 … 1,029,588                      （989,988 × (1 ± 4%)）
门 2 下限：    dMisses_outer >= 828,305                 （S × (1 + 4.0)）
期望中心：     989,988                                  （S + m2/4096 = 165,661 + 824,327）
```
（本节早前版本用 `989,990`：那是 `S × (1+4.976)` 按 `k_bytes` 反算的近似，与字节链差 2 笔，
已统一到 `989,988`。见 §5.5.1 的第二个 ⚠️。）

⇒ **P0 的期望值区间从原来的粗估收成 `[9.50×10^5, 1.03×10^6]`（4% 精度带），量级闸放宽到 `[1.66×10^5, 1.98×10^6]`。** 两个区间作用不同：量级闸判"这次测量是不是同一类实验"，精度带判"K 的取值是否落在 D-01 假设上"。**量级闸不过不许重判精度，直接 INVALID 重跑。**

## 8. 一句话给 team-lead

**你的撤回是对的，而且我上一轮犯的是同一个错 —— 我的"直读 `tgt`"就是"把 IRP 建在 `tgt` 上"，等于拆 `PoolBuf` 隔离。整段作废。**

**但封死这条路之后，答案反而更简单了：D2 的并行度只来自「发」，「收」严格串行 ⇒ `w->Stage` 那唯一一个槽在整个收阶段是独占的 ⇒ staging 不用加、`RbSyncCTX` 不用扩、buffer 形态一字节不用改。8 笔在飞 = 8 个 ctx = 8 个 `PoolBuf`，既有结构天然支持。**

**你算的 20 MB 高了 7.53 倍：同一切片的 8 条区间是同一个 128 KiB 窗口内的非重叠子区间，Σlen ≤ 139,264 B/worker ⇒ 峰值 2.66 MiB（20 worker）/ 4.25 MiB（32 worker），和"现状 1 笔按上界算"是同一个数 —— 并发度不改字节总量。所以「1 MB 池块按笔切分」不但不必要，而且会带来 7.5 倍浪费 + 一层新所有权纪律，否决。**

**`rbdev.c:151-158` 讲的是 `RB_SYNCCTX` 的 lookaside，不是 `PoolBuf`；`PoolBuf` 至今每笔一次 `ExAllocatePool2`（`:208`）且已上线验收。所以「必须池化」不是 D2 的准入条件，是可选优化（且可独立先做，QD1 单笔路径就受益）。**

**1.63× 一字不改**（收益只依赖 `k·L` 重叠；memcpy 次数与现状完全相同 = 2 次，不是减项）。

**`bm` 那条你判对了，量级是**：外层窗口首遍可精确扣（`dMisses` 扣 `S=165,661`、`dBytesMiss` 扣 `B=20,707.6 MB`），扣完 hot 占比 **83.3%（计数）/ 13.5%（字节）**；`dBytesMiss` 路径放大 **7.43ε**，2% 容差对应背景读预算仅 **329 KB/s** —— 现场不可控 ⇒ **它只能当一致性参考**。

**门 2 你两处都对，而且第二处比第一处重要**：`k_bytes` 真值是 **4.976**（我写的 `4.745` 无来源，同一节里我自己的算式却写着 `4.976`，自相矛盾）；但**改常数修不好这个门** —— 双侧窄带卡一个**单侧假设**，在 `k=1` 的 REFUTED 分支上偏差 398%，**会把最有价值的一次否证判成 INVALID**。已按裁决 11 改为 **单侧下限 `k_count >= 4.0`**（可复算：`h ≤ 0.86` 时 `k_bytes ≥ 4.48` 均安全，只有 `h=0.88` 才跌破；且 `MAX_SUBS=32` 已由 `read_plan.h:17` 编译期封上界），并**要求脚本打印 `k_count` 与 `k_bytes` 两个数**。门 1 前另加**量级闸** `165,661 < dMisses_outer < 1,979,976`（裁决 12）。**最有价值的一条仍是 `k_after ≈ k_before`（±2%）** —— D2 不合并不放大 ⇒ `k` 严格不变，且两跑共模污染相消。
