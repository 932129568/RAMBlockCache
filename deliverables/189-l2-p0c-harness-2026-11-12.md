## §0 一句话

开 L2 是这件事里**唯一不可逆风险动作**——BSOD 可以在任意一条 store/probe 路径上发生。所以夹具的重点不是"能开"，而是
**"无论从哪一步死掉，下次开机都能回到已知状态"**。设计成四条不变式，缺一条就不该按下去。

## §1 四条不变式

| # | 不变式 | 实现 | 为什么必须有 |
|---|---|---|---|
| I1 | **预检 fail-closed** | 13 项前置检查，任一不过 → `exit 2` 且**零改动** | 半开状态比不开更危险：`Flags` 置位但容器没建，驱动会在每次 IO 上反复走 refused 路径 |
| I2 | **崩溃安全** | 启用**之前**写 marker（`C:\ProgramData\rb-deploy\l2-p0c-state.json`）；下次启动发现残留 → **先回滚再退 3**，绝不在未知结局上续跑 | 测试如果蓝屏，脚本自己没机会收尾。残留 marker 是"上一次死过"的唯一证据 |
| I3 | **自动回滚** | 任何 FAIL → `l2 disable` → **清 `L2Letter`/`L2SizeGB`** → 删容器/索引 → 复验 | `L2Letter` 不清会让 `RbFeatRefuseLetter` 持续拒绝该卷自动挂载（真机 F: 两晚失联就是这个） |
| I4 | **不碰源码** | 全程不写 `src\` | `RB-sign-deploy-150.ps1:85` 会拿 `src\driver`+`src\core` 的最新 mtime 跟 sys 比；碰一下就把签名链判"驱动过期" |

## §2 判据（PASS 需要全部成立）

| 判据 | 阈值 | 证明什么 |
|---|---|---|
| 部署件哈希 == 三锚点 且 Authenticode Valid | 全部相等 | 测的是已审阅构建，不是野包 |

## §4 我自己 dry-run 抓出的三个缺陷（都属"看起来对、实际错"）

### 4.1 假 FAIL：无捕获组的正则 + `Groups[1]`

```powershell
# 改前
$m = [regex]::Match([string]$t, '[0-9A-Fa-f]{64}')
if ($m.Success) { $side = $m.Groups[1].Value.ToLowerInvariant() }   # 无捕获组 -> 永远 ""
```

`Match` 成功、`Test-Path` 为真、变量被赋值——但值是空串。于是三锚点比较里第三项恒为 `''`，
预检稳定 `exit 2`「deployed sys does not match the three anchors」。**这是假 FAIL，不是假 PASS**，
但它会让夹具永远开不了，且日志长得像"驱动真有问题"，很容易误导人去查驱动。

改法：`$side = $m.Value.ToLowerInvariant()`（或给正则加捕获组，两处必须一致）。

### 4.2 假 PASS：`Get-Flags` 读不到时返回 0

```powershell
# 改前
if ($null -eq $f) { return 0 }          # 「读不到」被伪装成「未开启」
```

PowerShell 里 `$null -band 4` 等于 0，因此 `if (($flags -band 4) -eq 0) { 通过 }` 会把
**注册表读取失败**判成"L2 没开，可以开"。这是标准 fail-open，且恰好落在最不该放行的地方。

改法：返回 `$null`；所有消费点显式判 `$null` → FAIL/UNKNOWN；新增 `FmtFlags` 避免 `-f $null` 抛错。

### 4.3 漏判：按行号取日志增量

改前记录"启用前日志行数"，之后只检查 `$log[$preLogCount..]`。若日志在窗口内被轮转/截断，
`$log.Count -gt $preLogCount` 为假 → **整段跳过** → 零 ERROR 被"证明"。

改法：`Get-ErrorSince -SinceUtc $enabledUtc`，逐行解析行首 `yyyy-MM-ddTHH:mm:ss.fffZ` 比较时间；
日志不可读返回 `$null`（=UNKNOWN），由调用方 WARN，不当作 PASS 证据。

## §5 这套夹具**没有**证明什么（防拔高）

1. **从未真正启用 L2**：`Features\Flags` 仍是 0，`rbL2.c` 的 store/probe/close 路径一次都没执行。
   本文所有"PASS"都是**预检级**结论。
2. **不替代 runbook**：开 L2 的正确入口、失败模式、回滚序列见 188 号（另一代理在写）。
3. **不覆盖 J11 残余**：本机 L2 从未启用，索引文件不存在，所以"中间一次无 L2 引导不递增 BootSeq"这条
   跨引导陈旧风险本轮不会触发；**第二次启用**之前必须先处理（或按 preflight 要求手工删索引）。
4. **Verifier 开着**：Special pool 会放大内存足迹，L2 打开后若 BSOD，需先区分"逻辑 bug"与"Special pool 耗尽"。
5. **读回路径可能没被覆盖（覆盖缺口，如实标注）**：负载是"写 128MB → 立刻读回"。Windows 文件缓存位于过滤器**之上**，
   刚写完的读回很可能由缓存直接满足，**不触达驱动**，因此 `RbL2ProbeFill` 未必执行。PASS 判据只依赖
   `L2Stores > 0`（写路径），所以结论不受影响；但**"读命中路径未被验证"**这句话必须跟着结果一起说。
   要真正覆盖读路径，得用 `FILE_FLAG_NO_BUFFERING` 直读（需扇区对齐缓冲），属独立改进项。

## §7 判据可达性核实（13:50–14:00，主线程独立核对）

§5 第 5 条留了一个"读回可能由文件缓存满足、不触达驱动"的缺口。这一轮把它和另外三条前提逐条落到了代码/注册表证据上。**四条全部成立，store 通路在结构上可达**；但每条都有前置条件，任一不满足就会变成"健康但什么都没测"——因此夹具新增了 `UNCOVERED` 退出码，而不是把 `stores=0` 当 PASS。

### 7.1 store 通路确实编译进了产物

`RB_WIRED_L2_ON_EVICT` 在 `src/common/rb_wiring.h:8` 定义为 `1`，所以 `cache_evict.c:90/102/121` 的三段（锁内捕获 → 锁外回调 → `chunk_free`）都在。为排除"宏为 1 但代码没链进去"，直接对产物做 UTF-16 字节匹配：

| 字符串 | UTF-16 出现次数 |
|---|---|
| `l2: evict rejected (cold` | 1 |
| `evict rejected (state!=opened)` | 1 |
| `l2:` 前缀（全部诊断） | 27 |

这两条是 `rbfeat.c:876`（state 预检）与 `:886`（`Hits<2` 冷块过滤）的独有诊断串，各出现恰好 1 次 ⇒ 两个守卫都在二进制里，即 `RbFeatOnEvict` 确实被编译并挂上了淘汰路径。

（旁注：`strings -el` 在该产物上不可靠，连已知串都报 0；用 Python 做 `utf-16-le` 原始字节计数才可信。）

### 7.2 三条计数/几何前提

| 前提 | 证据 | 当前值 | 结论 |
|---|---|---|---|
| 淘汰传出的 `len` 必须等于 64KB | `cache_evict.c` 传 `eng->chunk_size`；`rbL2.c:1022` `if (len != RB2_L2BLK) return` | — | 必须 chunk=64KB |
| `chunk_size = block_size × 16` | `cache.c:269` + `cache_internal.h:275` `RB_SUBS_FIXED=16` | `BlockSize=4096` ⇒ **65,536** | ✅ 等长，通过 |
| 几何门 `BlockSize×16 == RB2_L2BLK` | `rbL2.c:634`，不满足置 `state=3` | 4096×16 = 65536 | ✅ 不触发 refused-blocksize |
| `hits` 只在真命中时 +1 | `cache_read.c:54` `InterlockedIncrement(&c->hits)`（miss 分支不增） | — | 见 7.3 |

### 7.3 三遍读取是硬性下限（这是本轮改掉的真缺陷）

准入条件 `rbfeat.c:886` 是 `if (Hits < 2) return;`。而 `hits` 只在命中时自增，所以：

| 读遍 | 结果 | 该块 hits |
|---|---|---|
| 第 1 遍 | 全 miss → 回填 | 0 |
| 第 2 遍 | 全 hit | 1 |
| 第 3 遍 | 全 hit | **2** ← 才够准入线 |

原夹具只读两遍，**最多得到 hits=1，永远被 `Hits<2` 丢弃，stores 恒为 0**。这不是驱动问题，是夹具的负载构造不足以触发准入——属于"判据结构上不可达"，会让一轮真机测试以假 FAIL 收场。已改为三遍。

### 7.4 `shrink 100` 的生效条件（差点变成另一个假 PASS）

`rbio_ports.c:52-65` 的 shrink 有两条路径：

- `rb_engine_apply_pressure(eng, 2)`：`level>=RB_PRESSURE_HIGH` 时取 `dl = dynamic_limit`，**若 `dl==0` 则回落 `cfg.max_bytes`**，然后 `while (total_bytes > dl)` 驱逐。
- `rb_stream_idle_reclaim()`：`thr = idle_reclaim_ms`（默认 30 分钟，`cache.c:253`），`if (now < thr) return 0`。

由注册表实测：`AutoMemory=1`、`IdleReclaimSec=1800`。

- AutoMemory=1 ⇒ shrink 先把 `dynamic_limit` 压到 1MB 下限（`Pct=100` 时 `cur-cur=0`，被钳到 1MB），`total_bytes` 必然远超它 ⇒ **全量驱逐**，store 通路被真正执行。
- **反向风险**：若 `AutoMemory=0`，`dynamic_limit` 被清零（`rbconfig.c:28`），`dl` 回落 `max_bytes`（GB 级），128MB 远低于它 ⇒ **零驱逐、stores 恒 0**，而 `shrink` 仍返回 `exit 0`。**"shrink 成功"不等于"发生了驱逐"**，把它当已触发就是假 PASS。
- `IdleReclaimSec=1800` ⇒ 10 分钟窗口内 `rb_stream_idle_reclaim` 一定早退，**不能指望它**。

所以夹具不把 `shrink exit=0` 当证据，最终判据只看 counter：`stores>0` 才 PASS，`state=1 且 stores=0` 判 **UNCOVERED（exit 5）**，既不放行也不误杀。

### 7.5 本轮对夹具的改动汇总

| # | 改动 | 原因 |
|---|---|---|
| 1 | 负载读 2 遍 → **3 遍** | `Hits<2` 准入线，两遍结构性不可达 |
| 2 | 新增 `-SelfTestLoad` 自检模式 | Add-Type/P-Invoke 在 dry-run 里不会执行，真测试才炸 |
| 3 | 新增 `UNCOVERED`（exit 5）语义 | `stores=0` 不得冒充 PASS |
| 4 | `state=2` 需连续 3 次才判死 | state 2 含"无卷"可自愈瞬态（`rbL2.c:666`），一次即判死是假 FAIL |
| 5 | 日志读不到 → **FAIL**（原为 WARN 继续） | 否则"读不到"被当成"零 ERROR"写进 PASS 证据 |
| 6 | `Get-Flags` 读失败返回 `$null` 并全链路显式判 | `$null -band 4` == 0，否则"读不到"当"未开启"放行 |

## §8 拓扑修正：单卷方案作废（194 号审计结论）

§1–§7 隐含一个前提：「`l2 enable D:` 既是容器卷也是被加速卷」。**这个前提是错的**，194 号审计推翻了它：

| 事实 | 证据 |
|---|---|
| `l2 enable <X:>` 的 X: 是**容器卷** | `rbL2.c:246 RbL2Path` 用 `s_Letter` 拼 `\??\X:\RAMBoostL2.bin`；`.idx` 同卷 |
| 容器卷**不能被加速** | `rbfeat.c:801 RbFeatRefuseLetter` 闸住三条路径：自动 sweep（`rbattach.c:743`）、手动 attach（`:1133`）、运行时挂栈（`:1467`） |
| 已 attach 的卷在 enable 后**本会话仍加速** | `REFRESH` 只做 `Rb2ReloadFlags` + `RbL2LazyOpen`，不 detach |
| 同卷自指**没有显式递归防护** | 全仓无 top-level IRP / 线程 / 文件对象 / 文件名判断；只靠「未 attach 即透传」与「分页 IO + `CachePagingIo=0` 旁路」两条间接条件 |
| 同卷还有确定性自干扰 | `.idx` 截断（`FileEndOfFileInformation`）会触发 `flush + discard_all + RbL2DropAll`（`rbio.c:226-273`） |

**后果**：原方案 `enable D: + 负载 D:` 即便本会话能跑，也是自指拓扑，且 `.idx` 截断会周期性清空 L2 —— 既不可信也不可复现（重启后 D: 被拒挂载 ⇒ 无流 ⇒ stores 恒 0）。

### 8.1 改成双卷

| 角色 | 卷 | 理由 |
|---|---|---|
| 容器卷 | **C:**（72.2 GB free，未 attach） | 系统卷受 `RbIsBootCriticalPdo` 保护，结构上永不被加速 |
| 负载卷 | **D:**（712.2 GB free，attached=accelerated） | 唯一已挂载的卷，读路径才能真正进过滤器 |

参数：`-ContainerLetter`（默认 C）与 `-LoadLetter`（默认 D）；旧 `-Letter` 删除，`$L` 拆成 `$CL`/`$LL`。

### 8.2 新增的三道闸

1. **同卷硬拒**：`$CL -eq $LL` → `exit 2`（`-DryRun` 同样拒），并在输出里点名"容器卷不能被加速"。
2. **attach 状态断言**：新增 `Get-VolStatusMap` 解析 `rbfeatctl vols` 的 `  D: accelerated` / `  C: bypass`；**负载卷必须 `accelerated`、容器卷必须 `bypass` 或不在表内**。设备不可读时 `Get-VolStatusMap` 返回 **`$null`** 而不是空 hashtable（空表会让断言静默通过）。
3. **两卷空间分别校验**：容器卷需 `SizeGB + 2` GB，负载卷需 `LoadMB + 1` GB。

### 8.4 仍未消解的风险（如实标注）

- **C: 是系统卷**：2GB 容器落在 `C:\RAMBoostL2.bin`。回滚会删，但测试期间系统卷多占 2GB。若更保守，可改用 **F:**（953 GB free、未 attach）作为容器卷：`-ContainerLetter F`。
- **`RbFeatRefuseLetter` 的副作用**：L2 开启期间容器卷不进自动挂载。C: 本来就不 attach，故本机无额外影响；若改用 F:，则重启后 F: 会静默不加速（`l2 disable` 即恢复，`rbfeat.c:807` 在 L2 关闭时返回 FALSE）。
- **自缓存环**：本次靠"容器卷不 attach"这条拓扑不变量规避，代码里**没有防护**。这是一条隐含依赖，若将来允许容器卷与负载卷同卷，必须先补防护。
