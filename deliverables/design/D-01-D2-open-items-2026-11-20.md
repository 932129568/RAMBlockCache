## 0. 一页结论

| 项 | 判定 | 一句话依据 | 对 D2 的结论 |
|---|---|---|---|
| **O1** 非对齐读进 `tgt` | ✅ **不成立（不是风险）** | `RbSyncIo` **从不把调用方缓冲交给下层**（`rbdev.c:208` 自建 `PoolBuf`，`:216` 用它建 IRP，`:262` 读成功后才 `RtlCopyMemory` 回调用方 `buf`）。目标缓冲对齐对下层**不可见** | **zero-staging 可行**（D2 保持零分配、零读放大） |
| **O2** lookaside 深度 | 🟡 **不是阻塞项，但有新的资源天花板** | `Depth` 参数是保留位（传 0），ntoskrnl 硬编码 `Depth=4 / MaximumDepth=256` 并按需动态上抬。本机 20 逻辑 CPU ⇒ 并发上限 20×32=**640 > 256** ⇒ 稳态仍有约 384 笔走 `ExAllocatePoolWithTag` | D2 可做，**但建议把每切片在飞上限压到 8**（20×8=160 < 256 ⇒ 全新命中 list） |
| **O3** `RbDiagRecord` 配对 | ✅ **不影响 D2** | `s_DiagSeq` 是 `InterlockedIncrement64` 原子自增（`rbdriver.c:586`）；且**本机 `TestMode=0` ⇒ 整个函数在 `:585` 早退，是 no-op**；仓内**没有任何脚本或工具解析诊断环** | 不需为 D2 改任何判读逻辑 |

**三条需要更正的既有说法**（前两条是题面假设，第三条是我自己 `D-01` 里的错判）：

1. **`RbIsUnalignedIo` 在仓里不存在（题面假设）。** 全 `src/` 大小写不敏感搜 `unalign` → **0 命中**。题面所指 `rbio_worker.c:200` 附近那个函数是 `RbWriteNeedsInvalidate`（`:199-203`），它只判「写是否需要失效」，与读路径对齐无关。
2. **`ext->Alignment` 是死字段。** `rb_common.h:121` 声明、`rbattach.c:1542`+`rbmsg.c:492` 赋值，但**全仓无任何读取点**（`grep '\->Alignment'` 排除 `AlignmentRequirement` 后为空）。驱动自身不强制任何对齐。
3. **② 路径用 staging 不是因为"目标缓冲要对齐"。** 我在 `D-01` §3.5 写的「② 用 staging 正是因为 staging 已 4K 对齐」**是本轮的错判，现撤回**。staging 的真正理由是「读整块 → commit 整块 → 从整块里切出请求交集」（`rbio_worker.c:294-298`），与目标地址对齐无关。`RbStageGet` 的 4K 对齐来自 `RbAllocAlignedNonPaged`（`rbdev.c:18-27`）这个**共享分配器**的既有契约（其真正需要对齐的消费者是 `rbpref.c:96` 的 `IoAllocateMdl`），不是 `RbSyncIo` 提的要求。

**顺带查出一个独立缺陷（登记 L6，不属本任务范围）：**

> **`RbReadMissRange` 的 ① 直读快路径（`:253`，`> 1 MiB`）与超 ULONG 防御分支（`:242`，`> 0x80000000`）在 128 KiB 窗口下双双成为死代码。**
> 推导：`rb_read_plan_chunk` 返回 `≤ 131072`（`read_plan.c:22` + `read_plan.h:16-29` 的 `window_128k` 断言）⇒ `rb_read` 的 `miss[].len` 上界 `131072 + 2×4096 = 139,264 B`（`cache_read.c:65-66` 整子块对齐两端各越一个子块）⇒ **既不 > 1 MiB，也不 > 2 GiB**。
> 后果：① 在当前窗口下不可达，且它内含的 `RbFeatOnMiss`（`:256`）意味着 **L2 在 >1 MB 区间的回填语义从未被触发**。`RbReadMissRange` 的注释（`:214-227`）写于「单条 miss 区间最大 64MB」的年代，说明**曾有一个 >1 MB 窗口**；具体何时改成 131072 **未查**（`git log` 仅一次仓库重建提交，`deliverables/165` 只记录宏提升为头文件权威定义、未记录数值变更）。无任何门禁能发现这类"窗口收缩导致分支死亡"。

## 1. O1 — 非对齐读进 `tgt` 是否被下层接受

### 1.1 结论（明确二选一）

> **不成立。D2 可以直接读进 `tgt + (lo − rs)`，不需要任何 staging。**
>
> 而且这个结论**不是推断**——`RbReadMissRange` 内部此刻就有**三个**分支在做一模一样的事：把 `RbSyncIo` 的目标写成 `tgt + 非 4K 对齐偏移`。D2 只是把它们已经验证过的形态并行化。

### 1.2 决定性证据：`RbSyncIo` 根本不把调用方缓冲交给下层

这是整条推理的支点。`rbdev.c:188-270` 的同步盘 I/O **对数据缓冲做了全程池化**，IRP 永远只看见自己的 `PoolBuf`：

```c
/* rbdev.c:207-217 */
    /* 数据缓冲池化：IRP 全程只看见 PoolBuf，超时后调用者 buf 可立即失效。 */
    ctx->PoolBuf = ExAllocatePool2(POOL_FLAG_NON_PAGED,
                                   (SIZE_T)len, RB_POOL_TAG);
    if (!ctx->PoolBuf) { RbSyncCtxFree(ctx); return STATUS_INSUFFICIENT_RESOURCES; }
    if (doWrite) RtlCopyMemory(ctx->PoolBuf, buf, len);
    else         RtlZeroMemory(ctx->PoolBuf, len);

    irp = IoBuildSynchronousFsdRequest(doWrite ? IRP_MJ_WRITE : IRP_MJ_READ,
                                       ext->LowerDevice,
                                       ctx->PoolBuf, (ULONG)len, off,
                                       &ctx->evt, &ctx->iosb);
```

```c
/* rbdev.c:260-263 */
    if (NT_SUCCESS(s) && ctx->iosb.Information < (ULONG_PTR)len)
        s = STATUS_IO_DEVICE_ERROR;
    if (NT_SUCCESS(s) && !doWrite) RtlCopyMemory(buf, ctx->PoolBuf, len);
    if (pInfo) *pInfo = NT_SUCCESS(s) ? ctx->iosb.Information : 0;
```

于是：

| 事实 | 位置 | 含义 |
|---|---|---|
| IRP 的 `MdlAddress` / 缓冲来自 `ctx->PoolBuf` | `rbdev.c:216` | 下层的 MDL 建在**非分页池新分配**上，与调用方 `buf` 完全无关 |
| 调用方 `buf` 只在 `RtlCopyMemory` 里出现 | `rbdev.c:211`（写）/ `:262`（读） | `buf` 的**地址对齐对整条 IRP 链路没有任何影响**；它只是一个内核 `memcpy` 的终点 |
| 下层只消费两个数：`off->QuadPart` 与 `len` | `rbdev.c:216` | 目标对齐从来不进入 IRP |

**结论**：`RbSyncIo(ext, FALSE, &moff, tgt + (lo-rs), hi-lo, NULL)` 与 `RbSyncIo(ext, FALSE, &moff, st, clen, NULL)` 在下层看来**完全等价**——唯一的差别是 `moff`/`len`，而这两个值 D2 与现有 ② 路径用的是同一套 `lo/hi/cur/clen`。

> 这也解释了为什么 `RbSyncIo` 的注释把「池化」写成安全属性而非性能属性：`rbdev.c:121-134` 明说池化是为了「超时后调用者 buf 可立即失效、IRP 全程不触碰调用者缓冲」。**目标缓冲被隔离是设计意图，不是巧合。**

### 1.3 仓内的三处同形态代码（其中两处是死代码，先讲清楚）

`RbReadMissRange` 里有**三处**写死「读进 `tgt + 偏移`」的代码。但我在核对它们的**可达性**时得到了一个必须先说的结果——**其中两处是死代码**：

| 先例 | 位置 | 进入条件 | 可达性（本轮实测推导） |
|---|---|---|---|
| ① 「>1 MB 全覆盖直读」 | `:253` | `mr->len > 1 MiB && ms >= rs && me <= re` | ❌ **恒不可达** |
| ② 「超 ULONG 范围防御」 | `:242` | `mr->len > 0x80000000` | ❌ **恒不可达** |
| ③ 「staging 分配失败兜底」 | `:303-308` | `RbStageGet` 返回 NULL | ✅ **可达**（非分页池压力期） |

**可达性推导（可复算）**：`rb_read_plan_chunk` 的返回值上界是 `RB_READ_PLAN_MAX_BYTES = 131072`（`read_plan.c:22` `min(remaining, available)`，`available = (offset&~4095)+131072-offset ≤ 131072`；`read_plan.h:16-29` 的 `window_128k` 断言把窗口焊死）⇒ 切片 `chunk ≤ 131072`。`rb_read` 给出的 `miss[].len` 是整子块对齐的区间（`cache_read.c:65-66`），两端各最多越出一个子块 ⇒ **上界 `131072 + 2×4096 = 139,264 B = 136 KiB`**。

- `139,264 > 1 MiB (1,048,576)` → **假** ⇒ `:253` 恒不可达；
- `139,264 > 0x80000000 (2 GiB)` → **假** ⇒ `:242` 恒不可达。

> **这条推导同时更正了两处既有表述**：`D-01` §3.2 我说「D2 与 ① 路径（`:254`）同构」——同构没错，但**① 路径在当前窗口下不可达**。`RbReadMissRange` 的注释（`:214-227`）明写这是「[W1.5] 设计」，且同注释写「门 8MB→64MB 后单条 miss 区间最大 64MB」——说明**曾存在一个 >1 MB 的窗口**，与现窗口 131072 不相容。具体何时改、为何改，**我查不到**（`git log` 只有一次仓库重建提交；`deliverables/165` 只记录"把 `read_plan.c` 的私有宏提升为头文件权威定义"，未记录数值变更）。⇒ **我能证明的是"当前不可达"（可复算），不能证明"某日被改成不可达"（无提交史）**。凡涉及"何时变死"的表述一律记"未查"。
>
> 所以「与既有已验证路径同构」这个论据**我撤回**：① 没有运行时验证记录。O1 的成立**只**依赖 §1.2 的结构性事实（`RbSyncIo` 池化），那一条不依赖任何先例。
>
> 另外这是**一个独立缺陷**（不是本任务范围，登记为 L6）：`W1.5` 精心设计的 ① 直读快路径与超 ULONG 防御分支在**当前** 128 KiB 窗口下双双不可达，而现有门禁（`check_stack_frame_budget.py` 等）不会发现"窗口收缩导致分支死亡"这类退化。不可达代码里含一条 `RbFeatOnMiss` 调用（`:256`）——**L2 回填在 >1 MB 路径上的语义因此从未被触发过**。

下面逐条给证据，**重要性排序为 ③ > ①②**（①②仅供说明"设计意图曾经如此"）：

**先例 ①，① 快路径（>1 MB 全覆盖），`:253-259`：**

```c
    if (mr->len > (1UL << 20) && ms >= rs && me <= re) {
        PUCHAR dst = (PUCHAR)tgt + (ms - rs);   /* 交集已在 tgt 原位（全覆盖） */
        moff.QuadPart = (LONGLONG)ms;
        if (NT_SUCCESS(RbFeatOnMiss(ext, (ULONG64)ms, (ULONG)mr->len, dst))) {
            *ps = STATUS_SUCCESS;
        } else {
            *ps = RbSyncIo(ext, FALSE, &moff, dst, (ULONG)mr->len, NULL);
        }
```

`ms - rs` 当 `rs` 不是 4 KiB 倍数时**就不是 4 KiB 倍数**（数值见 §1.4）。**但这条分支在当前窗口下不可达**（§0 推导：`mr->len ≤ 136 KiB < 1 MiB`）；`D-01` 分析的 bench 读也**不走它**（8 MB 请求被切成 64 个 ≤128 KiB 的切片，每片 `miss[i].len ≤ 136 KiB`），而是走 ② 的 staging 分片。我初稿把这条写成「现网常态」是错的，现更正。

**先例 ②，超 ULONG 范围防御分支，`:245-246`：**

```c
            *ps = RbSyncIo(ext, FALSE, &moff, (PUCHAR)tgt + (lo - rs),
                           (ULONG)(hi - lo), NULL);
```

**先例 ③，staging 分配失败兜底，`:303-308`：**

```c
            } else if (chi > clo) {
                /* staging 分配失败：仅下盘读本片交集进 tgt，本片不入缓存并如实上报 */
                RbNoteBypass(ext, RB_BYPASS_RESOURCE);
                moff.QuadPart = (LONGLONG)clo;
                *ps = RbSyncIo(ext, FALSE, &moff, (PUCHAR)tgt + (clo - rs),
                               (ULONG)(chi - clo), NULL);
```

**只有先例 ③ 是活代码，而它恰恰是 D2 最需要的那条**：`RbStageGet` 返回 NULL（非分页池压力期，`rbio_worker.c:286-287`）时，直接走 ③ 读进 `tgt + (clo − rs)`。`clo − rs` 的非对齐性已实测（脚本输出）：

| `cur` | `clo` | `clo − rs` | `% 4096` |
|---|---|---|---|
| `0x2200`（切片 0，`rs=0x1200`） | `0x2200` | 4,096 | 0 |
| `0x2001000`（32 MB 分片后） | `0x2001000` | 33,553,920 | **3,584** ❌ |

> 判据强度（修正版）：① ② 是**设计意图的化石**，只能证明"作者认为这样写是对的"；**真正的运行时证据只有 ③**。而 ③ 的观测窗口极窄（只在非分页池压力期出现），所以严格说：**"非对齐目标缓冲在真机上被验证过"这件事，我无法给出证词，只能给出结构证明（§1.2）+ 一条低频活路径（③）+ 作者意图（①②）。**

这个诚实的降低很重要，因为 §4 第 5 条会指出：**D2 的难度不在对齐，在它必须动 `rbdev.c`**。对齐从来不是瓶颈。

### 1.4 题面问的数值：`lo − rs` 是否必然 4 KiB 倍数 —— **不必然，给反例**

**前提核对**（题面给的假设）：`BlockSize=4096`（注册表实测 `Parameters\BlockSize = 4096`，与 `cache.c:264` 的 `legal[] = {4096,...}` 一致）；`miss[].offset` 是整子块对齐（`cache_read.c:65-66` `ms_start = sub_start = cs + (idx << sub_shift)`）⇒ 恒为 4096 倍数。

**关键点：`rs` 不必是 4 KiB 倍数。** `rs = ctx->Offset.QuadPart`（`rbio_worker.c:409` → `:484` 传入），来自上层 IRP 的 `ByteOffset`；驱动侧只在 `rbio.c:469-473` 判 `len==0 || len > MaxCacheIoKB || offset<0` 才透传，**没有任何 4 KiB 对齐前置门**（`len` 门与 offset 门都看过，`:461-473`）。而切片函数本身**正是为"起点不对齐"设计的**：

```c
/* read_plan.c:18-22 */
        windowEnd = (offset & ~(RB_READ_PLAN_SUB_SIZE - 1ULL)) + RB_READ_PLAN_MAX_BYTES;
    if (windowEnd <= offset) return 0;
    available = windowEnd - offset;
    return remaining < available ? remaining : (size_t)available;
```

`(offset & ~4095) + 131072` ⇒ **`chunk` 会小于 131072，恰好因为 `offset` 不在 4 KiB 边界上**。所以"起点不对齐"是这条路径的**设计内输入**，不是异常输入。

**反例（数值可复算）**：`rs = 0x1200`（4608，512 对齐但不 4 KiB 对齐），`len = 0x20000`，`BlockSize = 4096`：

| 切片 | `cur` | `chunk` | `re = cur+chunk` | `re % 4096` |
|---|---|---|---|---|
| 0 | `0x1200` | `0x1FE00` | `0x21000` | 0 |
| 1 | `0x21000` | `0x200` | `0x21200` | 512 |

设切片 0 内偶数子块已命中、奇数子块 miss（`mcnt > 1`，正是 D2 的目标场景）：

| `miss[i]` | `ms` | `lo` | `lo − rs` | `(lo−rs) % 4096` |
|---|---|---|---|---|
| 0 | `0x1000` | `0x1200`（=`rs`） | **0** | 0 |
| 1 | `0x2000` | `0x2000` | `0xE00` = **3,584** | **3,584** ❌ |
| 2 | `0x4000` | `0x4000` | `0x2E00` = **11,776** | **3,584** ❌ |

> **反例成立**：`lo − rs = 11,776 B`，`11,776 = 2×4096 + 3,584`。**不是 4 KiB 倍数。**

第二个反例（长度方向，题面点名的"尾块钳后落在非对齐位置"）：`:276-277` 把 `me_io` 钳到 `ext->DiskSize`，而 `DiskSize` 来自 `IOCTL_DISK_GET_LENGTH_INFO`（`rbattach.c:406-412`），**不保证是 4096 倍数**。此时末片的 `clen = me_io − cur` 与 `hi − lo` 都可能不是 4 KiB 倍数。但注意：**这一条与 D2 无关**，因为它对 `off`/`len` 是既成事实，② 路径的 `clen` 已经是这样下发到 `RbSyncIo`（`:292`），D2 沿用同一套 `lo/hi` 计算 ⇒ **不引入新形态**。

**所以**：题面问的"是否必然 4 KiB 倍数"答案是**否**，但 §1.2/§1.3 已证明**这对 D2 无关**。两件事必须分开说，否则会误判成"必须退回 staging"。

### 1.5 `RbIsUnalignedIo` 不存在（题面假设更正）

| 检索 | 结果 |
|---|---|
| `grep -rin "unalign" src/` | **0 命中** |
| `rbio_worker.c:199-203` 实际是什么 | `static __inline BOOLEAN RbWriteNeedsInvalidate(LONGLONG off, ULONG len, rb_u32 bs)` —— 判「写是否需失效」：`return !((off % bs)==0 && (len % bs)==0);`。**只用于写路径**，读路径无此判定 |
| 驱动是否在别处拦非对齐读 | **没有**。`rbio.c:461-473` 的读入口门只有：`len==0`、`len > MaxCacheIoKB<<10`、`offset < 0` |
| `ext->Alignment` 是否被读 | **没有**（见 §0 更正 2） |

**含义**：驱动对读请求的对齐**完全不设防、也完全不做修正**——这既解释了为什么 ①/②/③ 三条路径能随意把目标写成 `tgt+偏移`，也说明「非对齐读」这件事在本驱动里从来不是被建模的对象，因为 `RbSyncIo` 的池化把它屏蔽掉了。

### 1.6 若将来必须退回 staging：最省的单块布局与常驻核算

题面要求核算这条。**结论是：不建议，但如果被迫，选"单块 128 KiB 切 32 份"，不要选"每区间一块"。**

| 方案 | 分配调用 | 每 worker 常驻 | 本机（20 worker）常驻 | 问题 |
|---|---|---|---|---|
| 每区间一块（`RbStageGet(w, 4096)` × 32 次） | 需要 32 个同时有效的缓冲 | **不可能**——`RbStageGet` 返回的是**同一个** `w->Stage`（`rbio_worker.c:119` `return w->Stage;`），第 2 次调用就直接覆盖第 1 次拿到的指针 | 不成立 | 语义上做不到"每区间一块"：`w->Stage` 是**单槽** |
| 单块 128 KiB 切 32 份（`RbStageGet(w, 131072)` 一次，然后 `st + i*4096`） | 1 次 | 128 KiB | **2.5 MB** | 可行；且 `RbAllocAlignedNonPaged` 保证 4K 对齐、`RB_STAGE_MAX = 32 MB` 远未触顶（`:108`） |

修正 `D-01` §3.4 的一个数字：那里写的「32 × 128 KiB = **4 MB**」是**按 `RB_IO_WORKERS_MAX = 32` 的上界**算的；本机 `NumberOfLogicalProcessors = 20`，`RbStartIoWorkers` 取 `n = min(KeQueryActiveProcessorCountEx(ALL), 32)`（`rbio_worker.c:1049-1052`、`:1104` 发布）⇒ 实际 `IoWorkerCount = 20` ⇒ 真实常驻 **2.5 MB**，4 MB 只是设计上界。

另注意 `w->Stage` **懒涨不缩**（`rbio_worker.c:113-119`：只在 `StageCap < need` 时换新；缩容点只有 `:1039` worker 退出）⇒ 一次 128 KiB 需求即**永久**钉住 128 KiB/worker。这是 staging 方案的隐性成本，且**与阈值大小无关**（只要触发过一次）。

### 1.7 O1 的残余风险（真风险，但与对齐无关）

O1 关掉之后，这一项**仍有三个必须写进实现规格的残余点**：

| # | 残余点 | 依据 | 要求 |
|---|---|---|---|
| R1-a | `RbSyncIo` 读路径每次都 `RtlZeroMemory(ctx->PoolBuf, len)` | `rbdev.c:212` | D2 把"每切片 1 次读"变成"每切片 ≤32 次读" ⇒ 零化成本 ×32。每切片 32×4 KiB = 128 KiB 零化，相对 4 KiB I/O 的 58.6 µs 可忽略（≈2–3 µs），但**必须在验收里计入**，不得声称"零额外成本" |
| R1-b | 短传归一化按**单笔** `len` 判 | `rbdev.c:260-261` | 单笔 CR 短传 ⇒ 该区间 `STATUS_IO_DEVICE_ERROR` ⇒ 与现状同语义（D2 必须按区间判 `NT_SUCCESS`，**不得**用"任一成功就算整片成功"） |
| R1-c | `RbFeatOnMiss` 返回 SUCCESS 表示 L2 已填充该区间，**必须跳过下盘** | `rbfeat.c:917-923`、② 路径 `:289-293` 的同款用法 | D2 逐区间先调 `RbFeatOnMiss`，返回 SUCCESS 的区间**不建 IRP**。如果 D2 先无脑全发再逐区间补调 hook，会把 L2 已命中的区间**多读一遍盘**（本机 `Flags=0` 时恒 NOT_FOUND，但这是配置相关，不能赌） |

> R1-c 是 D2 里唯一容易写错的地方：`RbFeatOnMiss` 的返回**决定要不要发 IRP**，不能像 staging 路径那样"先发再看"。

## 2. O2 — 并发 IRP 的 lookaside 深度

### 2.1 结论

> **不是阻塞项，但有一个必须显式定死的上限。** `RB_SYNCCTX` 的 lookaside 初始只留 4 个空闲项（`Depth = 4`，不可配），系统上限 `MaximumDepth = 256`；未命中时**自动回退到 `ExAllocatePoolWithTag`**（不是失败）。本机总并发上限 20 worker × 32 区间 = **640 > 256** ⇒ 高并发时至少 384 笔现分配、且空闲项会被 `Free` 回池（list 无法保温）。**建议把 D2 的每切片在飞上限设为 8**（20×8 = 160 < 256），让稳态全部 list 命中。

### 2.2 `Depth` 参数的真实语义：0 = 保留位，ntoskrnl 硬编码 4 / 256

```c
/* rbdev.c:161-166 */
VOID RbSyncCtxPoolInit(VOID)
{
    ExInitializeNPagedLookasideList(&g_Rb.SyncCtxLa, NULL, NULL, 0,
                                    sizeof(RB_SYNCCTX), RB_POOL_TAG, 0);
}
```
最后一个实参 `0` 就是 `Depth`。**它不影响任何东西**：

| 证据 | 内容 |
|---|---|
| WDK `wdm.h:26553-26561` 原型 | `_In_ USHORT Depth` |
| MS 文档原文 | "**Depth** [in] **Reserved. Must be zero.**" |
| ntoskrnl 实现（`ntoskrnl/ex/lookas.c` 公开源码） | `ExInitializeNPagedLookasideList` 内：`Lookaside->L.Depth = 4; Lookaside->L.MaximumDepth = 256;` —— **`Depth` 形参被完全忽略** |
| WDK 内联分配路径 `wdm.h:26689-26694` | `Entry = InterlockedPopEntrySList(&Lookaside->L.ListHead); if (Entry == NULL) { Lookaside->L.AllocateMisses += 1; Entry = (Lookaside->L.Allocate)(...) }` |
| 默认 `Allocate` 例程 | 传 `NULL` ⇒ ntoskrnl 填 `ExAllocatePoolWithTag`（`L.Type = NonPagedPool | Flags`） |
| 归还上限 `wdm.h:26730-26734` | `if (ExQueryDepthSList(&Lookaside->L.ListHead) >= Lookaside->L.Depth) { FreeMisses += 1; Free(Entry); } else { PushEntrySList(...) }` |

> 附带查清了 WDK 文档另一句常被引用的错误说法：「Depth 缺省为 4、最大 256」里那个 4 是 **ntoskrnl 赋的**，不是调用方传的。所以 `rbdev.c:163` 传 0 与传 4 传 32 **行为完全相同**——`Depth` 只是由系统按 `TotalAllocates/AllocateMisses` 统计周期动态上抬（上限 `MaximumDepth = 256`）。

**因此"`Lookaside.ListDepth` 是多少"的标准答案是：不可设，初始 4、可动态涨到 256。**

### 2.3 本机并发上限的实际数值

| 量 | 值 | 出处 |
|---|---|---|
| 逻辑 CPU | **20** | `Win32_ComputerSystem.NumberOfLogicalProcessors`（只读查询） |
| `RB_IO_WORKERS_MAX` | 32 | `rb_common.h:78` |
| `IoWorkerCount` = min(20, 32) | **20** | `rbio_worker.c:1049-1052`，发布于 `:1104` |
| 每切片 `mcnt` 上限 | `RB_MAX_RANGES` = **32** | `rb_common.h:60`；`rbio_worker.c:472` 以它传 `max_miss` |
| D2 后并发 `RB_SYNCCTX` 上界 | 20 × 32 = **640** | 每 worker 同时最多挂 32 笔 |
| lookaside `MaximumDepth` | **256** | ntoskrnl 硬编码（§2.2） |
| **超出 list 容量** | **≥ 384 笔必须现分配** | 640 − 256 |

`RbSyncIo` 对分配失败的处理是**直接失败**，不是退避：

```c
/* rbdev.c:197-198 */
    ctx = (RB_SYNCCTX *)RbSyncCtxAlloc();
    if (!ctx) return STATUS_INSUFFICIENT_RESOURCES;
```
```c
/* rbdev.c:208-210 */
    ctx->PoolBuf = ExAllocatePool2(POOL_FLAG_NON_PAGED, (SIZE_T)len, RB_POOL_TAG);
    if (!ctx->PoolBuf) { RbSyncCtxFree(ctx); return STATUS_INSUFFICIENT_RESOURCES; }
```

### 2.4 内存账（把上限压到 8 之后）

`sizeof(RB_SYNCCTX)` 按字段推算 ≈ **80 B**（`KEVENT` 24 + `IO_STATUS_BLOCK` 16 + `State` 4 + `Refs` 4 + `PoolBuf` 8 + `Len` 4 + `IsWrite` 1(+7 pad) + `CallerBuf` 8；**未编译核实，不作为判据**）。每笔同步读的**固定**成本是 `PoolBuf`（= `len`，这里 4096）+ IRP（`IoBuildSynchronousFsdRequest` 内部分配，量级 ~1 KB）：

| 在飞上限 | 并发笔数 | `PoolBuf` | ctx+IRP 估 | 合计峰值 |
|---|---|---|---|---|
| 32（不设限） | 640 | 2.50 MB | ~0.67 MB | **≈ 3.17 MB** |
| **8（建议）** | 160 | 0.62 MB | ~0.17 MB | **≈ 0.79 MB** |

两个上限都**不是问题量级**（本机 12 KB 栈、非分页池以 MB 计）；真正的差别在 §2.5。

> **关键澄清：`RbSyncIo` 的 `PoolBuf` 是每笔 I/O 一次 `ExAllocatePool2` + 一次 `ExFreePoolWithTag`（`rbdev.c:208` / `:264`），与 D2 无关、与并发无关。** D2 **不新增任何分配类型**，只把"同一 worker 内串行 5 次"变成"并行 5 次"。所以「32 路并发会不会打空 lookaside」的正确答案是：**会超出 `MaximumDepth`，但那是 list 命中率问题，不是失败问题**——失败只发生在非分页池真的紧张时，而那种时候现状的单笔 I/O 也一样会失败。

### 2.5 题面没问、但更该怕的：30 s 超时 × 32 的**串行放大**

这是我在核查中发现的**新风险，比 lookaside 深度重要一个数量级**：

```c
/* rbdev.c:229-248 */
    if (s == STATUS_PENDING) {
        to.QuadPart = -RB_SYNC_IO_STEP_100NS;     /* 5 s */
        budget = RB_SYNC_IO_DATA_BUDGET;          /* 6 */
        for (;;) {
            s = KeWaitForSingleObject(&ctx->evt, Executive, KernelMode, FALSE, &to);
            if (s == STATUS_SUCCESS) break;
            if (budget == RB_SYNC_IO_DATA_BUDGET) IoCancelIrp(irp);
            if (--budget == 0) { ...; return STATUS_IO_TIMEOUT; }
        }
    }
```

- `RB_SYNC_IO_STEP_100NS = 50,000,000LL`（`rb_common.h:49`）= 5 s，`RB_SYNC_IO_DATA_BUDGET = 6`（`:51`）⇒ **单笔最坏 30 s**。
- 现状：一片一次一笔 ⇒ 一片最坏 **30 s**。
- **D2 后：一片 ≤32 笔，若等待是串行的（D2 的设计就是"先全发，再逐个等"）⇒ 一片最坏 32 × 30 s = 960 s = 16 分钟**，期间该 worker（及其亲和 CPU 上的整个调度）被这一条 IRP 独占。

这不是理论：触发条件正是 0x7F 那次事故的同类条件——**盘不再响应**（`IoCancelIrp` 下层不响应取消）。而 `RbNoteIoResult` 的熔断是 `>=32` 次连续失败（`rb_common.h:90`、`rbio_worker.c:138-139`），需要 32 笔**都返回**才会计满 —— 也就是说最坏情况下要 16 分钟才攒够熔断所需的 32 次失败。

**必须写进 D2 规格的约束（I7，新增）：**

> **I7**：D2 的在飞上限必须是一个**显式常量**（建议 `RB2_MISS_INFLIGHT_MAX = 8`），且等待阶段必须用**单笔剩余预算**而不是每笔重开 30 s —— 即：一片的总排空墙钟上限 ≯ `RB_SYNC_IO_DATA_BUDGET × RB_SYNC_IO_STEP_100NS`（30 s），超出即对**剩余未完成的 IRP 全部 `IoCancelIrp` 并按 ORPHAN 语义放手**（`rbdev.c:177-185` 的 `Refs=2` 已经保证放手安全）。

压到 8 之后，一片最坏 8 × 30 s = 240 s = 4 分钟；配合 I7 的整片预算可压回 30 s 量级。**不做这条，D2 会把"盘挂死"从 30 s 恶化到 16 分钟**——这是比收益（**1.63× 下限，上界待 P1 实测**）严重得多的回归，必须红队单独过。

## 3. O3 — `RbDiagRecord` 配对

### 3.1 结论

> **不影响 D2，不需要任何判读逻辑改动。** 三条独立理由，任一条即可关掉此项：
> ① `s_DiagSeq` 是 `InterlockedIncrement64`，原子性没有问题；
> ② **本机 `TestMode = 0` ⇒ `RbDiagRecord` 在 `rbdriver.c:585` 直接 return，整个函数是 no-op**；
> ③ **仓内没有任何脚本/工具解析诊断环**（`src/scripts/*.py`、`tools/*` 全空命中），所谓"判读脚本误判"这件事**不存在**。
>
> 唯一真实的退化是：环只有 64 槽，D2 的记录量会让"enter/complete 相邻"这件事**必然不成立**——但那只是"环太小"，不是"配对被打乱"，而且**没有任何消费者**。

### 3.2 `s_DiagSeq` 的原子性

```c
/* rbdriver.c:576-602 */
static RB_DIAG_EVENT s_DiagRing[RB_DIAG_RING_COUNT];
static volatile LONGLONG s_DiagSeq;

VOID RbDiagRecord(ULONG Kind, ULONG Phase, NTSTATUS Status, ULONG Flags, ...)
{
    LONGLONG seq;
    if (!g_Rb.TestMode) return;       /* 仅隔离 TestMode 记录敏感地址 */   ← :585
    seq = InterlockedIncrement64(&s_DiagSeq);                              ← :586
    RB_DIAG_EVENT *e = &s_DiagRing[(ULONG64)(seq - 1) % RB_DIAG_RING_COUNT];
    e->Sequence = 0;                 /* 覆盖期间让读者跳过本槽 */
    ... 逐字段填 ...
    MemoryBarrier();
    e->Sequence = (ULONG64)seq;      /* 最后发布完整记录 */                 ← :601
}
```

- 序号：`InterlockedIncrement64` ⇒ **严格唯一、无重号**，并发安全 ✓
- 槽位：`(seq-1) % 64` ⇒ 不同 seq 不会争同一槽**的逻辑归属**，但会**覆盖**（§3.4）
- 发布协议：先 `Sequence = 0`（读者跳过）→ 填字段 → `MemoryBarrier()` → 最后写 `Sequence`（发布）✓ 与 `RbDiagSnapshot` 的 `:613-618`「读前/读后各读一次 `Sequence`，不等则跳过」严格配套 ✓

**原子性与发布协议都没有问题。** 配对问题的唯一来源是容量。

### 3.3 本机 `TestMode = 0` ⇒ 整个函数是 no-op

只读注册表查询结果：`HKLM\SYSTEM\CurrentControlSet\Services\RAMBlockCache\Parameters` → **`TestMode = 0`**（`rbdriver.c:1318` `g_Rb.TestMode = RbRegGetDW(L"TestMode", 0)` 读的就是这个值）。

⇒ `RbDiagRecord` 在本机**一条记录都不写**，`s_DiagSeq` 恒 0，`RbDiagSnapshot` 在 `:610` 因 `!g_Rb.TestMode` 直接 `return 0`。**所以「enter 全发 + complete 全收被打乱」在本机根本不发生。**

这也顺带说明：`RbSyncIo` 里那两行诊断（`rbdev.c:224-226` / `:254-256`）在**生产姿态下是零成本**的，D2 把调用次数 ×32 也不产生任何开销。

### 3.4 环容量 64 vs D2 的记录量：不是"打乱"，是"必然覆盖"

| 量 | 值 | 出处 |
|---|---|---|
| `RB_DIAG_RING_COUNT` | **64** | `rb_common.h:440` |
| `RB_DIAG_EXPORT_COUNT` | **16** | `rb_common.h:441` |
| 每笔同步读产生记录 | **2**（ENTER `:224` + COMPLETE `:254`） | `rbdev.c` |
| D2 后一片（`mcnt=5`，本机常态） | 5×2 = 10 | — |
| 20 worker 同时一片 | 10 × 20 = **200** | 20 逻辑 CPU |
| 环容量 / 一次爆发 | 64 / 200 ⇒ **≥3.1 次整环覆盖** | — |

⇒ 在 32 并发的极值下（640 笔 = 1280 条记录），**`XNOR` 意义上的配对彻底不可恢复**：某个 ENTER 必然在其 COMPLETE 落盘前被覆盖。**这不是"顺序变了"，是"信息丢了"。**

但见 §3.5——**没有任何消费者依赖它**。

### 3.5 消费者普查：仓内没有任何脚本解析诊断环

| 检索 | 结果 |
|---|---|
| `grep -rn "RB_DIAG\|DiagSeq\|diag_ring\|Sequence" src/scripts/*.py tools/*.py` | **0 命中** |
| `grep -rn "RB_DIAG_CRASH_BLOB\|2b91c607\|Events\[" tools/* deliverables/*.ps1` | **0 命中** |

> 第 5 条是 D2 落地时最容易走偏的工程选择，**它直接推翻我原先"改动面极小"的判断**。分两步说清：
>
> **第一步：`RB_SYNCCTX` 不可提出公共头。** 它定义在 `rbdev.c:135-149`（文件内 `typedef`），`rb_common.h` 里只有 `:308` 的 lookaside 字段与 `:46-48` 的状态常量。任何把它提到公共头的做法都要改 `rb_common.h`（公共 ABI 面）⇒ **否决**。
>
> **第二步：但 `RbSyncIo` 是同步原语，"先发 5 个再等"它做不到。** 它把「准备 → 下发 → 等 → 收尾」焊在一个函数里（`:197-228` 准备+下发，`:228-269` 等待+收尾）。所以"D2 只改 `rbio_worker.c`"**不成立**。两条路：
>
> - **路 A（推荐，= D1 的形态）**：在 `rbdev.c` 内把上述两段拆成 `RbSyncIoIssue` / `RbSyncIoWait` 对（纯加法，`RbSyncIo` 本体保留为二者的组合，**零语义变化**），`RB_SYNCCTX` 仍在 `rbdev.c` 内私有 ⇒ **公共头不动**。代价：动 L1 设备原语层，需要过 L1 契约审计（`rbdev.c` 头注释 `:4-13` 明写它的层契约）。
> - **路 B（明确反对）**：在 `rbio_worker.c` 里复制一份最小"发/收"实现 —— 等于把 `Refs=2` / ORPHAN / 短传归一**三套纪律再实现一遍**。本项目历史上 0x7E（late IRP 写已释放栈）与 0x9F（双重释放）正是这三套纪律缺失/写错的产物（`rbdev.c:121-134` 的注释就是逐条记录）。**重复实现 = 重新引入这两类 bug**。
>
> **⇒ 真实改动面是「`rbdev.c` 拆原语（纯加法）+ `rbio_worker.c` 换调用形态（一处循环 + 两个 static）」。这是对 P2 工作量估计的实质性上修，需要 team-lead 重新排期。**
