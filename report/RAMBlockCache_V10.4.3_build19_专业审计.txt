【执行摘要】
--------------------------------------------------------------------------------
本轮针对一次 0xA (IRQL_NOT_LESS_OR_EQUAL / ntoskrnl.exe) 随机蓝屏，定位到 PnP
Start/Remove 完成例程跑在 DISPATCH_LEVEL，却直接调用了要求 PASSIVE_LEVEL 的拆除/
探测函数。共修复 5 处（NEW-01~NEW-05），全部为 IRQL 契约与生命周期顺序问题：

  NEW-01  RbEnsureSystemVolumeInfo 的 PAGED_CODE() 被提前 return 绕过（第二次开机起）
  NEW-02  RbPnpRemoveComplete 在 DISPATCH_LEVEL 直接调 RbVolumeRemove（含 FastMutex）
  NEW-03  RbVolumeRemove 先毁流再等 worker 排空 → 在途 worker 解引用已释放 Stream = UAF
  NEW-04  DevCount-- 在节点未链入表时也执行 → 计数负漂移
  NEW-05  文件头 IRQL 契约注释更新（防后续回归）

结果：
  · 驱动编译 0 警告 0 错误；RAMBlockCache.sys = 93,408 字节；签名 verify 通过。
  · WPF 编译 0 警告 0 错误。
  · core 用户态引擎：Release 16/16 + ASan 16/16 编译全过；Release 运行 16/16 exit=0。
  · 系统侧当前处于安全回滚态（UpperFilters=volsnap、服务 demand-start），下次开机不会蓝屏。

【本版尚未在真机加载新驱动】：本机无法在不重启的情况下验证内核运行时行为。

第 2 章  驱动补丁逐字核对（P / D / R / E）
================================================================================

----------------------------------------------------------------------
[BUG-NEW-01]  PAGED_CODE 被提前 return 绕过 → DISPATCH 下取 FastMutex
----------------------------------------------------------------------
P (现象)：系统启动第二次起（SystemVolumeProbed=TRUE 分支），若 RbEnsureSystemVolumeInfo
         的调用方链落在 DISPATCH_LEVEL（PnP completion），则函数末尾 ExAcquireFastMutex
         在错误 IRQL 触发 0xA。首次开机探测时不复发，故极难稳定复现。
D (根因)：原代码顺序为
             if (g_Rb.SystemVolumeProbed) return;   // 提前 return
             PAGED_CODE();                          // 自检在 return 之后，缓存分支永不触发
         PAGED_CODE() 是 DEBUG 自检宏（KeGetCurrentIrql>PASSIVE 即断言），位置在 return
         之后等于对已探测分支完全失效。
R (修复)：把 PAGED_CODE() 提到任何 return 之前：
             PAGED_CODE();
             if (g_Rb.SystemVolumeProbed) return;
E (证据)：rbattach.c RbEnsureSystemVolumeInfo，已落地；驱动 Rebuild 0 警告。

----------------------------------------------------------------------
[BUG-NEW-02]  PnP Remove 完成例程在 DISPATCH_LEVEL 直接拆设备
----------------------------------------------------------------------
P (现象)：卷被拔出/禁用（PnP IRP_MN_REMOVE_DEVICE 完成）时随机 0xA / 0xC4。
D (根因)：RbPnpRemoveComplete 是 IoSetCompletionRoutine 回调，运行在 DISPATCH_LEVEL。
         它原本直接 RbVolumeRemove(ext)，而 RbVolumeRemove 内含：
             ExAcquireFastMutex（需 APC_LEVEL 及以下）
             KeDelayExecutionThread（PASSIVE）
             同步路径等待
         在 DISPATCH_LEVEL 上取 FastMutex = IRQL 违规。
R (修复)：改为"DISPATCH 只排队，PASSIVE 才拆除"：
           1) RbPnpRemoveComplete 内 IoAllocateWorkItem + IoQueueWorkItem(DelayedWorkQueue)
           2) 排队前 InterlockedIncrement(&ext->Refs) 保活，工作项末尾 RbDerefExt 释放
           3) RbRemoveWorkRoutine 在 PASSIVE 里调 RbVolumeRemove
           4) 给 RbVolumeRemove 加 PAGED_CODE()（置于函数首句、任何 return 之前）
           5) 分配失败兜底：仅当 KeGetCurrentIrql()<=APC_LEVEL 才就地拆除
E (证据)：rbattach.c RbPnpRemoveComplete / RbRemoveWorkRoutine / RbVolumeRemove。
         保活/释放范式与同文件 RbPnpStartComplete/RbGeoWorkRoutine 完全一致。
         注：交付文档示例漏了 IoFreeWorkItem，本实现按 RbGeoWorkRoutine 范式补齐，
             避免 work item 泄漏。

----------------------------------------------------------------------
[BUG-NEW-03]  拆除顺序颠倒：先毁流再等 worker → UAF
----------------------------------------------------------------------
P (现象)：拆除卷时随机 0xA / 0x50 / 链表损坏；在途 worker 仍在解引用 ext->Stream。
D (根因)：原顺序为
           (a) Removed=1; IsAttached=FALSE
           (b) rb_stream_destroy(ext->Stream)   // 先毁流
           (c) 再等 Refs 排空 60s
         问题：(b) 之后、(c) 之前，仍持 ext 引用的在途 worker 会解引用已被释放的
         ext->Stream = use-after-free。
R (修复)：调整为
           (a) Removed=1; IsAttached=FALSE（新 I/O 从此透传，不再引用 Stream）
           (b) 先等在途 worker 排空（Refs 回落 ≤1，宽限 60s）
           (b') 超时 → 僵尸队列，直接 return（不毁流，留僵尸收尾）
           (c) 排空完成后才 rb_stream_destroy(ext->Stream)
         即"先停新活、再等老活干完、最后销毁资源"。
E (证据)：rbattach.c RbVolumeRemove 第 2/3/3b 步；超时僵尸分支不毁流。

----------------------------------------------------------------------
[BUG-NEW-04]  DevCount 负漂移
----------------------------------------------------------------------
P (现象)：未链入全局表的 ext（如 AddDevice 早期失败路径）也走到 RemoveEntryList 之后的
         InterlockedDecrement(&g_Rb.DevCount)，计数被多减，长期负漂移。
D (根因)：原 Decrement 在 if(已链入) 判断之外。
R (修复)：把 InterlockedDecrement 移进 if(Flink!=NULL && Blink!=NULL) 块内，
         仅当确实从表中摘除时才减。
E (证据)：rbattach.c RbVolumeRemove "1) 从全局表摘除" 段。

----------------------------------------------------------------------
[BUG-NEW-05]  文件头 IRQL 契约注释
----------------------------------------------------------------------
R：rbattach.c 顶部"本文件所有例程均在 PASSIVE_LEVEL"改为明确契约：
   PnP Start/Remove 完成例程跑 DISPATCH_LEVEL，仅取指针+加引用+排队 workitem，
   一切阻塞/拆除落到 PASSIVE 工作项。防止后续维护者再次在 completion 里直接拆设备。
