## 1. 疑点 A：`dRead = 0` 但 copy 搬了 1,800 MB

### 1.1 先把「读请求」这个数是什么钉死（这是全节的关键）

**`ramboostctl status` 的「读请求」= `RB_STATS.ReadReq`**（`ramboostctl.c:96-97`）：

```
ramboostctl.c:96   printf("  读请求: %llu   读命中(次数): %.2f%%   读命中(字节): %.2f%%\n",
ramboostctl.c:97            (unsigned long long)s.ReadReq, readHitRate, readHitByteRate);
ramboostctl.c:79   double readHitRate = (s.ReadReq > 0) ? (100.0 * s.ReadHit / s.ReadReq) : 0.0;
```

来源链（逐跳可查）：

```
ramboostctl.c:73        rb_get_stats(&s)          → RB_MSG_GET_STATS（rb_proto.h:53，func=1）
rbctl.c:119             out->ReadReq = st.read_req;
cache_stats.c:26        out->read_req = (rb_u64)rq_;      ← rq_ = Σ_{sk_<64} stat_rd_req[sk_].v   (:21)
cache_internal.h:513    stat_rd_req[RB_NSTRIPES]            ← RB_NSTRIPES = 64，每槽 64B 独占（防伪共享）
```

**`stat_rd_req` 全仓只有两个写入点**（我 grep 过 `stat_rd_req|stat_rd_bytes|stat_rd_hit` 全部写入点）：

| 写入点 | 在哪个函数里 | 什么条件下才会走到 |
|---|---|---|
| `cache_read.c:24-26` | `rb_read()`（worker 路径） | 该请求**进了 `RbReadWorker` 且通过了 `RbFeatAdmit`**（`:452` `if (!ctx->Admitted)` 会提前 `goto done` 走 `RbReadDirectFallback`，**不计**） |
| `cache_read.c:157-161` | `rb_read_try_cache()`（dispatch 内联全命中快路径） | `IRQL ≤ APC` + `len ≤ 1 MiB` + `admitted` + `tgt` 可映射 + **全部命中**（`rbio.c:522-534`）；**任一 miss 就回退 worker，这两行不执行** |

⇒ **`ReadReq` 的定义是「进入缓存读逻辑（`rb_read` 或 `rb_read_try_cache` 命中）的读请求次数」，不是「过滤层看到的 `IRP_MJ_READ` 数」。**

**这个区别是决定性的。** 过滤层见到的 `IRP_MJ_READ` 可以完全不进缓存逻辑，至少有 7 条 early-return 在 `stat_rd_req++` 之前就把 IRP 送走了：

| 门 | 位置 | 结果 |
|---|---|---|
| 哨兵/熔断/几何/热开关 | `rbio.c:424-433` | → `RbDispatchPassthrough` ⇒ **不计** |
| 读方向关闭 | `rbio.c:435-439` | → passthrough ⇒ **不计** |
| `CachePagingIo=0 && IRP_PAGING_IO` | `rbio.c:450-453` | → passthrough ⇒ **不计** |
| view_mutating（改名/删除/截断窗口） | `rbio.c:458-461` | → passthrough ⇒ **不计** |
| `len==0` / `len > MaxCacheIoKB`（默认 64 MB） | `rbio.c:466-470` | → passthrough ⇒ **不计** |
| `RbFeatAdmit` 拒绝（进程排除） | `rbio.c:528` / `rbio_worker.c:452-456` | → `RbReadDirectFallback` ⇒ **不计** |
| 迟到 IO 重校验（重建窗/摘链/摘流） | `rbio_worker.c:435-446` | → `RbReadDirectFallback` ⇒ **不计** |

`RbReadDirectFallback`（`rbio_worker.c:205-212`）就是**裸的 `RbSyncIo`**，它一个统计字都不碰：

```c
rbio_worker.c:210    *ps = RbSyncIo(ext, FALSE, &moff, tgt, len, NULL);
rbio_worker.c:211    *pinfo = NT_SUCCESS(*ps) ? len : 0;
```

### 1.2 所以 `delta = 0` 有两个互斥解释，而**今天无法从用户态区分**

| 解释 | 物理机制 | 与观测一致？ |
|---|---|---|
| **H1（team-lead 的）**：Cc 命中 ⇒ **IRP_MJ_READ 根本没生成** | `Flush(true)` 只保证落盘、**不 evict** ⇒ A 的 900 MB 仍在 cache manager 的 active/standby 页 ⇒ `Copy-Item` 的 Source 读全由 `CcCopyRead` 满足，**不进卷栈** | ✅ 一致 |
| **H2（我的）**：IRP_MJ_READ 生成了，但**全部走了 passthrough / fallback** | 8 MB 块读 < `MaxCacheIoKB`（64 MB）⇒ 过尺寸门；但如果该进程被 `RbFeatAdmit` 排除，或正落在 view_mutating / 重建窗，就直读 | ✅ 一致 |

**为什么两个都成立**：`delta = 0` 只说明**「零个请求进了缓存读逻辑」**，它对「有没有 IRP」是**沉默**的。

**能不能区分？** 我查了三个可能的旁证，**三个都读不到**：

| 旁证 | 位置 | 为什么读不到 |
|---|---|---|
| 按原因的 bypass 计数 | `rb_common.h:155-164` `LastBypassReason` | **只有最后一次的原因，没有计数**；且注释明写「仅原子读写，**不进入 RB_MSG/V106**」⇒ 用户态**完全看不到** |
| `IoIssued / IoCompleted`（严格配对的 IO 计数） | `rb_common.h:394-396` `IoIssuedSlots[64]` / `IoIssuedG` | 全仓只在 `rbquiesce.c` / `rbrebuild.c` 内部消费；**`rb_proto.h` 里零字段**（我 grep 过）⇒ 不外露 |
| `RB_STATS.ReadBytes` | `rbctl.c:121` 有赋值，`rb_proto.h:158` 有字段 | **`ramboostctl status` 不打印它**（`ramboostctl.c:96-100` 只打 `ReadReq` + 两个百分比）⇒ 脚本日志里 `readBytes=MISSING` 就是这个原因，team-lead 的日志第 261 行已经如实记了 |

⇒ **这是本轮唯一一条「我有两个解释、且我证明不了哪个对」的诚实边界。** 按纪律：**记 MISSING/UNRESOLVED，不当 0，不冒充观测。**

### 1.3 我试过用 `copy` 的速率去区分 H1/H2 —— **失败了，这次尝试作废**

我一度想用这条推理分辨：`Copy-Item` 端到端 339.6 MB/s，若源读也下盘则盘要承担 1,800 MB 流量（用时 2.65 s ⇒ **总吞吐 679 MB/s**），若源读由 Cc 满足则只承担 900 MB（⇒ 341 MB/s）。**「679 MB/s 对 NVMe 并非不可能」⇒ 两种假设都能满足 339.6 MB/s。**

⇒ **这条路证不出 H1。我把它作废，不留半成品推理。**

**§1.2 的结论因此不松动：`delta=0` 的成因（H1 无 IRP / H2 有 IRP 但全走 passthrough）在用户态不可区分，记为 UNRESOLVED。**

**唯一能确定的正面事实**：`copy` 的 2.65 s 里，**目标写的 900 MB 一定过了盘**（VDL 断言 + `dWrite` 增量已证），而 §3.2 从同一份日志独立解出**写带宽下界 ≥ 340.7 MB/s**。这两个数在数值上接近（339.6 vs ≥340.7），**但它只是"不矛盾"，不是证据** —— 因为 340.7 的下界本身就是从这两组数解出来的，**循环**。这一点我必须说清，否则下一个人会把循环当印证。

### 1.4 裁决：**① 保留但明示 UNINFORMATIVE**

三个选项逐个判：

| 选项 | 判定 | 理由 |
|---|---|---|
| **① 保留 + 明示 UNINFORMATIVE** | ✅ **采纳** | 见下 |
| **② 加一个「冷却缓存」的前置步骤** | ❌ **否决** | 技术上无效 + 有系统级副作用。要 evict A 的 900 MB 页，只有 `SetSystemFileCacheSize`（需 `SeIncreaseQuotaPrivilege`）或清 standby list（`NtSetSystemInformation`/`MemoryEmptyWorkingSets`，需 `SeProfileSingleProcessPrivilege`）——**都要改这台机的全局内存行为，且会影响其它进程**。而 bench 早就有更好的做法：`FILE_FLAG_NO_BUFFERING`（`ctl_bench.c:326-330`）直接绕开 Cc。**用一个全局副作用的土办法去补一个本来就不该由它承担的检验，是错的。** |
| **③ 删除** | ❌ **否决** | 它抓到了一件真事：`dMisses=0` **且** `bm` delta=0（日志 `:280` / `:445`，`25,089,642,496 → 25,089,642,496`）⇒ 这是**互为零的两个计数器同时不动**，把「写路径不喂 miss 计数」从**断言**变成**观测**。删了就退回断言。 |

**改判据文字（这是要 team-lead 转达 QA 的那一句）**：

```
现状（脚本 log :452 / :454）：
    dMisses = 0  -> ZERO-AS-EXPECTED
    P0 state     : ZERO-AS-EXPECTED

应改为：
    dMisses = 0  -> WRITE-PATH-CLEAN（写路径确实不喂 miss 计数 —— 本控制的唯一目的，已达成）
                    READ-PATH-UNINFORMATIVE（读路径未被检验：0 个请求进入缓存读逻辑，
                    或全部走了 passthrough/fallback —— 两者今天不可区分）
    P0 state     : SPLIT（一半达成，一半不可判）
```

**为什么必须改**：现在的措辞 `ZERO-AS-EXPECTED` 会让下一个人读成「**读路径被检验过了，结果是干净的**」。而真相是「**读路径一个样本都没进来**」。这两种读法的差别在 D-01 落地后是**致命的**：D-01 的 P3 要用 `dMisses` 当判据，如果团队继承了「`dMisses=0` 是好消息」这个直觉，那么 D2 落地后看到 `dMisses` 不涨会误判成「D2 生效」。

### 1.5 写路径有没有任何路径能喂到 `RbFeatOnMiss`？ —— **没有，闭合**

这是 team-lead 点名要的，我给完整证明而不是结论：

```
RbFeatOnMiss 全仓 2 个调用点（grep 复核，只有 .c 里的这两处）
  rbio_worker.c:256   ← ① 快路径（:253  mr->len > 1 MiB && ms>=rs && me<=re）
  rbio_worker.c:289   ← ② staging 路径
        两个都在 RbReadMissRange(ext, w, mr, ...) 的函数体内（:230 起）

  rbio_worker.c:230   定义
  rbio_worker.c:484   唯一调用（在 RbReadWorker 的 miss 循环里）

  rbio_worker.c:404   定义
```

| 候选 | 位置 | 为什么不是 |

## 2. 疑点 B：`+1.5%` 是不是元数据

### 2.1 先看你给的那 1.5% —— 它在两轮里**异号**

日志 `:309` / `:363` / `:472-473`：

| 轮 | `dWrite` | 期望 | 偏差 | **相对偏差** | 方向 |
|---|---|---|---|---|---|
| R1 | 1,863.68 MB | 1,800.00 MB | **+63.68 MB** | **+3.538%** | **正** |
| R2 | 1,792.00 MB | 1,800.00 MB | **−8.00 MB** | **−0.444%** | **负** |
| 合计 | 3,655.68 MB | 3,600.00 MB | +55.68 MB | +1.547% | 正（净） |

**「元数据」这个词不足以解释这张表，因为元数据永远是正的：** 每一轮都会新增 `$MFT` 记录、`$LogFile` 条目、目录项 —— 它们**只会让 `dWrite` 变大**，**不可能让 R2 少 8 MB**。

⇒ **R2 的负数是一个独立信号，它证明「至少有一项不是元数据」。**

### 2.2 你列的四项，我逐条判（有两项你问对了，一项不成立，一项我主动排除）

| 你的项 | 判定 | 依据 |
|---|---|---|
| **① NTFS `$LogFile` / `$MFT` 穿过过滤层并被计入 `IRP_MJ_WRITE`** | ✅ **成立，但量级远小于 1.5%** | 它们确实是 `IRP_MJ_WRITE` 到卷上、确实穿过我们的过滤层、确实进 `write_bytes`。但量级：900 MB 按 8 MB 块写 = **113 次扩展**，每次 `$LogFile` 记几百字节；单个 900 MB 文件只有 **1 条 `$MFT` 记录**（+ 属性列表）。**一个 1.8 GB 的文件集（4 个文件）元数据总量在 1 MB 量级，即 0.03%** —— 与 1.5% 差 **50 倍**。⇒ **成立但不是主因** |
| **② VDL / `SetEndOfFile` / `SetAllocationInfo` 走 WRITE 还是 SET_INFORMATION** | ✅ **你的问法对，答案是 SET_INFORMATION ⇒ 不计入** | `IRP_MJ_SET_INFORMATION` 有**独立分派**：`rbdriver.c:1271 drv->MajorFunction[IRP_MJ_SET_INFORMATION] = RbDispatchSetInformation;`。而 `write_bytes` 全仓**只有 3 个累加点**：`cache_write.c:351-352`（`rb_write_ex`）、`cache.c:601-602`（`rb_engine_note_direct_write`）、`rbio_worker.c:886`（直写记账调上一行）。**三处都在 READ/WRITE 路径上，`RbDispatchSetInformation` 一个都不碰。** ⇒ **不重复计，不计入** |
| **③ `Flush(true)` 本身是否会再产生一次写** | ✅ **成立：不会** | `Flush(true)` = `FlushFileBuffers` = `IRP_MJ_FLUSH_BUFFERS` ⇒ 进 `RbDispatchFlush`（`rbio.c:580`），它只 `RbSubmitIo` 转 worker 做 `rb_stream_flush` + `RbForward`，**不碰 `write_bytes`** |
| **④ 过滤层对同一笔写重复计数（split 后子 IRP 各计一次）** | ❌ **不成立，我主动排除** | 见 §2.3 |

### 2.3 为什么「重复计数」这条我要主动排掉（含两处可能被误解的地方）

**误解 1：写 worker 会按 8 MB 块切分（`rbio_worker.c:687` `cend = ... + (8UL << 20)`），是不是每块计一次？**

不是。`write_bytes` 的增量是**原始 IRP 的逻辑长度 `len`**，不是块长 `clen`：

```c
/* 回写模式（WriteBack=1）：rb_write_ex 一次吃掉整段 len，计一次 */
cache_write.c:351    RB_AADD64(&eng->stats.write_req,1);
cache_write.c:352    RB_AADD64(&eng->stats.write_bytes,len);      ← len，不是 clen

/* 直写模式：整个 IRP 一笔 */
rbio_worker.c:884    s = RbSyncIo(ext, TRUE, &o, tgt, len, NULL);
rbio_worker.c:886    rb_engine_note_direct_write(g_Rb.Engine, len);  ← len
```

`rb_engine_note_direct_write`（`cache.c:598-603`）内部也是 `+= len`。**8 MB 切块循环里一次都没调它。**

**误解 2：回写模式下「`rb_write_ex` 吸收 + 后续直写 direct 区间」会不会同一笔既 `+= len` 又 `+= Σ(direct 区间)`（双计）？**

不会，两条记账是**互斥**的：

```c
/* 内联快路径（rbio.c:489-517）：吸收成功且 dcnt==0 → 就地完成，不进 worker */
```

### 2.4 那 55.68 MB 到底是什么？ —— 量化 + 背景写，不是元数据

**（a）量化下限：单轮 ±10.24 MB，而且这是不可消除的**

`ramboostctl.c:97-100` 打的是 `%.2f GB`（`bytes/1024^3`），一步 = `0.01 GB = 10.24 MB`；两次读各舍入 ±5.12 MB ⇒ 差值最坏 **±10.24 MB**。脚本自己算过这一笔（`RB-write-load.ps1:1116-1136`，结论「0.57% of a round」）。

```
单轮 1800 MB：10.24 / 1800 = 0.569%
全局 3600 MB：10.24 / 3600 = 0.284%
```

⇒ **R2 的 −8.00 MB 完全落在 ±10.24 MB 的量化箱内。它根本不需要任何物理解释。** 这也解释了为什么它是唯一的负数。

**（b）量化之后还剩什么：采样窗口里的背景写（`N`）**

`dWrite` 是**两次独立 `ramboostctl status` 的差**。日志 `:256`（pre，15:18:53）→ `:395`（post，15:19:09）= **16 秒窗口**。这 16 秒里这台机上的**任何**其它写（Defender 扫描日志、`$LogFile` 自身轮转、事件日志、Shell 遥测、索引器）都会进入 `write_bytes`，**无法扣除**。

**关键：不要对两轮取平均 —— `N` 在两轮里根本不是同一个数。** 逐轮拆开（`N ≥ 0` 恒成立，量化 `q ∈ [−10.24, +10.24] MB`）：

```
R1：+63.68 = N₁ + q₁   ⇒  53.44 ≤ N₁ ≤ 73.92 MB
R2： −8.00 = N₂ + q₂   ⇒   0.00 ≤ N₂ ≤  2.24 MB      ← 因为 q₂ 最低只能到 −10.24
```

⇒ **R1 的背景写是 53–74 MB，R2 的背景写是 0–2 MB。差 30 倍以上。**

**这个不对称本身就是一条结论**：段（b）不能用一个"平均背景写率"去建模，因为**背景写是突发的**（16 秒窗口里有没有赶上一个扫描/日志轮转，是随机的）。所以：

| 用法 | 是否可行 |
|---|---|
| 用「平均 N ≈ 1.5%」去**校正** `dWrite` | ❌ **不行** —— 单次不可预测，校正会把 R2 推成负数 |
| 用「最坏 N ≤ 73.9 MB = 4.1% of 1800」去**定上界** | ✅ **可行** —— 这是观测到的最大单侧值，只能当上界用 |

⇒ **`N` 的量级（最坏 4.1%）比元数据（0.03%）大两个数量级**，而它的**分布不可建模**。这一点直接决定了 §2.5 的上界只能宽、不能紧。

**（c）所以 `+1.5%` 的完整分解（按可解释性排序）**

| 项 | 量级 | 可扣？ |
|---|---|---|
| 量化（两次 `%.2f GB` 读数） | ±0.284%（全局）/ ±0.569%（单轮） | ❌ 结构性，只能靠**加大 SizeMB** 稀释 |

⇒ **你的 1.5% 是「量化 + 背景写」的巧合和，不是「元数据」。** 元数据贡献不到它的 2%。而**背景写的量级（0–4.1%）比 1.5% 本身还大** —— 这说明 **1.5% 这个数字本身没有诊断价值**：它落在 `N` 的分布内部，换个 16 秒窗口就可能是 −1% 或 +4%。

## 3. 疑点 C：`289.7 / 282.9 MB/s` 该不该被引用为「本机写带宽」

### 3.1 这两个数是什么 —— 一个复合量的代数

脚本的写法（`RB-write-load.ps1:368-392`）：

```
chunkMB = 8                                  # :369  每次 fs.Write 8 MB
if (($written % (16MB)) -lt $chunk.Length)   # :383  每 16 MB 一次 Flush($true)
```

⇒ **900 MB / 16 MB = 56.25 次 `FlushFileBuffers`**。`Flush($true)` 是**同步**的：它把该文件的脏页 + NTFS 日志推到盘，**调用线程阻塞等待完成**。

所以实测速率不是盘的带宽，而是：

```
Rate_measured = 900 MB / ( 900 / BW_disk  +  N_flush × RTT_flush )
                 900 = 有效载荷
                 BW_disk   = 盘在该写模式下的有效带宽（未知量）
                 N_flush   = 56.25
                 RTT_flush = 每次 FlushFileBuffers 的往返时间（未知量）
```

**两个未知量、一个方程 ⇒ 单靠这 3.11 s 解不出来。** 这就是为什么它不能当带宽。

### 3.2 用两轮的对比解出**界**（不是点估计 —— 这里只有 2 个方程、3 个未知量）

先把方程写全，**别偷项**。copy 那一轮除了写，还有一次源读，所以它有三个未知量：

```
设  T0      = 900 / BW        （纯写时间）
    T_read  = 源读耗时（只有 copy 轮有）
    RTT     = 每次 FlushFileBuffers 的同步等待

copy（R1，只 1 次 flush） :  T0 + T_read + 1.00  × RTT = 2.65
直写（R1，56.25 次 flush）:  T0          + 56.25 × RTT = 3.11
```

**两个方程、三个未知量 ⇒ 解不出点估计。但能解出界，而这恰好是我需要的**（我要证的是「286 不是带宽」+「带宽至少多少」）：

```
由直写式：RTT = (3.11 − T0) / 56.25
代入 copy 式并消去 RTT：
    56.25·T0 = 56.25·(2.65 − T_read) − (3.11 − T0)
    ⇒ 55.25·T0 = 145.945 − 56.25·T_read
    ⇒ T0 = 2.641 − 1.018 · T_read
```

| 量 | 结论 | 为什么是**界**而不是点 |
|---|---|---|
| **写带宽 `BW`** | **≥ 340.7 MB/s**（R1）/ **≥ 350.3 MB/s**（R2）| `T_read ≥ 0` ⇒ `T0 ≤ 2.641` ⇒ `BW = 900/T0 ≥ 340.7`。**源读越慢 ⇒ 真带宽越高**，所以这个下界**与「源读多快」无关**，是硬的 |
| **单次 flush 分摊 `RTT`** | **≥ 8.33 ms**（R1）/ **≥ 10.86 ms**（R2） | `RTT = (3.11 − T0)/56.25`，`T0` 取**上界** ⇒ `RTT` 取**下界**。⇒ 每次 `FlushFileBuffers` 至少摊 8.33 ms |

⚠️ **上一版我把 `RTT` 写成了「≤ 8.33 ms（上界）」—— 符号反了，已改。** 从 `T0 ≤ 2.641` 只能推出 `RTT ≥ 8.33`：`T_read` 越大 ⇒ `T0` 越小 ⇒ `RTT` **越大**。**`RTT` 的上界不可得**（需要先知道 `T_read` 的上界，而那正是 §1.2 分不开的那个量）。这也说明为什么这一节只能给**单侧界**。

**敏感性检验（目的是证明结论不依赖 §1.2 里那个分不开的 H1/H2）**：

| 假设 `T_read`（copy 的源读耗时） | `T0` | `BW` | `RTT` |
|---|---|---|---|
| **0 s**（极端 H1：全由 Cc 满足） | 2.641 s | **≥ 340.7 MB/s** | **≥ 8.33 ms** |
| **0.132 s**（copy 的 5%） | 2.507 s | ≥ 359.0 MB/s | ≥ 10.72 ms |
| **0.265 s**（copy 的 10%） | 2.372 s | ≥ 379.5 MB/s | ≥ 13.12 ms |

⇒ **无论源读多快，`BW ≥ 340.7` 与 `RTT ≥ 8.33 ms` 都成立。** 结论对那个分不开的问题**不敏感** —— 这是我能给出这个界、却给不出点估计的根本原因。

### 3.3 所以 286.3 MB/s 是什么

**它是「8 MB 块 + 每 16 MB 一次 `FlushFileBuffers`」这个特定写形态的端到端吞吐**（`RB-write-load.ps1:369/:383`）。可以引用，但**必须连粒度一起引用**：

> ✅ 可引用：「本机 D: 卷在 **8 MB 块 / 16 MB flush 粒度**下的端到端直写吞吐 = **286.3 MB/s**（R1 289.7 / R2 282.9）」

> ✅ 可引用：「每 16 MB 一次 `FlushFileBuffers` 至少摊 **≥ 8.33 ms**」（单向界）
> ❌ 不可引用：「本机写带宽 = 286 MB/s」（错：它含 56 次同步 flush 等待）
> ❌ 不可引用：「本机写带宽下界 = 286 MB/s」（**方向反了**：flush 只会让它变慢，286 是**带 flush 的吞吐**，真带宽比它高 ≥ 54 MB/s）

**反证检查（这条让结论更硬）**：如果 flush 不是主因，那么「56 次 flush 的直写」与「1 次 flush 的 copy」速率应当接近 —— 实测差 **R1 14.7% / R2 18.9%（均值 16.9%）**（`289.7 vs 339.6`、`282.9 vs 348.8`）。**这个差值无法由盘带宽解释（同一块盘、同一个过滤层），只能由那多出来的 55 次同步等待解释。**

### 4.3 `passes−1` 陷阱 —— ✅ **已落盘，并补上「为什么不能拆两次跑」**

`D-01-D2-buffer-form...` §5.6 末段已写「必须按 `passes − 1` 除」。**这里补上 team-lead 点名的那一条，因为它的理由比"要除"更根本**：

```
为什么不能「拆成两次 -passes 1」分别测首遍和热读：
  ctl_bench.c:384-393   每次进程启动，只要驱动在线，都先跑 CliFlushFileRange(...)
                        ⇒ 第二次启动会把第一次建立的热缓存**刷掉**
  ctl_bench.c:409       for (i = 1; i < passes; i++)     ← passes=1 时循环体一次都不执行
  ctl_bench.c:408/:420  s0/s1 仍各采一次，但 ReadBytes delta = 0
  bench_policy.c:21-25  if (readBytesDelta == 0) return -1.0;
                        ⇒ secondHitRate = -1.0000（不是 0，是"不可测"）
```

⇒ **`-passes 1` 既拿不到热读，又必然把上一次的热缓存刷掉 ⇒ 「拆两次」在物理上不可行。唯一正确的形态是 `-passes N` 一次跑完，`k` 按 `passes−1` 除。**

**并且这条与 §4.2 的量级闸有一个联动**：`passes` 越大，首遍占 `dBytesMiss` 的比例越低（86.5% → 90.9% → 93.8%），因为热读分母变大了。所以 **`-passes 3` 不只是"降放大"，它同时让闸 0 的上界更宽松**（`dMisses_outer` 的期望从 `S(1+k)` 变成 `S(1+2k)`，闸 0 必须随之改成 `S < d < 2·S·(1+2k)`）。**QA 改 `passes` 必须同步改闸 0 的上界，否则会把正常跑判成 INVALID。** ← 这条我之前没写，本轮补上。

### 4.4 §3.4b 内存账 136.0 KiB/worker + 「8 笔 ≠ 8 块」—— ✅ **已落盘（并做了第三次修正）**

`D-01-miss-coalescing-verdict...` §3.4b / §3.4c / §10 修订 11 + `D-01-I7c...` §6.4：

## 6. 一句话给 team-lead

**A：你的方向对，但问的量错了 —— `ReadReq` 不是 IRP 计数，它是「进入缓存读逻辑」的计数（全仓只有 `cache_read.c:25` / `:158` 两处写）。所以 `delta=0` 只能说「零个请求进了缓存读逻辑」，它对「有没有 IRP」是沉默的。`Cc 命中` 和「全部走 passthrough/fallback」两个解释今天分不开 —— 因为没有按原因的 bypass 计数（`rb_common.h:155` 只有"最近一次"且不外露）。判据必须从 `ZERO-AS-EXPECTED` 改成 `WRITE-PATH-CLEAN / READ-PATH-UNINFORMATIVE`，否则下一个人会读成「读路径被检验过了」。**

**B：你那 1.5% 不是元数据。R1 +3.54% / R2 −0.44% 异号，元数据永远不可能异号。你列的七项里，元数据成立但量级只有 0.03%（差 50 倍）、SET_INFORMATION 和 FLUSH 确实不计入、而「重复计数」我主动排掉了（回写/直写/内联三条记账互斥且完备，一笔恰恰一次）。真正的主因是量化（0.284% 全局）+ 16 s 采样窗口里的系统背景写（1–4%）。上界：单轮留 1.15，全局收到 1.04 —— 1.15 在全局上等于给「任何模型都不解释的 13.7%」发通行证，那正是脚本 `:1195` 自己记下的那次 2.03 被放过的同一个坑。**

**C：286.3 MB/s 不能当写带宽引用，它是 `900/(900/BW + 56×RTT)` 的复合量。同一份日志里有第二个条件（copy 只做 1 次 flush），两组联立只能得到单侧界：写带宽 ≥ 341 MB/s、每 16 MB 一次 flush 至少摊 ≥ 8.33 ms —— 上界都不可得，因为 copy 那一轮的源读耗时本身分不开（就是 A 那条的 H1/H2）。所以：可引用「8 MB 块 + 16 MB flush 粒度下 286.3 MB/s」，可引用「写带宽下界 ≥ 341 MB/s」，不可引用「写带宽 286」。另外，「286 落在 145.8 和 580 中间」这个比较请撤掉 —— 那两个都是读（`firstMbps` 是 `ReadFile`，580 是读带宽盈亏平衡反解），和写不在一条数轴上。**

**还有一处我必须自我更正，因为它是我上一版写错的符号**：我一开始把 flush 分摊写成了「≤ 8.33 ms（上界）」，那是反的 —— `T_read` 越大 ⇒ `T0` 越小 ⇒ `RTT` 越大，所以只能得**下界**。这条我留了原文对照，因为「界的方向搞反」正是这一整轮反复出现的错误形态（门2 的双侧、286 当带宽、286 当下界，都是同一类）。

**四处欠账全部落盘（§4），并且我顺手补了三条你没提但会咬人的**：`k_bytes` 有恒等式 `32(1−h)`（所以它是常数不是观测量，这直接解释了为什么双侧必然炸）；`4.0` 的临界 h 是 **0.875**（不是我上次说的 0.86）；`passes` 一改，闸 0 的上界也必须跟着改（否则正常跑会被判 INVALID）。
