## 6. SUP-01 判读：`NO_EVIDENCE` 的成因分解

重启前 `Parameters\` 四键 **全 absent**；重启后（`RbBootFailLoad` 抄 Prev + 复位本体）为：

| 键 | 值 | 含义 |
|---|---|---|
| `ShutdownPersistWhy` | `0xFF` | 本次引导的占位值（boot-reset，**不是证据**） |
| `ShutdownPersistWhyPrev` | `0xFF` | 上次关机也没写 ⇒ 无证据 |
| `PersistSkipReason` | `0xFFFFFFFF` | boot-reset（同） |
| `PersistSkipReasonPrev` | `0xFFFFFFFF` | 无证据 |
| `LastCleanShutdown` / `LastCleanWithheld` | `0` / `0` | 每引导被清（`rbdriver.c:346` / `:381`），只作参考 |
| `DiagShutdownSeq` | `3` | 累计分派序 |

判读器结论：`PERSIST CODE: NO_EVIDENCE`，`PERSIST VERDICT: NOT_REACHED (rc=3)`。

**但「派发」这一环已被这轮数据加固**（比 `263` 更硬）：哨兵 144 B/6 条 → **240 B/10 条**，新增 4 条全部落在
`utc=2026-11-17T14:52:19Z`（= 本地 22:52 那次关机）：

```
total=3  irql=0 isControl=1    ← 控制设备
total=1  irql=0 isControl=0    ← 卷设备 ×3
```

`irql=0` ⇒ `IRP_MJ_SHUTDOWN` 在 **PASSIVE_LEVEL** 到达每个设备对象，且**关机瞬间 `Zw*File` 可用**（4 条都落盘了）。
控制设备的 `total` 序列 1→2→3 与 `DiagShutdownSeq=3` 精确对齐 ⇒ 每次关机在控制设备上恰好分派一次。
上一版记录里「`total` 是本次关机第几次分派」的解释由此闭环（`268` B7 提过 `total` 非原子，这里三值单调无回退）。

⇒ **症结与 A4-d 无关**：A4-d 处在 `RbDispatchPower` 之后（`rbmsg.c` 持久化函数体内），而该函数体这一轮**从未进入**
（否则 `Why` 至少会被写成 `CLEAN/DIRTY/…` 之一，A4-d 的 withheld 分支也会写 `LastCleanWithheld=1`）。
A4-d 的价值是「一旦进入，不再谎报 `CLEAN`」；它**不负责让代码进入**。

**新登记 N-09（判读器口径错配）**：`read_shutdown_sentinel.py` 打印
`DISPATCH VERDICT (legacy rc=4): INCONSISTENT: reg=3, records=10, raw=240 B`。
这是把「reg = 本次关机控制设备分派序」和「records = 全历史全设备累计条数」当同一量纲比较；
正确口径应是 `reg == 最后一条 isControl=1 记录的 total`（本轮 3 == 3，一致）。
`rc` 未受影响（仍由 PAIR 判据决定 = 3），但这段文案会误导人以为「派发不可信」。**未改**（R7：先记录，改须单独决策）。

3. **不得称「SUP-01 判据已修好」**。判读器改的是「怎么读成对读数」，不是「为什么没有读数」。
4. `rc=0`（若将来出现）仍非「本次关机干净」的充分证据 —— 受 `275` 的 **R-b2**（Prev 两次写都可能失败 ⇒ 旧对自洽）与 **R-d**（成对读数无 epoch）限制。
5. `verdict()` 未能逐字节证明未改（无 git、无改前副本），只证契约与分支形状。
