# 10 竞品对比与独立优化（PrimoCache × 显存可行性 × 本机调优）

> 本文为「甲方评审」交付的一部分：回答三个问题——
> ① RAMBoostFS 与 PrimoCache 到底差在哪、为什么；② 用 RTX 4070 显存做缓存层
> 是否更快；③ 针对 i7-12700H + 64G + 4070 的独立优化怎么做（且换电脑仍可用）。

## 一、PrimoCache 深度对比（事实来源：Romex Software 官方规格页与官方延时写入文档）

### 1.1 架构层（最本质的差异）

| 维度 | PrimoCache | RAMBoostFS | 为什么不一样 |
|---|---|---|---|
| 工作层级 | **卷级扇区过滤驱动**（位于文件系统与缓存管理器之下，直接处理磁盘扇区） | **WDM 卷块上层过滤驱动**（V9-V10 迁移完成：运行时定向挂载、无类级 UpperFilters，位于文件系统与 Cc 之下，按"卷+块"粒度） | PrimoCache 看不见文件语义，但**所有 IO 都会经过它**（含系统缓存的分页 IO、页面文件、任意文件系统）。RAMBoostFS 已迁至同层位置，I/O 分类经准入门（进程镜像名单 + panic 门）统一进缓存通路、不按 I/O 类型区分；旧版（minifilter 时代）主动放行分页 IO 导致普通应用命中率 0 的问题结构性理由已消失，但覆盖证据待验证冻结（见 `deliverables/block-coverage-matrix-2026-10-15.md`） |
| 分页 IO | 缓存（含系统卷） | 架构已纳入统一缓存通路（准入门不按 I/O 类型区分）；**已加速待验证**（架构就位，证据待采）；系统卷默认排除（安全取向差异） | 旧版（minifilter 时代）怕"双重缓存"而放行分页 IO → 普通应用命中率 0；V9-V10 迁移到卷块层后该结构性理由已消失（Cc 之下单一视图，不产生双写者），但"结构上应该安全"≠"验证过安全"——证据链见覆盖矩阵报告。PrimoCache 接受双重缓存（系统缓存 + 卷缓存），这也是它命中率高的根本 |
| 缓存粒度 | 卷内扇区块（默认 4KB~64KB 可配） | 64KB 块 + 4KB 子块位图 | RAMBoostFS 子块位图做部分命中更省内存；PrimoCache 块小、命中粒度细 |
| 多级缓存 | **L1（内存）+ L2（SSD/闪存盘）双级** | 仅内存一级 | PrimoCache 的 L2 是持久缓存：重启后热数据仍在，开机即热。RAMBoostFS 重启缓存清空 |
| 缓存策略 | 读写/仅读/仅写，每卷独立 | 读/写独立开关，每卷可选 | 基本对齐 |

### 1.2 功能层

| 功能 | PrimoCache | RAMBoostFS | 差异原因 / 完善方向 |
|---|---|---|---|
| 延迟写入（write-back） | ✅ 官方称可大幅提升写性能并减少 SSD 磨损（同一地址多次写合并为一次） | ✅ 回写 + 脏段合并回写 | 语义一致。RAMBoostFS 回写按周期/水位/句柄关闭触发 |
| 直写模式 | ✅ | ✅ | 一致 |
| TRIM | ✅ | ❌ 无主动语义（透传天然具备，与卷级驱动同位置） | 卷级驱动天然透传 TRIM；"截断/删除丢弃缓存"的主动语义需额外实现，已列入路线图（P1-02）——旧稿"minifilter 需主动透传 IRP_MJ_... TRIM/Delete 语义"的推论随架构迁移作废 |
| 永久 L2 缓存 | ✅ | 代码已落地（2026-10-15 M1 淘汰接线：容器文件 + 逐记录 CRC + 单卷硬约束，默认 OFF，**待 WDK 真机验证后开放**） | PrimoCache 的 L2 经 15 年实机验证；本品 L2 尚未经真机验收——验证前不开放、不宣传 |
| 预取 | ✅ | 代码已落地（2026-10-15：倒流跟踪顺序预取 + 每卷窗口 + 温度护栏，默认 OFF，**待真机验证后开放**） | PrimoCache 支持启动预取 / 空闲预取 / L2→L1 预取。本品 M1 为运行中顺序读预取，启动预取列 M2 |
| 未识别内存（32 位系统） | ✅ | ❌（仅 64 位） | 无关紧要（现代系统均为 64 位） |
| 断电数据保护 | 官方明确：延时写入在断电/崩溃时会丢数据，建议配 UPS | 安全模式 + 关机全量回写 + LostDirty 统计 | 两者风险本质相同（回写缓存的固有权衡） |
| 命令行 | ✅ | ✅（ramboostctl） | 一致 |
| 价格 | 标准版授权（个人单机约 $29.95，增强/专业版更高） | 免费开源 | — |

### 1.3 性能机制对比

- **命中路径**：PrimoCache 命中 = 内存直接返回（卷缓存）；RAMBoostFS 命中 =
  核心内存拷贝 + 锁外拷贝自完成（卷块层 pending + PASSIVE worker 模式，DISPATCH 级不取缓存锁）。两者命中延迟
  都在微秒级；旧稿"minifilter pre-op 自完成"表述随 V9-V10 卷块层迁移作废。实际差异主要来自 IO 是否进入各自的缓存（见架构层——位置差距已消除，差距移入"证据/验证"维度）。
- **写放大**：PrimoCache 延迟写入把同一地址多次写合并；RAMBoostFS 同样按
  4KB 子块去重 + 64KB 块内合并 + 相邻块边界合并（V5.1 修复后单次回写
  最大 4MB 配置、典型 ≥128KB），都能显著降低 SSD 写放大。
- **多核**：PrimoCache 对多物理盘/多分区并行；RAMBoostFS 64 分片条纹锁，
  同一文件不同区域多核并行（已测：12 线程压力无竞态）。

### 1.4 结论：为什么不一样、怎么完善

1. **命中率差异根因（历史）不是"算法"，是"位置"**：PrimoCache 在卷层，天然看见
   所有 IO；RAMBoostFS 旧版在文件层（minifilter），自己放行了分页 IO → 普通场景命中率 0。
   **V9-V10 已迁移到 WDM 卷块上层过滤层，位置差距结构性消除**；当前口径为"架构就位、证据待采"——
   命中率声明须以覆盖矩阵验证冻结为准（对外声明永远滞后于证据）。V5.1 的 `CachePagingIo`
   为 minifilter 时代缓解措施，已被卷块层统一通路取代。
2. **持久性差异**：PrimoCache 有 L2 永久缓存，重启即热；RAMBoostFS 的 L2 M1 接线
   已于 2026-10-15 代码落地（容器文件 + 逐记录 CRC + 单卷硬约束，默认 OFF），但
   **未经 WDK 真机验证前不开放**——验证计划见《覆盖矩阵验证报告》与路线图 Gate。
   （核心已抽象 writeback/readback 回调，后端天然可插拔。）
3. **TRIM/删除语义**：卷级驱动透传 TRIM（RAMBlockCache 迁至卷块层后同此位置，透传天然具备）；
   "截断/删除丢弃缓存"的主动语义为独立路线图项（P1-02）——旧稿"作为 minifilter 拦截
   `IRP_MJ_SET_INFORMATION`"的路径随架构迁移作废，以减少无效回写为目标不变。
4. **预取**：增加顺序读检测 + readahead（对影视/大文件/数据库扫描有效）。
5. **稳定性验证**：PrimoCache 有 15+ 年历史与大量实机验证；RAMBoostFS 的核心
   层已通过全量测试，但驱动层仍待按 `11-实机验证清单.md` 实机验收。

## 二、RTX 4070 显存加速可行性分析

### 2.1 你的配置（i7-12700H / 64G 内存 / RTX 4070 笔记本 / 2T+1T SSD）

| 通道 | 理论带宽 | 有效带宽（估） | 备注 |
|---|---|---|---|
| 双通道 DDR5-4800（64G，2×32G） | 76.8 GB/s | ~55–65 GB/s | 12700H 笔记本平台 |
| （若为 DDR4-3200） | 51.2 GB/s | ~40–48 GB/s | 部分 12700H 机型为 DDR4 |
| RTX 4070 笔记本 8GB GDDR6（128-bit） | ~256 GB/s | ~230–250 GB/s | 显存带宽确实远高于内存 |
| RTX 4070 桌面 12GB GDDR6X（192-bit） | ~504 GB/s | — | 若你其实是台式机 |
| PCIe 4.0 x8（笔记本独显常见） | 16 GB/s（单向） | ~13–14 GB/s | **瓶颈在这里** |
| PCIe 4.0 x16（台式机） | 32 GB/s（单向） | ~26–28 GB/s | — |

### 2.2 为什么"显存更快"在这里不成立

1. **缓存命中路径多一次 PCIe 往返**：读命中时数据必须从显存经 PCIe 拷回内存
   再交给应用。PCIe x8 有效 ~14GB/s，而内存命中 ~60GB/s —— **显存命中比内存
   命中慢 4 倍以上**。缓存的意义是"命中要快"，用更慢的路径做缓存等于负优化。
2. **内核驱动无法直接访问显存**：CUDA 是用户态运行时，Windows 内核驱动没有
   通用"写显存"API（WDDM 内核接口极其受限）。只能做"内核 → 过滤通信端口 →
   用户态服务 → CUDA → 显存"的桥接：每次传输有固定开销（IPC + CUDA 调用 +
   锁页拷贝），4KB 小块约 10–100 微秒，而内存命中约 0.1–1 微秒 —— **慢 1–2
   个数量级**。
3. **容量不占优**：64G 内存分 16G 做缓存还剩 48G 给系统；显存总共 8G（且打
   游戏时独占）。
4. **空闲功耗与唤醒**：独显空闲 10–15W（笔记本还会抬风扇），为缓存常驻显存
   不划算。
5. **唯一理论上成立的方向**：大块顺序传输（>1MB）时 PCIe 带宽接近饱和，
   显存缓存延迟劣势被摊薄——但大块顺序场景 SSD 本身已够快，且命中率提升
   主要靠小块的重复读。**结论：在 64G 内存的机器上用显存做缓存层，收益为负。**

### 2.3 那"额外优化"该做什么（可移植，换电脑照用）

1. **自动内存预算（已实现）**：`CacheSizeMB=0` = 物理内存 25%，上限 32G。
   64G→16G、32G→8G、16G→4G，换电脑零配置。
2. **分页 IO 参与（架构就位，证据待采）**：卷块层统一通路下，普通应用的缓存方式 I/O 架构上已纳入缓存；命中声明待覆盖矩阵验证冻结（当前不得对外宣称"已实现/可命中"，见 `deliverables/block-coverage-matrix-2026-10-15.md`）。
3. **配置持久化（已实现）**：注册表保存，重启即恢复。
4. **建议手动档（针对你的 64G 机器）**：
   - 缓存大小：自动（16G）或手动 16~24G；
   - 高/低水位：60/40（默认）即可；
   - 回写周期：10 秒（默认）；下载/编译任务重时可调 30 秒增大合并窗口；
   - 并行回写：开（双 SSD 可叠加吞吐）；
   - 空闲释放：开（30 分钟）——笔记本待机省内存；
   - 系统卷：**不开**（你的 2T+1T 数据盘加速即可，C 盘交给系统缓存）。
5. **后续方向（路线图）**：
   - **L2 SSD 持久缓存**（对标 PrimoCache 永久二级缓存）：M1 接线 2026-10-15 已
     代码落地（默认 OFF，待真机验证后开放）；多卷键扩展 / 写缓存 / L2→L1 提升列 M2；
   - TRIM/删除透传（独立路线图项 P1-02）、启动预取（M2，依赖 L2 持久化）；
   - 缓存后端抽象（内存/SSD/未来的显存），把"显存"做成可选实验后端而非默认。
