## §3 `L2Hits=0` 根因分析（只读代码级，未改驱动）

### 3.1 已排除
- **槽位不一致**：Store 与 ProbeFill 都用 `slot = RbL2HashWith(blk, slots)`，`rbL2.c:1004` / Store 的同式计算一致；idx 报告亦证 `slot` 自洽。
- **未走 filter driver**：`readMode=unbuffered`，且 `coreMiss +1033`、`l2m +8` 证明读确实穿透到 `RbFeatOnMiss` → `RbL2ProbeFill`。
- **记录头三重校验失败**：`l2m` 计数点包含 `:1006`（IdxProbe MISS）与 `:1020`（记录校验失败）；无法从聚合计数器区分，但两者都归 MISS。
- **未定稿索引**：`l2 disable` 后解析得 Magic 有效、CRC 匹配。

### 3.2 结构性约束（最可能的主因）
`rbL2.c:978`：**`if (!dst || len == 0 || len > RB2_L2BLK) return STATUS_NOT_FOUND;`**
`RB2_L2BLK = 64KB`（`:39`），且 `:995` 还有 `off + len > RB2_L2BLK` 的跨槽拒绝。
而 `rbio_worker.c:256/289` 传给 `RbFeatOnMiss` 的是 **miss 区间长度**（`mr->len` 或 32MB 分片的 `clen`），
`rbfeat.c:823` 的转发门是 `Len <= 1MB`。⇒ **绝大多数读请求因 `len > 64KB` 在 ProbeFill 入口就被拒**，
根本不会查索引、不会 `Rb2Count(7,1)`。这解释了「`coreMiss +1033` 却只有 `l2m +8`」。

### 3.3 另一个可能的叠加因素
`shrink 100` 只把 **3 个块**送入 L2，而重读覆盖 **128MB / 64KB = 2048 个块**。
即使有少量 ≤64KB 的 probe 请求，命中那 3 个块的概率也极低。
⇒ **本轮 `hits=0` 同时受「请求尺寸门」与「采样覆盖率」影响，不能单凭此结果判定驱动读侧有缺陷**。

### 3.4 未闭合项
`.idx` 已被 `Invoke-Rollback` 第 [4] 步删除，**3 个已存块的具体 LBA 明细未留存**（idx 报告当时未打印条目明细）。
`parse_l2_idx.py` 本轮已补条目明细输出（仅输出增强，不改判据），下一轮可据此做定向重读。
