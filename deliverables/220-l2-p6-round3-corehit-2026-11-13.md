## §4 代码层根因链

1. `rbio.c:531-552`（`[OPT F8]` 内联全命中快路径）
   ```c
   if (sp->MajorFunction == IRP_MJ_READ && KeGetCurrentIrql() <= APC_LEVEL && len <= (1u << 20)) {
       ...
       allHit = rb_read_try_cache(ext->Stream, offset, tgt, len) != 0;
       if (allHit) { IoCompleteRequest(irp, ...); return STATUS_SUCCESS; }   /* 直接完成，不进 worker */
   }
   ```
   → 1MB ≤ 1MB，全命中即就地完成；`workerpath` 与 `RbFeatOnMiss` 全部跳过。
2. `rbio_ports.c:53`（shrink 的下限钳位）
   ```c
   ULONG64 lim = cur - (cur / 100) * Pct;      /* Pct=100 ⇒ 0 */
   if (lim < 1024ULL * 1024ULL) lim = 1024ULL * 1024ULL;   /* → 1MB */
   ```
   → `shrink 100` 之后 core 动态上限 = **1MB = 正好 16 个 64KB 块**，也就是**恰好等于阶段 D 的窗口大小**。
3. warm-up 的第三次读 pass 是顺序读，`shrink 100` 之后残留在 core 里的就是**最后那 1MB 的连续块**。
   阶段 A（931 次单块 probe）与阶段 C（931 次定向 64KB 读）都**没有**把它挤出去——
   这反过来说明：**L2 命中不会回填 core**（否则阶段 C 的 931 次读早把残留替换掉了）。
   于是阶段 D 选中的窗口正好落在残留里 ⇒ 全命中 ⇒ 走 §4-1。
4. 另一个佐证：阶段 C 的 931 次定向读里 **924 次是 `coreMiss`**（`coreHit` 只 +7），
   说明 core 确实只留有约 1MB，与 §4-2 的钳位一致。

**这不是「运气不好」，是结构性的**：`shrink 100` 的钳位把上限设成 1MB，正好是阶段 D 窗口的大小，
所以「窗口的第一个 1MB 」极可能正是残留。修法必须从「让窗口落在冷区」和「探针有效性判据」两头下手。

## §5 已落地的修法（只改夹具与 Python 工具；未动驱动）

| 编号 | 修法 | 位置 |
|---|---|---|
| R4-1 | **阶段 D 前驱逐 core**：对 load 文件的**尾部 64MB** 做 `FILE_FLAG_NO_BUFFERING` 读。必须无缓冲——缓冲读被文件缓存（在过滤器之上）吃掉，什么也驱逐不了。这批块不在 L2 里，因此每次都是真落盘读，**一定进入 core** | 夹具阶段 D；`p5b_directed_reread.py:displace_core` |
| R4-2 | **窗口后移 32 块**：把被测量的 16 块窗口从连号段起点向里挪 32 块，与残留的 1MB 结构性错开（工具内做钳位，段长不足时自动贴尾） | `--span-offset 32` |
| R4-3 | **新增有效性判据**：`coreMiss` 增量 ≥ 1 才认为「探针有机会被调用」。增量 = 0 ⇒ 判 `INCONCLUSIVE`（WARN），**不计 FAIL** | `Write-Probe` 的 `$LastProbeDcm` / 总判 |
| R4-4 | 新增 **3 分钟窗口** 的快速入口，避免每次验证都花 12 分钟 | `RB-l2-c-slice-fast.cmd`（`-WindowMin 3`） |

判据改动后的语义：

```

```
