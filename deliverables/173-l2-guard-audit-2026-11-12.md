## 1. 判决

**不能带着这批改动去签名部署。** 有四条必须先修，其中两条是阻断级的：

1. **`RbL2DropRange` / `RbL2DropAll` / 新的关机 `RbL2IdxSave` 都不持 `s_Ops`，而 `RbL2CloseIntEx` 会在排空 `s_Ops` 之后
   free `s_Idx`**（`rbL2.c:588-590`）。这不是"极窄窗口"：`RbL2CloseIntEx` 可以由 `Rb2Tick` 在 `s_Reopen` 时**自动**触发
   （`rbL2.c:344`），不需要用户动作。后果是 8.4MB 索引被 free 之后仍在被清/被遍历 → 池损坏 → bugcheck。
   在 `WriteMode=BACK` 卷上，一次 bugcheck 就等于丢掉未回写的已 ack 脏数据。
2. **A.2 的信任根是"索引文件里的 Magic"，而不是"自此之后没有任何未被观察的写"**。由于 L2 是懒开
   （`rbL2.c:584` / `rbL2.c:665`：只有 probe/store 才会开），**任何一次"卷被写但一次 64KB 读都没发生"的引导
   （或卷未 attach、或 `l2 disable` 的那次引导）都不会执行 unseal**；`RbL2IdxSave` 在未开时直接 `return TRUE`
   且不落盘（`rbL2.c:303`），于是上一次干净关机封好的索引原样留在盘上，**在下一次打开时被完整加载**
   （`RbL2IdxLoad` 只看 Magic/Build/SlotCount/Count/VolId/CRC，`rbL2.c:243-250`，**不看 `LastCleanShutdown`**）。
   这条路径返回的是静默错数据，而且记录头的 `Lba/VolId/CRC` 三重校验**挡不住**（记录本身是自洽的）。

另外两条（P0-3/P0-4）同属"这个特性存在的意义"层面，改动都只有几行，但都是静默陈旧数据或崩溃后的陈旧数据：
drop 的世代号 bump 得**太早**（在数据真正生效之前），以及 unseal 是**未持久化**的缓存写。

方向是对的（127 号 A.1–A.4 的骨架都对，五个挂钩点的位置基本正确，`Lba` 的单位问题经核实**不存在**，
见 §2.1），但这批代码**没有一条**经过内核验证，而上面四条都不需要跑测试就能从代码里读出来。
建议：修完 P0-1~P0-4（合计约 30 行）再签名；P1 里至少 H5 去耦合（`rbmsg.c:250`）应在签名前处理，因为它会
把 L2 的磁盘写失败升级成整个驱动的自断。

## 2. 逐条结论

### 2.1 `RbL2DropRange` 的索引比较：**成立**（任务里怀疑的单位不一致，实测不存在）

证据链（三处互证）：

| 位置 | 代码 | 说明 |
|---|---|---|
| `rbL2.c:668-669` | `blk = lba / RB2_L2BLK; off = (ULONG)(lba % RB2_L2BLK);` | 探测入口的 `lba` 是**卷内字节偏移**（`off` 直接用于 `rec+1+off` 的字节拷贝，`rbL2.c:686`） |
| `rbL2.c:751` / `rbL2.c:682` | 存 `rec->Lba = blk << 16`；探 `rec->Lba == (blk << 16)` | 记录头里存的是**块起始字节偏移** |
| `rbL2.c:260` | `slot = RbL2Hash(es[k].Lba >> 16)` | 索引加载时把 `Lba` 当字节偏移右移取块号 |
| `rbL2.c:154` | `L2Idx()[i].Lba == (b << 16)`，`b = off >> 16` | 与上完全同单位 |

所以 `Lba` = 块起始字节偏移，`b<<16` = 块起始字节偏移，比较成立。**drop 不会"永远不命中"**。
（推断部分：所有挂钩点传进来的 `off` 都是字节偏移——`rbio_worker.c:543` 的 `ctx->Offset.QuadPart`、
`rbio.c:337/380` 的 `sp->Parameters.Read.ByteOffset.QuadPart`，均为 IRP 字节偏移，已逐个核对。）

`b0/b1` 的边界：

- `len == 0` 直接返回、**且不 bump 世代**（`rbL2.c:142`）——语义正确（零长度写不改盘面）。但由此有一条纪律：
  任何"必须作废"的调用都不能靠 `len==0` 触发，见 P0-3 的修法。
- 溢出钳位正确（`rbL2.c:149-151`）：`end` 钳到 `UINT64_MAX` 后再算块号，`b1` 再钳到 `slots`；`b0 > b1` 时循环自然不执行。
- **但钳位钳的是"快照的 slots"，不是"当前缓冲区的真实容量"**——这就是 P0-1 的越界面。

### 2.2 「取一次 `s_Slots` 局部快照以避免 #DE」这个理由：**理由成立，但治的不是主症**

- #DE 这一条是真的：`RbL2CloseIntEx` 会在 `rbL2.c:590` 把 `s_Slots = 0`，而 `RbL2Hash` 内部 `% s_Slots`（`rbL2.c:128`）。
  若照 167 骨架直接调 `RbL2Hash`，并发 Close 落在循环中间就是除零。局部快照后这条消失。**这一点实现者是对的。**
- **但真正的坏结局不是 #DE，是 UAF/OOB**，而局部快照把它放大了而不是消除：
  - `rbL2.c:147` 读 `s_Idx`，`rbL2.c:154` 每轮再经 `L2Idx()` 解引用；`RbL2CloseIntEx` 在 `rbL2.c:588` 用
    `InterlockedExchangePointer` 摘指针后 `Rb2Free(old)`（`:589`）。DropRange 不持 `s_Ops`，Close 的 5s 排空
    （`rbL2.c:575`）对它**完全无保护**。→ 读已 free 的 8.4MB 非分页池。
  - 更坏的一种：快照 `slots` 取的是 Close **之前**的值，而 Close 之后若立刻重开、且 `L2SizeGB` 被改小，
    新 `s_Idx` 更小 → `i < slots` 不再保证 `i` 在界内 → **越界写 4 字节到池**（不是 UAF，是 OOB 写）。
  - `RbL2DropAll`（`rbL2.c:164`）更糟：`RtlZeroMemory(s_Idx, s_Slots * 16)` **一次写 8.4MB** 到可能已 free 的内存。
- 触发面（实现报告 §9.3 说"只在 REFRESH/flags-off/卸载/降级路径"——**不准确**）：
  `rbL2.c:344` 的 `RbL2Periodic` 在 `s_Reopen=1` 时会**自动**调 `RbL2CloseIntEx(FALSE)`，而 `s_Reopen` 由
  卷身份变化（`rbL2.c:395`，detach/换卷/多卷）自动置位。也就是说：**插拔一个卷、或 attach 第二个卷**，就能在
  写流量进行中触发 free。这不需要用户敲 REFRESH。
- 同类问题第三处：**H5 的新 `RbL2IdxSave` 调用点把这个保护弄丢了**。被删掉的 60s 周期块
  （`git diff` 可见 `rbL2.c` 旧 `:273-278`）原本有 `InterlockedIncrement(&s_Ops)` 包住 `RbL2IdxSave`；
  `rbmsg.c:250` 的新调用点裸调，`RbL2IdxSave` 内部还要遍历 `s_Slots` 个条目（`rbL2.c:305`、`:314`）。
  关机时若 `Rb2Tick` 恰好因 `s_Reopen` 正在 close，就是同款 UAF。

### 2.3 `s_Gen` 的自增顺序：**选对了（先 bump 后清），但 bump 的时机整体错了**

先 bump 后清是唯一正确序，理由链：
- Store 的 ③ 复核（`rbL2.c:768`）是在"赋值之后再看世代"。若 drop 是"先清后 bump"，Store 可以在
  "清"与"bump"之间读到旧世代并 `Use=1`，之后 drop 再 bump 却不再回头清 → **条目复活**。
  先 bump 则 Store 的 ②/③ 必然看到不匹配（`rbL2.c:759`、`:768`）→ `Use=0`。实现选的正是这一种，正确。
- ② 失败时不计数不记日志（`rbL2.c:759-772`），口径与"成功必计数"一致，可接受。

**但真正的问题不在这条顺序，而在"drop 相对于数据生效的相对位置"**（P0-3，见 §3）。

### 2.4 五个挂钩点的覆盖性

| 钩子 | 位置 | 结论 |
|---|---|---|
| H1 | `rbio_worker.c:159`（`RbInvalidateAfterFlush` 首行） | 覆盖 5 个调用点，实测确认只有这 5 处（`rbio_worker.c:586/631/862`、`rbio.c:337/379`），无第六处。`RbInvalidateAfterFlushKeep`（`:185-192`）确实未动。**正确** |
| H2 | `rbio_worker.c:695` | `cur`/`clen` 就是本块实际写盘范围（`cb = tgt + (cur-off)`，`rbio_worker.c:684`；7 个 `rb_stream_invalidate_range*` 的区间都被裁到 `[cur,cend]`：`:709 :734 :749 :755 :776 :785 :800`，前序块回滚区间 `[off,ok_end)` 由前几轮的 drop 覆盖）。**覆盖成立，且无子路径写出 `cur..cend`** |
| H3 | `rbio_worker.c:870` | 位置正确；见 §2.5 的"多丢"分析 |
| H4① | `rbio.c:273` | 在 L1 discard 之后，正确；但**在 `RbForward` 之前**，见 P1-3 |
| H4② | `rbctl.c:992` | 同上；对 TRIM 从"范围化"退化成"整卷清"，见 P1-4 |
| H4③ | `rbctl.c:694` | 紧跟 Keep 调用，PASSIVE（`rbctl.c:633` 的 `PAGED_CODE`），正确 |
| H5 | `rbmsg.c:250` | 顺序对（先 save 后 Clean），但**耦合错**，见 P1-1 |

**未覆盖的写路径（实现报告的"5 处覆盖全部"不成立）**：

1. `rbio.c:372-386`：**ctx 池耗尽 + IRQL > PASSIVE 的透传写**——日志明写
   `"passthrough write without invalidate"`，既不失效 L1 也**不 drop L2**。写已经落盘、L2 仍是写前内容。
   该缺口对 L1 是已知登记项，对 L2 是**新引入的同型缺口**（本次改动声称"写路径全覆盖"）。
2. `rbio.c:127`（`RbWritebackCb`）：回写落盘本身没有 drop。当前靠"H2/H1/H3 在吸收时已经 drop 过"来兜底，
   属于**约定覆盖**而不是**构造覆盖**——这正是 167 §F1 那个 bug 当初长出来的方式。
   建议在这两个点各补一行（成本 2 行），或在头文件里把"新增脏块来源必须自己 drop"写成硬纪律。

### 2.5 H3「写盘前 drop、写失败也不回滚」会不会反过来造成数据丢失

**不会。** 逐层给理由：
- L2 里只有"某一时刻盘面内容"的副本，**没有脏位**，也没有 L2 → 盘的回写通道（`RbL2Store` 只写容器文件，
  容器不是被加速卷）。drop 一个 L2 条目在任何时候都不可能丢掉"只存在于 L2 的已 ack 数据"。
- 写失败时 L1 的处置完全没被这次改动触碰：H3 分支本身不失效 L1（fastview），失败后既不 commit 也不
  `view_gen_bump`（`rbio_worker.c:876-883` 都有 `NT_SUCCESS(s)` 门），脏块留在 L1 等下一轮。
- 所以"写失败 + L2 已 drop"= 多丢一份可重建的副本（安全方向），不是丢失。
- 只有在 P0-1 的 bugcheck 场景下，才会经由"崩溃"这条**间接**通道丢 BACK 卷上的未回写脏数据（见 §6）。

## 3. P0：必须修才能部署

### P0-1（阻断）`RbL2DropRange`/`RbL2DropAll`/H5 的 `RbL2IdxSave` 没有生命周期保护 → UAF + OOB 写

**证据**
- `rbL2.c:139-156`（DropRange）：`slots = s_Slots`（`:146`）→ 解引用 `s_Idx`（`:147`、`:154`），全程不持 `s_Ops`。
- `rbL2.c:161-165`（DropAll）：`RtlZeroMemory(s_Idx, s_Slots * 16)`，同样的读法，写 8.4MB。
- `rbL2.c:567-594`（CloseIntEx）：`:575` 只等 `s_Ops`；`:588` 摘指针、`:589` `Rb2Free`、`:590` `s_Slots = 0`。
- `rbL2.c:344`、`:364`、`:371`、`:397`、`:406`、`:427`、`rbfeat.c:625` —— 七条 Close 入口，其中 `:344`/`:364`/`:397`
  与 `s_Reopen` 联动，**自动可达**。
- 新建的 H5 调用点（`rbmsg.c:250`）没有补 `s_Ops`，而被删掉的周期块（旧 `rbL2.c:273-278`）原本有。

**为什么必须修**：`RtlZeroMemory` 8.4MB 到已释放的非分页池，几乎必然在几十毫秒内触发
`BAD_POOL_HEADER`/`PAGE_FAULT_IN_NONPAGED_AREA`（0x19/0x50/0x7E）。这不是"极窄窗口"，是"一个自动触发的
UAF 加上一个 8.4MB 的放大系数"。

**建议改法**（最小，且不改变 167 已评审的形状）
```c
/* DropRange / DropAll / RbL2IdxSave 三处统一 */
InterlockedIncrement(&s_Ops);
idx = (PRB2_L2E)InterlockedCompareExchangePointer(&s_Idx, NULL, NULL); /* 与 slots 同一次读 */
slots = s_Slots;
if (idx && slots) { ...循环... }
InterlockedDecrement(&s_Ops);
```
`CloseIntEx` 已有的 5s 有界排空就是为这个计数设计的；DropRange 是纯内存操作，不会把排空拖长。
（若担心 8.4MB 的 `DropAll` 延长排空，可只在 `DropAll` 里持计数 + 分片零——但不要不做。）

### P0-2（阻断）A.2 覆盖不到"L2 本次没有打开"的引导 → 跨引导陈旧命中

**证据**
- unseal 只在打开成功路径上（`rbL2.c:531-538`，`RbL2IdxUnseal()` 在 `:538`）。
- L2 是懒开：`rbL2.c:665`（probe 才 `RbL2LazyOpenInt`）、`rbL2.c:738`（store 才开）。**写路径不开 L2**
  （`RbL2DropRange` 在 `s_Idx==NULL` 时只 bump 世代、什么也不落盘，`rbL2.c:147`）。
- 关机时若没开：`RbL2IdxSave` 在 `rbL2.c:303` 直接 `return TRUE`，**不碰 `.idx` 文件**。
- 载入侧不看任何"本次引导"令牌：`rbL2.c:243-250` 只有 Magic/Build/SlotCount/Count/VolId/CRC。
- `LastCleanShutdown` 在 `rbdriver.c:295` 被读后立即清零，而 L2 **从不读它**（全驱动 grep：
  `rbL2.c` 里只有注释提到它，见 `rbL2.c:350`）。

**可复现序列（只需"某个引导里卷被写但一次都没读"）**
```
B1  L2 开，读冷块 → 索引封盘（干净关机 H5 写 Magic=1），Clean=1
B2  卷被写（下载/备份/编译），但没有任何 64KB 读 miss → L2 从未打开 → 无 unseal、无 drop 落盘
    关机时 RbL2IdxSave 因 s_IdxFile==NULL 提前 return TRUE（rbL2.c:303），.idx 原样保留 B1 的 Magic=1
B3  读同一块 → L2 打开 → IdxLoad 加载 B1 的索引 → 记录头 Lba/VolId/CRC 全对 → 命中 → 返回 B1 的内容
```
同一形状还有两条更省事的入口：卷那次**没有 attach**（写根本不经过过滤器）；或用户那次 `l2 disable`。

**为什么必须修**：这正是本改动要消灭的"静默错数据"，而且是**永久**的（索引下次还会被再封一次盘）。
记录头三重校验在这里无用——B1 写进容器的那条记录自洽且未被覆盖。

**建议改法**（二选一，都小）
- 最直接：把 unseal 从"打开时"前移到 `DriverEntry`——从注册表读 `Features\L2Letter` 拼出 `.idx` 路径，
  无条件把 Magic 写 0。这样任何一次引导都在 L2 能打开之前先作废，B2 的漏洞消失。
- 或者：`DriverEntry` 捕获 `LastCleanShutdown`（`rbdriver.c:286` 已经读到了，只是消费掉了），
  存一个 `s_IdxTrusted`；`RbL2IdxLoad` 增加一道 `if (!s_IdxTrusted) return;`。

> 注意：这条不是 172 引入的新发明，它来自 167 §A.2 的设计前提（"打开时作废 ⇒ 崩溃/重启一律不可采信"）。
> 但那个前提对懒开模块不成立，落地时就变成了真漏洞。

### P0-3（阻断）世代号在"数据生效之前"就 bump，落在窗口内的 Store 会被放行

**证据**
- H2：先 drop（`rbio_worker.c:695`），后 `rb_write_ex` 吸收（`:700`）；H1：先 drop（`:159`），后 `RbForward`/
  `RbSyncIo`（`rbio.c:340` / `rbio_worker.c:588` / `:873`）；H3：先 drop（`:870`），后 `RbSyncIo`（`:873`）。
- Store 的世代快照在淘汰回调里取（`rbfeat.c:919`），而淘汰回调对**同一个 64KB 块**可以在上面那个窗口里发生：
  淘汰只挑干净块（`src/core/cache_evict.c:101` `if(c->dirty==0)`），块的 chunk 大小 = `BlockSize*16` = 64KB
  （`rbL2.c:426` 的几何门保证），与 L2 记录粒度一一对应，所以淘汰一个 chunk 正好就是"把一个 64KB 块的
  **写前内容**写进 L2"。

**失效时序**
```
T0 写线程：RbL2DropRange(B)  →  s_Gen = G+1（B 的条目清掉）
T1 回收线程：evict_victim(B)（B 仍是干净的、内容还是写前）→ gen 快照 = G+1（晚于 drop）→ 拷走写前内容
T2 写线程：rb_write_ex / RbSyncIo 把新数据写入 L1 或盘面
T3 Store 入口复核：Gen(G+1) == s_Gen(G+1) → 放行 → L2 里留下 B 的**写前**记录，且再无 drop
T4 关机封盘 → 重启 → 命中旧内容
```
H1/H3 的窗口包含一次**同步盘写**（`rbio_worker.c:873`），毫秒级；期间并发读者以新 `view_gen` 读旧盘面并
commit（`rbio_worker.c:882`）也会产生同样的"旧内容 + 新世代"块。**这正是 150 号 N-150-10 已经为 L1 修过的窗口
（`rbio_worker.c:876-877` 的 `view_gen_bump` 就是它的补丁），L2 侧没有对应补丁。**

**建议改法**：在"数据已经生效"之后再 drop 一次（清不清条目无所谓，关键是把世代再推一格）：
- H2：`rb_write_ex` 返回（成功与否都行，失败是多丢，安全）之后补 `RbL2DropRange(cur, clen)`；
- H3：`if (fastview && NT_SUCCESS(s) && ext->Stream)` 分支里，紧挨 `rb_stream_view_gen_bump` 补一行；
- H1：`RbInvalidateAfterFlush` 的五个调用点无法统一补（它自己的 `off/len` 就是数据范围），
  最小做法是在 `rbio_worker.c:586/631/873` 与 `rbio.c:340/389` 的写完成之后补一次。
成本 6~8 行。若不改，必须给出"该窗口内不可能淘汰同一个 64KB 块"的锁序证明——我没有找到这样的证明。

### P0-4（阻断，但成本 1 行）unseal 是未持久化的缓存写，A.2 的"崩溃即作废"不成立

**证据**：`rbL2.c:283` 一次 4 字节 `ZwWriteFile`，句柄是 `FILE_SYNCHRONOUS_IO_NONALERT`（`rbL2.c:230-232`），
既无 `FILE_WRITE_THROUGH` 也无 `ZwFlushBuffersFile`（全文件 grep 0 命中）。实现报告 §8 第 17 行自己也承认"未证明"。

**后果**：`[首次打开, lazy writer 把 4 字节刷下去]` 这个窗口（NTFS 上可达数秒）里的掉电，会让盘上仍是上一次
干净关机封好的 Magic=1 → 下次开机加载旧索引 → 该窗口之前的写全部没有 drop 记录 → 陈旧命中。
窗口窄，但它攻击的正是"崩溃"这个 A.2 唯一的存在理由。

**建议改法**：`FILE_WRITE_THROUGH`（打开时加一个标志）或写完 `ZwFlushBuffersFile`；失败按现有日志记为
"本会话 L2 不可信"（更狠：置 `s_Halt`，本会话直接不用 L2——fail-closed）。

## 4. P1：可以部署但必须记录

### P1-1（强烈建议在签名前处理）H5 用"L2 索引保存失败"去掐 `LastCleanShutdown`，把 L2 的故障升级成整个驱动的自断

- 代码：`rbmsg.c:250-257`。
- 后果链：`Clean` 不写 → 下次引导 `rbdriver.c:302-312` `fails++` → `rbdriver.c:318` `BootLoopGuard(fails>=2)`
  → `rbdriver.c:325-331` `SafeMode=1` + 拒绝挂载；若 `FilterArmed`，`rbdriver.c:321-324` 直接 `self-disable`。

- 建议：恢复 `rbmsg.c` 原来的无条件（引擎无脏即写 Clean）；`RbL2IdxSave` 的返回值只用来打日志。

### P1-2 世代是全局的：任何一笔写都会杀掉所有在飞 Store

`rbfeat.c:919` 快照 + `rbL2.c:711` 入口复核 ⇒ 拷贝/入队/池排队（每组默认 4 worker、最多 8 组，
`rbpools.c:112-116`）期间只要卷上有
**任何**一笔写（NTFS 元数据/日志写是常态），这个淘汰作业就被丢弃。功能上安全（多丢），但活跃卷上

若确实塌了，改成按块区间做世代（例如块级 `drop_seq[blk]` 或按 1GB 分段计数）。

### P1-3 H4① / H4② 的 `RbL2DropAll` 在元数据操作**之前**执行

`rbio.c:273` 与 `rbctl.c:992` 都在 `RbForward` 之前。L1 在这段窗口里有 `rb_stream_set_view_mutating`
（`rbio.c:239`/`:279`、`rbctl.c:969`/`:994`）挡住回填，**L2 没有任何等效挡板**：窗口内在飞的淘汰仍可把
"即将被 delete/rename/重排作废的内容"写进 L2，而 DropAll 已经跑过了。正确位置应是 `RbForward` 返回之后
（失败也要 drop，但那时 drop 是幂等的）。窗口是毫秒级，命中要求"同一块在这段时间被淘汰"，概率低但形状与
本改动要修的 bug 完全一致。

### P1-4 `RbL2DropAll` 的代价与粒度

- 8.4MB `RtlZeroMemory`（32GB 配置，`s_Slots`=524096 × 16B）。每个簇相关元数据操作（删除/改名/截断/分配，
  `rbio.c:226-234` 的 8 个 class）都要付一次，且 L1 侧本来已经有一次全量 discard（`rbio.c:265`）。

### P1-5 H5 可能每个卷设备各执行一次

`RbDispatchPower`（`rbmsg.c:214`）拿的是 `dev->DeviceExtension`（每个被加速卷一个 `RB_DEV_EXT`）。

每次最多 8.4MB 索引写。功能无碍，关机时间与日志会重复。推断，需真机数一下日志条数。

### P1-6 `RbL2IdxSave` 自身与其他 `s_Idx` 写者的并发

但和 P0-1 是同一个根因，建议一并修。

## 5. Gate14 的登记：程序上合规，实质上不成立

**门禁在找什么**（`check_buffer_write_contract.py`）：
- `WRITE_RE`（`:25`）：`\w+ [ \w+ ++ ] =`，即"定长数组 + 无钳位自增下标写入"。
- `CAP_RE`（`:26`）：`<\s*(cap|Capacity|q\.MaxCount|RB_[A-Z0-9_]+|\d+)`。
- `:82-84`：**只要一行以 `for|while|if (` 开头且命中 `CAP_RE`，就被当成"受审计的写入行"**（`guarded`）。
- `:108-122`：R2 要求这些行文本 **multiset 与 baseline 完全一致**，多一行就红。

**为什么这行会红**：新增行
`if (L2Idx()[i].Use && L2Idx()[i].Lba == (b << 16)) L2Idx()[i].Use = 0;` **不是**自增下标写
（`WRITE_RE` 不命中），但它命中了 `HEAD_RE`，而 `(b << 16)` 里的 `"< 16"` 被 `CAP_RE` 当成"容量钳位"匹配上了
（`<` + 空格 + `16`）。这是一次**假阳性**：位移运算符被读成了比较。

**所以这是"打洞"吗**：程序上不是（`:9` 的注释与 R1 的设计本来就要求"新增必须人工审计并登记"），
但**实质上是**——因为这条登记把一个**真实的越界写点**从审计视野里拿掉了：

- 实现者给的理由是"`i` 来自 `RbL2Hash` 的 `% slots`，且 `b` 已钳到 `slots`，写点在界内"。
- **这个论证不成立**：`slots` 与 `s_Idx` 不是同一份快照。`slots` 是 `rbL2.c:146` 的局部读，`s_Idx` 在
  `rbL2.c:154` 每轮重读，而 Close 可以在两者之间把旧缓冲 free、把新缓冲装成更小的 `s_Slots`
  （`rbL2.c:588-590`）⇒ `i < slots_old` 不保证 `i < slots_new` ⇒ 池越界写。
- 这正是 Gate14 存在的理由（"固定容量数组 + 无钳位自增下标"），却被"登记"消音了。

**建议**：
1. 修 P0-1（持 `s_Ops` + 指针与 slots 同一次读）之后，这行才真正"在界内"；届时登记可以保留，
   但要在 baseline 旁或注释里写明理由（"CAP_RE 假阳性，安全性由 s_Ops 生命周期保证"）。
2. 顺手修门禁的假阳性：`CAP_RE` 至少要求 `<` 不是 `<<` 的一部分（例如 `(?<!<)<(?!<)\s*...`），
   并把"位移被误判"作为回归用例——否则下一处 `x << 16` 还会再来一次。
3. 注意登记的双向代价：这条行文本从此**不能改**，将来想给它加一个实时边界复核，门禁会以
   "R2 write lines changed" 报红，反而阻碍加固。

## 9. 特别回答：这批改动有没有可能造成**用户数据丢失**？

**直接路径：没有。** 逐条排除：
- L2 只保存"某时刻盘面内容的副本"，没有脏位、也没有回写通道（`RbL2Store` 只写容器文件 `RAMBoostL2.bin`，
  `rbL2.c:757`）。drop 一个 L2 条目在任何情况下都不是"丢掉唯一副本"。
- `RbL2DropAll` 不删容器、不截断容器（`rbL2.c:158-165`，全文 grep 无 `ZwDeleteFile`）。
- A.2 的 unseal 只写 `.idx` 的 4 字节（`rbL2.c:283`），**不碰** `.bin`；容器的 Magic 是另一套常量
  `RB2_L2_MAGIC`（`rbL2.c:56`），与索引的 `RB2_IDX_MAGIC`（`:57`）是两个文件两套值。
- 唯一会"重写容器头 + `SetInformationFile` 定长"的分支（`rbL2.c:477-519`）由**容器尺寸**触发，与本次改动无关；
  而且它对"非本驱动容器"是明确的 fail-closed 拒绝（`rbL2.c:495-503`：首 16 字节不是 `RB2_L2_MAGIC` 就
  绝不截断），**不会误毁同名的用户文件**。
- 所以问题 3 里担心的"重格式化 32GB / 删掉容器 / 每开机死循环重建"——**都不存在**：
  `.idx` Magic=0 的结局是 `RbL2IdxLoad` 整份拒绝（`rbL2.c:245`）→ 空索引 → 冷启动；容器尺寸检查稳定，
  不会重建；每次开机的代价只是"4 字节写 + 一次冷启动"，不是 32GB 重格式化。

**但有三条间接通道会造成数据损失，必须写进去：**

1. **P0-1 的 UAF → bugcheck → 在 `WriteMode=BACK` 卷上丢失未回写的已 ack 脏数据。** 这是唯一能把本次改动
   接到"真丢数据"上的路径。触发条件不需要用户动作（插拔卷即可）。
2. **P0-2 / P0-3 / P0-4 的静默陈旧读 = 数据完整性损失**，性质比丢失更坏：应用拿到的是**自洽的旧内容**，
   没有任何错误码、CRC 或日志能提示它。其中 P0-2 是"永久"的（每次开机都会再封一次盘）。
3. **P1-1 不会丢数据**，但会把 L2 的磁盘写失败升级为整个驱动进安全模式/自断（可用性损失 + 现场难判）。

一句话：**这批改动不会直接吃掉用户数据；但它引入了一个能蓝屏的 UAF（间接丢脏数据）和三条能返回旧数据的
路径——对"读缓存"来说，返回旧数据和丢数据是同级的错误。**
