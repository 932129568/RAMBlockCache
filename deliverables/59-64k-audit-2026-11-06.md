## 1. TL;DR

**判断：64K 禁令维持；解禁前置 = ①临时收紧白名单堵住"策略裸奔"（F1，唯一高风险新发现）→ ②补 64K 核心几何测试（现有 test_geom.c 恰好漏了 65536 这一档）→ ③WinDbg 复现 11-03 形态。** 用户态静态审计本轮全部通过、无 P0/P1 代码缺陷——与 11-03 审计（deliverables 48 R2/R3：驱动侧 P0/P1=零）结论一致，崩溃点不在可见的几何数学里，仍在内核态。

三行依据：
1. 入口 clamp 白名单 `{4K,8K,16K,32K,64K,128K}`（rbctl.c:122）**本来就放行 65536**——禁令没有代码强制，用户今天就能把 BlockSize 设成 64 并在下次引擎重建（重启）后拿到 64K 几何（F1）。
2. core 几何全派生（chunk=block×16、sub_shift、chunk_mask），掩码 uint16 恰 16 子块，无任何 4096 硬依赖（cache.c:886-894）；驱动侧读/写/回写/预取路径逐条过检，64K 下无溢出、无越界、无假设破坏——**除 slab 留池上限 ×16 放大（F4，内存面而非正确性面）**。
3. 唯一的运行期几何耦合（config 副本 vs 引擎几何，F10）已有 W12 推迟纪律闭合，只剩 RMW 性能损耗面，无正确性风险。

## 2. 入口校验事实

**RbClampConfig 的 BlockSize 合法集（rbctl.c:121-127）：**

```c
static const ULONG rb_legal_bs[] = {4096, 8192, 16384, 32768, 65536, 131072};
... if (!rb_ok) c->BlockSize = 4096;     // rbctl.c:126
```

- **65536 被允许**（rbctl.c:122）。→ **崩溃点在几何数学/运行期，而非入口校验**；禁令不是 clamp 层面的。
- core 同款白名单：cache.c:887 `legal[] = {4096,8192,16384,32768,65536,131072}`，非法回落 4096（:890）。
- CLI 同款：ramboostctl.c:1528-1531（`block=64` → 65536，白名单外警告回退 4K）。
- 白名单是 2026-11-02 F6→DECOUPLE 时解开的（rbctl.c:114-120 注释：core 无 4096 硬依赖、掩码恰 16 子块；F6 实证损坏的真正根因是【引擎存活期热改】，已由 W12 推迟纪律拒绝）。
- 运行期热改防护：rbctl.c:196-199（W12）——引擎存活期 SET_CONFIG 改 BlockSize 只持久化、运行值保持，"BlockSize deferred until engine recreate" 留痕；引擎重建（RbEnsureEngine，rbattach.c:377 `cfg.block_size = g_Rb.Config.BlockSize`）后生效。
- 加载路径：rbdriver.c:282（注册表 `BlockSize` 字段表）→ rbdriver.c:303 RbLoadConfig 内统一过 clamp。
- 当前部署默认 4096（交接 58 §一：开机策略 BlockSize=4096），与代码默认一致（rbdriver.c:1355 RB_DEFAULT_BLOCK_SIZE）。

**推论（重要）：所谓"64K 禁用"目前只是运维纪律，代码零强制。** 任何用户/脚本写注册表 `BlockSize=65536` 或 `ramboostctl set-config block=64`，重启后引擎即以 64K 几何创建。见 F1。

## 4. 溢出阈值速查（64K 档量化边界）

| 数学点 | 公式 | 4K 档 | 64K 档 | 结论 |
|---|---|---|---|---|
| slab 留池滞留（F4） | `2048 × chunk(=BS×16)` | 128MB | **2GB**（128K 档 4GB） | 累计淘汰 ≥2048 块（≈2GB churn）后永久滞留，不受预算约束——**64K 解禁前必修** |
| slab 单批分配（F5） | `16×chunk + 64KB + 头` | ≈1.06MB | ≈16.07MB | 单次非分页分配大额化；失败→direct 兜底 |

| 读片 miss 区间数 | `128KB/BS 子块，交替最坏 ⌈n/2⌉` | ≤16 ≤ RB_MAX_RANGES=32 | ≤2 | ✓ 无溢出面 |
| 写块 direct 区间数 | `8MB/BS 子块，排除集交替` | 最多 1024 > 32 | 最多 128 > 32 | 两档均可溢出→已有 -2 整块直写兜底（rbio.c:774-787），非 64K 新增面 |

| 预取 MDL 页数 | 8MB/4K=2048 页，块无关 | ✓ | ✓ | ✓ |
| chunk_size 乘法 | `bs×16`（rb_u32） | 64KB | 1MB（128K 档 2MB） | rbL2 门同式（ULONG，2MB 不溢出）✓ |

## 5. 解禁前置清单

### 5.1 必修项（按风险排序）

1. **F1（高）**：解禁归因完成前，把 65536 从 **四处** 白名单临时摘除——rbctl.c:122 / cache.c:887 / ramboostctl.c:1528 / **MemoryView.xaml.cs:17 `_blockSizes`**（或驱动侧加显式解锁开关+日志，UI/CLI 跟随驱动拒绝回显即可少改两处）。理由：当前禁令纯靠纪律，WPF 下拉一键、CLI 一条命令、注册表一个值都能让未归因的崩溃形态复现。
2. **F4（中-高）**：slab free-stack 改字节上限（256MB 量级）或接 reclaim trim。理由：64K 档 2GB 非分页滞留是唯一随块大小放大的**资源面**缺陷，长跑必然命中；亦是 11-03"内核踩踏"归因前必须排除的内存压力变量。
3. **F5（低-中）**：64K 档 slab 批次 16→4，降低单次 16MB 非分页分配失败率（失败=静默直写性能悬崖）。
4. **F10（低）**：写切块改用引擎几何 getter，消除 config/引擎几何推迟窗的 RMW 面（归因后可降低 Verifier 噪音）。
5. **F11/F6/F7/F15（低）**：清理死常量注释、读片/预读对齐到 BlockSize、excl_hit 端点复测——解禁后的性能/维护项，非阻断。

### 5.2 必补测试（core 级，形态参考 test_geom.c / test_race1106.c / test_wsconc.c）

## 6. 与 11-03 / 11-04 事故的关联假设（只标注，不定论）

- **H1（11-03 64K 崩溃）**：静态面唯一随 64K 放大的资源缺陷是 slab 滞留/批量分配（F4/F5）——非分页池压力可间接诱发系统级失稳（如池耗尽后任意驱动分配失败），但**无直接"踩踏 DEVEXT"的代码路径证据**；本审计与 48 号审计（R3："core 分配形态 64K 审计（崩溃真凶嫌疑）→均安全"）交叉确认：用户态审计已尽，根因仍需内核调试（U-4 维持 ⏳）。
- **H2（11-04 四次蓝屏 0xC0000096+0xBCC，U-8）**：rbpref.c:189-191 的回滚注释记录了**完全相同签名**的历史崩溃——"0x7B/0x7E, dump: 基址+0xBCC 特权指令异常"，发生于 2026-10-24 预取扩档（128/256/512MB ReadAheadMB）部署后，二分回滚扩档。0xBCC 应理解为**模块内偏移**（异常 EIP=驱动基址+0xBCC），0xC0000096=STATUS_PRIVILEGED_INSTRUCTION。假设：11-04 与 10-24 为同族（同一偏移=同一函数/跳转点被同一方式破坏），嫌疑面在预取链（RB2_PRD 生命周期/池作业）而非块几何——**待验证**：用 WinDbg `ln` 解析任一现存 dump 的 rbc+0xBCC 即可证实/证伪；二者都与 64K 解禁无必然联系，但若同族成立，解禁压测前应先闭环 U-8。
- **H3（旁证）**：rbio.c:1325-1327 注释（FIX REDTEAM-1）显示历史曾有一次 0xC0000096 级蓝屏归因于 **APC_LEVEL 下取 ERESOURCE**——第 4 次蓝屏同族。说明本代码库的 0xC0000096 至少存在过两个已知生成机制（IRQL 越权 / 偏移 0xBCC 未知点），归因时不可混同（KNOWN_ISSUES 亦注明另有 0xC4 新形态）。
