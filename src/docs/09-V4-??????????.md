# 09 V4：分片条纹锁多核并行 · 长效签名 · 游戏模式干净切换

本篇说明 V4 在 V3 基础上的核心重构、检查长式跨模块审查发现并修复的问题、
极限测试结果与仍需在真实 Windows 上验证的事项。

## 一、分片条纹锁：同一文件多核真正并行（核心重点）

### V3 的瓶颈
V3 的核心本身无锁，锁在驱动层，且是「每流一把 `FAST_MUTEX`」：`flt_io.c`
在**整个读写路径**（含磁盘回调）都持有 `ctx->Lock`。后果是——即便两个线程
读写的是**同一个大文件的不同区域**、彼此完全不相关，在多核上也被这把锁
**串行化**，多余的 CPU 核用不上。

### V4 方案
- 核心层引入可移植锁抽象：每流 **64 把分片条纹锁**（内核态 `FAST_MUTEX`
  数组，用户态测试 `pthread_mutex` 数组），按块哈希取模：
  `stripe = bucket_of(chunk_start) % 64`。
- 同一流**不同分片**的读写在多核**真正并行**；只有命中同一分片才短暂互斥。
- LRU 链与脏链由独立的 `chain` 锁「短持」保护，不再与数据锁混用。
- 引擎共享字段（`total_bytes`/`total_dirty`/`nstreams` 及各计数器）保持
  原子操作，无数据竞争。

### 锁序（严格规定，杜绝死锁 / 重复加锁）
```
streams_lock  →  stripe（多片时按分片号【升序】2PL 加锁）  →  chain
```
- `FAST_MUTEX` 不可递归：同一 IO 触及多个分片时，先收集分片号、排序去重，
  再按升序依次加锁（`lock_stripes`），用完逆序释放。
- 磁盘回调（writeback/readback）在 **stripe 锁内、chain 锁外**调用：只阻塞
  该分片（约 1/64 区域），其它分片与其它流在多核继续并行。
- 不存在 `chain→stripe` 或 `stripe→streams_lock` 的反向获取，因此无环、无死锁。

### 驱动层协同迁移
- 移除 IO 路径、工作项、配置快照、关机/卸载路径上的外层 `ctx->Lock`，并删除
  已无用的 `Lock` 字段（核心已自锁）。
- **保留**底层文件对象以 `FILE_SYNCHRONOUS_IO_NONALERT` 同步打开：物理磁盘
  IO 由 IO 管理器按文件对象安全串行化，彻底消除「重叠盘 IO」这一类竞争；
  不同流 / 不同卷（各自独立文件对象）仍天然并行。
- 稳态下绝大多数前台读写命中缓存（不触盘）→ 完全并行；仅磁盘 miss / 直写 /
  回写这类少数路径由 IO 管理器串行，安全且不影响主路径。
- 核心 API 的**语义契约（返回值、miss/direct 对齐、RMW、水位）保持不变**。

## 二、长效签名（100 年 / 纯本地 / 不联网 / 无 CRL）

- `scripts/sign_test.cmd` 重写：创建/复用自签名代码签名证书，
  **RSA 4096 / SHA256 / 有效期 100 年**（`-NotAfter (Get-Date).AddYears(100)`），
  证书导入本地 `Root` 与 `TrustedPublisher`，再对 `RAMBoostFS.sys`（及存在时的
  `ramboostctl.exe`）做 Authenticode 签名。
- **不指定时间戳服务器**：签名全程离线，不访问任何时间戳/吊销服务器；
  证书链在本机闭环，**不依赖公网 CA，不依赖 CRL/OCSP**。
- 兜底：证书存在且未过期即复用，缺失/过期自动重建重签；脚本可重复运行，
  重跑即「重新签名」。
- 个人单机使用，证书 100 年有效，正常情况下不会出现「用着用着不能用」。

## 三、游戏模式：干净的一键切换（需重启）

开启测试签名后，带**内核反作弊**的游戏（如 Valorant / Vanguard）会拒绝启动，
普通软件不受影响。RAMBoostFS **不提供、也不可能提供**「隐藏测试签名 / 让反作弊
识别不到 / 欺骗 CI-DSE / hook 反作弊」的办法——这类做法既不合规也会被反作弊
判定为作弊。正确做法是**干净地双模式切换**：

| 模式 | 动作 | 重启后 |
|---|---|---|
| 游戏模式 | `bcdedit /set testsigning off` | 驱动**不加载**，Vanguard 等正常启动 |
| 加速模式 | `bcdedit /set testsigning on` | 恢复内存加速（右下角「测试模式」水印正常） |

- `scripts/game_mode.cmd`：自带 UAC 自提权，菜单或参数 `game` / `accel`，
  切换前明确提示「**需重启生效**」，可选 10 秒后自动重启。
- 可视化前端新增「游戏模式 / 加速模式」按钮，经控制台 `api/gamemode?to=game|accel`
  触发 UAC 提权执行上述 bcdedit，并提示重启；**不欺骗任何软件**。

## 四、检查长式审查：发现并修复的「配合类」问题

以下问题单看单个函数往往正常，必须跨文件 / 跨模块 / 多线程配合才触发，
均已定位「如何复现」并修复：

1. **硬上限早退直写 → 陈旧干净缓存（数据正确性，最关键）**
   缓存达硬上限时，`rb_write` 曾在逐子块循环**之前**「整段直写并 return」。
   复现：整段被直写盘，但未合并进一个**已加载的干净子块**（其内容停留旧值），
   之后读该子块返回**陈旧数据**，而磁盘已是新值。
   修复：删除该早退；硬满时先本流整理并请后台回写，**始终**跑逐子块循环；
   新增 `can_create()`——硬满只拒绝**新分配**，已加载子块始终合并、direct 只
   覆盖未加载子块。

2. **回写「遇首个失败即整体中止」→ 磁盘满时本可挽救的数据被丢**
   旧实现按分片哈希序遍历，且任一段回写失败就终止整轮。磁盘满（仅低偏移仍有
   空间）时，可能先遇到高偏移不可写段而中止，低偏移可写数据未被落盘、最终在
   流销毁时被计为丢失。
   修复：失败仅保留该段脏位，**继续扫描并挽救其它所有可写段**；force 多轮
   （4 轮）重试，零进展才停止。修复后磁盘满场景仅丢失**真正无法落盘**的字节，
   计数精确（见测试 C7）。

3. **在线配置字段非原子 → 数据竞争**
   `rb_engine_set_max_bytes` / `set_idle_reclaim` 普通写各水位与
   `idle_reclaim_ms`，而前台/flush 无锁并发读（驱动前台也不取 ConfigLock）。
   修复：7 个在线变更字段全部改为原子发布/读取（创建期默认值在发布前单线程
   写入，保持普通写）。TSAN 复检零竞争。

4. **每流聚合计数在分片后裸奔**
   `cur_bytes`/`dirty_bytes`/`chunk_count` 在 V3 由外层流锁保护，V4 多线程打
   同一流后变为非原子 RMW。修复：所有站点统一为原子加减。

5. **`chunk_destroy` 调试构建 use-after-free**
   曾在 `CORE_FREE(c)` 之后才调用调试事件 `ev(...)`（内核构建为空、仅调试构建
   触发）。修复：把事件移到释放之前。

6. **控制台 `json_stats` 格式串/参数不匹配（跨模块断链）**
   `IdleReclaimBytes`/`LostDirtyBytes` 被当作**多余 printf 实参**传入却无格式
   占位符，导致 JSON 实际**未输出**前端要读的 `idleBytes`/`lostBytes`。
   修复：重写 `json_stats`，完整输出 `idleBytes`/`lostBytes`/`stripeCount`/
   `stripeRead[]`/`stripeWrite[]`，JSON 缓冲扩到 16KB。

## 五、极限测试与验证矩阵

| 验证项 | 方式 | 结果 |
|---|---|---|
| 14 项核心用例 | -O2 / ASAN / TSAN | 全过 |
| 刁钻场景 edge_v3（6 组） | -O2 / ASAN | 全过 |
| 跨模块刁钻 edge_v4（C1–C7） | -O2 / ASAN / TSAN | 全过 |
| 多核分片压力 stress_v4（12 线程） | -O2 / ASAN / TSAN | 全过 |
| 连续重复压力 | stress_v4 + edge_v4 连续 **6 轮**，带 timeout 死锁探测 | 全过，零死锁 |
| 高负载变体 | **24 线程**、操作量加大，normal 2 轮 + ASAN 1 轮 | 全过 |
| ASAN / UBSAN | 全部套件 | 零报告 |
| TSAN | 全部多线程套件 | 零数据竞争、零死锁 |
| 权威磁盘逐字节校验 | force flush 后脏=0、非预期丢弃=0、磁盘逐字节==影子 | 通过 |

edge_v4 覆盖：force flush/trim/idle+时钟大跳变/跨分片 RMW/在线配置 与前台同分片
并发；磁盘满→脏保留（lost=0）→恢复→回写成功（lost=0）；磁盘永久满时
`lost` **精确等于**无法落盘的脏字节。

> 测试代码已先自查越界与同步（审计数组容量、精确 len、共享磁盘加锁），
> 历史上「确定性数据丢失」最终确认均为测试代码自身越界，核心引擎无此问题。
