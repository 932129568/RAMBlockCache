## 3. 新发现 I48c：热开启 attach 无条件丢脏（实测丢失 7,872,512 B）

### 3.1 触发路径（本次终验的收尾动作）

e5 的 `finally` 先 `SET_CONFIG` 回旧配置（被 I48 守卫拒绝，符合预期），再 `ATTACH D: Attach=0`（软 detach，I48b 保留脏视图）。随后为做 P4 取证，我执行了 **`ATTACH D: Attach=1`（热开启）**：

```
INFO [1310] volume attached (hot switch on)          ← 03:46:15.079
stats: DirtyBytes 7,872,512 → 0
       CurBytes   7,929,856 → 0
       LostDirtyBytes        0 → 7,872,512           ← 一次 attach 全额计入丢失
```

### 3.2 根因（源码点名）

`src/driver/rbctl.c RbMsgAttachVolume`（热开启分支，约 600–603 行）：

```c
if (ext->Stream) {
    if (rb_stream_dirty_bytes(ext->Stream)) rb_stream_flush(ext->Stream, 1);
    rb_stream_discard_all(ext->Stream);   /* [FIX DATA-13] 无条件 */
}
```

`rb_stream_discard_all`（core `cache.c:1234`）**含脏块一并销毁并 `count_lost=1`**。flush 结果未检查 ⇒ 回写失败（当前环境必然失败）时，已 ack 脏数据被静默丢弃并计入 lost。**与 I48/I48b 完全同族**，且比二者更易触发：用户只要在回写失败后点一次"重新开启加速"。

### 3.3 同类未守护站点全量枚举（本轮源码审计）

| # | 位置 | 语义 | flush 结果检查 | 处置建议 |
|---|---|---|---|---|
| I48 | `rbctl.c RbApplyConfig` | 全局 WB→直写 / Enabled→0 | ✅ 已修（dirty_after!=0 拒绝降档） | 已完成 |
| I48b | `rbattach.c RbDetachVolumeByLetter` | 软 detach | ✅ 已修（left==0 才 discard） | 已完成 |
| **I48c** | `rbctl.c:600-603` | **热开启 attach（DATA-13）** | ❌ **无条件 discard** | **本次实测丢 7.87MB** |
| **I48d** | `rbctl.c:558-561` | `SET_VOLUME` 切每卷直写 | ❌ 无条件 discard | 同族，未实测 |
| I48e | `rbctl.c:936-938` | FSCTL 簇重排类（变更窗） | ❌ `if dirty { flush; discard; }` | 同族；FSCTL 语义需单独决策（见 §3.4） |
| I48f | `rbctl.c:991-994` | DeviceIoControl 簇重排类 | ❌ 同上 | 同族 |

### 3.4 修复设计（下一批）

- **核心**：新增 `rb_stream_discard_clean(s)`——只销毁 `dirty==0` 的块；对"部分脏"的 chunk 清 `loaded`（干净子块）而保留脏子块数据，使脏数据既不离场也不被旧干净数据污染。零 lost 记账（真正丢弃的只有可从盘重建的干净块）。
- **I48c/I48d**：改为 `flush; if dirty==0 → discard_all; else → discard_clean + 日志 KEPT`。语义上 DATA-13（离场期盘面可变 ⇒ 干净块必须失效）与数据安全同时满足，无需二选一。
- **I48e/I48f**：簇重排会让脏数据的 LBA 语义失效，仅"保留脏"并不安全。建议 **fail-closed**：flush 后仍有脏 ⇒ 拒绝转发该 FSCTL/IOCTL（`STATUS_DEVICE_BUSY` 或 `STATUS_IO_DEVICE_ERROR`），由 FS/defrag 重试；不要在盘面即将重排时把脏数据留在缓存里。此条需设计确认后再实现。
- **门禁**：Gate13 增 A11（attach 守卫）/ A12（SET_VOLUME 守卫）/ A13（簇重排 fail-closed），并做变异验证（守卫恒真 ⇒ data-loss regression）。

## 4. P4：证据缺口与对 136 号假设的更正

### 4.1 事实

- `RbWritebackCb` 的失败日志 `writeback sync io failed (dirty retained)` **在本次全程未出现一次**（日志文件与驱动 512 环形缓冲 method 9 快照均无；二进制中该字符串存在，确认镜像含该代码）。
- `rb_stream_flush_fail_seq` 确实递增（否则 FLUSH IRP 不会判失败）⇒ `cfg.writeback` 返回过非 0。`RbWritebackCb` 只有三条非 0 出口：`!ext`（**静默 return 1，无日志**）、`len>2GB`（本场景不成立）、`RbSyncIo` 失败（**必打日志**）。⇒ **本次失败极可能是 `RbGetExt` 返回 NULL，回写根本没有发起磁盘 I/O**。

### 4.2 时间学反驳「5s 首超时取消」

136 号 P4 假设：AV 接管使单笔回写 >5s → 首超时 `IoCancelIrp` → `STATUS_CANCELLED`。本次数据不支持：

- D: attach 于 `03:41:08.883`；5 条 FLUSH IRP 失败在 `03:41:10.264 … 13.015`，即 attach 后 **1.38–4.13s**；整段 e5 从 attach 到 detach 仅 **4.2s**，**不足一个 5s 步进**。
- 结论：失败是**快速返回**（立即错误或回调早退），不是同步 I/O 超时。136 号的 P4 方向需改写为"先确认回写是否真的发起"。

### 4.3 下一步取证（需重编 + 部署 + 一次重启）

1. `RbWritebackCb` 入口增日志：`ext` 是否 NULL、`Refs/Magic/Removed`、`file_id`、`len`（限流，避免风暴刷环）。
2. `RbSyncIo` 的 enter/complete 各一条诊断（已有 `RbDiagRecord`，但无用户态消费接口；可复用限流日志）。
3. 重演 e5（杀软在位）→ 直接看第一手失败原因，再决定 P4 修法（超时策略 / ext 生命周期 / 其它）。
