## 1. 现状定位（旧判据 = git index 版本，行号以 `git show :tests/core/test_race1106.c` 为准）

### 1a) 30s 时点快照与退出码

| 位置 | 行号（旧） | 行号（新工作树） | 内容 |
|---|---|---|---|
| 固定等待 | 503 | 510 | `Sleep(30000);` |
| 快照 | 504 | 511 | `f_err0 = g_f_err; c_err0 = g_churn_err;` |
| 停线程 | 505–508 | 512–515 | `g_stop=1` → `Sleep(500)` → `WaitForSingleObject` |
| 退出码决定 | 525–530 | 556–577 | 旧：`if (f_err0 \|\| c_err0) return 2;` 否则 `return 0;` |

**结论**：旧判据的退出码**只由第 504 行那个 30s 时点快照决定**。第 505 行之后发生的任何错误都不影响 `return`。

### 1b) 最终 F 扫描与 `bad` 的去向

| 位置 | 行号（旧） | 行号（新） | 内容 |
|---|---|---|---|
| 最终扫描块 | 511–520 | 518–540 | 逐 64KB 格扫描 F 区并比对 `pat_f(off+k, g_fgen)` |
| 打印 MISMATCH | 519 | 540 | `printf("final F sweep: %s\n", bad ? "MISMATCH" : "clean");` |
| `bad` 的去向 | — | — | **旧版：块结束即离开作用域，`bad` 被完全丢弃，只影响那一行打印。** |

**结论**：旧版 `bad` 是纯打印变量；`[FINAL-F]` 行和 `final F sweep: MISMATCH` 都是**装饰**。`read_like_driver` 返回非 0（miss-plan 溢出）在旧版也不置 `bad`，连打印都没有。

### 1c) `Sleep(30000)` 挡的到底是什么事件

读代码（不是猜）：

- `main` 在第 503 行固定睡 30s，**没有任何 `WaitForSingleObject`/事件/条件变量在等**；线程只在 `g_stop` 置位后退出，而 `g_stop` 正是这 30s 之后才置位。所以它**不是"等某个事件发生"**，而是**人为设定的采样窗口**。
- 窗口内各线程的周期由代码写死：
  - `passthrough_cycler`（mode 0）：`Sleep(2000)` + 150ms 透传窗 → 30s 内约 **14–15 个透传窗**；
  - `trimmer`（mode 0/3/4）：`Sleep(1700)` → 约 **17 轮** TRIM；
  - `relocator`（mode ≥4）：`Sleep(3000)` → 约 **10 轮** 重定位（mode 4 是唯一推进 `g_fgen` 的线程）；
  - `reader`：每轮 `Sleep(1)`，30s 约 2–3 万轮读校验（旧记录 reads≈13–21K）。
- 这是**统计型竞态复现器**：判据要的是"在足够多的 passthrough/TRIM/relocator 窗口交错下都没错"。窗口跑不满，覆盖的周期数就下降，判据强度下降。

> 处置结论见 §5（先测耗时再定），但代码形态已经确定：它挡的是"故意跑满的竞态采样窗口"，不是可观测事件。

## 2. 改动（只动 `tests/core/test_race1106.c`）

判定块结构（新，`main()` 内最终扫描之后）：

```
1) final F sweep          : 逐 64KB 格比对 pat_f(off+k, g_fgen)
                            读失败（miss-plan 溢出）也置 bad
                            -> 打印 cell / off / got / want
2) mode3 专属分支（最先判）: ferr==0 && bad==0 && cerr>0  -> exit 2   (C7 语义原样)
3) 空跑保护                : g_f_reads==0                 -> exit 1   (零证据不许判绿)
4) 真失败                  : bad || ferr || cerr          -> exit 1
                            逐条打印 FAILED assertion + 快照值/增量
5) 否则                     : exit 0
```

与旧版差异（逐条）：

| # | 旧 | 新 | 性质 |
|---|---|---|---|
| 1 | `bad` 只打印，作用域结束即丢弃 | `bad` 直接进 4) | 加牙（本次核心） |
| 2 | 读失败（`read_like_driver` 返回非 0）既不置 bad 也不打印 | 置 `bad` 并打印 `cell/off/read failed` | 加严 |
| 3 | `return 2` 由**任何模式**的快照 `f_err0\|\|c_err0` 触发 | 只有 mode3 的 C7 形态 → 2；其他模式任何非零 → 1 | mode3 语义不变且优先；其他模式的 2 变 1 仍是红色，未弱化 |
| 4 | 快照之后的增量错误完全不可见 | `ferr/cerr` 取终值，并打印 `window_end` 与 `delta` | 加牙 |
| 5 | 无空跑保护 | `g_f_reads==0` → exit 1 | 新增（防"零证据判绿"）；正常量级 1e4，不会误报 |
| 6 | `== RESULT:` 无 mode/gated/delta | 增加 `mode`、`gated`、`f_reads`、`final_bad`、`window_end`、`delta` | 可诊断性 |

`gated=1` 的 mode 0–5 判据口径未改：clean 仍必须是 `f_err=0 && churn_err=0 && final sweep clean`。

## 5. `Sleep(30000)` 处置

### 5.1 实测耗时

| 项 | 实测 |
|---|---|
| Release `test_race1106.exe`（mode 0，`-Target core` 同参数） | **30.8s** |
| ASan `asan_test_race1106.exe` | **30.91s** |
| `-Target core` 总墙钟（改动后） | **288.8s** |
| 单个宿主占 core 总时长 | 30.8 / 288.8 = **10.7%** |
| Release+ASan 两次运行合计 | 61.7s = **21.4%** |
| 其中固定 Sleep 占这对运行时间 | 60.0 / 61.7 = **97%**（其余 1.7s 是线程 join + 4MB 最终扫描） |

### 5.2 它挡的是"事件"还是"采样窗口"——代码判定

- `main()` 在第 510 行固定睡 30s，**没有任何等待原语**（无事件/无 `WaitForSingleObject`
  /无条件变量）；`g_stop` 是睡完之后才置位。所有工作线程只受 `g_stop` 控制。
- 因此它不挡任何"必须发生的事件"，它是**竞态采样预算**。窗口内实际发生的周期数由
  各线程自己的 `Sleep` 决定，实测：
  - mode 0：13 个 passthrough 窗（日志 `[pt-cycle 13]` 为最后一条）；
  - mode 4：9 次 F 重定位（日志 `[reloc 9]` 为最后一条）；
  - mode 3：约 17 轮 TRIM（`Sleep(1700)`，30/1.7≈17.6，代码推定）；
  - 读者：每模式 0.8–2.2 万次成功 F 校验（`f_reads`）。

### 5.3 结论：**不动**，理由

1. **它不是等待事件，改成事件驱动没有对应物**。如果要改成"跑满 N 个周期"，那只是把
   墙钟换成周期计数，代价（每周期 2–3s）不变，却必须新增"线程卡死"的超时兜底，
   复杂度上升而墙钟收益≈0。
2. **缩短它就是任务明令禁止的"缩短竞态窗口换速度"**。每个 passthrough/reloc/TRIM 周期
   是一次独立的竞态触发机会；已知 C7 存量问题的历史复现率只有 2/6（33%），mode 4 的
   discard/commit 竞态也依赖重定位次数。把 30s 砍半 = 触发机会砍半 = 检出概率下降，
   判据变弱，不是变快。
3. **代价占比不足以成为优化点**：单宿主 10.7%、Release+ASan 合计 21.4%，但其中几乎
   全是"必须跑的采样"；真正可压缩的只有 1.7s 的收尾。
4. 反过来说，`-Target core` 里更贵的单点是 33 个宿主 × 2 种构建的编译开销；要提速应
   从那里下手，而不是抽掉竞态测试的采样时间。

## 6. `RUN_FAIL=0` 到底证明了什么（读 `build/build.ps1`）

### 6.1 结论

**`RUN_FAIL=0` = 「66 个已编译的二进制全部被调用过，且全部返回 0」。不是"没跑就跳过"。**
不存在"编译失败被算成 skip"的降级路径。

证据（`build/build.ps1`）：

| 行 | 代码 | 含义 |
|---|---|---|
| 156 | `$hosts = $Manifest.tests.hosts \| Where-Object { $_.suite -eq 'regression' }` | 参与集合 = manifest 的 regression 宿主，当前 33 个 |
| 160 | `if ($h.skip) { "[SKIP] ..."; $skipped++; continue }` | **唯一的 skip 路径**：manifest 里显式写了 `skip` 字段；当前 33 个里 0 个有该字段 |

`asan_*.out` 全部存在且非空（`test_race1106` 两份都有 13 条 `[pt-cycle]`）。

### 6.2 但它不证明的四件事（诚信边界）

1. **10 个非 regression 宿主完全不参与**：`qa` 2 个（`test_counter_seed`、
   `test_bench_policy`）、`bench` 3、`diag` 1、`e2e` 4。它们既不编译也不运行，**也不计入
   `skipped`**。所以 `skipped=0` 只表示"没有 regression 宿主带 skip 字段"，不表示
   "仓库里没有测试被跳过"。`test_race1106` 在被 164 号任务从 `qa` 提升到 `regression`
   之前，就是这 10 个之一——那时 `-Target core` 的 RUN_FAIL=0 与它无关。
2. **exit 0 ≠ 断言真的跑了**：`build.ps1` 只看退出码。一个"启动即 return 0"的宿主是绿的。
   旧版 `test_race1106` 就是活例：打印 `MISMATCH` 仍 exit 0（§4 M1 实证）。本轮加的
   `g_f_reads==0 → exit 1` 只堵住这一个宿主的空跑路径；其它宿主没有同类保护。
3. **计数不是固定期望值**：`compiled=66` 是 manifest 推导出的，不是断言值。若一个宿主
   被从 manifest 删除，构建仍然"全绿"，没有任何东西会发现少了一个测试。
4. **PS 5.1 下还有假红路径**：`$ErrorActionPreference='Stop'` + 原生程序写 stderr 会让
   run 阶段在计数前中止（实测 `test_p0v2` 的 `[init] engine create enter` → EXIT=1，
   205.1s）。这是假红不是假绿，但说明 RUN_FAIL 的语义依赖运行环境（本报告统一
   `pwsh -NoProfile`）。

## 7. 这个测试现在到底证明什么、不证明什么

### ✅ 有真实宿主（真的跑了真东西）

- 链接的是**真实的 `src/core` 引擎**（`cache.c` / `cache_read.c` / `cache_write.c` /
  `cache_flush.c` / `cache_evict.c` / `cache_stats.c`），调用真实 API：
  `rb_read_try_cache` / `rb_read` / `rb_read_commit_gen` / `rb_read_copy_dirty` /
  `rb_write_ex` / `rb_stream_flush` / `rb_stream_invalidate_range` /
  `rb_stream_discard_all` / `rb_stream_view_gen`。
- 真实并发（4 读 + 2 写 + 形状线程），真实 Windows 线程调度；读者每轮都是逐字节比对，
  F 区还做了 1ms 后重读的"持久化"判别。
- 真实回写落盘：`writeback` 回调把脏块写进 64MB 模拟盘，`readback` 从盘读回。
- 判据真的会红：§4 的两个变异都让新判据 exit 1，并报出正确格子/断言。

### ⚠️ 部分（是模型，不是真路径）

- **panic passthrough 是模拟的**：驱动在 panic 窗口把所有 IO 直接下发；测试用
  `g_passthrough` + 直接写 `g_disk` 表达，没有 IRP/分发例程参与。
- **TRIM 的数据正确性没有被验证**：`trimmer` 只零化/失效 `TRIMV` 区
  （[32MB,40MB)），而两个读者只校验 F 区与 CHURN 区，**没有任何读者读 TRIMV**。
  因此 TRIM 在本测试里只作为"视图失效/世代推进"的扰动源存在。
- **重定位撕裂读按设计不检**：`relocator` 期间 `g_relocating=1`，读者整段跳过验证
  （测试声明这是应用级独占的合法窗口）。所以"读到半新半旧 F"这一类错误不会被本测试发现。
- **mode 3 的 exit 2 是"已知不稳定"而不是通过**：C7 存量时序敏感，历史 2/6 复现；
  本轮 6 次矩阵里没复现（churn_err=0）。它仍然是红色信号，只是不与新判据合并。

### ❌ 仍无（不能由本测试下结论）

- **无内核驱动 / 无真实卷 / 无 IRP、IOCTL、缓存管理器交互**：驱动层结论不能由本测试给出。
- **无真实应用形状**：没有微信进程、没有 DLL 加载器、没有文件系统元数据钩子。
- **mode 0–5 矩阵不自动化**：`-Target core` 只跑 mode 0（无参数、gated=1）；其余 5 个
  模式靠人工按 §3.1 跑。矩阵不进 RUN_FAIL。
- **无 gated=0 阳性对照自动化**（修复前语义的 A/B 只在人工流程里）。
- **无法区分"缓存污染"与"模拟盘被改"**：最终扫描只报第一处 mismatch 的 off/got/want，
  没有磁盘真值对照（`g_disk` 在同一进程里可读，但当前没有打印）。
- **没有每模式的最小活动量断言**（只加了全局 `f_reads>0` 的空跑保护；不校验
  passthrough/reloc 周期数是否达到预期）。
