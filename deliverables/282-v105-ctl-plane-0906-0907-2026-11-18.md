## 2. 关键改动（逐文件）

### 2.1 `src/driver/rb_common2.h`（13,437 → **16,792 B**，223 → 274 行，无 BOM + LF）

```c
#define RB2_FUNC_SHUTDOWN_DIAG  0x906U
#define RB2_FUNC_HEALTH_COMMIT  0x907U
#define IOCTL_RB2_SHUTDOWN_DIAG  CTL_CODE(FILE_DEVICE_UNKNOWN, RB2_FUNC_SHUTDOWN_DIAG, METHOD_BUFFERED, FILE_ANY_ACCESS)
#define IOCTL_RB2_HEALTH_COMMIT  CTL_CODE(FILE_DEVICE_UNKNOWN, RB2_FUNC_HEALTH_COMMIT, METHOD_BUFFERED, FILE_WRITE_ACCESS)
#define RB2_IOCTL_SHUTDOWN_DIAG  IOCTL_RB2_SHUTDOWN_DIAG   /* 旧惯例别名 */
#define RB2_IOCTL_HEALTH_COMMIT  IOCTL_RB2_HEALTH_COMMIT
```

`RB2_SHUTDOWN_DIAG_OUT` 严格按文档定义：`StructSize / BootEpochLo32 / ShutdownPersistWhy /
PersistSkipReason / BootFailCount / BootLoopGuard / Reserved[3]` = **24 B**，并加编译期断言：

```c
typedef char RB2_SHUTDOWN_DIAG_OUT_IS_24_BYTES[(sizeof(RB2_SHUTDOWN_DIAG_OUT) == 24) ? 1 : -1];
```

**为什么加断言**：改字段却忘同步 ctl 副本时，24 B 不变而偏移全错 —— 读到的是别人的值
（表现为「守护态莫名消失」）。让它在编译期炸，而不是在真机上猜。

**为什么留 `RB2_IOCTL_*` 别名**：文档用 `IOCTL_RB2_*`，本仓惯例是 `RB2_IOCTL_*`。
两组同名同值，避免「文档抄的符号在源码里搜不到」这类转述漂移。**但承载 `CTL_CODE` 的
名字必须两侧逐字相同** —— 见 §4.1 的 Gate17 教训。

### 2.2 `src/driver/rbctl.c`（66,069 → **72,122 B**，1,161 → 1,274 行，BOM + CRLF）

新增两个处理器 + 三个接入点：

1. **`RbCtlShutdownDiag(PIRP, outLen)`** — 只读：
   - `BootEpochLo32 = (ULONG)((ULONG64)g_RbBootEpoch & 0xFFFFFFFF)`；
   - `why / skip` 从 `Parameters\ShutdownPersistWhy` / `PersistSkipReason` 读（`Rb2GetDW`，
     `def` 就是 `0xFF` / `0xFFFFFFFF`）；
   - **缺键不补零**：`WHY_CLEAN` 也是 0，与「键不存在」同值，猜一个就等于凭空造出一条 CLEAN 证据；
   - `BootFailCount` / `BootLoopGuard` 取内存值（不是注册表快照）。
2. **`RbCtlHealthCommit()`** — 显式人审清零，四道纪律：
   - 前置拒绝：`RbPanicActive()` → `STATUS_DEVICE_NOT_READY`（熔断走 panic-clear 的自愈握手）；
   - 前置拒绝：`RbShutdownPersistInFlight()` → `STATUS_DEVICE_BUSY`（落盘在途，状态正被改写）；
   - **先留证再清零**：`HealthCommitPrevFails` / `HealthCommitPrevGuard` / `HealthCommitEpoch`
     三个键先落盘，再清 `BootFailCount` / `BootLoopGuard`；
   - **回读确认**：`RbRegSetDW` 是 `VOID`（失败只记日志），清完必须 `Rb2GetDW` 读到 0，
     否则返回 `STATUS_UNSUCCESSFUL` —— 不核对就宣布成功，下一轮引导仍按 `fails>=2` 拒绝挂载，
     那就是一条假成功（A4-d 要根除的正是这种东西）；
   - `HealthCommitSeq` **最后**推进：它是「已完整执行」的完成标记，提前写就等于谎报。
3. **分派**：放在特性层转发块**之前**，各自 `return`（`RbFeatDispatch` 内部自行完成 IRP，
   两处都走会混层）。
4. **重建窗口门**：把 `0x907` 与 `BOOTCFG`/`EXCLUDE` 同门拒（状态变更类）；`0x906` 只读放行。

清零写点仍然只有两处：既有 `panic-clear` 与本函数。`RbRegSetClean` 内**没有**复活副作用。

### 2.3 `src/ctl/rbfeatctl.c`（25,158 → **32,192 B**，489 → 619 行，无 BOM + CRLF）

- `SHUTDIAG` 手工副本（与驱动同序同型，24 B）；
- `WhyText()` / `SkipText()` 两张码表（`0..7 + 0xFF` / `1..9 + NONE`，另允许 `0=unset`）；
- 子命令 **`shutdiag [-json]`**：只透出原值 + 码名，**不做判决**（判决唯一实现是

- 子命令 **`health-commit --yes`**：`0x906` 前读 → 无 `--yes` 拒（rc=2）→ 本来就干净则
  no-op 不写键 → 发 `0x907` → **再读一次回读验证**（工具自己也做闭环，不只信驱动返回值）。

## 4. 设计取舍（文档没规定、我按项目纪律定下的，全部明示）

### 4.1 承载 `CTL_CODE` 的符号名必须两侧逐字相同

第一版按「文档名 `IOCTL_RB2_*` + 仓内名 `RB2_IOCTL_*` 双名」写，**Gate17 立刻红**：

```
[FAIL] 撞号: DeviceType=0x22 Function=0x906 被 2 个不同符号占用
       (IOCTL_RB2_SHUTDOWN_DIAG@rb_common2.h:81, RB2_IOCTL_SHUTDOWN_DIAG@rbfeatctl.c:32)
```

Gate17 按 `(DeviceType, Function)` 分组，它**无从知道**两个名字是同一个 IOCTL。
结论：`CTL_CODE` 由 `IOCTL_RB2_*` 承载（两侧同名），`RB2_IOCTL_*` 降级为纯文本别名。
这不是妥协 —— 「同一个 IOCTL 两个名字」本身就值得被门禁喊一次。

### 4.2 `check_proto_sync` 走豁免而不是补 C# 镜像

`check_proto_sync --strict` 的硬规矩是「新增结构不许静默放过」。三条路：

1. 补 `DriverService.cs` 镜像 —— **超出文档范围**（§3.1 只要控制面，WPF 至今没有 0x906 消费者）；
2. 塞进 `ABI2_TABLES` —— 该表只能表达 C↔C#，而本结构的第二份副本是 **C**（`rbfeatctl.c`）；
3. **登记 `ABI2_EXEMPT` + 写明「谁在比它」** —— 选了这条。

豁免理由里写清了：C↔C 对由 Gate25 P5 逐字段/偏移/24 B 比对；**将来若加 C# 镜像，必须从
豁免转登记到 `ABI2_TABLES`**，否则 C# 侧漂移不在任何门禁视野内。门禁本身也有存在性校验
（登记项必须真实存在），不会变成死条目。

### 4.3 页面级判断：为什么 `0x906/0x907` 落在 `rbctl.c` 而不是 `RbFeatDispatch`

它们读写的是**引导与关机状态**（`g_RbBootEpoch` / `BootFailCount` / `BootLoopGuard` /
`Parameters` 的 why+skip），不是 `Features\Flags` 特性位。塞进特性层会让关机语义挂在
「特性开关」上，与 Gate24 对 `rbmsg.c` / `rbfeat.c` 的钉法互相污染。

### 4.4 幂等 no-op 不写键

本来 `fails==0 && guard==0` 时直接返回成功，**不写任何键、不推进 `HealthCommitSeq`**。
否则「人审覆盖」的证据会被日常无意义调用冲淡，`Seq` 也就不再是「发生过一次真实覆盖」的凭据。

### 4.5 登记一条既有语义（不改）

`panic-clear` 只写注册表 `BootFailCount=0`，**不清 `g_Rb.BootFailCount`**（内存值留到下次
引导覆盖）。所以 Gate25 的赋值点分布是 `{rbdriver:1, rbctl:1}` 而不是 `{…, rbctl:2}` ——
这个差值是被登记的语义，不是漏数。

## 5. 未落地三项：阻断原因（不是没做，是前置缺失）

### 5.1 §3.2 排序 2 —— 缺 `BootEpochPrev` 这个锚

文档要求「`rec2[4]`（epoch32）必须严格等于**上一引导**的 `BootEpochLo32`」。实测：

- 哨兵 `'RBD4'` 的 `rec2[4]` 确实带 `g_RbBootEpoch` 低 32 位（`rbmsg.c:395` 区段）；
- **但「上一引导的 epoch」在用户态不可得**：`g_RbBootEpoch` 是**当前**引导的值，
  `Parameters` 下没有 `BootEpochPrev` 之类的键（`RbBootFailLoad` 只抄 `ShutdownPersistWhyPrev`
  与 `PersistSkipReasonPrev` 两个）。
- 要落这条判据，必须在 `RbBootFailLoad` 里新增一个纪元键 —— 而该函数体被 Gate24 逐坐标钉着
  （`*Prev` 先抄再复位、`BootLoopGuard = (fails >= 2)`、A4 门、宽限首启）。改它属于内核语义
  变更，按纪律需要独立决策记录 + 三路红队，不能顺手带进控制面批次。

**结论**：`R-b2`（旧对自洽假绿）与 `R-d`（成对读数无 epoch）**仍然成立**，本轮没有削弱也没有
扩大它们。`0x906` 只是把 `BootEpochLo32` 变成**可被外部读到**，为将来那条交叉校验准备了原料。

### 5.2 §3.3 排序 3 —— 需要 1 次电源循环，且本轮没改关机路径

`rbmsg.c` 一个字节没动，所以真机预期不变：`Why=0xFF` / `Skip=0xFFFFFFFF` ⇒ `SUP01-VERDICT:
NO_EVIDENCE`。**本轮不消耗电源预算**（`D-08` 只剩 4 次，A4-d 已用 1 次）。

### 5.3 §3.4 排序 4/5 —— 索引版本化迁移未做

`RB2_L2IDX_MAX` 262,144 → 1,048,576 会改变 `RbL2HashWith(blk, slots)` 的取模掩码，
磁盘上既有 `RAMBoostL2c.idx` 的槽位映射全部失效。文档要求「同步升级 `.idx` 头 Magic 版本号 +
`RbL2IdxLoad` 检测到旧版本即丢弃重建」；`RbL2DropRange` 还要同步改 `check_l2_contract.py`
的断言 D 并给出零漏槽证明。这是独立一件，且失败面在内核数据路径（错 = 返回错误卷数据）。

## 7. 不可宣称清单（写在最前，也写在最后）

1. **`0x906` / `0x907` 从未在真机上执行过一次**。E1 = 编译 + 静态门禁，仅此。
2. **不得称「V10.5 已落地」**：只落了排序 1（§3.1），排序 2–5 全部未落。
3. **不得称「BootLoopGuard 现在可以安全解除」**：`health-commit` 的三道前置拒绝、回读确认、
   `Seq` 完成标记都只在源码里成立；真机一次没跑过。且按设计，**已挂载卷不受影响，
   守护态对 attach 的封锁要重启后才解除**。
4. **不得称「门禁 27 条 = 质量达标」**：Gate25 只覆盖 `rb_common2.h` 家族的控制码 + 白名单
   写点；`ioctl` 语义正确性、并发、真机行为都不在它的射程内（它也没声称覆盖）。
5. **不得称「A4-d 已被证实」**：本轮没碰关机路径，`SUP-01` 仍 `NO_EVIDENCE`。
6. **不得称「`R-b2`/`R-d` 已修」**：`0x906` 只是把 epoch 暴露出来，交叉校验还没写（§5.1）。
