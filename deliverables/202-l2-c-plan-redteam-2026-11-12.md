## §1 201 断言是否成立：索引层真的完全支持任意 `blk`？

201 §1.1 断言「索引层完全支持任意 `blk → 0..s_Slots-1` 的映射」，§1.3 断言「索引格式不变」。**逐条核 5 个子项**：

```c
:47  typedef struct _RB2_L2E     { ULONG64 Lba; ULONG Stamp; ULONG Use; } RB2_L2E;        /* 内存项 16B */
:49  typedef struct _RB2_L2IDX_E { ULONG64 Lba; ULONG Stamp; ULONG Slot; } RB2_L2IDX_E;  /* 落盘项 16B */
:45  #define RB2_L2IDX_MAX   262144
:68  static PVOID   s_Idx; static ULONG s_Slots, s_Stamp;
:145 #define RB2_L2HASH_MUL  2654435761ull
:147 static ULONG RbL2Hash(ULONG64 blk) { return (ULONG)((blk * RB2_L2HASH_MUL) % s_Slots); }
:707 s_Slots = (ULONG)(((ULONG64)s_SizeGB << 30) / RB2_L2REC);      /* RB2_L2REC=65560, :43 */
:760 s_Idx = Rb2Alloc((SIZE_T)s_Slots * sizeof(RB2_L2E));           /* :759-761 */
```

**(1) `s_Idx` 大小** — `:760` 按 **`s_Slots`**（槽数）分配，不是按卷 LBA。`2GB→32756×16B=512KB`，`32GB→524096×16B=8.4MB`。数组下标是**哈希槽**，与 `blk` 无直接关系。⇒ 索引层**结构上**支持任意 `blk`。✅

**(2) `RbL2Hash` 取模** — `:147` 对 `s_Slots` 取模，结果恒 `< s_Slots`。`blk * MUL` 是 ULONG64 乘法，即便极端 `blk` 使乘积回绕，`% s_Slots` 的结果仍 `< s_Slots`（取模的商余性质，与乘法是否溢出无关）；`RB2_L2IDX_MAX`/`s_Slots` 都 `< 2^32`，`(ULONG)` 转换无损。⇒ 哈希槽恒有界。✅

**(3) `IdxLoad` 的 `h.SlotCount == s_Slots` 校验** —

```c
:292     h.Magic != RB2_IDX_MAGIC || h.Build != RB_DRIVER_BUILD ||
:293     h.SlotCount != s_Slots || h.Count == 0 || h.Count > RB2_L2IDX_MAX ||
:296     h.VolId != InterlockedOr64(&s_VolId, 0) ||
:308     (h.BootSeq != s_BootSeq && h.BootSeq + 1 != s_BootSeq))
:309     return;                                    /* 任何不符 -> 空索引，安全 */
```
C 方案**不改 `:707` 的 `s_Slots` 公式、不改容器大小**，所以 `SlotCount` 维度跨新旧不变，该校验仍适用。✅ 但注意：它**保证不了**新旧容器布局一致（见 §5）——`SlotCount` 相同而「哪个 blk 放哪个槽」变了，正是本次格式变更的内容，校验对它是盲的。

**(4) `RB2_L2IDX_MAX=262144` 钳位** —

```c
:439 for (i = 0; i < s_Slots; i++) if (L2Idx()[i].Use) used++;
:445 if (used > RB2_L2IDX_MAX) { ...; used = RB2_L2IDX_MAX; }
:458 for (i = 0; i < s_Slots && n < used; i++)
:459     if (L2Idx()[i].Use) {
:460         es[n].Lba = L2Idx()[i].Lba; es[n].Stamp = L2Idx()[i].Stamp; es[n].Slot = i; n++;
:461     }
```
钳位仍安全（`Count ≤ MAX`，`:293` 不拒）。**但语义变了**：直接寻址时代 `i == blk`，截断 `:458` 丢的是「槽号 ≥ 阈值」= 卷前 16GB 之后的块；C 方案后 `i = Hash(blk)`，截断丢的是「**哈希槽号大**」的条目，对应**随机分布的高 LBA 热块**，不是卷后段。⇒ 32GB 默认配置下，持久化索引随机少一半热块，每次引导这部分必 MISS。功能退化（安全），201 号未提，须写进 202。

**(5) `es[k].Slot` 字段的实际用途（201 号含糊处）** —

```c
:319     ULONG slot = RbL2Hash(es[k].Lba >> 16);      /* 重算，不读 es[k].Slot */
:320     if (slot < s_Slots && !L2Idx()[slot].Use) {
:321         L2Idx()[slot].Lba = es[k].Lba; L2Idx()[slot].Stamp = es[k].Stamp;
:322         L2Idx()[slot].Use = 1;
:323     }
```
**结论：`Slot` 是「写而不读」的死字段。** `:460` 写入 `i`（内存槽号），`:319` 完全忽略它、用 `RbL2Hash(Lba>>16)` 重算。两者恒等**当且仅当**不变式 `slot == Hash(blk)` 成立：
- Store `:1065–1066` `i = RbL2Hash(blk)`、容器偏移也将改成 `Hash(blk)` ⇒ `IdxSave` 的 `es[n].Slot = i = Hash(blk)`；
- `IdxLoad` 的 `Hash(es[k].Lba>>16) = Hash(blk)` = `i`。⇒ **直映射下自洽**。

**⇒ 201「索引格式不用改」是【有条件成立】**：条件 = **锁死直映射**（不改 `:145` 乘数、不改 `RbL2Hash`、不引入线性探测/2 路组相联）。201 §1.4 风险 1 自己提出了「是否引入 2 路组相联或线性探测」——**一旦选它，`slot ≠ Hash(blk)`，`:319` 的还原会把条目放错槽，与容器记录系统性错位** ⇒ 那时**必须**改 `IdxLoad` 去读 `es[k].Slot`（= 动索引语义 + 重走 magic 作废）。201 把「不用改索引格式」写成无条件结论，是本次审查要补的第一条硬约束。

**【增补 · 主线程同步 2026-11-12】`IdxLoad :320 !Use` 会不会丢条目 / `h.Count`+CRC 是否仍自洽**（主线程问题②，纳入 §1/§2 证据）：

```c
:320 if (slot < s_Slots && !L2Idx()[slot].Use) { ... }
:450 h.SlotCount = s_Slots; h.Count = used;
:462 h.Crc = RbCrc32(es, n * sizeof(RB2_L2IDX_E));
:313 h.Crc == RbCrc32(es, h.Count * sizeof(RB2_L2IDX_E))
```
- **直映射不变式下不会丢条目**。`IdxSave :458–460` 每个内存槽 `i` 最多写一条 `es[n]`；Store `:1065–1066` 保证 `i == Hash(blk)`，故 `es[k].Lba>>16` 的还原 = `Hash(blk)` = `i`，**任意两条 `es` 的还原槽互不相同** ⇒ `:320 !Use` 在合法往返里**永不触发**。「冲突时被覆盖的旧条目」**根本不在内存索引里**（`:1066` 直接覆盖 `idx[i]`，旧 `Lba` 已丢），`IdxSave` 不会写出「两条同槽」的条目 ⇒ **不存在「重启后因 `!Use` 只保留第一个而丢条目」**。
- **`h.Count` / CRC 恒自洽**。`h.Count = used`（`:450`）、CRC 对**整个 `es` 数组**算（`:462`），`IdxLoad :313` 用 `h.Count*sizeof` 重算比对；即便 `:320` 因伪造/损坏索引注入「两条同槽 Lba」而丢弃后一条，**CRC 在丢弃之前已完成且与丢弃无关** ⇒ 不会整份拒绝，只少一条内存条目（安全 MISS）。J12 钳位（`:445–448` 截断 `used` 到 `MAX`）同理：`h.Count` 与 CRC 对截断后数组算，仍自洽。
- **但 `:320 !Use` 是「直映射不变式」的又一处隐性依赖**：若 v2 引入探测/组相联（`slot ≠ Hash(blk)`），`IdxSave` 的 `es[n].Slot = i`（真实槽）被 `IdxLoad` 忽略、仍用 `Hash` 重算 ⇒ 多条 `es` 重算到同一槽 ⇒ `:320 !Use` **大量静默丢弃**，重启后索引条目系统性丢失、命中率坍塌，而 CRC 仍自洽**不会报错**。⇒ 再次印证 P1-1「锁死直映射」不是可选优化，是跨引导一致性的硬约束（§1(5)/§2）。

> **§1 判定：需补守卫（有条件成立）。** 没有任何一处仍隐含 `blk < s_Slots`（前 4 项全过），但第 5 项暴露「不变式未被文档化、未被约束」，且它是 §2/§5/§10 的总闸门。主线程同步的 `IdxSave :459–460` / `IdxLoad :319` 现取与本报告 §1(5) 完全一致：`es[k].Slot` 写而不读、`IdxLoad` 靠哈希还原；只要「容器内记录也放在 `slot = RbL2Hash(blk)`」，`i` 与还原恒等 ⇒ **索引格式确实不用改**，但以上述直映射不变式为前提。

## §2 哈希冲突的正确性（最危险项）

`M = 2654435761`，`s_Slots` 非 2 的幂（`2GB→32756 = 2²×19×431`；`32GB→524096 = 2¹⁹`）。先给结论：**读侧不会给错数据**，但**命中率与可用性会塌**，且现有三重校验是唯一防线。

**(a) 冲突是常态，不是边缘**。改哈希槽后，不同 `blk` 争用同一槽。生日界：热块数达 `≈√(2·32756·ln2) ≈ 213` 时即有 50% 概率至少一次冲突；缓存接近满时鸽巢原理**保证**冲突。而 C 方案的目标正是「缓存任意 LBA 的热块」——热块集合往往远超 `√s_Slots`。201 §1.4 风险 1 说「随机冲突会导致热块互相驱逐」是对的，但把它列为「评估项」而非「v1 必须接受并观测的已知退化」是低估。

**(b) Store 覆盖写 + 读侧 MISS 推演（安全）**。设 `Hash(A)=Hash(B)=S`：

```c
:1059 NTSTATUS stw = RbL2Io(s_File, TRUE, 4096 + blk * RB2_L2REC, rec, RB2_L2REC);  /* 待改为 slot */
:1065     i = RbL2Hash(blk); idx = L2Idx();
:1066     idx[i].Lba = blk << 16; idx[i].Stamp = rec->Stamp; idx[i].Use = 1;
:944 i = RbL2Hash(blk); idx = L2Idx();
:945 return (idx[i].Use && idx[i].Lba == (blk << 16)) ? TRUE : FALSE;
:984     rec->Lba == (blk << 16) &&                 /* 记录头校验 */
:985     rec->VolId == InterlockedOr64(&s_VolId, 0) &&
:986     rec->Crc == RbCrc32(rec + 1, RB2_L2BLK))
```

| 步骤 | 状态 |
|---|---|
| Store(A) | 容器 `S` 写 A（`rec.Lba=A<<16`）；`idx[S]={Lba=A<<16,Use=1}` |
| Store(B) 同槽 | 容器 `S` **覆盖**写 B（`rec.Lba=B<<16`）；`:1066` 直接把 `idx[S]` 覆盖成 B |
| 读 A | `:945` `idx[S].Lba == A<<16`？现为 `B<<16` → **FALSE → MISS 下盘**（安全） |
| 读 B | `:945` TRUE → 读容器 `S` → `:984 rec.Lba==B<<16` ✓ / `:985 VolId` ✓ / `:986 Crc` ✓ → 返回 B 数据 |

⇒ `RbL2IdxProbe` 的 Lba 比对**先挡一道**，`rec->Lba` **再挡一道**。**201 §1.3「Store 覆盖时旧记录作废属正常淘汰语义」这点成立**：不会把 B 的数据当 A 返回。

**(c) `rec->VolId` / `rec->Crc` 的挡错能力（逐条）**：
- `rec->Crc`：`:1056` 对 `rec+1` 的 64KB 数据算 CRC，`:986` 校验。它只保证「**记录自一致**」——覆盖写是合法写，CRC 必然自洽，**挡不住「本槽属于别的 blk」**；挡「A 请求读到 B 记录」的是 `rec->Lba`，不是 CRC。
- `rec->VolId`：`:1054` 写入、`:985` 比对，防跨卷，**与同卷内哈希冲突无关**。
- `rec->Lba`：`:1053` 写 `blk<<16`、`:984` 比对，**这是唯一区分「本槽是不是本次请求块」的字段**，也是整个 C 方案安全性唯一的最终防线。
- `Stamp`：`:1053` `rec->Stamp = ++s_Stamp`（容器）、`:1066` `idx[i].Stamp`（内存）、`:460` `es[n].Stamp`（落盘）、`:321` 回读——**从头到尾没有任何一处读取或比对它**（`:983–986` 不碰 Stamp）。`s_Stamp` 是 `ULONG`（`:68`），`++` 在 2³² 次 Store 后回绕，但**因无读者，回绕无害**。201/202 不得基于「Stamp 校验链」做任何设计。

**(d) `Slot` 未参与 `IdxLoad` 还原 / `s_Stamp` 溢出会不会错位**：见 §1(5)——直映射下 `Hash(Lba>>16)` 与 `es[k].Slot` 恒等，**不错位**；溢出/死字段均无害。**但这是有条件的**：`IdxLoad :320 if (!L2Idx()[slot].Use) 只填空槽`——若磁盘索引里两条不同 Lba 恰好哈希到同一槽（C 方案下完全可能，因为保存时槽内只有一个 Use 条目，但**截断钳位 `:445–448` 后 `n<used` 的取法 + 冲突遗留**理论上可构造），后一条会被静默丢弃（安全方向）。不成 correctness 问题，但说明 `IdxLoad` 的还原**不校验 `es[k].Slot`**，一旦不变式破，错位不会被发现。

**(e) 并发冲突 Store 竞态（201 号未推演）**。文件头 `:19–22` 说「特性层串行化」，但 `:673` 注释明写「并发 miss（per-CPU worker）」，`s_Ops`（`:100`）是**计数不是锁**，允许多 probe/store 并发持有：
- T1 `Store(A)`：写完容器 `S`（A），尚未执行 `:1066`；
- T2 `Store(B)`（同槽）：写完容器 `S`（B），`idx[S]=B`；
- T1 恢复：`:1066` `idx[S]=A` ⇒ **`idx[S]` 指向 A，容器 `S` 里却是 B 的记录**。
- 读 A：`:945` TRUE → `:984 rec.Lba==B<<16 ≠ A<<16` → **MISS**（安全）；读 B：`:945` FALSE → MISS（本可命中）。

⇒ **内存索引与容器记录之间没有任何原子性/锁保护**，「写盘成功后才更新索引」的顺序在冲突下仍 correctness-safe，**全靠 `rec->Lba` 单点兜底**。201 号把这点轻描淡写成「回读 `rec->Lba` 校验会挡住」——对，但必须在 202 里把它**升格为不变式**：任何后续改动（组相联、批量写、异步 IO）都不得移除 `:984` 的 `rec->Lba` 比对。

**(f) thrashing**。A、B 同槽且都热 ⇒ 每次 miss 后回填 Store 又驱逐对方 ⇒ 互相乒乓驱逐、命中率趋近 0、产生大量无用 64KB 容器写 IO。**v1 若采用「简单覆盖」必须接受并观测**（新增冲突计数），且**不能拿 `l2s>0`（`Rb2Count(8)`）当成功判据**——写进去了但读不出来，`L2Hits`（`Rb2Count(7)`）上不去。

> **§2 判定：需补守卫。** correctness-safe（无错数据），但 201 低估了「冲突即常态」的可用性后果；任何冲突缓解策略都会打破 §1(5) 的直映射不变式 ⇒ 与「索引格式不用改」直接冲突，必须在 202 里显式二选一并写死。

## §3 越界保护回归（删 `:976` 门）

```c
:973  /* [FIX R6-08] 与 Store 的 [F4] 守卫对称：损坏/伪造的索引文件可注入越界键
:974   * （IdxLoad 只校验 slot<s_Slots，不校验 Lba>>16<s_Slots）。探测读偏移
:975   * 4096+blk*RB2_L2REC 在极端 blk 下 64 位乘加可回绕成小偏移。 */
:976  if (blk >= s_Slots) goto cleanup;
:982  st = RbL2Io(s_File, FALSE, 4096 + blk * RB2_L2REC, rec, RB2_L2REC);
:1045 if (blk >= s_Slots) { ... "store rejected (out of window)" ...; goto cleanup; }
:1059 NTSTATUS stw = RbL2Io(s_File, TRUE, 4096 + blk * RB2_L2REC, rec, RB2_L2REC);
```

**(a) R6-08 的原意**：`IdxLoad :319–323` 从磁盘读 `es[k].Lba`，只校验 `slot < s_Slots`（`:320`），**不校验 `Lba>>16 < s_Slots`**（`:974` 注释自承）。伪造/损坏索引可注入极大 `Lba` 进内存索引，探针在「Lba 恰好匹配」时会用 `4096 + blk*REC` 算出回绕后的小偏移，读到容器内任意位置。删门后若偏移改成 `4096 + slot*REC` 且 `slot = Hash(blk) < s_Slots`：
- `slot` 恒 `< s_Slots`（§1(2)），`4096 + slot*65560` 最大 `≈3.4×10¹⁰`（`s_Slots≤524096`），**远小于 2⁶⁴，不回绕**；
- 偏移恒落在 `[4096, 4096+s_Slots*REC)` 容器内，**物理上不可能越界**。
⇒ **R6-08 的 64 位乘加回绕风险被哈希取模结构性消除**，201 §1.4 风险 4 的判断成立。✅

**(b) 但删门引入新的、更严重的蓝屏风险 —— `% 0` / `#DE`**。这是本报告认定「有致命漏洞」的核心：

```c

:886     s_Slots = 0;                                    /* RbL2CloseIntEx 关闭末尾 */
```
`RbL2Hash` 读**全局** `s_Slots` 做除数。**现有代码的全部调用点都有非零保护**：
- `RbL2IdxProbe :943` `if (!s_Idx || !s_Slots) return FALSE;`
- `RbL2IdxLoad :284` `if (!s_IdxFile || !s_Idx || !s_Slots) return;`（`:293` 之前）

**而 `:976` / `:1045` 两道门在 `s_Slots==0` 时 `blk >= 0` 恒真 → 全部 `goto cleanup` → 现有 ProbeFill/Store 从不调用 `RbL2Hash`**。删门后，作者必然要在 `:982` / `:1059` 之前新增一次 `slot = RbL2Hash(blk)` 计算（或把 `Hash(blk)` 塞进偏移表达式）。**若这次新增计算沿用 `RbL2Hash`（读全局）而不照抄 `DropRange` 的局部快照 + `!slots` 守卫**，则存在一条窗口：控制面 `RbL2CloseIntEx` 在 `:884` 先 `InterlockedExchangePointer(&s_Idx,NULL)`、`:886` 再 `s_Slots=0`；数据路径虽持 `s_Ops`（`:964`/`:1037`）且 Close 先 drain（`:851`），但 `RbL2Hash` 与 `RbL2IdxProbe` 的**先后**取决于作者把计算放哪——若放在 `:976` 原位置（删门后的自然写法），就在 `:978 RbL2IdxProbe`（唯一带 `!s_Slots` 保护处）**之前**，保护失效 ⇒ `% 0` ⇒ x64 `#DE` ⇒ **内核 BugCheck 蓝屏**（不是 MISS、不是可捕获异常）。

## §4 `RbL2DropRange` 边界

```c
:158 VOID RbL2DropRange(ULONG64 off, ULONG64 len)
:168     InterlockedIncrement(&s_Ops);
:172     if (s_Halt) goto cleanup;
:173     InterlockedIncrement64(&s_Gen);
:176     slots = s_Slots;
:177     if (!s_Idx || !slots) goto cleanup;
:179     end = (off > (ULONG64)-1 - len) ? (ULONG64)-1 : off + len;
:180     b0 = off >> 16; b1 = (end >> 16) + ((end & 0xFFFF) ? 1 : 0);
:181     if (b1 > slots) b1 = slots;                    /* ★ 钳到容量：越界块天然无条目 */
:182     for (b = b0; b < b1; b++) {
:183         i = (ULONG)((b * RB2_L2HASH_MUL) % slots);
:184         if (L2Idx()[i].Use && L2Idx()[i].Lba == (b << 16)) L2Idx()[i].Use = 0;
:185     }
:187     InterlockedDecrement(&s_Ops);
```

**(a) `:181` 钳位在 C 方案下是 correctness bug，不只是性能**。201 §1.3/§1.4 风险 3 都把它当「遍历边界/循环爆炸」处理，**漏了更严重的一面**：
- 直接寻址时代 `blk == 槽号`，`b > slots` 的块天然没有容器记录，钳位是对的。
- C 方案后 `blk` 是**任意卷 LBA**（可 `≫ slots`，真机 `blk_min` 57343 / 1030317，`slots=32756`），条目落在 `Hash(blk) ∈ [0,slots)`。**`:181` 把遍历上限钳到 `slots`，意味着块号 `b ≥ slots` 的失效请求根本不进入循环** ⇒ 高 LBA 块被写后，其 `idx[Hash(b)].Use` **永不被清** ⇒ 探针继续命中旧记录 ⇒ **静默返回写前陈旧数据**。这是给错数据，不是「多丢一次 Store」。

**(b) 去掉钳位后的循环爆炸（201 §1.4 风险 3 的部分，成立）**。`b0..b1` 是**块号区间**，不是槽号区间。931GB 卷、`off=0, len=全卷` ⇒ `b1-b0 ≈ 931×2³⁰/2¹⁶ ≈ 1420 万` 次迭代，每次 `64 位乘 + 取模 + 两次非分页池访问`。发生在**写完成路径（`rbio_worker.c` / PASSIVE）且全程持 `s_Ops`（`:168`）**：
- 不持 spinlock（`:153` 纪律），故**不是 0x7B 硬死锁**；但 `:851` 的 `RbL2CloseIntEx` drain 是「10ms 步进、5s 上限」，长时间持 `s_Ops` ⇒ Close 走 `:853` leak-by-design（不关成、留待下 tick），叠加 `:107` `s_Halt` 单向闩风险（J17）；
- 该 I/O worker 被独占数百 ms~数秒，写完成路径堆积；`RbL2DropAll :200` 的 `RtlZeroMemory(8.4MB)` 反而是 O(slots) 常数时间，不构成此问题。
- 201 号自己也承认需「按槽数上界而非块号上界限制，或改为遍历槽表反查 Lba」——方向对，但没给可落地的判据。

**(c) 安全替代（必须写进 202）**：**遍历槽表反查 Lba**，O(slots) 常数时间、与 `len` 无关、天然处理哈希冲突、不持锁、持 `s_Ops` 时间有界：
```
lo = off & ~0xFFFFull;                 /* 区间首块首字节（64KB 对齐） */
hi = end;                              /* 字节单位，已含跨块尾，:179 钳过溢出 */
for (s = 0; s < slots; s++)
    if (L2Idx()[s].Use && L2Idx()[s].Lba >= lo && L2Idx()[s].Lba < hi)
        L2Idx()[s].Use = 0;
```
要点：① 比较**字节偏移**（`Lba` 存的是 `blk<<16`）而非块号，避开 `b1<<16` 在 `end==(ULONG64)-1` 时的 64 位溢出；② 与哈希无关 ⇒ 冲突/探测/相联都正确；③ 不引入 `b0..b1` 大循环；④ `:173 s_Gen++`、`:187` 配对、`s_Halt` 短路全部保留。
**若坚持按块号遍历，必须设迭代上界**（如 `b1-b0 > slots*4` 时退化为 `RbL2DropAll()`）——但 `DropAll` 会清掉**所有**槽（含区间外热块），是多丢，安全但命中率受损，不如槽表反查。

**(d) `:184` 的 Lba 比对在冲突下是否正确**：✅ 正确。`i=Hash(b)`，只有「槽里恰好是块 b」才清。设槽 S 里是 A、`Hash(B)=S`，drop 覆盖 B：`:184` `Lba==B<<16`？槽里是 A ⇒ 不清（B 本不在缓存）；drop 覆盖 A ⇒ 清（A 在缓存）。**不会误清、不会漏清**——前提是遍历能到那个块号（即 (a) 的钳位必须删）。

> **§4 判定：有致命漏洞。** 201 把 `:181` 当性能边界，实际它是**静默陈旧数据的 correctness bug**；「去掉钳位」又会引入长循环。两条必须一起改（删钳位 + 换遍历策略），只做一半都留缺陷。

**(b) 致命点：格式变更后 `EndOfFile` 不变 ⇒ 整个校验/重建块被跳过**。C 方案只改「哪个 `blk` 的记录放在哪个 `slot`」，**不改** `RB2_L2REC`（`:43`）、**不改**记录结构、**不改** `s_Slots`（`:707`）、**不改**容器大小公式（`:716`/`:749` 仍是 `4096 + s_Slots*RB2_L2REC`）。于是：
- 旧容器（按 `blk` 直接寻址写的）与新容器（按 `Hash(blk)` 写的）**文件大小完全相同、magic 完全相同、build 完全相同、每条记录格式完全相同**；
- `:716` 判据 `EndOfFile != 期望值` 为**假** ⇒ **`if` 整块（`:717–755`）被跳过** ⇒ `:734` 的 `old[0] != RB2_L2_MAGIC` 校验**根本不执行**（它嵌在「大小不符」分支里，注释 `:718` 也写明「截断前校验既有头 magic」——只在截断时校验）；
- ⇒ **换 `RB2_L2_MAGIC` 的值完全无效**：大小相符时没人读 `old[0]`，旧容器被当作新格式**原样复用**。

**(c) 即便强制造「大小不符」，换 magic 也会把 L2 永久 `refused`**。若作者改文件大小公式（如头加大 4B）使 `:716` 为真，代码走 `:732–734`：读到旧容器 `old[0]` = 旧 magic ≠ 新 magic ⇒ `:735–738` **`ZwClose` + `s_State=4` + `return`（拒绝启用）**，不是「截断重建」。`:718` 的设计意图是「防路径冲突误毁他人数据」，所以它**拒绝**而非**覆盖**。结果：老用户盘上只要留着 `RAMBoostL2.bin`，升级后 L2 永久卡在 `refused(4)`，**必须手工删文件**才能启用——与 201 §1.3「旧文件一律截断重建」完全相反。

**(d) 不作废的后果（201 §0 说「按新布局读旧字节」——对，但要说清是哪种错）**：
- **索引文件是独立的 `.idx`**（`:265` `RbL2IdxOpen` 用 `RAMBoostL2.idx`）。`IdxLoad :319` 会把旧 `.idx` 里的 `Lba` 用 `Hash(Lba>>16)` 还原到**新槽**；而旧 `.idx` 记录的是旧方案按 `blk` 直接寻址缓存的块（`blk < s_Slots`），其数据实际躺在旧容器的 `偏移 blk*REC`，**不是** `偏移 Hash(blk)*REC`。⇒ 探针 `idx[Hash(blk)].Lba == blk<<16` 命中 → 读容器 `Hash(blk)*REC` → 那里是旧容器里块号 `Hash(blk)` 的记录（`rec.Lba = Hash(blk)<<16 ≠ blk<<16`）→ `:984` 挡成 **MISS**。
- ⇒ **主后果是「索引与容器物理位置系统性错位 ⇒ 热数据全废、静默冷 MISS」**（安全但违背设计意图）。
- **但不能排除错数据路径**：存在「不动点」`blk == Hash(blk)`。对 `s_Slots=32756`，`M mod 32756 = 145`，条件 `144·blk ≡ 0 (mod 32756)` ⇒ `8189 | blk` ⇒ 窗内不动点 `blk ∈ {0, 8189, 16378, 24567}`；对 `s_Slots=524096`，`M mod 524096 = 413617`，不动点 `32768 | blk`（16 个）。这些块新旧寻址物理位置相同 ⇒ 记录自洽 ⇒ 若旧 `.idx` 通过 `IdxLoad` 的 `BootSeq/VolId/Build` 校验（同盘、同版本、BootSeq 恰好 `s_BootSeq` 或 `s_BootSeq-1`）被加载，就可能**返回上次引导之前的陈旧内容**——正是 **J11 跨引导陈旧命中**的形状。概率低但形状真实，且 C 方案让 store 落盘后 J11 从 dormant 变 live（见 §6）。

**(e) 具体作废方案（201 号要求「给具体的」，三选一，推荐 a）**：
- **(a) 换容器文件名（推荐，最干净）**：`:689` `L"RAMBoostL2.bin"` → 新名（如 `L"RAMBoostL2c.bin"`）。`:692` 是 `FILE_OPEN_IF` ⇒ 新文件从零创建、走 `:716` 大小不符分支、`:722` 写新头、`:749` 定长；旧文件**永不被打开**，天然作废。**代价（必须写进 202 的改动面）**：全仓硬编码 `RAMBoostL2.bin` 的取证/部署/回滚脚本与文档要同步——`RB-l2-p0c-test.ps1`/`.cmd`、`RB-l2-p0c-forensics.cmd`、`RB-l2-observe.ps1`、`188-*.md` runbook、`rbfeatctl` 的 `l2 enable` 提示文案（199 §3.1 引过 `will create X:\RAMBoostL2.bin (N GB)`）；并定义「旧文件留在盘上、不自动删」的清理策略（磁盘占用）。注意 `.idx` 文件名（`:265`/`:397`）与容器名无关，但**仍需连带作废**（见 §9 P0-4）。
- **(b) 利用 `hdr[4]` 的空闲第 4 个 ULONG 作 `LayoutVer`**：`:722` 写 `LayoutVer=2`；在 `:716` 条件里**增加**「读现文件头 `LayoutVer != 2`」判据，让格式不符也进入重建分支；并把 `:734` 拆成两类——`old[0] != RB2_L2_MAGIC` 仍「拒绝启用」（防误毁他人文件），`old[0]==MAGIC && LayoutVer 旧` 则**允许截断重建**（`:743` 写新头 + `:749` 定长）。⚠️ `:743/:749` 只重写 16B 头、**不清空 64KB 记录体** ⇒ 旧记录体残留必须靠「索引作废 + `:984 rec->Lba` 校验」兜底，**必须同步作废 `.idx`**（否则又回到 (d)）。
- **(c) 换 `RB2_L2_MAGIC` 值 + 改文件大小公式**：牵动 `:707/:716/:749` 三处 + 容器语义，**不推荐**。

**(f)【增补 · 主线程同步 2026-11-12】三条现取事实 + 作废方案定案**

**1. 「仅换 magic 值」不是效果弱，是根本不触发**（主线程③，纳入 (b) 的硬证据）。`:714–756` 的「重写头 + 定长」分支**只在 `si.EndOfFile.QuadPart != 4096 + s_Slots*RB2_L2REC`（`:716`）时进入**；旧容器是**同一公式**定长的，换 `RB2_L2_MAGIC` 值后**大小不变 ⇒ 永远走 else**（不读 `old[0]`、不重写头）⇒ 旧布局被当新布局读。⇒ 除非同时改期望长度公式、或**无条件读 magic**，否则换 magic 值**零效果**。这是「推翻 201 §0/§1.3 主要改动」最硬的一条代码证据，202 必须原样收录。

**2. `:734` 只比 magic 不比 Build：是有意，不是漏洞**（主线程①提问）。容器头 `hdr[4]` 带 `RB_DRIVER_BUILD`（`:722` `:86`），索引侧 `:292 h.Build != RB_DRIVER_BUILD` 会整份拒绝；但容器 `:734` 只读 `old[0]`（magic）。**有意**：容器数据正确性不依赖头，而依赖**每条记录的 `rec->Lba` / `rec->VolId` / `rec->Crc` 三重校验**（`:984–986`）；头只作「定长 + 防误删」标记，同 magic（同 v2 记录格式）不同 Build 的容器逐记录读仍安全。索引 `.idx` 是整份加载的内存索引加速器，故需 Build/BootSeq 严格一致，粒度不同。**但这恰是 §5 的又一层盲区**：`MAGIC / BUILD / slots / 0` 四个头字段在「大小相符」时**全都不被读取**（(b)）⇒ 容器头在升级路径上**整体是死字段** ⇒ 「换布局绝不能指望头字段自动识别」，必须靠文件名或无条件读头。

**3. `:53` 注释 / J11 先例：思想可借鉴，实现不能照抄**（主线程①③）。`:53` 与 J11 的既有实践是「索引 v2 加 `BootSeq` ⇒ 换 `RB2_IDX_MAGIC`」，其所以**生效**，是因为 `IdxLoad :284` 之后**无条件读整个头**再逐字段校验（`:292 Magic/Build/SlotCount/Count/VolId/BootSeq`）⇒ 换 magic 立即整份拒绝。而**容器侧 `:734` 的 magic 校验嵌在「大小不符」分支里、不无条件执行** ⇒ 把「换 magic」照抄到容器侧**必然不生效**（(b)/(f)1）。⇒ 可借鉴的是「显式作废 + 换 magic 标记格式代际」的**思想**，**不是**「改一个常量就完事」的**实现**；且 `:734` 的保护是为**防路径冲突误毁他人数据**，**不能简单删掉**（主线程①明确约束）。

**4. 作废方案定案（主线程要求给推荐 + 理由）：推荐「换名」，且容器与 `.idx` 一起换**。
- `:246 RbL2Path(WCHAR* path, ULONG cap, PCWSTR name)` 是显式传名；容器/索引分别在 `:689` / `:265` 传 `L"RAMBoostL2.bin"` / `L"RAMBoostL2.idx"`（主线程③现取）。改 `RAMBoostL3.bin/.idx`（或 `…L2c.*`）⇒ 旧文件**自然孤立**：不被读、不触发 `:734` 的「magic 不符拒绝启用」、不误截断他人数据；`:692 FILE_OPEN_IF` 从零创建新格式。
- **决定性理由**：容器与 `.idx` **同时换名 ⇒ 旧 `.idx` 永不加载**，一次性解决 §9 P0-2「旧 `.idx` 连带作废」——**不需要** `RbL2IdxUnseal()`、不需要换 `RB2_IDX_MAGIC`、不需要新增任何内核作废分支；比 (e)(b) 的「LayoutVer 主动重建」少动 `:714–756` 的全部控制流。
- **不选「无条件读旧 magic 主动重建」(e)(b) 的理由**：它要放宽 `:734`（削弱既有防误删保护）、改 `:716` 判据、新增内核重建分支 + `.idx` 作废分支，且 `:743/:749` 只重写 16B 头、**不清 64KB 记录体**（P1-6 残留）。C 方案本就是内核改动（重编→重签→重启红线，199 §3.3，未过 WDK/Verifier 完整验证），**每多一行内核打开路径逻辑就多一分风险**；换名把作废完全交给既有 `FILE_OPEN_IF` 语义，内核侧只改 2 个字符串字面量，风险最低。
- **代价全部在用户态、可控**：夹具/脚本/文档硬编码同步（见 §9【增补】P0-6），可全量 `grep`、`check_ps_syntax` 静态校验、193 敌意复验，不增加内核签名链风险；另需定义「旧文件留盘不删」的清理策略（2GB 占用）。命名建议用 `…L2c.*`（贴 C 方案）而非 `…L3.*`（易与「L2 特性」层级混淆），二选一即可，**关键是新旧名不同且全仓同步**。

> **§5 判定：有致命漏洞（推翻 201 §0/§1.3 的主要改动）。** 「换 magic 作废重建」在现有 `:714–756` 控制流下**根本不触发**（EOF 相符 ⇒ 不读 magic）或**反效果**（`:734` 拒绝启用(4)）；必须重做作废协议。**定案：容器 + `.idx` 一起换名**（§5(f)4），旧 `.idx` 随换名自动作废（201 号完全没提这个新接口）；`:734` 防误删保护保留不动。当前现场（199/201 §4）「容器/索引全无」恰好**掩盖**了这个缺陷——它只在「升级前已有旧容器」的真机/回退场景触发，属必现的部署级故障。

## §6 J11 / J12 / J17 的连带影响

**(a) J11（跨引导陈旧索引）被放大：从 dormant → live**。199 §4.1 第 2 条与 J.4 明确：J11 是「**让 store 真落盘之后**才能验证的前置项」，本轮 `l2s=0` 既未证实也未证伪。C 方案的**全部目的**就是让 `RbL2Store` 真正写盘（删 `:1045` 门）⇒ 一旦生效，`.idx` 会被 `RbL2IdxSave` 定稿（`:431`），J11 的复现链「引导 A 定稿 → 引导 B `l2 disable` 大量写但不递增 BootSeq → 引导 C 重新启用加载 A 的索引」**首次具备触发条件**。更糟的是 §5(d)：若容器作废没做、旧 `.idx` 与旧容器组合错位，不动点槽会叠加 J11 给出陈旧内容。⇒ 202 必须写明「P1 前是否同步闭合 J11」，或明确「P5 验收不得宣称跨引导正确性、必须在受控引导序列下做内容比对」。**不能沿用 199「本轮未触发」的口径。**

**(b) J12（32GB `s_Slots=524096 > RB2_L2IDX_MAX=262144`）Distribution 语义变，但钳位仍安全**。`IdxSave :439` 遍历 `s_Slots` 统计 `used`；C 方案后「有效条目」不再是卷前段连续块，而是哈希到各槽的任意 LBA 块，`used ≤ s_Slots` 仍成立，`:445–448` 钳位 + `:293` 拒绝判据仍自洽（§1(4)）。**新增面**：截断 `:458` 按「槽号 i 从小到大」取前 `used` 个，丢掉的是哈希槽号大的条目（随机高 LBA），而非「卷后段」——32GB 默认配置下**每次引导随机少一半热索引**，功能退化但安全。另：`es[n].Slot = i` 与 `IdxLoad` 的 `Hash(Lba>>16)` 恒等**仍依赖直映射不变式**（§1(5)）——若 v2 引入探测/相联，钳位 + 重算会系统性错位，J12 的「安全方向」不再成立。

**(c) J17（`s_Halt` 单向闩）源码不被放大，但验收必踩**。C 方案不改 `s_Halt` 逻辑（`:107`、`:966/:1039` 短路、`:653/:811` 清零点、`:847/:875` `haltPrev` 还原）。但：① 容器作废若采用方案 (b)/(c) 落进 `:735` 拒绝分支，会置 `s_State=4` 而**不置 `s_Halt`**——这是「拒绝启用」不是「关闭」，与 J17 的 Close 路径不同，不放大；② **P5 真机验收要重启 + 重新 `l2 enable`**，199 §4.1 第 1 条 / J19 明确「任何 L2 启用都必须先重启或带 `refresh + L2State==1` 硬闸」，否则 `rbfeatctl.c:271` 不校验 Xfer + `rbL2.c:582` 300ms 节流可静默吞掉 enable 的 REFRESH ⇒ 静默空转（`s_Halt` 停 1）。**若回归夹具漏了这条硬闸，会把「C 方案没生效」误判成「C 方案有缺陷」**。⇒ 202 的验收章节必须把 J17/J19 前置写进去。

**(d) J2（全局世代，未修）叠加冲突进一步压低 `L2Stores`**。199 §4.1 第 3 条列 J2 为「store 真落盘后才暴露」的数据面项：`rbfeat.c` 快照全局 `s_Gen`（`rbL2.c:1013/:1061/:1070` 三次复核），卷上任何写都 bump 全局世代，杀掉所有在飞 Store。C 方案生效后 J2 首次 live，再叠加 §2 的哈希冲突驱逐与竞态 MISS，`L2Stores`（`Rb2Count(8)`）/ `L2Hits`（`Rb2Count(7)`）可能塌到接近 0。⇒ **真机判据不能只看 `l2s>0`**，且 202 需提醒「活跃卷 + 小容器」组合下数据面可能结构性不显现。

> **§6 判定：需补守卫。** 三条已知项在 C 方案后统一从「未验证/未触发」变为「live」，201 §1.4 五条风险**一条都没覆盖 J 段前置项**；202 必须显式声明这些前置项的状态与验收口径，否则会把稳定性证据误当可用性证据（199 §4.1 的原话）。

## §7 并发与生命周期契约

**(a) `s_Ops` / `s_Gen` / `s_IdxDirty` / Close 排空 —— 契约未被破坏**。C 方案只改容器偏移计算，不触碰：`:964/:1037` 计数、`:966/:1039` `s_Halt` 短路、`:1013/:1061/:1070` 三次世代复核、`:851` drain、`:884` 原子摘指针、`:886` `s_Slots=0`。**唯一的接口变化**是新增的 `RbL2Hash` 调用点必须自带除零守卫（§3），且要用局部快照与 `DropRange` 对称——这是 §3 的内容，不是契约破坏。

**(b)「Store 写盘成功后才更新索引」顺序 + drop 落在写盘与索引更新之间 —— 仍安全，但要点明单点防线**。
```c
:1059 stw = RbL2Io(s_File, TRUE, 4096 + blk*REC, rec, REC);   /* 先写容器 */
:1060 if (NT_SUCCESS(stw)) {
:1061     if (Gen == InterlockedOr64(&s_Gen, 0)) {              /* ② IO 期间无 drop */
:1064         if (s_Idx && s_Slots) {
:1065             i = RbL2Hash(blk); idx[i].Lba = blk<<16; ... Use=1;   /* 后更新索引 */
:1070             if (Gen != InterlockedOr64(&s_Gen, 0)) idx[i].Use = 0;  /* ③ 赋值窗口复核 */
```
drop 落在 `:1059` 与 `:1066` 之间 ⇒ `:1061` 判据失败 ⇒ **不更新索引**；容器 `slot` 里残留「写前内容」记录，但 `idx[slot]` 要么被 `DropRange` 清了 `Use=0`、要么 Lba 不匹配 ⇒ **不可达**；即便被探针读到，`:984 rec->Lba`/`:986 Crc` 也挡成 MISS。⇒ 顺序在哈希冲突下 **correctness-safe**，201 号对。**但必须升格为不变式**：内存索引与容器记录之间**无原子性、无锁**（`s_Ops` 只是计数），§2(e) 的并发冲突竞态证明「错位」可真实发生，全靠 `:984 rec->Lba` 单点兜底。202 须禁止任何移除/弱化 `:984` 的改动。

**(c) 事实更正：Periodic 60s 索引落盘已删除，`s_IdxDirty` 是无读者残留**。201 §1.4 风险 5 提「CRC/VolId/Stamp 校验链不变，容器记录与内存索引的 `Slot` 一致性要重新核对」，但没说清落盘契约现状：
```c
:541  /* [172/A.2] 60s 周期落盘已删除：... 现在索引只在干净关机（H5）与
:543   * 显式关闭（CloseIntEx(Persist=TRUE)）落盘 ... s_IdxDirty 保留写入，
:546   * 已无读者，仅作诊断残留。 */
:1073 InterlockedExchange(&s_IdxDirty, 1);
:879  if (s_File && Persist) RbL2IdxSave();        /* Close 的排空后持久化 */
```

### 索引格式到底要不要动 —— 精确结论

> **字段布局：`RB2_L2E` / `RB2_L2IDX_E` / `RB2_L2IDX_H` 全部不用动**（201 §1.3「索引格式不变」**结论成立**）。索引层确已支持任意 `blk`，`:293 SlotCount`、`:293 Count≤MAX`、`:296 VolId`、`:308 BootSeq` 四重校验 + `:319 Hash(Lba>>16)` 还原在 C 方案下全部继续适用。
>
> **但 201 的论证漏了两个必须补的附加条件，缺一即「索引格式不用改」不成立**：
> 1. **必须锁死直映射不变式 `slot == Hash(blk)`**（§1(5)/P1-1）：`es[k].Slot` 写而不读、`IdxLoad` 靠 `Hash` 重算。只要 **v1 不改哈希常量、不引入线性探测/组相联**，自洽成立；**一旦 201 §1.4 风险 1 选择「2 路组相联或线性探测」，`slot ≠ Hash(blk)`，`:319` 还原必与容器记录错位 ⇒ 那时就必须改 `IdxLoad` 去读 `es[k].Slot`（= 动索引语义）并重走 magic 作废**。所以「索引格式不用改」是**有条件的、只对 v1 简单覆盖成立**。
> 2. **必须补「旧 `.idx` 作废」这一步**（§5(d)/P0-2）：旧 `.idx` 的 `Slot` 语义绑定旧容器布局，格式变更后若被 `IdxLoad` 接受会系统性错位。推荐复用 `RbL2IdxUnseal()` 写头 0 ⇒ **连 `RB2_IDX_MAGIC` 都不用换、零格式变更**；若改选「换 `RB2_IDX_MAGIC`」则属于**索引格式标记变更**（非字段布局变更），且要说明与 J11 已用过一次 magic 变更的叠加。
>
> ⇒ **一句话给作者**：**索引结构体不用动、索引 magic 最好也不用动（用 Unseal 作废旧 `.idx`）；但要补「旧 `.idx` 作废协议」+ 把「直映射不变式」写成 v1 硬约束。201 号「不用改索引格式」结论对、论证不完整，202 必须补这两条，否则 v2 任何冲突优化会静默破坏跨引导一致性。**
