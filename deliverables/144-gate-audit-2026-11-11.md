### G10 — proto 消息号循环漏掉 14（含自指校验陷阱）

`src/scripts/check_proto_sync.py:299`、`:432`

`range(1, 14)` 硬编码上界，而 `RB_MSG_GET_EVENTS = 14`（`src/ctl/rb_proto.h:66`）自 V10.6/B-7 加入后**从未被校验**——删掉 C# 侧 `MSG_GET_EVENTS` 也不报警。

**第一版修法（已推翻）**：改为 `max(msgs.values())` 派生上界。**变异测试证明这是自指校验**：删掉最大号后 `max` 跟着降，`expected` 随之缩小，`missing` 恒空 → 仍 PASS。

```
变异后运行：result: PASS (0 fail)  ← 假绿
```

**最终修法**：锚定一个**独立于被测数据**的下界：

```python
MSG_FLOOR = 14     # V10.6/B-7：RB_MSG_GET_EVENTS=14 为当前协议上界
top = max(max(msgs.values()), MSG_FLOOR)
missing = sorted(set(range(1, top + 1)) - set(msgs.values()))
```

新增消息（> MSG_FLOOR）只需连续，不必改常量；删除已发布消息必然被抓。

**验证（变异）**：删掉 `RB_MSG_GET_EVENTS=14` →
```
[FAIL] rb_proto.h 消息号不连续/缺失: 缺 [14]（MSG_FLOOR=14，实测上界=13）
result: FAIL (1 fail)   EXIT=1
```
恢复后 PASS。

> **方法论教训**：任何"从被测数据派生的期望值"都是自指校验，必然恒真。必须有一个不随输入变化的外锚。这条适用于所有门禁设计。

### 6.1 修复过程中的两起自伤事故（已闭环，记录以示警戒）

**事故 A — 变异测试污染 `rb_proto.h` 的 mtime**（导致 Gate9 误红）

做 G10 变异测试时用 `cp /tmp/rb_proto.bak src/ctl/rb_proto.h` 恢复文件，文件**内容**与 HEAD 完全一致（`git diff` 为空），但 **mtime 被刷新到 18:26**，而 `src/ctl/ramboostctl.exe` 是 11:55 → `check_ctl_freshness.py` 判：

```
[FAIL] ramboostctl.exe is older than src/ctl/rb_proto.h -- rebuild the CLI
```

这**恰好实证了 G11 描述的漏检形态的另一面**：新鲜度门禁只认 mtime，任何"不改变内容但触碰时间戳"的操作（`cp`/`touch`/`git checkout`）都会造成误红。方向是安全的（fail-closed），但操作时必须用 `git checkout` 或保持原 mtime 恢复。

**处置**：把 mtime 还原到 11:55:00，Gate9 复 PASS。内容正确性由 `git diff` 为空独立证明。

**事故 B — Gate15 误红 `_gates.log`**（我自己造的临时文件）

为绕过管道缓冲，把 gates 输出重定向到仓库根的 `_gates.log` → Gate15 遍历文件系统，立刻判：

```
[FAIL] root entry outside whitelist: _gates.log
```

这是 G17 的**第二次现场复现**：该门禁的核心缺陷是"遍历文件系统而非 git 索引"，任何本地临时产物都会造成假红。白名单只能一个个补，不是根本解。

**处置**：临时日志一律写到仓库外（`%TEMP%`）；根目录不留任何构建输出。
**根本修法建议（下轮）**：Gate15 改为遍历 `git ls-files` 派生的顶层条目 + 显式允许列表，使"未跟踪的本地产物"不再触发假红——但这会把"禁止提交构建产物"的检查从 Gate15 移到 CI，需一并评估。

---

## 7. 方法论沉淀（写给下一次审计）

1. **自指校验必然恒真**。任何"期望值从被测数据派生"的门禁（G10 第一版）在数据退化时同步退化。必须有外锚（`MSG_FLOOR`）。
2. **路径漂移的失效形态是"零 finding"，不是报错**（G1：21 个宿主全找不到 → 静默跳过）。所有"遍历 + 过滤"型门禁都必须有**存活自检**：遍历到 0 项且输入确实存在时判 FAIL。
3. **静默跳过比误红危险**。`if not exists: continue`（G6/G9/G11）让门禁在文件被删/改名时消失。至少应输出 warn，关键契约应 FAIL。
4. **描述不是保护**。`build_setup.ps1` 的注释准确描述了 G8 的风险，却没有阻止它。
5. **写门禁的人会写错正则**。G8 第一版 `'\\build\\|\obj\\'` 无效，且失败形态是"管道返回空 ⇒ 放行"。任何 `Where-Object` 过滤后为空的结果，都必须区分"本就没有"与"过滤写错了"。
6. **mtime 型门禁天然脆弱**。恢复文件用 `cp` 会刷新时间戳 → 误红（事故 A）。凡"内容未变但 mtime 变了"的操作，都必须用 `git checkout` 或显式还原时间。
7. **"遍历文件系统"型门禁会被本地产物误红**（事故 B、G17）。这类检查只应在 CI 干净 checkout 上跑，或改为从 `git ls-files` 派生。
