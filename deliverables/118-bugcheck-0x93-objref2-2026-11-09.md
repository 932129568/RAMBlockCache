## 2. 静态根因：110 号未修完的同族缺陷

全库 9 处 `PsCreateSystemThread` 逐一核对：

| 文件:行 | 修复前 ObjectAttributes | 后续 `ObReferenceObjectByHandle` | 状态 |
|---|---|---|---|
| `rbfeat.c:504` / `:592` | `NULL` → 已改 `&oa` | `KernelMode` | ✅ 110 号已修 |
| `rbio.c:1212 / 1292 / 1909 / 2019` | `&oa` (`OBJ_KERNEL_HANDLE`) | `KernelMode` | ✅ 原本正确 |
| **`rbio.c:2374` `RbStartFlushThread`** | **`NULL`** | `KernelMode`（:2378） | ❌ **本批修** |
| **`rbpools.c:119` `Rb2PoolInit`** | **`NULL`** | `KernelMode`（:130） | ❌ **本批修** |
| **`rbwback.c:96` `RbWbInit`** | **`NULL`** | `KernelMode`（:98） | ❌ **本批修** |

**缺陷机制**：不传 `OBJ_KERNEL_HANDLE` 时，线程句柄落在**当前进程句柄表**（用户态句柄）；随后以 `KernelMode` 调 `ObReferenceObjectByHandle`，内核会在内核句柄表中解析该值 → 拿到无效/错误对象 → Verifier 的 0xF6 专项规则（09:34 实捕）或内核 bad handle detection（`0x93`，12:22）触发 bugcheck。两条检测路径不同，**根因同一**。

`rbL2.c` 的 3 处 `InitializeObjectAttributes`、`rbattach.c` 2 处、`rbdriver.c` 4 处均带 `OBJ_KERNEL_HANDLE`，无需改动——已逐一核对。

**为什么 110 号之后还崩**：110 号是针对 09:34 `0xC4/0xF6` 的定点修复，覆盖了当时栈上被点名的 `rbfeat.c` 两处，但没有做全库同模式扫描。本批补上剩余 3 处，并用 `grep` 断言全库 `PsCreateSystemThread(&h, ... NULL, NULL, NULL` 命中数为 **0**。

1. 复制全部 minidump 到 `o9\dumps\`（ACL 需管理员）。
2. 用 **`98f150ba…` 对应的归档 PDB** 对最新 dump `110926-13859-01.dmp` 跑 `!analyze -v; kb; lm m RAMBlock; !verifier 3` → `cdb_1222_0x93.txt`，给出 0x93 的精确调用栈。
3. 归档本代 PDB（按签名哈希分目录 + `index.tsv`）。
4. 签名新 sys（验签不 Valid 即中止）→ 同步 dist / sidecar / 三锚点并回读 → 部署 → 门禁⑤。
5. 保留 Verifier 在岗；配置内核转储与 `CrashOnCtrlScroll`（已生效，本次无需重配）。

**重启一次**后，回来由主理人复核 `cdb_1222_0x93.txt` 的 `FAILURE_BUCKET_ID` / `STACK_TEXT`：
- 若点名落在本批 3 处之一 → 静态归因闭环；
