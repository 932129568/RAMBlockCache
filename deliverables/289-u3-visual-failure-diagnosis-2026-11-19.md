## §2 P-1：底层玻璃不透 —— 62% 白遮罩是主凶

### 2.1 证据链

| 事实 | 位置 | 值 |
|---|---|---|
| 桌面透色基底铺满整页，`z-index` 在最底 | `App.tsx:99` `<div className="rbc-desktop-bleed-canvas" />` | 全屏 `position:fixed` 装饰节点 |
| 该基底的背景被设为 scrim | `liquid-glass.css:571` `background: var(--rbc-layer-host-scrim)` | — |
| scrim 实值 | `tokens.css:1170` / `:1208`（`html.rbc-host-transparent` 内） | **`rgba(255, 255, 255, 0.62)`** |
| 流光影被强制关闭 | `liquid-glass.css:576-580` `background-image:none; animation:none` | 透色模式下唯一的光学层次被关掉 |

**推论**：底层玻璃（`.rbc-section`）的填充是 `--rbc-layer-section-fill`，最亮端 `rgba(255,255,255,0.24)`、最暗端 `rgba(248,250,252,0.08)`（`tokens.css:1185-1189`）。它叠在 **62% 纯白**的 scrim 上 ⇒ 合成后整块区域是 **0.62 + 0.24×(1−0.62) ≈ 0.71 的白**。

这个值在视觉上就是「灰白底板」，**与页面的 `#f3f5f9` 几乎无法区分**。用户看到的「一块玻璃都没有」，在物理上是正确的：**62% 白遮罩把 DWM 亚克力透上来的一切颜色都糊掉了**。

### 2.2 为什么我上一轮会漏掉

我上一轮的 11 条 CSS 契约测试断言的是「令牌存在且被消费」，具体是：

- `--rbc-layer-section-fill` 被 `.rbc-section` 消费 ✅
- `html.rbc-host-transparent` 规则存在 ✅
- `forced-colors` 退化为 `none` ✅

**这 11 条没有一条断言「合成后的不透明度」**。一个 62% 的白遮罩完全满足全部 11 条断言，同时让整个分层光学**物理上不可见**。这是判据设计缺陷（`278` F-04 维度不匹配）。

### 2.3 修复方向（未实施）

| 方案 | 做法 | 风险 |
|---|---|---|
| **A（推荐）** | `--rbc-layer-host-scrim` 改为 `transparent` 或 `rgba(255,255,255,0.10)`，靠 `--rbc-layer-section-fill` 自身保对比度 | 需要实测文字对比度是否仍达 WCAG AA；桌面壁纸若很亮（浅色壁纸）可能反而看不清文字 |
| B | 保留 scrim 但降到 0.18–0.25，同时把 `--rbc-layer-section-fill` 提亮 | 折中，透色更弱 |
| C | 引入壁纸亮度自适应：WPF 侧把壁纸平均亮度一起推过来，页面按亮度插值 scrim α | 最稳，但要改 WPF + 桥接 + 新令牌，跨三个端 |

**必须由用户拍板选 A / B / C**。这是光学取向，不是技术正确性问题 —— 我无权替你决定「透到什么程度」。

## §3 P-3：波浪「卡住」—— 渲染预算导致画面冻结

### 3.1 代码级根因

`useLiquidWave.ts:155` 默认参数：

```ts
const { root, selector = DEFAULT_SELECTOR, coupling = true, maxRendered = 4 } = options;
```

`App.tsx:51` 调用时**没有传 `maxRendered`** ⇒ 恒为 **4**。

而当前页面的玻璃块数量（DOM 静态计数）：

| 类 | 使用处 |
|---|---|
| `.rbc-card` | **23** 处组件定义 |
| `.rbc-section` | **57** 处组件定义 |

即便实测同时可见的只有十几块，也**远超 4**。

`tick()` 里的预算分配（`useLiquidWave.ts:335-365`）：

```ts
for (let i = 0; i < awake.length; i++) {
  const surf = awake[i];
  stepWave(surf.field);                    // ← 物理照常步进
  const peak = wavePeak(surf.field);
  if (i < budget) {                        // ← 只有前 4 个能上传
    ... putImageData(...)
  } else if (peak < 0.005 || now - surf.lastActive > IDLE_SLEEP_MS) {
    sleepSurface(surf);                    // ← 其余：满 1200ms 直接清屏
  }
}
```

**这就是「卡住」的机理**：第 5 个及以后的波场，物理仍在算、`cur` 数组仍在变，但 `putImageData` 从不被调用 ⇒ **canvas 停留在注入瞬间的那一帧**。用户看到的就是「一块玻璃上糊着一个静止的斑」。然后满 1200ms，`sleepSurface` 把 `opacity` 设 0（0.25s 淡出）—— 用户看到「卡住 → 自己消失」。

与用户原话「**卡住等自己消失**」**逐字对应**。

### 3.2 仿真量化

我写了独立仿真（复刻 `liquidWaveCore` 的完整物理，不引用源码）：

```
=== sleepSurface 的 peak<0.005 判据要多久 ===
  peak<0.005 @ 131 frames (2184 ms)

=== 冻结时长上界 ===
  IDLE_SLEEP_MS=1200 触发清屏
  冻结窗口 = min(1200ms, 2184ms) = 1200 ms
  => 超出预算的波场：画面冻结 1200ms，然后 opacity 0.25s 淡出
```

**即：卡 1.2 秒，再花 0.25 秒淡出。** 用户说「效果不好」，物理上就是这 1.45 秒的静止画面。

### 3.3 为什么它「在别的玻璃上也能看到」

因为 `dispatchCoupling` 会把波投给**父 section 和兄弟 card**（`liquidWaveGraph.ts:453-550`）。这些目标收到投递后 `wake()` 唤醒，但**排在预算之外** ⇒ 立刻进入冻结态。所以是「鼠标一动，好几块玻璃同时糊上一个死斑」。

### 3.4 修复方向（未实施）

| 方案 | 做法 | 评价 |
|---|---|---|
| **A** | 把 `maxRendered` 提到 **12–16**，并用「最近活跃优先」重排（已有 `sort`，但每帧都排） | 改动最小；`putImageData` 160×90=14,400 px，实测单次 < 0.3ms，16 张 ≈ 4.8ms，60fps 下可接受 |
| **B** | 超预算时**降帧率上传**（每 2–3 帧传一次）而不是完全不上传 | 视觉上「慢动作」而非「冻结」，体验好得多；CPU 也更省 |
| **C** | 改为「单张全屏 canvas」统一渲染所有波场，彻底取消预算概念 | 架构最干净，但要重写 hook + 重新定位每块玻璃的裁剪区，工作量最大 |
| D | 波场按元素真实尺寸分配网格（与 P-2 合并修） | 见 §4，必须做，否则改了预算只会看到**更大的**糊斑 |

**推荐 A + B 合并，且必须与 §4 一起做。** 单独提预算 = 让糊斑更大更明显。

## §4 P-2：波浪不成形 —— 固定 16:9 网格被 CSS 拉伸

### 4.1 代码级根因

`liquidWaveCore.ts:12-14` 把网格写死：

```ts
export const WAVE_COLS = 160;
export const WAVE_ROWS = 90;
```

`useLiquidWave.ts:411-412` 把 canvas 内部尺寸固定为网格尺寸：

```ts
canvas.width = WAVE_COLS;    // 160
canvas.height = WAVE_ROWS;   // 90
```

`useLiquidWave.ts:413-425` 再把显示尺寸拉到 100%：

```ts
width: '100%', height: '100%'
```

⇒ **canvas 总是 160×90 的位图，被 CSS 拉伸到元素的实际宽高。**

### 4.2 拉伸比实测（当前页面真实元素尺寸）

| 元素 | 实际尺寸 | 横向缩放 | 纵向缩放 | **横向拉伸比** |
|---|---|---|---|---|
| 大统计卡 | 340 × 150 | 2.13 | 1.67 | **1.27 : 1** |
| 中卡 | 240 × 96 | 1.50 | 1.07 | **1.41 : 1** |
| **横长 section** | 1400 × 120 | 8.75 | 1.33 | **6.56 : 1** ← 灾难 |
| 整页 section | 1400 × 700 | 8.75 | 7.78 | 1.13 : 1 |

**横长 section 的圆形涟漪被横向拉成 6.56 倍扁的糊斑。** 用户截图里那两圈**横长条状**的斑，形态完全对上 —— 它们不是「波纹」，是被拉伸后的波。

### 4.3 与用户原始诉求的偏离

用户要的是「**波浪相互碰撞**」—— 也就是看得见的**圆形波纹传播 + 触边反射**。当前实现给的是：

1. 波本来就不传播到边界（我上一轮已量化：`DAMPING=0.95` 下波前 400 帧内走不到 x=140/159，中心滑动单位帧通量峰值 **0.0009**，比门槛 `0.02` 低 **22 倍**）⇒ 所以改用「解析投递」代偿；
2. 解析投递打进去的波，又被拉伸成横条；
3. 横条再被预算冻结。

**三重打击叠加** ⇒ 用户看到的既不是「碰撞」，也不是「波纹」。

### 4.4 修复方向（未实施）

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 网格按元素真实宽高比分配：`COLS = clamp(round(160), 32, 256)`、`ROWS = round(COLS × h/w)`，并对极扁元素设 `ROWS` 下限（如 24） | 需要 `attachSurface` 时读 `getBoundingClientRect`，并在 `ResizeObserver` 里重建 field；`liquidWaveCore` 从「常量」改为「参数」，会影响 113 个用例中的一部分 |
| B | 保持 160×90，但用 `ctx.setTransform` 做各向同性缩放（等比 + 裁切） | 视觉圆了，但大 section 会有大片空白（波走不到），治标 |
| C | 改用「以屏幕像素为单位的方波网格」：`COLS = w / 8`、`ROWS = h / 8` | 最精确；但 1400×700 的 section 会变成 175×88 ≈ 15,400 格，可接受；小卡片则格数过少 |

**推荐 A。** 这是唯一能同时满足「圆涟漪」和「不浪费算力」的方案。

## §5 三个问题的耦合关系（重要）

这三条**不能分开修**，因为：

```
修 §3（提预算到 16）
  └─ 不修 §4 ⇒ 16 块玻璃同时显示 6.5:1 的横向糊斑 → 比现在更丑

修 §4（网格自适应）
  └─ 不修 §3 ⇒ 圆波纹依然被冻结在某一帧 → 用户仍看到「卡住」

修 §2（放开 scrim）
  └─ 不修 §4+§3 ⇒ 桌面透上来了，但玻璃上的波是糊的+卡的 → 反而暴露更多缺陷
```

**正确顺序：§4（几何） → §3（预算） → §2（光学）**。先让波「圆」，再让它「动」，最后才让它「透」。

## §7 本轮最重要的发现：验收判据失效

### 7.1 事实

| 我上一轮宣称 | 实际情况 |
|---|---|
| 「16 文件 / 113 用例全过」 | ✅ 属实 |
| 「11 条 CSS 契约全过」 | ✅ 属实 |
| 「变异测试 4 组全部 KILL，门禁有牙」 | ✅ 属实 |
| 「**不能说 113 用例通过 = 液态玻璃达标**」 | ✅ 我说了这句 |
| 但我**没说**：**这些用例根本不测下面三件事** | ❌ 漏说 |

### 7.2 三类被漏掉的判据

| 应测项 | 当前测试 |
|---|---|
| **合成后不透明度**（scrim × fill 的最终 α） | 只测「令牌存在 + 被消费」，**不测合成值** |
| **canvas 拉伸比**（`canvas.width/height` vs 元素 `clientWidth/Height`） | **零测试** |
| **冻结帧数**（超预算波场连续多少帧未 `putImageData`） | **零测试** |

**这三项全部是纯静态/可计算的，完全可以在 jsdom 里断言。** 我上一轮没写，是因为我在照着手册的验收清单（V1–V15）做，而**手册的清单里也没有这三项**。

### 7.3 判据设计原则（本轮新增，写入后续纪律）

1. **凡是「视觉属性」，判据必须落在「合成后的值」上**，不能只落在「声明存在」上。
   反例：`expect(css).toContain('--rbc-layer-section-fill')` —— 62% 白遮罩也能通过。
   正例：解析 `scrim.alpha * (1 - ...)` 算出最终不透明度并断言区间。
2. **凡是「尺寸相关」，判据必须断言「位图尺寸与显示尺寸的比值」**。
   反例：只测 `canvas.width === 160`。
   正例：`expect(Math.max(w/160, h/90) / Math.min(w/160, h/90)).toBeLessThan(1.5)`。
3. **凡是「预算/节流」逻辑，判据必须断言「最差情况下某块玻璃连续多少帧未刷新」**。
   反例：只测 `awakeCount === 0`。
   正例：记录每块 surface 的 `lastUploadFrame`，断言 `max(now - lastUploadFrame) < 2`。

## §11 一句话给接手人

> U3 的代码结构和测试基础设施是好的，但它交付的是「**在单测里成立的液态玻璃**」，不是「在真实 DOM 几何下成立的液态玻璃」。三个根因都是**可测量**的：`scrim=0.62`、`拉伸 6.56:1`、`budget=4`。先修几何再修预算最后修光学，顺序错了会更丑。
