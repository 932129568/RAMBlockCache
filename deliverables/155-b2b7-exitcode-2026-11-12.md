## 4. 反向用例 `tests/e2e/test_e2e_exitcode_contract.py`

### 4.1 隔离方式（怎么保证"不连设备、不发 RPC、不写盘、不起 exe"）

`rpc` 是这 5 个脚本**唯一**的 HTTP 出口，把模块级 `rpc` 换成进程内假实现即物理上不可能出网。
其余副作用点逐个 patch（均为模块全局遮蔽，`tearDown` 还原）：

| 被 patch 的名字 | 作用 |
|---|---|
| `mod.rpc` | 假桥接：method 1/2/4/7 各自的返回，`hook` 用于按用例注入异常 |
| `mod.time` | `sleep` 空转、`time()` 快进 30s/次（让 e4 的 60s 实时循环只跑 1 轮） |
| `mod.subprocess` | `run()` 返回假 CompletedProcess（不启动 `rbc_e2e_verify.exe`） |
| `mod.open` | 模块全局遮蔽内建 `open`：备份/结果 JSON 写进 `StringIO`，不落盘 |
| `mod.os` | `os.remove` 空转，`os.path.isfile/exists` 由用例指定 |
| `mod.phase` | e1 / a2_writeback 的 `phase()` 换成记账桩，其内部 lambda **一律不执行**（不碰 D:\ 真实文件、不调 ctypes） |
| `mod.run` / `mod.oracle` / `mod.make_main` | a2c 的 oracle 子进程、e2 的 32MiB 造盘、e2 的 verify 全部桩掉 |
| `mod.LOGF` / `mod.OUT` / `mod.BACKUP` / `mod.WORK` | 假 Path 对象，不落 `C:\Users\Public\o9`、`C:\ProgramData\RAMBlockCache` |

> 代价（如实说明）：因为 `phase()` 被替换，这些用例验证的是**恢复段与退出码的接线**，
> 不验证各相位判据本身。相位判据仍需真机。

## 7. §未核实项

1. **`status:-1` 不会被当成恢复失败（最大的遗留口子）**。
   这 5 个文件的 `rpc()` 全是 `return json.loads(r.read().decode())`，**不检查 `status`**。
   因此：
   - 桥接/HTTP 层挂掉 → 抛异常 → 现在能正确变红 ✅
   - `{"status":-1,"message":"..."}` 且 HTTP 200 → **不抛** → 恢复"逻辑失败"仍然退出 0 ❌
   - 唯一例外：`config()`/`stats()` 走 `rpc(4)["data"]` / `rpc(1)["data"]`，若 `status=-1`
     的响应没有 `data` 键，会 `KeyError` → 被兜住变红；但只要响应里带 `data:{}`，就静默。
   要真正闭环需要给 `rpc()` 加 status 判定或给恢复调用点单独判 `resp.get("status")`——
   **这会改变所有调用点语义，超出本次"只改退出码"的范围，我没有做**。建议作为 156 号单独决策。
2. **detach 失败不计入退出码**（e4 `DETACH_BEST_EFFORT`）：依据是 153 §B.3"detach 失败不等于
   配置污染"。但这意味着"卷被留在 attach 态"这种半污染状态仍会退出 0，只留一行日志。
   是否为它单独开码，需用户拍板。
3. **e4 的 `verdict: null`**：新增了"读不到最终 stats 就写 null 而不是不写文件"的行为。
   下游若假设 `verdict` 一定是 dict，需相应判空——我没有找到仓库内消费 `e4_result.json`
   的代码（`grep e4_result` 仅命中文档），但这个结论只覆盖本仓库。
4. **测试的假桥接不模拟真实驱动的返回细节**（例如 `status=-1`、`data` 缺键）。所以"恢复段
   在真实异常形态下的行为"仍只有 §7.1 的静态判断，没有实证。
