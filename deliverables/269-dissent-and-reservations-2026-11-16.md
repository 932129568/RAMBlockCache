## A. 我认为被写强了、应降级的既有结论

### A1 「P1 补丁真机生效」是强推断，不是直接观测

**现状表述**：HANDOVER 文首与 `257` 写「P1 补丁生效」「容器由数据路径打开」。

**证据是什么**：`.idx` mtime 从 prepare 的 `13:56:49Z` 变为开机后 `13:59:31Z`（仍 4 B、头 32 B 全 0）；`RbL2BootUnsealInt` 只在 `magic == RB2_IDX_MAGIC` 时才写（`rbL2.c:446`），头是 0 故它不写 ⇒ 该写只能来自 `RbL2IdxUnseal`（`:371`），而它只在 `RbL2LazyOpenInt` 成功路径执行（`:813/:819`，`:844` 置 `s_State=1`）；开机后无 REFRESH（控制面唯一入口 `rbfeat.c:718`、`Rb2Init` 只调 `Rb2ReloadFlags`、两个守护脚本无 refresh）。

**我的异议**：这是**排除法**。它的强度取决于「`.idx` 的写者集合是否被穷尽」。我当时的做法是 `grep` 关键字，不是对 `ZwWriteFile` / `ZwSetInformationFile` 的机器穷举；宏封装或间接调用会漏。因此结论应写成「**强推断（代码路径唯一性 + 时间戳互证）**」，不能写「已证」。

**代价与处置**：加一行运行时打点即可转成直接观测（复用 `264` 的同步标记设施，在 `RbL2LazyOpenInt` 成功分支写一次 `Parameters\DiagL2OpenedSeq`）。**我不建议为这一条单独花一轮部署**——它不影响 B1 的处置方向，搭 v2 一起做即可。真正要防的是：后续报告把它当「已验证」继续引用。

### A2 `volumes:0` 的根因是「最可能解释」，不是定案

**现状表述**：`245` §4 的根因链是「旧版 `boot_guard.ps1` 在 unarmed 但健康的机器上无条件剥离 `UpperFilters`」，HANDOVER 转述为结构性必踩。

### A3 「L2 的唯一真实价值 = J6 跨引导命中」是过窄的价值判断

**现状表述**：`250`/`259`/记忆里多处写「J6 是 L2 唯一真实价值」。

**我的异议**：L2 的写入源是 core 淘汰回调（`RbFeatOnEvict`，`rbfeat.c:867`，冷块过滤 `:886` 要求 `Hits>=2`）⇒ L2 里存的是**被 core 淘汰过的块**。同一引导内 core 再次 miss 到这些块时，L2 本可以命中。所以「跨引导命中」是强度最高的验收场景，但不是**唯一**收益场景。

把两者混为一谈的后果很实际：J6 在当前构建结构性不可能（空索引）⇒ 容易顺势得出「L2 没价值、不必修」。而「同引导内命中率/延迟收益」从来没有测过（R26 未执行，项目里没有任何性能数字）。

**处置建议**：决策时拆成两个独立问题——
1. 跨引导命中是否可达（J6）？
2. 同引导内 hit 率与延迟收益是多少（R26）？

不要把 2 当作 1 的附属。是否投 R26，需要用户拍板。

### A4 `RbRegSetClean(1)` 的连带影响不是「削弱计数」，而是**结构性绕过 BootLoopGuard**（对 v2 的阻断级异议）

**代码事实**：`rbdriver.c:213-218` 在 `v=1` 时同时写 `LastCleanShutdown=1` **和** `BootFailCount=0`；开机自检在 `:286` 读 clean、`:295` 清零、`:303` 处 `healthy==1 || clean==1 ⇒ fails=0`。

**推演**（这是我认为 v2 必须先解的原因）：

```
引导 N：驱动未 attach（self-disable / SafeMode / UpperFilters 被剥）  → 无 logon_disarm，healthy=0
        v2 的控制设备关机回调仍然执行 → RbRegSetClean(1) → clean=1, BootFailCount=0
引导 N+1：clean==1 → fails=0 → BootLoopGuard(fails>=2) 永不成立
        → 再次失败 → 再次干净关机 → 再清零 …… 无限循环
```

**为什么现在没暴露**：`RbRegSetClean(1)` 从未真正执行过（P2 根因：`IRP_MJ_POWER` 不派发）。v2 一旦修好关机通道，这个路径**第一次被激活**。也就是说：v2 会用「能存索引」换掉「能自愈」。

**我的异议**：`259` 只说它「会抹平累积失败、`257` 的安全网首次上线是高估」，这个描述偏轻。正确的表述是：**v2 必须同时修改 clean 的语义**，例如只在「本引导曾成功 attach 过卷且引擎未 panic」时才置 1；否则 v2 不应上线。

**这是我认为 v2 草案的第三个必答项**（前两个是 F3 停 tick、设备门去重）。

## B. 我对红队结论的异议

### B1 `259` F3 的严重度被高估（我转述时也照抄了，这条算我的错）

**红队原文（`259`）**：`Rb2Tick` 关机时仍在跑 → `RbL2Periodic` → `RbL2CloseIntEx(FALSE)` 置 `s_Halt` → `RbL2IdxSaveGuarded` 直接 FALSE，索引仍不定稿。

**代码核实**：`RbL2Periodic` 的关闭动作在 `if (s_Reopen && s_File)`（`rbL2.c:564`）里；`s_Reopen` 只在打开路径的两个拒绝分支被置 1——多卷拒绝（`:630`）与卷身份不匹配/无卷（`:656`）。而 `s_Halt = 1` 共四处：`:629` / `:655` 就在这两个拒绝分支内，`:883` / `:904` 在 `RbL2CloseIntEx` 内（先闸断新操作、drain 后二次置位）。也就是说，「拒绝打开」本身就会置 `s_Halt`，不必等 tick 去关。

**修正结论**：F3 是**条件性阻断**，不是每次关机的必然路径。单卷、容器已开、且本引导打开路径未走「多卷 / 卷身份不匹配」拒绝分支 ⇒ `s_Reopen==0` 且 `s_Halt` 未被置位 ⇒ tick 不会关容器，`RbL2IdxSaveGuarded` 能正常落盘。

**但最终处置不变**：v2 仍应先停 tick（或在 `RbL2IdxSaveGuarded` 入口显式声明依赖）。理由有二：① `s_Reopen` 一旦非零就是真阻断，而现场确实出现过「多卷拒绝」路径；② 依赖一个「恰好为 0」的变量做正确性保证，本身不可接受。

**我要更正的地方**：`268` 把 F3 列为「仍未解」时没标条件性；`259` 的表述我照抄进 HANDOVER。这条记在我账上，不是红队的错——红队给的是风险提示，我负责核。

### B2 `259` F2 应升级为**通用规则**，而不是「删掉这个闩」

**事实仍成立**：`s_ShutdownDone` 是 `rbmsg.c` 文件内 `static`；hiberfile 恢复不重跑 `DriverEntry`；`RtlZeroMemory(&g_Rb)` 覆盖不到它。

**我的异议**：把它当成「这个闩设计错了」会漏掉同类问题。真正的规则是：

> **任何跨引导必须为 0 的 `static` 状态，在 hiberboot 机型上都不可信。**

工程里还有一批 `static`：`s_DiagShutdownSeen`、`s_RejVol`、`s_RejLen`、`s_RejIdx`、`s_Panic`、`s_CrcReady`……它们目前**只用于节流/诊断/惰性初始化**，所以无害。但这个「无害」是**偶然的**，不是设计保证的——只要将来有人拿其中一个做正确性判断，就会复现 F2。

**处置建议**：在 `rb_common.h` 的文件头纪律区加一条硬规则（不是注释，是可被 audit 的规则）：「影响正确性的跨引导状态必须能从注册表/磁盘重建，或在使用前校验 BootId」。这条比删一个闩有价值得多。

| 1 | C3 文档归档 + C1 单源 pin | 0 | 无 | 零风险，且能防止下个会话读错指令 |
| 2 | A4 clean 语义 + B1 F3 条件化 + A1 打点设计 | 0 | 写进 v2 草案，不落地 | 这三条决定 v2 是否安全，必须在写 diff 前定 |

| 4 | v2 落地 | **4 次电源动作** | 用户明确接受电源预算 | 部署 1 + 2 干净 + 1 非干净 |
| 5 | R26 性能测量 | 0 | v2 稳定 | 决定 L2 是否值得保留 |

**我不同意的默认路径**：直接写 v2 然后部署。A4 未解时，v2 会让自愈机制失效——这比「L2 不能用」严重得多。
