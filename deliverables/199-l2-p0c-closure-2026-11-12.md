1. **两次都不是 PASS**：`UNCOVERED` 只证明"L2 打开了、机器健康、store 路径没执行"，不证明缓存可用。
2. **Verifier 开着**：只作稳定性结论，**不作性能峰值或缓存数据面正确性结论**。
3. **静态 vs 真机分开写**：196 的代码层结论（如 `lba` 语义）由 198 的 `lba|` 行实证；但 `[1048]` 类诊断带 `&0xFFF` 节流，看到 1 条只代表次数落在 **[1,4096]**，不能写成"≥4096 次"。

## §3 待决策：是否认定 J18 为驱动缺陷（C 方案）

> 用户选的是"收口"，**本节只备齐决策材料，不启动任何改动**。

### 3.1 支持"是缺陷"的论据

- 语义不符：「L2 二级缓存」的通常语义是缓存**任意 LBA 的热块**，容器大小决定能存多少块；现实现把容器当成**卷前缀镜像**，`GB` 参数实际含义变成「覆盖卷前 N GB」。
- 本机实证：931GB 卷、2GB 容器，负载整段在窗口外，**L2 数据面结构性永不生效**。换 128GB 容器（上限）也只能覆盖 extents 的一部分（实测分布到 199.5GB）。
- 无文档化：188 号 runbook 查遍 `rbfeatctl.c` 与 `rbL2.c`，未见任何"仅卷前 N GB"的用户可见说明；`l2 enable` 的提示只有 `will create X:\RAMBoostL2.bin (N GB)`。
- 与 J12（32GB 索引钳位）叠加，说明容量语义在设计与实现间存在系统性落差。

### 3.2 支持"是设计取舍 / 暂不改"的论据

- **零拷贝、O(1) 寻址**：`blk = lba/64KB` 直接当槽位号，无需哈希或索引查找，容器即镜像，CRC + 卷身份 + 记录头校验保证"错即 MISS"，实现极简且失败安全。
- 改为"按热块分配槽位 + 索引记 Lba"会牵动**索引格式 v2、CRC、`RbL2IdxSave/Load`、跨引导一致性（J11）、`RB2_L2IDX_MAX` 钳位** —— 磁盘格式兼容面已经被 J11 的 magic 变更占用过一次。
- 本轮全部真机都在 Verifier + 2GB 小容器下，**没有性能或正确性基线**；改动收益无法量化。
- 本机 `Features\Flags=0`、L2 默认 OFF，未影响线上行为。

|---|---|

| 红线流程 | 改源码 → 重编 driver → **重新签名** → `sync_anchors.ps1`（验签名链 Valid 后写三锚点）→ `deploy.ps1` → 重启 → 全量门禁 + core 66 回归 |
| 门禁 | `check_proto_sync.py --strict`、`refcount_model.py`、`check_ps_syntax.ps1`、`check_signature.ps1`、`check_repo.py`，另 `qa_teeth.ps1` 变异门禁 |

| 风险 | 内核未过 WDK / Driver Verifier 完整验证；J17 单向闩、J11 跨引导陈旧索引、J12 钳位都在这条路径上 |
| 验收 | 至少一次「窗内 store 成功（`l2s>0`）+ 索引回读一致 + 重启后命中」的真机闭环，且需在 Verifier 关闭后复测性能 |

### 3.4 更轻的替代（不认定为缺陷时）

- **文档化**：在 188 号 runbook 与 `rbfeatctl` 提示里明确写「`GB` = 覆盖卷前 N GB，非缓存容量」；把 `-SizeGB` 默认值与卷大小的关系写进配置建议。
- **配置建议**：大卷要启用 L2 时，容器卷用独立大盘、`SizeGB` 尽量大（上限 128），并接受只能覆盖卷前段。
- **保持现状**：`Flags=0` 默认 OFF，L2 属于可选特性，不影响主数据面。

### §4.1 收口结论必须随附的边界条件（200 号收口复核 §3，8 类缺项已补齐）

> 只写「数据面因窗口约束未覆盖」不足以交接。以下八条必须与结案结论一起说，否则后续接手者会把稳定性证据误当成可用性证据。

1. **J17 / J19 `s_Halt` 是未修的驱动设计约束**：第一次 `disable` 后 `s_Halt` 确定停在 1；`rbfeatctl.c:271` 不校验 Xfer + `rbL2.c:582` 300ms 节流可静默吞掉 enable 的 REFRESH，`Rb2Tick` 不调 `LazyOpenInt` ⇒ 无自愈、静默永久失效。**后续任何 L2 启用都必须带着这条**：优先重启，或依赖已真机验证有效的「补 `refresh` + `L2State==1` 硬闸」。⚠️ **J19 的准确口径**：「等价替代在夹具内有效」**不等于**「`s_Halt` 缺陷已修」——驱动本体一行未改。后续任何 L2 启用（含 C 方案回归、换机部署、脱离本夹具手工操作）都必须先重启或保留该硬闸。
2. **J11 跨引导陈旧索引：本轮既未触发、也未验证**：`l2s=0`、`.idx` 只有 4B 废头，所以 J11（中间那次无 L2 引导不递增 `BootSeq` ⇒ 加载陈旧索引）根本没机会跑。**它是"让 store 真落盘"之后才能验证的前置项**，不能写成"已排除"。
3. **J2 / J10 / J12 / J3 / J4 / J6 等数据面已知项，本轮一条都没被验证**：这些都是 `store` 真落盘 / 索引真生成之后才暴露的风险（世代全局、引擎回写、`RB2_L2IDX_MAX` 钳位等）。本轮 `l2s=0`，所以**既没证实也没证伪**。
4. **Verifier 开着只作稳定性结论**：两次真机都在特殊池开启下运行（V5「特殊池=开 失败分配=0」），零 BugCheck / 零新 dump / 零 ERROR **不能外推**为性能峰值或缓存数据面正确性结论。
5. **189 §7.6 三条的精确销项**：① `RbL2Store` 的 `ZwWriteFile` 是否真落盘 — ❌ 未回答；② 2GB 下 `stores` 数量与索引回读一致性 — ❌ 未回答；③ Verifier + Special pool 足迹是否触发额外失败 — ✅ **已由两次 V5「失败分配=0」回答**。不得笼统写"三条依然 unanswered"。
6. **C 方案风险边界**：把 `blk = lba/64KB` 改成「按热块分配槽位 + 索引记 Lba」是**架构级改动**，牵动索引格式 v2、CRC、`RbL2IdxSave/Load`、跨引导一致性（J11）、`RB2_L2IDX_MAX` 钳位（J12）；磁盘格式兼容面已被 J11 的 magic 变更占用过一次。`-SizeGB` 上限 128，而实测 extents 分布到 199.5GB ⇒ 放大容器**只能部分缓解**。流程：改 `src/` → 重编 → 重签 → 三锚点同步 → `deploy.ps1` → 重启 → 全量门禁 + core 66 回归。
7. **夹具加固分支缺独立复验回执**：193 的「9/9 通过、未修缺陷 0 处」适用于**加固前**版本。本轮新增的 `-ProbeStats`（7 采集点）、补采 `l2state`/`admitRejects`/`workers`、`Write-LbaProbe`、`s_Halt` 硬闸四段代码，虽在第二次真机上跑通且无异常，**但没有独立验证者按敌意用例复验过**（判据/回滚逻辑未改）。这是明确的待办，不是已销项。⚠️ **200 号收口复核不覆盖此项**：它只做交付物一致性与现场只读核验，**不是夹具代码级敌意复验**，不能拿来销项。
