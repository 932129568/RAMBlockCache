核心结论

1
[内+外]总体可行，但一处关键假设被推翻：「TestMode 可复活 V9 代码资产」不成立——无 git、备份目录（src.backup-2026-10-14）与隔离区均已清理，现存仅 rbctl.c 一行旧行为注释与 Build16 审计报告。运行时挂栈是重写而非复活，且必须用 IoAttachDeviceToDeviceStackSafe（现行 AddDevice 路径用非 Safe 版，靠「设备未启动无 IRP」侥幸安全，运行时无此侥幸——见 winprogger）。U0-1 成本由 ~2 上调至 ~2.5–3 人周。
2
[内+外]免重启测试模式整体可行，且 ROI 最高：驱动显式设计「sc stop 干净卸载」（rbdriver.c:879：全量回写→停线程→逐卷 detach 删设备）；install.ps1 的 sc create start=demand 是先例；外部证实 sc 加载不会为既有设备触发 AddDevice——运行时挂栈是必选项，方案技术路线判断正确。
3
[内]安装器 GUI 化/首跑向导/托盘/静默均可行且低风险：安装原语全是标准 Win32（CreateService/RegMultiSz/CopyFile/WinVerifyTrust，C# 一一对应）；向导接口与动效设施已预留（IFirstRunExperience/FeatureRegistry/Motion/Toast）。真正风险只在「重写丢失 fail-closed 纪律」——用「WPF 外壳包现有 exe」分期对冲。
4
[外]「安装后一次重启」不可协商有竞品实证：PrimoCache 安装后同样必须重启（教程原话+0x7B 警示），卷级过滤驱动品类固有成本。生产模式话术应为「一次重启+重启后自动配好」，不可承诺免重启安装——原方案此判断正确。
5
⚠ 未覆盖运行时挂栈三个未证项：与 volsnap 的相对位置（AddDevice 挂于 PDO 之上=volsnap 之下；IoGetDeviceObjectPointer 取到的栈顶=volsnap 之上，I/O 位置不同）、VSS 快照交互、热插拔竞态——未经真机验证。本报告给验证矩阵而非结论；建议 3 天 Spike 先行证伪。

关键要点

  • 先做 U0-1，它是复利项：之后每轮驱动改动（含 W1.5 读写路径专项）都跑零重启 dev loop，收益跨所有后续波次兑现——排期应第一。
  • 成本修正：U0-1 → 2.5–3 人周；U0-2 分 stage（v1 外壳 ~1.5pw + v2 全 C# ~2.5pw）；P0 合计 ~6–7 人周；全单 ~8.5–10.5 人周。
  • 三条硬实现纪律：Safe 版挂栈；ext 挂栈前完全初始化（!IsAttached → passthru 现行门恰好使早期 IRP 天然安全）；detach 按拆除铁律重写。
  • 最大风险不是技术是范围：安装器全量重写有吃掉波次的惯性——stage 化拆成两次交付。
  • 验证已具体到可执行：3 天 Spike → Verifier 矩阵 → WinDbg !irp → 生产/测试 A/B → 安装器四路径×签名失败注入 → 向导可用性测试。

薄弱环节与改进建议（按严重度）

  • 【高】「复活 V9」是错误假设——无 git、备份已清。改进：预算按重写计；先做 3 天 Spike（TestMode 下打开一卷→Safe 挂栈→建流→透传门翻转→两遍读验证命中），用 Spike 结论校准估算再 commit。
  • 【高】挂栈位置差异未验证——AddDevice 挂于 volsnap 之下，运行时挂栈在其之上。改进：(a) 从栈顶向下走到 FS 卷设备再挂（复刻 AddDevice 位置，建议为目标）；(b) 接受栈顶位置（测试模式专用）+ VSS 创建/删除/回滚矩阵验证（Spike 快速路径）。
  • 【中】安装器重写的范围惯性——stage 化（v1 外壳解决「黑窗恐惧」，v2 移植解决「技术债」），每 stage 独立验收。
  • 【中】sc stop 失败路径——join 超时驱动中止卸载（保数据设计），devloop 必须识别并提示「需重启一次」而非假装成功；可抄 install.ps1 的 15s 超时模式。
  • 【中】测试模式的签名边界易被误读——「测试模式」不是「可以不签名」：MS Learn 与 adersaytech 均证实 TESTSIGNING 放开的是"证书谁签发"，驱动仍必须带签名；HVCI 开启时只认自建证书签名。本工程现状恰好满足（自签 CN=RAMBoostFS Root + testsigning ON），但文档与安装器必须把「testsigning 未开 → 测试模式加载失败」翻译成用户可操作的指引。
  • 【低】devloop 签名依赖——/sm 用户证书库在沙箱/CI 不可用；devloop 分 -Sign/-NoSign 两模式。

验证思路（按执行顺序）

  • 1. 3 天 Spike（go/no-go）：TestMode 最小闭环（demand-start + 单卷运行时挂栈 + 两遍读命中）。过→全额投入；不过→退化「devcon rescan 半免重启」（设备级重扫触发 AddDevice，省整机重启）。
  • 2. Verifier 矩阵：特殊池+IRQL+死锁下，sc stop/start ×50、attach/detach ×100、USB 热插拔 ×20、睡眠/恢复 ×10；判据=零新告警、!devobj 无残留。
  • 3. 路径在位验证：WinDbg !irp 确认过滤设备在 I/O 链路每层栈单元可见（外部工程实践标准手段）。
  • 4. 位置等价 A/B：生产模式（BOOT_START）vs 测试模式（运行时挂栈）同负载同统计对账（ReadReq/ReadHit/延迟分位数一致）。
  • 5. 安装器矩阵：Win10 22H2/Win11 26H2 × 四路径（新装/升级/重装/卸载）× 签名失败注入；判据=验签先于一切变更。
