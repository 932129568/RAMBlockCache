## 2. A 批三未闭环项的最终结论

### 2.1 CacheSizeMB 收缩不回收（125 §7 缺陷 B）→ **A3 已修已部署，闭环**
- **E1 判别**（真机，两轮一致）：`AutoMemory=0/CacheSizeMB=8` 后填充 64MB，`CurBytes` 129→194MB（超限 24 倍）、`ΔEvictBytes=0` ⇒ 固定上限被整体旁路。
- **根因**：`rbctl.c RbApplyEngineConfig` 只 `rb_engine_set_max_bytes`，**从不清 `dynamic_limit`**；`cache.c rb_effective_caps` 只要 dl≠0 即全程以 dl 为准。AutoMemory=1 期间预算线程已把 dl 置为数 GB → 1→0 切换后 sticky。与 `rbctl.c:102` 注释「AutoMemory=0 → 以配置值 CacheSizeMB 为准」语义矛盾。
- **修复**：`RbApplyEngineConfig` 增 `if (!cfg->AutoMemory) rb_engine_set_dynamic_limit(g_Rb.Engine, 0);`。部署后真机实证：E2 P0 探针 32MB 写入下 `CurBytes` 6.0MB、`PeakBytes` 6.5MB ≤ 8MB、驱逐触发。**附带**：更正 `rbio.c RbRefreshMemoryBudget` 注释③失实陈述（「预算不超过 CacheSizeMB」实现中从无此钳位——自动模式预算即上限，需要硬上限用 AutoMemory=0，与 rbctl.c:99 语义一致）。
- ⚠️ **注意**：A3 使「小上限」第一次真正生效 → **驱逐/flush 并发路径在真机上第一次大规模激活** → 暴露 I47 P0。这不是 A3 引入的缺陷，是 A3 揭开的既有未验证面（125 号「不能把没触发写成通过」的预言成真）。

### 2.2 RmwReads 补读（H8）→ **真机触发 PASS，闭环**
- A2 P3b 全程 0 的原因：`ensure_file` 预填充已把目标子块载入缓存，写走 loaded 分支。
- **E3 判别**（真机，两轮一致）：冷子块 512B NO_BUFFERING 部分写 → `RmwReads` 0→**1**（触发证据）；缓存命中读与 FLUSH/关回写丢视图后的盘面读内容断言全对（[0..4K)=0x11、gap=0x00、[4608..5120)=0x5A）；`LostDirtyBytes=0`。

### 2.3 并发驱逐正确性 → **触发成功，正确性判据未闭合（被 I47 阻断）**
- E2#1：ΔEvictBytes=33MB、4 并发读者零读错、cap 契约成立、LostDirtyBytes=0 —— **触发证据充分**。

- **在 I47 根因修复前，WB+小上限姿态冻结，E2 不得复跑。**

## 3. I47 P0：0x3B 取证定界（症状级已点名，代码级归因未完成）

### 3.1 事件序列
1. boot A：E2#2 运行中黑屏挂死（无内核事件、无 dump）→ 用户硬重启。
2. boot B：注册表残留 `WriteBack=1/AutoMemory=0/CacheSizeMB=8`（E2#2 finally 未执行）→ **空闲系统 IO 全走 WB+8MB 驱逐+flush** → ~4 分钟后 bugcheck `0x3B (0xC0000005, 0xfffff805ebe9ce3d, 0xffffb8009fb72900, 0)`。
3. boot C：boot_guard 摘除过滤器 → passthrough 稳态（当前）。

### 3.2 转储证据链（单机，9 代归档 PDB，`a155de45` 代精确匹配）
- **崩溃栈**（python.exe 的读路径）：`NtReadFile → IopReadFile → … → FLTMGR → Ntfs!NtfsFsdRead → NtfsCachedRead → CcCopyReadEx → CcMapAndCopyFromCache → CcFetchDataForRead → MmWaitForCacheManagerPrefetch → KeLeaveGuardedRegion → KiCheckForKernelApcDelivery → KiDeliverApc → nt!IopCompleteRequest+0x3da → nt!KeSetEvent+0xad ← AV`。
- **出错指令**：`mov rax, qword ptr [r12]`，`r12 = 0x00750063_00650053` = **UTF-16LE `"Secu"`** —— 完成事件的指针被 UTF-16 文本整体覆盖（与 00:32 池腐坏 `" (ou"` 同族形态）。
- **APC 归属**：APC 对象位于 **MmRl**（nt!mm "temporary readlists for file prefetch" 0x900 块）内部；邻接池块为 free/TTcb，无我方分配。
- **被引用 IRP**：tag `Irp`、标记 Allocated，但 `!irp` 显示 **0 个栈位、CurrentStackLocation=0、内容含 ASCII `Ir p` 复用残迹** ⇒ **陈旧完成 APC 指向已释放并被复用的 IRP**（双重完成 / 完成后触碰族）。
- **`!verifier 3`**：崩溃瞬间我方 30+ 个 Special Pool 在途分配（chunk_create ×N + stage_run 4MB）全部健在；**崩溃现场无我方指令帧** ⇒ 覆盖写不经过我方 Special Pool 窗口（经已释放池的滞后写/非特池窗口发生）。
- **我方二进制**含 UTF-16 `"Security"`（wdmsec 静态库数据）；运行时写入者未定论（被覆盖块现内容已不含完整字符串）。
- bucket：`AV_VRF_nt!KeSetEvent`（mini）/ `AV_VRF_IMAGE_disk.sys`（full，误归）。
