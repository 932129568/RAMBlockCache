### B-4 「单次原子写入 64 位 QWORD」实为 3 次写，R-b2 未解反被放大

> 原文（L541-542 注释）：`单次原子写入 64 位 ShutdownPersistPairPrev QWORD（解决 D-04 / R-b2 双写非原子与 R-d 缺 epoch）`

代码本体（L568-572）：

```c
(VOID)RbWriteRegDword(hKey, L"LastCleanShutdown", CleanBit ? 1U : 0U);      /* 写 1 */
(VOID)RbWriteRegDword(hKey, L"LastCleanWithheld", WithheldBit ? 1U : 0U);  /* 写 2 */
RtlInitUnicodeString(&uName, L"ShutdownPersistPairPrev");
status = ZwSetValueKey(hKey, &uName, 0, REG_QWORD, &packedPair, sizeof(packedPair)); /* 写 3 */
```

它要解决的是"两次写可能只成功一次 ⇒ 旧对自洽 ⇒ 假绿"（R-b2）。但实现从**2 次非原子写变成 3 次非原子写**，且第 1、2 次与第 3 次之间没有任何事务边界。中间掉电后注册表里会出现「`LastCleanShutdown=1` 而 `ShutdownPersistPairPrev` 仍是上一纪元」的组合——比原缺陷多一种可自洽的假态。

> 附带：`RbWriteRegDword` 的返回值被 `(VOID)` 丢弃（L568-569），写失败完全不可见。这正好是 R-b2 描述的那条失败路径。

**类型**：F-01 + 内部自相矛盾。
**判定**：假。宣称的机制与其代码不符。

### B-5 QWORD 只写不读：`RbBootFailLoad` 从不消费 `ShutdownPersistPairPrev`

`RbBootFailLoad`（L503-538）只读三个 DWORD：

```c
RbReadRegDword(hKey, L"BootFailCount", &failCount);
RbReadRegDword(hKey, L"LastCleanShutdown", &cleanShutdown);
RbReadRegDword(hKey, L"LastCleanWithheld", &cleanWithheld);
```

全文检索该文档：`ShutdownPersistPairPrev` 只出现在 `RbWriteAtomicShutdownSentinel` 的写入侧与注释里，**没有任何读取点**。

所以：

- `BootEpoch` / `PersistSeq` 打进去以后无人解码 ⇒ R-d（成对读数无 epoch）**未解**；
- 判读器要用的"上一次关机结论"仍取自两个**每次开机被清零**的 DWORD（L533-534 亲手清零）⇒ 又是 F-06（观测点被自己清零）。

**类型**：F-01（声称解决但机制未闭环）。
**判定**：假。

### B-6 `clean==1 || withheld==1 ⇒ fails=0` 就是 A4 的形状，换个名字重犯

> 原文（L499-500）：`LastCleanShutdown == 1 或 LastCleanWithheld == 1 均证明上次正常走完关机（无崩溃/掉电），清零 BootFailCount。`

代码（L522-526）：

```c
if (cleanShutdown == 1U || cleanWithheld == 1U) { failCount = 0; } else { failCount++; }
```

这正是本项目 A4 缺陷的判据形状：**"某一位为 1 ⇒ 一票清零"**。仓库的修复方向恰好相反——`rbdriver.c:246` 明确写了「[A4] 写侧副作用删除：**不再**顺带写 `BootFailCount=0`」。

尤其 `withheld=1` 的语义是"**本纪元根本没挂过卷，所以故意扣留 CLEAN**"（`rbdriver.c:216-248`）。拿"故意扣留"当作"上次干净"的证据去清零失败计数，等于把 A4 的"假干净"从 `clean` 搬到 `withheld` 上，BootLoopGuard（`rbdriver.c:435`，`fails >= 2`）仍可被单票洗白。

而文档 L28 声称此设计"兼顾无卷测试机零误判与登录后崩溃零漏判"——**零漏判这一半与代码相反**：登录后崩溃但关机时 `clean=1`（有卷、脏页刷净）的引导，会在下一次开机被清零。

**类型**：F-01 + F-04（把"没崩"与"刷净"混为同一判据，正是它自己列的 D-02 罪名）。
**判定**：假。**这是全文最危险的一条**——它不是没修，是把原缺陷重新实现了一遍。

### B-7 引导失败门限从 `>=2` 放宽到 `>=3`

> 原文（L735-739）：`if (g_Rb.BootFailCount >= 3U) { ... RbModeReadOnly } else { ... RbModeFull }`

真实判据：`g_Rb.BootLoopGuard = (fails >= 2);`（`rbdriver.c:435`），消费点拒绝 attach。

文档改为 3 ⇒ 允许连续 2 次失败引导后**仍以 Full 回写模式挂载**（回写模式下 0x7B 循环的代价是数据面损坏，不只是启动失败）。这在"修安全网"的文档里属于**反向放宽**。

**类型**：F-09（"彻底解决 D-02"名不副实）。
**判定**：假，且方向性错误。

## §3 🟡 数值、量纲与绝对化断言（6 条）

### Y-1 「262,144 截断 32 GB」——实际是 **16 GiB**，且与它自己的公式矛盾

> 原文（L30）：`RB2_L2IDX_MAX=262,144 截断 32 GB`

262,144 × 65,536 B = **17,179,869,184 B = 16 GiB**。

而同一行它说新方案 `1,048,576 槽（64 GB）`：1,048,576 × 65,536 = 68,719,476,736 = 64 GiB ✓。

两句话用的是同一个换算关系（1 槽 = 64 KiB），那么 262,144 槽只能是 16 GiB。**它自己的两个数字不能同时为真**。

**类型**：F-04（量纲/换算错配）。

### Y-2 「写失效提速 30,000× ~ 500,000×」——无基准，且 `O(1)` 在构造上不成立

范围失效覆盖 N 个 64 KiB 块。文档自己的寻址是 `slot = (blk * 2654435761) % slots`，块号到槽号是**散列**的，相邻块不落在相邻槽。要把一段连续区间全部作废，必须**逐块探测**——N 次，不是"≤16 步"。

`≤16` 只是**单块**的探测窗上限（`RB2_PROBE_LIMIT 16`）。把一个"单块 ≤16 步"写成"范围失效 O(1)"，是**把单次复杂度冒充整体复杂度**。

至于 30,000×–500,000×：E0 阶段没有任何基准数据。仓库同类结论的纪律是"任何性能数字禁止宣称"（`279` 卷二 §2.5 E 组）。**类型**：F-01 + F-04。

### Y-3 「非分页池常驻占用降低 >95%（节省 >950 MB）」——基准是虚构的，新方案反而新增常驻

- 那个"1,024 MB"来自 F-5 的误读（假设每 worker 常驻 32 MB）。实际是按需增长，现场 4 个 worker。
- 新方案自己引入的常驻：
  - L1：`RB1_SHARD_COUNT 64 × RB1_DEFAULT_BLOCKS_PER_SHARD 64 × 64 KiB` = **256 MiB** 非分页，在 `RbL1Init` 里一次性 `RB_ALLOC_NPAGED`（L895-896）；
  - L2 索引表：`1,048,576 × sizeof(RB2_IDX_SLOT)`，按其结构体（4+4+8+4+1+3）= 24 B ⇒ **24 MiB** 常驻；
  - 合计 **≈280 MiB 新增常驻**。
- 净效果可能是"减少"（若原方案真占 1 GB），但**基准不存在**，所以"节省 >950 MB"无法成立。**类型**：F-01 + F-06（拿一个不存在的观测点当基准）。

### Y-5 `sync_anchors.ps1` 被描述为"同步 5 处锚点"

> 原文（L45、L2300、L2408、L2496）：`自动校验并同步全部 8 个源文件与 5 处锚点`

实测：`src/scripts/sync_anchors.ps1:2` 原句是 `the three anchors below`——**三个**。

## §6 处置建议

**一句话：不能把它当作 v10.5 的落地依据，但可以把它当作"待验证的架构提案 + 一份需要重做的现状勘误"。**

1. **现状勘误先做**（零成本、零风险）：把 §2 的 7 条按 F-01 更新进 `279` 卷二 §1 的 D-06（"文档线与源码脱节"），并把本报告作为该条的第一个实例。否则下一个人还会读到"缺 FLUSH_BUFFERS"这种已修好的缺陷。
2. **B-6 必须单独立项红队**：`clean||withheld ⇒ fails=0` 若真落地，等于把 A4 修复倒回去。这一条比其余六条加起来更值得花时间。
3. **B-1/B-3 决定这份文档的性质**：它是一份**重写提案**（连控制接口和文件划分都换了），不是补丁。任何"直接替换"的尝试都会破坏 `rbfeatctl`/bridge/验收器。
4. **Y-1 这类错误说明它的数字没有经过检查**：16 GiB 写成 32 GB、524,096 写成 524,288 的变体——这类错误在 E0 阶段无害，但一旦被抄进 E2 判据就会变成假绿。建议要求作者对每个数字给出算式。
5. **不建议现在编译**：B-2 已证明按它自己声明的构建方式必然链接失败。先修符号归属，再谈 E1。

## §7 本报告的自我边界

1. 本报告只核了**可静态判定的部分**（符号、常量、接口码、结构体尺寸、调用点存在性）。**没有**核它的算法正确性（CLOCK-Pro 淘汰、CRC32C 回退、墓碑回收的并发安全）——那需要独立红队逐函数读，不在本轮范围。
2. 本报告**未评价**其架构方向是否优于现行实现。方向对不对与事实真假是两件事；本报告只做后者。
3. 本报告对 `rbL1.c` / `rbioctl.c` 的"不存在"判定，依据是本仓库 `src/driver/` 实际文件列表（25 `.c` + 2 `.h`）。若作者另有未提供的文件，需其自行举证。
4. 所有"假"判定都可用一条 `grep -n` 复现，命令已在各表中给出 `file:line`。**不接受"我记得是那样"作为反证。**
5. 该文档作者未参与本报告。按本项目纪律（作者≠验证者），若作者有异议，应另写覆盖回执，不得修改本报告原文。
