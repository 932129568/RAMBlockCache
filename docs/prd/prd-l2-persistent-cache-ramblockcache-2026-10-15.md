## 📌 TL;DR（执行摘要）

- **一句话**：把已在代码中落地但默认关闭、且未接数据来源的 L2 只读层（`src/driver/rbL2.c`）完成**淘汰接线、配置面产品化与掉电恢复验收**，使 RAMBlockCache 获得对标 PrimoCache 的持久化缓存能力——关机不丢、开机即热。
- **为什么是它**：竞品分析证实 L2 持久缓存是技术用户（S3）为 PrimoCache 付费的**核心理由**（"关机不丢缓存，开机依然飞快，杀手锏"【社区检索】）；本品核心引擎已抽象 writeback/readback 回调，L2 读路径已完整实现，**边际工程量集中在接线与产品化，而非从零构建**。
- **范围冻结（M1）**：core 淘汰→L2 接线（`RB_WIRED_L2_ON_EVICT` 0→1，含签名调和）；单个被加速卷；只读缓存（写缓存 `RB_WIRED_WBCOAL` 预留至 M2）；容器文件 `X:\RAMBoostL2.bin` + 索引 `X:\RAMBoostL2.idx`；默认容量 32GB（1–128GB 可配）。
- **硬门禁**：掉电恢复零错数据（CRC+MISS 方向安全）；重启后第二遍 L2 命中率可量化；无新增归因崩溃；多卷场景 L2 不启用（防跨卷 LBA 污染）。
- **最大技术风险**：淘汰钩子签名两侧不一致（core 传 2 参 / 驱动定义 5 参）+ 高 IRQL 淘汰静默丢弃存储机会 + 索引键仅 LBA 无卷标识（多卷即污染）——均已定位，M1 以「单卷硬约束 + 排队补全」化解。

## 1. 功能背景与目标

### 1.1 背景：为什么必须做 L2

**用户问题**：V10.4.3 的缓存全部位于内存（L1）。关机后缓存清空，开机后常用数据需从慢盘重新读取——对大内存混合存储用户，"开机头几分钟的卡顿"和"每次重启后重新预热"是体感最强的残留痛点。竞品分析（【社区检索】Chiphell/V2EX）显示：技术用户为 PrimoCache 付费的首要理由正是 **L2 SSD 持久缓存 + 启动预取**；仓库 FAQ 13 亦自认"真正的额外加速应做 L2 SSD 持久缓存"。

**业务目标**：L2 是路线图 Phase 1 的 P0 交付物（RICE≈15，估计值），是把"可信的产品"变成"有卖点的商品"的关键拼图；无 L2 时对开机速度敏感的技术用户，产品价值主张不完整。

**工程现状（代码事实，2026-10-15 核验）**：

| 组件 | 状态 | 证据 |
|---|---|---|
| `rbL2.c` L2 读层 | **已实现，默认 OFF** | 容器格式 v2（4096B 头 + N×[16B 记录头+64KB 数据]）、逐记录 CRC32、单 IO 原子整记录写、索引 `RAMBoostL2.idx` 仅作重建加速器、60s 周期落盘、关机保存 |
| 特性开关 | `Features\Flags` 位 `RB2F_L2=0x4`，**部署默认 0 全关** | `rb_common2.h`；安全红线：Flags=0 时钩子零开销空转，IRP 行为与 V10.2 字节等价 |
| 数据来源 | **未接线** | `common/rb_wiring.h`：`RB_WIRED_L2_ON_EVICT=0`；`rbfeat.c:301` 注释"【当前状态：未接线】core 淘汰路径不感知特性层，本函数无调用方" |
| 签名一致性 | **两侧不一致** | `core/cache.c:54` 声明 `RbFeatOnEvict(PVOID key, ULONG64 seq)`（2 参）；`rbfeat.c:303` 定义 5 参（Ext, Lba, Len, Src, Hits）。宏=0 时互不编译，翻 1 必须调和 |
| 探测/存储门 | 已实现安全方向 | 探测 ≤64KB 且不跨槽；存储仅收整 64KB 块（"杜绝 v1 越界读/零填充污染"）；panic/高 IRQL 一律 MISS/忽略 |
| 统计 | 计数器已预留 | `RB_STATS2.L2Stores/L2Hits/L2Miss`（Rb2Count 槽 7/8/9） |

> **接力关系声明（防评审打穿）**：L2 决定"已能命中的热数据能留多久、开机多快"，其价值以"可命中工作负载"为前提；PRD-02 解决"哪些负载进得了缓存"。两者是接力非替代——若被质疑"普通应用都命中不了，L2 给谁用"，以此回应：M1 目标负载为可命中场景（重复读工作集：数据库类应用、游戏素材二次加载、大量小文件随机读、开发构建中间产物）。

### 1.2 目标（可衡量）

| # | 目标 | 目标值（估计基线，以基准库实测校准） |
|---|---|---|
| G1 | 重启后热工作集第二遍 L2 命中率 | ≥50%（预热充分的工作集；L1 32GB 缓存下的典型重复读负载） |
| G2 | 开机后常用应用启动的磁盘读下降 | ≥30%（A/B 对照：L2 开/关，同一镜像同一操作序列） |
| G3 | L2 探测路径延迟 | P99 <100µs（本地 SSD 顺序读 64KB 记录） |
| G4 | DRAM 元数据开销 | ≤8MB @32GB 容器（524,288 槽 ×12B ≈ 6.3MB） |
| G5 | 数据损坏事件 | **0**（掉电/撕裂/旧容器/索引错位场景，CRC+MISS 方向安全） |
| G6 | 归因本品的新增内核崩溃 | **0**（Driver Verifier + attach/detach 循环 + L2 开关循环） |

### 1.3 Non-goals（本功能不做什么）

1. **M1 不做 L2 写缓存/延时写**——`rbwback.c`（WBCOAL）为预留件，接线前提是 L2 有真实数据来源（M1 交付后才排期）；对齐路线图 MVP 冻结口径。
2. **M1 不做多卷 L2**——索引键仅 LBA 无卷标识，多卷共享容器存在跨卷污染风险（见 §6.2 R1）；单卷为硬约束。
3. **M1 不做 FlushL1ToL2 高级选项**（PrimoCache 的 L1→L2 主动转储）——M1 仅淘汰被动流入。
4. **不迁移独立逻辑卷**——已决策保留容器文件形态（见 §附录 A 决策记录）；独立逻辑卷列为远期评估项，不占 M1/M2 范围。
5. **不做 L2 容器加密/压缩**——远期。
6. **不做应用级缓存指定**——卷层驱动看不见文件语义（PrimoCache 同样不能），诚实声明，不画饼。

## 2. 目标用户与使用场景

### 2.1 目标用户

| 用户层 | 画像 | L2 价值 |
|---|---|---|
| **S3 技术用户（主）** | 32-64GB 大内存、HDD+SSD 混合或 QLC 寿命焦虑、逛 Chiphell/V2EX、愿意为"关机不丢缓存"付费 | 核心转化理由；社区 KOL 与口碑放大器 |
| **S1 存量混合存储用户** | 老机器 HDD 系统盘/仓库盘 + 闲置小 SSD | 开机头几分钟卡顿缓解；不换硬件提速 |
| **运维/批量部署者** | 网吧/电竞酒店/工作室，需统一下发配置 | CLI/注册表面免交互卷创建（对比 PrimoCache 需 GUI 建二级存储卷） |

### 2.2 使用场景与用户故事

**场景 A：开机即热（核心场景）**
> 作为技术用户，我希望关机后 SSD 上的 L2 缓存不丢失，以便开机后常用数据即刻命中、缩短开机和软件启动时间。

**场景 B：内存不够时的容量放大**
> 作为 HDD+SSD 混合存储用户，我希望热数据从内存淘汰后进入 SSD L2，以便在有限内存预算下获得更大的有效缓存容量（L1 管延迟，L2 管容量与持久）。

**场景 C：掉电不怕（信任场景）**
> 作为稳定性敏感用户，我希望掉电/异常关机后 L2 缓存自动验证、损坏块自动弃用，以便永远不错数据、不因缓存损坏蓝屏。

**场景 D：批量零交互启用**
> 作为网吧运维者，我希望 L2 配置（容器位置/容量）可经 CLI 或注册表统一下发，以便在 100 台机器上免交互启用并校验生效。

## 3. 核心功能列表及详细描述

优先级：P0=M1 必须；P1=M1 应该；P2=M2。

### FR-L2-01 淘汰接线：core → L2 数据来源（P0）

- **描述**：将 `RB_WIRED_L2_ON_EVICT` 由 0 翻为 1，使 core 淘汰路径的热干净块流入 L2。执行"一格 commit 只翻一个开关"纪律（`rb_wiring.h` 门禁由 `check_repo.py` 强制）。
- **详细要求**：
  1. **签名调和**：统一钩子契约为 `RbFeatOnEvict(Ext, LbaBytes, Len, SrcVa, Hits)`。core 侧在 `evict_victim()` 的 `chunk_destroy` **之前**捕获：块数据指针（Src）、长度、命中数（Hits，需在 chunk 结构或统计中可得——当前 core 传 `epoch` 作 seq，需评估 hits 来源，缺失时以访问次数近似或先传 0 由驱动侧策略决定）；卷标识 `Ext` 需经 `rb_stream → engine → 卷设备扩展` 映射获得（设计评审点，见 §6.2 R2）。
  2. **IRQL 排队**：淘汰可能在 >PASSIVE 的持锁路径发生。当前驱动侧直接 return（静默丢失存储机会）。M1 必须补 `Rb2PoolSubmit` 排队到 PASSIVE 执行 `RbL2Store`（`rbfeat.c:308` 注释已预留该意图）。
  3. **锁序保持**：沿用 core 既有"锁内摘链、锁外回调"模式（`cache.c:1466`），严禁回调内再取同层锁。
  4. **冷块过滤**：维持 `Hits < 2` 不进 L2 的既有策略（热数据才配持久化）。
  5. **回归**：core 16 自测目标 Release/ASan 双构建全绿；新增用例：接线开启后淘汰流路径数据完整性（存什么、探测得什么）。

### FR-L2-02 单卷硬约束与跨卷污染防护（P0）

- **描述**：L2 索引键仅为 64KB 块号（`rbL2.c`：`UNREFERENCED_PARAMETER(Extp)`，无卷标识）。多个被加速卷共享一个容器时，同 LBA 会互盖——**可能把 B 卷的数据当 A 卷的命中返回（CRC 能验证记录自一致，但验证不了"这是哪个卷的"）**。M1 以硬约束化解：
  1. L2 启用时若检测到 **>1 个被加速卷**，驱动拒绝启用 L2 并在日志/UI 明示原因（fail-closed，不静默降级）；
  2. 容器宿主卷自身不参与缓存（`RbFeatRefuseLetter` 既有机制保持，并纳入验收）；
  3. 多卷支持（键中加入卷标识）入 M2（FR-L2-09）。
- **验收**：构造双卷 + 同 LBA 写不同数据场景，验证 L2 不启用/无污染。

### FR-L2-03 配置面产品化（P0）

- **描述**：将注册表层配置（`Features\L2Letter`、`Features\L2SizeGB`）产品化为用户可理解、可校验、可持久化的配置面。
- **详细要求**：
  1. **WPF 缓存页**：「L2 持久缓存」区——启用开关、容器所在盘符下拉（仅列候选 SSD/非系统卷）、容量滑块（1–128GB，默认 32GB）、空间占用预估（容器大小 vs 宿主卷剩余空间，不足时禁用并提示）；
  2. **CLI**：`ramboostctl l2 status|enable <Letter> <GB>|disable`（或经 `rbfeatctl` 既有入口，保持协议 9 兼容——新消息需走三副本同步门禁 `check_proto_sync.py`）；
  3. **创建前警告**：首次启用明示"将在 X:\ 创建 RAMBoostL2.bin（N GB），该空间被缓存专用；删除缓存=删除该文件"；
  4. **持久化与回退**：注册表持久化；非法值（盘符不存在/容量越界/宿主卷空间不足）回退安全态并日志；
  5. **默认值**：默认关闭（与 `Flags=0` 部署红线一致）；用户启用后经 `RB2_IOCTL_REFRESH` 热加载（既有 `RbL2LazyOpen` 路径）。

### FR-L2-04 只读默认与写缓存预留（P0）

- **描述**：M1 L2 仅承接淘汰的**干净读块**（core 淘汰路径本就只淘汰干净块——脏块走回写），与"L2 默认只读、减少 SSD 写入磨损"的 PrimoCache 默认哲学一致，也最大化 M1 安全面。写缓存（延时写经 L2 落盘）为 M2 FR-L2-10，依赖 `RB_WIRED_WBCOAL` 接线，门禁纪律要求其独立 commit。

### FR-L2-05 掉电恢复与容器自愈（P0）

- **描述**：将既有安全语义产品化并验证——"掉电撕裂/旧容器/索引错位物理上不可能给出错数据，只可能 MISS"（`rbL2.c` 头注释）。
- **详细要求**：
  1. 保留逐记录 CRC32 + 记录头 Lba 双重校验；索引文件损坏/缺失 → 空索引重建（安全已有）；
  2. 容器大小不符（v1 旧容器/半途创建）→ 重写 v2 头并定长，旧数据一次性作废（既有行为，纳入 UI 提示"检测到旧版缓存，已重建"）；
  3. **真机验证矩阵**：异常关机（拔电/硬重启）×20；运行中 Kill 驱动；索引手工破坏；容器尾部截断——每种场景重启后探测零错数据（对账：重启前后同 key 数据字节级一致或 MISS）；
  4. UI/日志可见：重启后如发生容器重建/索引重建，明确告知用户（对齐 PrimoCache 4.0.1"验证恢复而非清空"的透明化做法）。

### FR-L2-06 统计与可观测（P1）

- **描述**：`L2Stores/L2Hits/L2Miss` 计数器接入 WPF 缓存页与 CLI 展示；新增"重启后 L2 命中"叙事指标（本次开机 L2 命中字节/次数），支撑"开机即热"的效果可感知（用户研究 M1/R3：效果 3 秒可感知）。
- **验收**：计数器与基准测试实际 IO 对账一致（用 diskspd/自建基准驱动可复现负载）。

### FR-L2-07 生命周期与热加载（P1）

- **描述**：L2 容器随驱动加载 lazy-open、60s 周期索引落盘（`RbL2Periodic`）、关机/卸载前保存（`RbL2Close`）；配置变更经 REFRESH IOCTL 热生效；detach 被加速卷时 L2 数据保留（卷级操作不影响容器）。

### FR-L2-08 安全边界保持（P0）

- **描述**：panic（安全模式）期间禁存禁取（既有 `RbPanicActive()` 门保持）；IRQL 自检保持（PASSIVE 之外一律 MISS/忽略）；容器宿主卷排除缓存保持；L2 相关全部走非分页池受控分配（`Rb2Alloc`）。

### FR-L2-09 多卷键扩展（P2，M2）

- **描述**：索引键与记录头加入卷标识（如卷 GUID 或设备扩展指针哈希），解除单卷约束；需重新设计容器格式（v3）与迁移策略。

### FR-L2-10 L2 写缓存（延时写）（P2，M2）

- **描述**：接线 `RB_WIRED_WBCOAL`：写入先落 L2 容器、延迟回写被加速卷；脏块管理、紧急写（urgent write）、写缓存水位；设计输入参考 bcache 脏限速（dirty throttle）与 Open CAS write-back 语义；数据安全对齐本品既有回写链（句柄关闭/Flush/卸载/关机全量回写）。

### FR-L2-11 L2→L1 提升与智能策略（P2，M2）

- **描述**：L2 命中块按频次提升至 L1（对齐 PrimoCache 4.3.0 L2→L1 预取）；直接映射冲突淘汰评估升级为组相联；cleaning/promotion 策略参数化（Open CAS ACP/ALRU 参考）。

### FR-L2-12 块粒度对齐（P2，M2）

- **描述**：L2 记录粒度现固定 64KB；与 core 可配置块大小（4K–128K）对齐评估（探测 ≤64KB 且不跨槽的约束随块放大而收紧，需基准数据支撑）。

## 4. 竞品对比分析（重点对标 PrimoCache）

### 4.1 PrimoCache L2 深度画像（事实来源：Romex 官网规格页/知识库/已知问题列表，2026-10-15 检索）

| 维度 | PrimoCache 事实 |
|---|---|
| 架构 | L1（物理内存/UIMMI 不可见内存）+ L2（SSD/闪存盘）双级；L2 持久，重启后热数据仍在 |
| 存储形态 | **专用「二级存储卷」**——SSD/闪存盘上的 PrimoCache 专用逻辑卷，存索引+缓存数据；需 GUI 创建管理 |
| 默认策略 | L2 **默认仅缓存读数据**（减少二级存储卷写入磨损）；可经高级设置开写 |
| 采集机制 | 自动记录被加速盘常用读数据，**系统空闲时**保存至 L2；「忙时采集间隔」参数控制忙时保存速度 |
| 层级互动 | L1 未命中→查 L2；L2 命中→部分数据转储到 L1（4.3.0 起 L2→L1 预取） |
| 掉电恢复 | **4.0.1 起：非正常关机后启动时验证恢复而非清空** |
| 容量 | 规格页 0–128TB（视版本）；标准版约 2TB、Pro 32TB（竞品矩阵口径） |

### 4.3 GitHub 开源项目调研与可借鉴设计（检索时间 2026-10-15）

| 项目 | 形态 | 可借鉴点（落入本 PRD 的位置） |
|---|---|---|
| **Open CAS / OCF**（Open-CAS/open-cas-linux，open-cas.github.io） | Linux 块缓存框架（C meta-library + 内核适配器） | ① **cache/core 设备模型**：本品 = 被加速卷（core）+ 容器（cache），映射清晰；② **模式矩阵语义**（WT/WB/WO/PT/WA）——M2 写缓存的模式命名对齐行业术语；③ **fail-closed**：cache 设备无响应时对相关 core fail all IO——本品 Zw 文件 IO 失败即 MISS（读路径 fail-open 但方向安全：宁可多下盘），M2 写路径须显式 fail-closed 设计；④ **metadata 与容量成正比**、cache-line-size 可调降开销——本品索引 12B/64KB 槽（≈0.02%），固定 64KB 记录粒度，M2 评估可调；⑤ **块大小兼容约束**（cache 逻辑块不得大于 core）——本品"探测 ≤64KB 且不跨槽"同构；⑥ **空闲 opportunistic flush**——本品 60s 周期 + 关机保存，M2 增加空闲触发 |
| **bcache**（Linux mainline；bcache-tools） | 块级 SSD 缓存 | ① **脏数据限速**（dirty throttling）——M2 L2 写缓存的回写速率控制设计输入；② 顺序写检测与写合并——与 PRD-03 预取共用顺序流检测思路；③ miss 旁路不阻塞——本品读路径同构 |
| **dm-cache**（device-mapper） | 策略插件化块缓存 | cleaning/promotion **策略与机制分离**——M2 FR-L2-11 策略参数化的架构输入 |
| **flashcache**（facebookarchive/flashcache） | 早期 SSD 缓存实践 | 模式语义（write-back/through）与脏块管理的工程教训；写入放大治理（合并 vs 放大权衡，PrimoCache 已知问题 #007 同题） |
| **RapidDisk / ImDisk** | RAM disk / 虚拟磁盘（Linux/Windows） | 容器/设备生命周期管理工具化模式；ImDisk 的 Windows 存储栈驱动工程实践（签名、PnP、altitude 处理）对 PRD-02 有直接参考价值 |
| **mhtvsSFrpHdE/prefetch** | 用户态文件级预取 | 反向证据：算法调度型缓存"无法指定缓存内容"、用户态方案受 OS 缓存机制制约——佐证卷层驱动方案的存在必要性（本品立场） |

**调研结论**：Windows 侧无成熟开源「块缓存驱动」可直接对标；L2 的持久化/恢复/策略设计参考主要来自 Linux 生态（Open CAS 最同构），模式语义、cleaning/promotion 分离、fail-closed、metadata 开销控制均可借鉴；**本品的差异化空间不在"再实现一个 L2"，而在安全语义透明化 + 零卷管理形态 + 安全工程链**。

## 5. 差异化亮点

1. **「验证恢复」语义的块级透明化**：PrimoCache 4.0.1 做到"启动验证恢复而非清空"（卷级）；本品容器逐记录 CRC + 记录头校验，**块级**保证"撕裂/错位只可能 MISS、不可能错数据"，且 UI 明示重建事件——把安全做成用户看得见的证据（对打破解生态与蓝屏恐惧）。
2. **零卷管理形态**：容器文件 vs PrimoCache 专用逻辑卷——无分区表操作、无盘符占用、删除文件即彻底移除、宿主卷空间不足时优雅降级；批量部署可纯注册表/CLI 下发（对比 PrimoCache 需 GUI 建二级存储卷）——直接服务网吧/电竞酒店批量场景（竞品分析机会 3）。
3. **安全工程链延伸到 L2**：SHA256 部署门禁、崩溃修复台账、异常退出安全模式（panic 禁存禁取）、宿主卷自动排除——L2 不是裸功能，是装在既有安全框架内的功能。
4. **「省」经济学叙事承接**：L2 承接 L1 淘汰热块 = 用闲置 SSD 空间放大有效缓存，配合自动内存预算（物理内存 25%）与延迟写合并，在存储超级周期（内存/SSD 涨价）讲"不花钱扩缓存"的故事。
5. **低价 + 中文原生 + 现代 UI**：对标 $29.95 的传统 Win32 界面，本品以 ¥39-69 卡位（竞品分析定价建议）+ WPF 五页控制台 + 实时 L2 统计图表。

## 6. 技术可行性初步评估

### 6.1 现状盘点（代码已验证）

- **读路径完备**：探测（索引→记录读→CRC→拷贝，≤64KB 不跨槽）、存储（整块、单 IO 原子写、直接映射索引）、持久化（v2 容器 + idx 加速器 + 60s/关机落盘 + LazyOpen 重建）、门（flag/panic/IRQL/冷块）、统计（槽 7/8/9）。
- **部署安全**：`Flags=0` 全关时零开销空转，IRP 行为与 V10.2 字节等价——L2 可在验证基建未完成前合入主干而不改变现网行为。
- **核心引擎双栖**：`core/cache.c` 平台无关（RB_KERNEL_BUILD 条件编译），淘汰路径已有"锁外回调"模式与 `#if RB_WIRED_L2_ON_EVICT` 守卫——接线是"翻转开关 + 补实现"，不是架构改造。

### 6.2 关键风险与技术债（按严重度）

| # | 风险 | 影响 | 化解 |
|---|---|---|---|
| R1 | **索引键仅 LBA 无卷标识**：多卷共享容器时同 LBA 互盖，可能跨卷错配数据（CRC 验证不了卷归属） | **数据损坏（正确性）** | M1 单卷硬约束（FR-L2-02，fail-closed 拒绝启用）；M2 键扩展（FR-L2-09）。**不接受"M1 先开着、用户只会用一个卷"的侥幸** |
| R2 | **钩子签名调和 + Ext/Hits 来源**：core 淘汰点只有 (start, epoch)；驱动需要 Ext/Len/Src/Hits | 接线返工、锁序争议 | 设计评审先行：数据指针在 `chunk_destroy` 前捕获；Ext 经 stream→engine→卷扩展映射（或流上携带）；Hits 缺失时以 epoch/访问统计近似并在 PRD 备案 |
| R3 | **高 IRQL 淘汰静默丢存储**：当前直接 return，持锁路径淘汰的块永远进不了 L2（无错，但命中率损失） | 效果不达 G1 | M1 补 `Rb2PoolSubmit` 排队（FR-L2-01.2） |
| R4 | **直接映射冲突互踢**：同槽块互盖，64KB 粒度下 32GB=524288 槽，冲突率需基准确认 | 命中率低于预期 | M1 基准测冲突率；M2 组相联评估（FR-L2-11） |
| R5 | **宿主卷空间/IO 竞争**：容器与宿主卷用户数据争 IO；宿主卷满/故障 | L2 不可用或拖慢宿主 | 创建时空间校验；宿主卷不缓存（RefuseLetter）；Zw 失败即 MISS；宿主卷故障时 L2 自动禁用并告警 |
| R6 | **验证债（组织级）**：本机无 WDK/MSVC/.NET SDK，编译与真机均未验证；两次 No-Go 共识 | 一切"已实现"未经运行证明 | M1 排在 Phase 0 验证基建（Gate 0）之后启动；本 PRD 所有验收以真机 + Driver Verifier 为凭 |
