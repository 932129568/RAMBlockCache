# 218 — C 方案第二刀：`RbL2ProbeFill` 支持跨块 miss 区间切片

> 触发：`217` §6-2，用户 2026-11-13 00:24 选 C。
> 范围：**只改 `src/driver/rbL2.c` 一个文件**。不动 `rbfeat.c` / `rbio_worker.c` / `rbio.c` / 索引格式 / 容器格式 / 三副本 proto。
> 状态：设计定稿 → 实现 → 构建 → 门禁 → **待用户 UAC 签名部署 + 重启 + 真机验收**。

---

## §1 问题

`RbL2ProbeFill` 的入口门是「单块」语义：

```c
if (!dst || len == 0 || len > RB2_L2BLK) return STATUS_NOT_FOUND;   /* :978 */
...
if ((ULONG64)off + len > RB2_L2BLK) goto cleanup;                   /* :995 跨槽拒绝 */
```

而调用方传的是 **core 的整个 miss 区间长度**：

| 调用点 | 传入 len | 后果 |
|---|---|---|
| `rbio_worker.c:256`（路径①，>1MB 全覆盖直读入 tgt） | `mr->len`，可到 64MB | `rbfeat.c:823` 的 `Len<=1MB` 门已先拒（路径① 恒 >1MB ⇒ **永久不命中**） |
| `rbio_worker.c:289`（路径②，32MB 分片） | `clen` ≤ 32MB | >1MB 被 rbfeat 门拒；≤1MB 但 >64KB 被 `:978` 拒 |

**结果**：只有「miss 区间 ≤64KB 且不跨槽」的读才会命中 L2。实测 1MB 分块顺序读 128MB 只换来 `l2m +8`（`217` §3），真实负载的多数 miss 区间被整段跳过。

`rbfeat.c:823` 的 `Len <= (1u<<20)` 注释已自认「阈值与 L2 自门 1MB 对齐」。

---

## §2 方案（最小改动）

**把 `RbL2ProbeFill` 从「单块填充」升级为「区间填充」，内部按 64KB 块边界切片。**

### 2.1 不变量（正确性根基）

1. **返回值语义不变**：`STATUS_SUCCESS` ⇔ **整个 `[lba, lba+len)` 已被写入 `dst`**；`STATUS_NOT_FOUND` ⇔ 调用方必须整段重读覆盖。
2. **部分填充 + NOT_FOUND 是安全的**，已逐个调用点核实：
   - `rbio_worker.c:256-260`：成功 ⇒ `*ps=SUCCESS` 免下盘；失败 ⇒ `RbSyncIo(..., dst, mr->len, NULL)` **写满整段**。
   - `rbio_worker.c:289-293`：同上，`RbSyncIo(..., st, clen, NULL)` 写满整个 staging 片。
   - 唯一调用方是 `rbfeat.c:824`，没有第三条路径。
3. **每片不跨槽**：切片按块边界切，`off + take ≤ 64KB` 恒成立。
4. **`lba` 无需 64KB 对齐**：`off = lba % 64KB`，首片 `take = 64KB - off`，`RbL2ProbeFill` 的记录拷贝本身就是 `(rec+1)+off, len`，天然支持非对齐首部。（core 的 miss 区间按 4K 子块对齐，所以 `off` 必是 4K 倍数，但不依赖该性质。）

### 2.2 两阶段（避免"最后一片 miss 导致前 15 片白拷"）

```
阶段 1 预检（零 IO、零拷贝、零分配）：逐片 RbL2IdxProbe(blk, slots)
        任一片不在索引 → 立即 NOT_FOUND（L2Miss +1），一行不写
阶段 2 填充：alloc 一次 65560B 缓冲，逐片复用
        RbL2Io 读 65560B → 校验 Lba/VolId/CRC → 拷 [off, off+take) 到 dst
        每片成功 L2Hits +1；任一片失败 → NOT_FOUND（L2Miss +1）
        每片前检查 s_Halt（Close 排队时尽快让路）
```

预检把「16 片里有 1 片不在」的常见情形的代价从「1MB memcpy + 16 次容器读」降到「16 次哈希表查」。

### 2.3 代码结构

```c
static BOOLEAN RbL2FillPiece(PRB2_L2HDR rec, ULONG64 blk, ULONG slot,
                             ULONG off, ULONG take, PVOID dst);   /* 新增 */
static NTSTATUS RbL2FillSpan(ULONG64 lba, ULONG len, PVOID dst, ULONG slots); /* 新增 */

NTSTATUS RbL2ProbeFill(...)
{
    ... 门检查；len 上限 64KB -> 1MB ...
    ... VolId 闸 / s_Ops / LazyOpen / s_Halt / slots 快照（全部一次，与现在相同） ...
    blk = lba / 64KB; off = lba % 64KB;
    if (off + len <= 64KB) {  /* 单块快路径：逐字节保持原样，零回归风险 */ }
    else                   { st = RbL2FillSpan(lba, len, dst, slots); }
}
```

**单块路径（`:993-1022`）一个字节都不改**——它已被 2048 次真机命中验证过（`217`）。切片只走新分支。

### 2.4 为什么不同时放宽 `rbfeat.c` 的 1MB 门

**刻意不动。** 理由：
1. 门槛放大是**独立的性能参数决策**。若同时改两处，真机出问题无法归因。
2. 1MB = 最多 17 片，单次调用上限 17 次 64KB 容器读（~1-2ms）。放到 32MB 就是 512 片，可能引入数十 ms 的数据路径延迟。
3. 最小改动优先（R10）。门槛放大可在切片机制真机验证后单独一轮。

**已知代价**：路径①（>1MB 全覆盖）仍永久不命中；路径② 中 >1MB 的分片仍不命中。⇒ 本轮收益上限是「≤1MB 的 miss 区间」。

## §3 行为变化清单（必须同步进文档与判据）

| 项 | 改前 | 改后 | 影响 |
|---|---|---|---|
| `len > 64KB` 的读 | 一律 NOT_FOUND | 切片填充 | 目标行为 |
| **`L2Hits` 计数粒度** | 每次 probe 调用 +1 | **整段成功后按片追加**（1MB 全中 = +16；任一片失败 = **+0**） | 判据 `dL2h>0` 仍等价于「这次调用没下盘」；「hits==读次数」的旧假设失效，新口径 = 真正被 L2 服务到的块数 |
| **`len<=64KB` 但跨块的读** | 一律 NOT_FOUND | 切片成 2 片，可能命中 | **新行为**（红队指出原 §3 漏登记）。core chunk=64KB 时正常不会出现；只有调用方传非块对齐区间才可能。纯增益：原本整段放弃 |
| `L2Miss` | 每次 probe 调用 +1 | 每次 span / 单块调用 +1（**不按片计**） | 一个 16 片的 span 全 miss 只 +1，与"读操作 miss 次数"一致 |
| `s_Ops` 在飞窗口 | 1 次 64KB 读 | 最多 17 次 64KB 读 | `RbL2Close` 排空等待从 ~0.1ms 到 ~2ms；循环内每片查 `s_Halt` 早退 |
| 内存 | 每片 alloc 65560B | span 内复用 1 次 | 更好 |
| 单块读（≤64KB） | 原路径 | 原路径 | **零变化** |

## §4 风险与缓解（自审，21 条）

| # | 风险 | 判断 | 缓解 |
|---|---|---|---|
| R1 | 部分填充 + NOT_FOUND 导致 dst 脏 | **安全** | 已核实两个调用点都是整段覆盖写（§2.1-2） |
| R2 | 新增调用方将来破坏该假设 | 合同风险 | 在 `RbL2ProbeFill` 头注释里把「NOT_FOUND ⇒ 调用方必须整段覆盖」写成显式契约 |
| R3 | 预检与填充之间索引被覆写/Drop | **原论证错误（红队必修 P2）**：三重校验只证明「记录本身没坏」，**不覆盖** `Use=0` 而载荷仍为旧值（DropRange 先 `++s_Gen` 再清 Use，载荷留给下次 Store 覆写，`rec->Lba` 仍是旧值 ⇒ 校验全过）。单块路径暴露 1 次 IO，切片把它放大到最多 17 次 | **已修**：span 首尾 `RbL2Gen()` 夹逼 + 每片 `RbL2IdxProbe` 复检，任一不符整段放弃 |
| R22 | `lba + len` 回绕 ⇒ 两个循环一次都不执行 ⇒ 返回 SUCCESS 而 dst 零写入 ⇒ 调用方跳过下盘把未初始化缓冲交给用户态 | **红队必修 P1**。当前两个调用点不可达（core 区间钳在 DiskSize 内），但「契约不变量不能建立在未校验的调用方假设上」 | **已修**：入口 `if ((ULONG64)len > (ULONG64)-1 - lba) return NOT_FOUND`（与同文件 DropRange 的饱和钳位同款防御） |
| R23 | 「15 片命中 + 1 片失败」也会让 `dL2h>0`，而该次读实际仍下盘 ⇒ 判据失真 | **红队建议 4，成立** | **已修**：计数改为整段成功后按片累加；失败一分不加 |
| R4 | `RbL2Io` 短读留旧残留 | 安全方向 | 短读 ⇒ CRC 不匹配 ⇒ NOT_FOUND |
| R5 | `lba+len` 溢出 | 无 | len ≤ 1MB；卷偏移 < 2^63 |
| R6 | `off+take > 64KB` | 无 | `take = min(64KB-off, end-cur)` |

| R9 | 循环内 s_Halt | 已处理 | 每片前检查，早退 |
| R10 | 片数爆炸 | 已限 | len ≤ 1MB ⇒ ≤17 片 |
| R11 | 缓冲复用污染 | 无 | 每片 `RbL2Io` 写满 65560B |
| R12 | 计数口径改变破坏现有判据 | **需同步** | §3 明列；`p5_verdict.py` 与夹具的硬判据只依赖 `dL2h>0` / `dL2m=0`，不受影响 |
| R13 | 性能负收益（16 次随机 64KB < 1 次 1MB 顺序） | **真实存在** | 用户已明确「不要求收益性」；必须在报告里如实写明，不作性能结论 |
| R14 | 跨引导陈旧数据被"放大命中"（J11） | 既有风险 | VolId+BootSeq+CRC 三重校验不变；J11 仍为未验证项 |

## §5 验收判据（真机，必须新增阶段 D）

现有 `-P5B` 只做 64KB 定向读 ⇒ **走单块路径，验证不到新代码**。必须新增：

**阶段 D：跨块切片定向读**
1. 从阶段 A 的 2048 条 LBA 中找出**连续 64KB 对齐块段**（本轮实测最长连续段 = **474 块**，起始 blk `3046401`，`3046401*65536 % 65536 == 0`）。
2. 取前 16 个连号 blk = **1MB 连续区间**，`\\.\D:` + `FILE_FLAG_NO_BUFFERING` 单次 1MB 读，byte offset = `blk0 * 65536`。
3. 判据：
   - `ok = 1/1`（1MB 读成功、off=0）
   - **`dL2h = +16`**（16 片各计 1 hit）
   - **`dL2m = 0`**
   - `dL2s = 0`，`l2state = 1`
4. 对照（旧驱动/旧路径）：同一 1MB 读 `dL2h = 0`（`:978` 长度门拒）——本轮改动前已由首轮 P5 的 `hits=0` 间接证明。
5. 附带验证「不完整段」：读 1MB + 4KB（跨 17 片，尾部 4KB 无对应块）⇒ 期望 NOT_FOUND 语义下**不该出现 dL2h=17 而数据不全**；由于工具无法直接观测返回码，改为**取 16 块内的 1MB 区间**为主判据，不构造尾部残缺。

**回滚/安全**：夹具默认 `ROLLBACK COMPLETE`；本轮改动不改变回滚路径。

**通过线**：`dL2h == 16 && dL2m == 0 && l2s > 0 && ERROR == 0` ⇒ 切片生效。
`dL2h == 0` ⇒ 切片未生效（新镜像未加载 / 门未放宽 / 索引缺失），**必须区分三者**（看 `p5b` 阶段 A 是否拿到 16 连号块 + 部署件 sha）。

### 8.1 结论分布

| 编号 | 红队判定 | 是否成立 | 处理 |
|---|---|---|---|
| 1 | **缺陷 P1**：`lba+len` 可回绕 ⇒ 两个循环一次都不跑 ⇒ 返回 SUCCESS 而 dst 零写入 ⇒ 调用方跳过下盘，把未初始化缓冲交给用户态 | **成立**（当前两个调用点不可达，但契约不变量不得建立在未校验的调用方假设上） | **已修**（R22） |

| 4 | 建议：L2Hits 每片即时 +1 会让 `dL2h>0` 不再等价于「这次没下盘」 | **成立** | **已修**（R23：整段成功后按片累加） |
| 5 | 建议：更简实现——在调用方按 64KB 切片，ProbeFill 契约完全不动（零内核风险） | 技术上成立 | **不采纳**，理由：会增加 16 次 `RbFeatOnMiss`/`Rb2Count`/`RbSyncIo` 协调开销与错误语义（任一片失败时前几片已写进 dst，调用方必须能按片回滚），把复杂度从「一个函数内」搬到「数据路径主循环里」。当前实现把两阶段与计数都收在 `RbL2FillSpan` 内部，对外契约仍是「整段全中或整段放弃」，更难写错 |
| 6 | 阶段 D 只覆盖「16 片全中」一种分支；预检失败 / 中途 drop / 部分命中在真机取证里未构造 | 成立（红队建议） | **未处理**，如实记为验收边界。这三条分支都是「返回 NOT_FOUND ⇒ 整段下盘」的安全方向，其代价是性能而非正确性；构造它们需要注入式故障（改驱动或容器篡改），本轮不做 |

### 8.2 红队明确确认无问题的部分

- 切片算术（首片非对齐 / 尾片 / `len` 非 64KB 整数倍）经手工代入核验正确
- 与单块路径的校验字段、失败计数**语义等价**（失败一律 NOT_FOUND）
- 调用方契约核实：`rbio_worker.c:259` / `:292` 两处在 NOT_FOUND 时都用 `RbSyncIo` 写满整段 ⇒ 部分填充无害
- `L2Hits` 的消费者（`rbfeat.c` 导出、UI、桥接）没有任何"hits 必须等于读次数"的假设会因此被破坏
