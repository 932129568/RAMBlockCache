## 2. P1：为什么 `INCONCLUSIVE` 实际是 PASS（B4 判据缺陷）

### 2.1 决定性证据：`.idx` mtime 在开机后变化

`RbL2BootUnsealInt`（`rbL2.c:418-455`）**只在磁盘头 `magic == RB2_IDX_MAGIC` 时才写 4 B zero**（`:446`）。prepare 之后头是 `00000000`，所以它开机时**不写、mtime 不动**（`250` 已确认，本轮再次成立）。

因此 21:59:31 那次 4 B 写入**只能来自 `RbL2IdxUnseal()`**（`rbL2.c:371-380`，无条件 `ZwWriteFile` 写 4 B zero）。该函数只在 `RbL2LazyOpenInt` 的**成功路径**里被调用（`:813` / `:819`，`:844` 紧随其后 `s_State = 1`；`rbL2.c:383` 注释明确「A.2 的 unseal 只在 `RbL2LazyOpenInt` 的成功路径里执行」）。

⇒ **新引导里 `RbL2LazyOpenInt` 成功执行过，容器确实被打开**，与 `pre stats state=1` 一致。

### 2.2 是谁调用的：开机后没有 REFRESH

| 路径 | 证据 |
|---|---|
| 控制面 `RbL2LazyOpen()` = `RbL2LazyOpenInt(TRUE)` | **唯一调用者** = `rbfeat.c:718` 的 `RB2_IOCTL_REFRESH` |
| 开机初始化 | `Rb2Init`（`rbfeat.c:542`）只调 `Rb2ReloadFlags()` 读 Flags，**不打开容器** |
| 守护脚本 | `C:\ProgramData\RAMBoost\boot_guard.ps1` / `logon_disarm.ps1` 无 `refresh` / `rbfeatctl` 调用（只有一行 L2 注释） |
| 用户动作 | 21:58:32 开机 → 21:59:55 才双击 verify，其间无人工 refresh |

⇒ 打开容器的只能是数据路径 `RbL2LazyOpenInt(FALSE)`（`rbL2.c:1112` 探针 / `:1215` 存储）。

### 2.3 与旧构建的前后对照

旧构建 `7125d219…` 的 `rbL2.c:1093` 卷身份门位于懒开**之前**：开机后 `s_VolId==0`，请求直接 `return STATUS_NOT_FOUND`，懒开根本不执行 ⇒ `state` 保持 0、`.idx` 不被写、必须人工 REFRESH 才能打开（`249` 真机实证：`state 0→1` 只在 refresh 后）。

本轮新构建：`state=1`、`l2m=1`（开机后第一次 IO 就产生一次 L2 探测）、`.idx` mtime 开机后更新 —— 三条同时成立。**P1 放行补丁生效。**

### 2.4 B4：我方判据缺陷（不改判据，只登记）

`l2_p1_verify.py` 要求 `pre.state==0` 才判 P1。但 Windows 开机后到用户双击脚本之间必然有自然 IO（本例 59 秒、`bm=8192` 即 8 KiB 已读），容器会被抢先打开 ⇒ 该前提**在真机上结构性不可满足**。这与 B3 同属「判据设计错误」，不是驱动缺陷。

**纪律处置**：本轮**不修改判据、不改退出码、不把 INCONCLUSIVE 改写成 PASS**。§0 的「P1 生效」是基于 §2.1–§2.3 的**独立代码 + 真机证据链的分析结论**，不是脚本判定。若需要脚本级 PASS，须先由独立红队复核 B4 修正提案（例如把判据改为「开机后无 REFRESH 且 `.idx` 在开机后被 unseal 写」），再跑一轮。

## 3. P2：机理升级（本轮最重要的负面结论）

### 3.1 这次零行是有效证据

上一轮（`255`）的零 `pwr:` 行不能判，因为 20:05 关机时内核仍是 15:08 加载的旧映像。本轮不同：

- `7d6222f3…` 于 20:06:14 引导加载（`DriverEntry ok`），一直跑到 21:58 关机；
- **二进制验证**：`dist/RAMBlockCache.sys` 中 `pwr: SYSTEM power irp` 与 `pwr: DEVICE power irp` 的 UTF-16LE 字符串**各存在 1 次**（`192,736 B` 文件内搜到），`shutdown: L2 index save failed` 也在 ⇒ P2 打点代码确实编译进部署件；
- `rbdriver.c:1113` 确实注册了 `MajorFunction[IRP_MJ_POWER] = RbDispatchPower`；
- 全 `driver-*.log` 目录 `grep -rn "pwr:"` **零命中**，且本引导段 `ERROR=0 / l2:=0`。

⇒ **`RbDispatchPower` 入口一次都没有被调用**，即 `IRP_MJ_POWER` 没有派发到这个卷过滤设备对象。

### 3.2 与 `250` 表述的差异

`250` 推断「`SystemPowerState` 的 SET_POWER 只发到 PDO，卷过滤器只收 `DevicePowerState`，故 `rbmsg.c:239-258` 是死代码」。本轮打点表明**连 `DevicePowerState` 都没到**。合理机理：卷是逻辑设备栈，不参与 D0–D3 设备电源状态转换，Po 不向该栈下发 `IRP_MJ_POWER`（R7：这是与证据一致的解释，**未做运行时 IRP 追踪**）。

### 3.3 连带影响（全部为真，但有边界）

`RbFlushAllDirty` / `RbHotSnapshot` / `RbL2IdxSaveGuarded` / `RbRegSetClean(1)` 全部位于 `RbDispatchPower` 内（`rbmsg.c:239-279`），因此：

- 干净关机时的索引定稿、热区指纹持久化**从未发生**；
- `RbRegSetClean` 唯一写 1 的调用点是 `rbmsg.c:279`（写 0 在 `rbdriver.c:213` 读后消费）⇒ `LastCleanShutdown=1` **从未被置过**。`250` 中「清零 vs 从未置 1」两因并列，可收敛为**后者为主因**；
- **不能据此声称「关机会丢数据」**：`IRP_MJ_FLUSH_BUFFERS` 由文件系统下发（`RbDispatchFlush`，`rbio.c:580`），该路径在关机序列是否被调用**未验证**。能确定的只是：写回模式的关机兜底**不能**建立在 `RbDispatchPower` 上。

## 6. 根除 B2 的正确机制（**提案，未落地，待红队 + 独立复核 + 用户拍板**）

既然 `IRP_MJ_POWER` 不到卷过滤设备，改 `RbDispatchPower` 的 `if` 条件或改用 `DevicePowerState` 都无效。正确做法是 WDM 的**显式关机通知**：

```
1) AddDevice 成功后：IoRegisterShutdownNotification(FilterDeviceObject)
2) MajorFunction[IRP_MJ_SHUTDOWN] 从 RbPassThrough 改为新的 RbDispatchShutdown
   （rbdriver.c:1117 当前已有占位分派，但没有注册 ⇒ 系统不会给它发 IRP_MJ_SHUTDOWN）
3) RbDispatchShutdown 内做：
      RbFlushAllDirty() -> RbHotSnapshot() -> RbL2IdxSaveGuarded() -> RbRegSetClean(1)
   再按标准完成/向下转发 IRP
4) 移除/卸载路径：IoUnregisterShutdownNotification
```

`IRP_MJ_SHUTDOWN` 由 I/O 管理器在**文件系统仍可用、PASSIVE_LEVEL** 时派发给注册过的设备对象，适合做 `Zw*File`，不需要 `IoQueueWorkItem` 延迟完成 power IRP 那套复杂骨架 —— 比 `251` §P4 设想的方案更简单、更符合 WDM 语义。

**风险与必做验证**：
- `RbRegSetClean(1)` 一旦真正生效，`rbdriver.c:302-331` 的 `BootFailCount` / SafeMode / self-disable 安全网**第一次上线**，须单独一轮验证（2 次干净重启 + 1 次非干净重启）；
- `IoRegisterShutdownNotification` 的注册对象是 FiDO，需确认每个卷设备只注册一次、移除时配对注销，否则关机回调打到已释放对象 ⇒ 0x9F/蓝屏；
- 修改共享代码前先看全部调用方（R10）；内核改动前须过独立红队 + 独立复核，再重编 → 重签 → `sync_anchors.ps1` → 部署（R2/R8）。
