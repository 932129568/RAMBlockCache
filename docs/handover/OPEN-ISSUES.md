### H-3 `RbStartIoWorkers` 的 6,328 B 单帧未改池

**现状**

- 线上件里 `mov eax,0x18a0`（= 6,304）出现 **1 处**（本轮字节级复核，`3C696E14`）；`frame.log` 记「全映像最大单帧 = 6328 B（51.5% of 12KB）」。
- 来源已确证：`rbio_worker.c:1049` 的 `ULONG n = KeQueryActiveProcessorCountEx((USHORT)0xFFFF)` 是唯一源码指纹；`auxT[RB_PCPU_MAX=256] × RB_AFFIN_TARGET(24 B) = 6,144 B`。
- **它不在 0x7F 的崩溃路径上**：崩溃走的是 `RbDispatchDeviceControl` 的透传分支（`298 §1.2`）。

**为什么没做**

`298` 明确把它列为**候选 3（P1，独立批次）**，理由是不建议与候选 1/2 同批：

> 它碰线程调度/亲和性语义，改动面与验证面都大得多，会把「栈帧修复」这一批的验收搅在一起。

这是正确判断——0x7F 这一批的验收还没完成（只有「未复现」），混入第二类改动会让崩或不崩都不可归因。

**做之前必须先解决什么**

- 先让 0x7F 这一批**结束**（复测窗口关闭、Verifier rearm 决策做出）。
- 6,328 B 帧是**线程创建时**的栈，不是 IRP 路径 ⇒ 它的风险面与 0x7F 完全不同（影响 worker 线程自身会不会 overflow），需要独立的栈核算，不能套用 `slack(F) = 1,448 − F` 那个公式（那是卷栈预算，不是线程栈）。
- 改池化会改变 `auxT` 的生命周期 ⇒ 要重新审 `RB_AFFIN_TARGET` 的对齐/亲和性假设。

### H-4 `299 §3.2` 的 slack 表数值不自洽（本轮新发现）

**现状**

`299` §3.2 的表：

| 状态 | 入口帧 F（表内） | slack（表内值） | 用 `slack = B − F − D` 复算（B=11,208） | 复算 vs 表内 |
|---|---|---|---|---|
| 现状（旧件 + VF ON） | 1,480 | **−32** | 11,208 − 1,480 − 9,760 = **−32** | **一致** ✓ |
| 修复后 + VF 保留 | 120 | **+1,128** | 11,208 − 120 − 9,760 = **+1,328** | 复算**多 200** |
| 修复后 + VF 关闭 | 120 | **+8,216** | 11,208 − 120 − 2,640 = **+8,448** | 复算**多 232** |

三行的 `B` 由第一行反解唯一确定为 11,208（`−32` 只有这一个解，因为 `B` 是栈预算常量）。**后两行用同一个 B、同一个 F 复算不出表内值。**

**这不是「约等于」，是口径混用**：`F=120` 是 `check_stack_frame_budget.py:156 rsp_alloc()` 的口径（**只累计真正下移 RSP 的字节**：7 push = 56 B + `sub rsp,0x40` = 64 B = 120 B，本轮已用线上件机器码复核：`55 56 57 41 54 41 55 41 56 41 57 … 48 83 ec 40`）。

逐行反解隐含的 F（`F = B − D − slack`）：

| 行 | 反解 F | 与实测 120 的差 |
|---|---|---|
| 1（旧件） | 1,480 | 与实测崩溃件帧 1,480 一致 ✓ |
| 2（修复 + VF ON） | **320** | **+200** |
| 3（修复 + VF OFF） | **352** | **+232** |

**这里有两个独立的问题，不是一个：**

1. **F 不是 120**：第 2、3 行反解出 320 / 352，都不是本轮机器码实测的 120（`55 56 57 41 54 41 55 41 56 41 57` = 56 B，`48 83 ec 40` = 64 B，合计 120）。
2. **两行反解出的 F 还互不相同**（320 vs 352，差 **32 B**）。同一个修复件、同一张表，两行的「入口帧」不可能不同 ⇒ 说明表格不是用同一个 `F` 列算出来的，而是三个 slack 各自独立估出来的。

**32 B 这个差值不是巧合**：它恰好等于原缺陷的缺口（`−32 B`）。**极可能是把「修复带来的增量」和「剩余缺口」在同一列里相加/相减时符号搞混了一次**。但这是推测，**未证实**。

**性质判定**：结论方向**不变**（用实测 F=120 复算是 +1,328 / +8,448，都远大于 0，「保留 Verifier 也安全」这个判断依然成立），但**表里三行的 slack 有两个是错的，而且错得不一致**。这是「同一错数三处一致 ≠ 正确」的更坏版本——**三处连一致都做不到**。三行共用一套说辞，所以三层错误一起通过了对读。

**为什么本轮没改**

`299` 是**已归档的交付文档**（`6b32684` 已提交）。改它要连带改 `FROZEN-BASELINE.md` 的引用（若有）、并在 git 上产生一次「订正」提交。本轮任务是交接文档，擅自动已归档文档会打乱别人手上的引用。

**做之前必须先解决什么**

- 先定「入口帧 F」到底报哪个口径：`rsp_alloc()` 的 **120 B**（只算真正下移 RSP 的字节，`check_stack_frame_budget.py:156` 的算法），还是「路径和」（`298 §5.3` 要求 `F(dc) + F(RbMsgGetStats) ≤ 512 B`）。**两者不能混在同一列**，也不能拿路径和去和单帧预算做减法。
- 再查 320 / 352 这两个数从哪来。如果是「入口帧 + 第一层被调帧」，那它就不是 `slack(F)` 公式里的 F——那个公式的 F 是**本函数自己的帧**，下游消耗全在 D 里。**混用会让 slack 重复扣减**。
- 重算整张表，并把 `D_OFF` 定死（文档写 2,640，第 3 行反解需要 2,672 才对得上 8,216）。`298`:`271` 的原始推法是 `9,760 − 7,120 = 2,640`，这条本身是可检的；要改就得连带改 `298`。
- **改动必须在文档里留订正块，不能静默改数字**——静默改会让「谁在什么时候把 1,128 改成 1,328」无从追溯，正是 `PROBLEM-HISTORY.md §4.4` 那类假锚的形态。

> **本条对本轮结论的影响**：无。0x7F 只能写「未复现」，本来就不依赖这张表的精确值。

### M-3 第三类卷 `IsAttached && Stream==NULL` 不在任何重建扫描里
