# 108 · 重建窗引导期 IO 设计（两道闸门重触的前置设计）

> 2026-11-09 深夜 · 107 批 0x7E→0x7B 事故的设计层结论。本文档是 rbio.c:1394/:1452 两道「红线禁改」闸门未来任何重触的**前置条件**——先有此设计评审，再谈改代码。

## 1. 事故教训（为什么要这个文档）

107 批尝试解除两门当日即 0x7E（池堆腐坏）→ 0x7B（引导卷 IO 失败）。根因：**崩溃脏态重启会走进重建窗，而引导卷 IO（NTFS 日志/元数据写、分页读）会穿过透传路径**——卸载/重建窗内的 flush 与异步化在引导期与卷栈存在致死交互。96 号「红线禁改」的真正含义：**不是这两处代码不许动，而是「重建窗+引导期」场景的设计没做完之前不许动**。

## 2. 引导期约束枚举（设计输入）

| 约束 | 内容 | 来源 |
|---|---|---|
| B1 | BOOT_START 过滤器在卷栈挂载早期即绑定，启动卷的分页 IO 可在 DISPATCH 到达 | MM 路径 |
| B2 | NTFS 日志/元数据写在引导期是**同步关键**——完成时间不可被推迟到任意 WorkItem | 0x7B 实测 |
| B3 | 崩溃脏态重启 → SafeMode/重建窗可在引导期进入 | 0x7B 现场 |
| B4 | 重建窗内流处于换装中：持 stripe ERESOURCE 的 flush 禁止（96 锁序） | 96 号 |
| B5 | ExQueueWorkItem 延迟完成=引导期致命（B2） | 0x7B 实测 |

## 3. 现行闸门语义（107 回滚后，为什么正确）

| 路径 | 窗内行为 | 残余风险 |
|---|---|---|
| READ | 不刷脏直接读盘（!Unloading 门） | 毫秒级陈旧读（仅回写卷+窗内+透传读三重组合） |
| WRITE PASSIVE | 内联 flush+失效+同步前转（DATA-10 纪律） | 无 |
| WRITE DISPATCH | 直接前转，**不失效** | P0-1 旧盖新窗（DISPATCH+窗内+回写卷组合，登记不扩） |

现行设计在 B1-B5 下**是正确**的：它选择「宁可陈旧/旧盖新（有界、罕见），绝不挂死引导」。

## 4. 未来安全设计（闭合两个残窗的条件）

### 4.1 WRITE DISPATCH 残窗（P0-1）——「世代闸 + 异步维护」设计

关键洞察：**前转必须同步（B2），但缓存维护不必同步**。

```
DISPATCH 窗内透传写:
  1) rb_stream_bump_view_range(stream, off, len)   // 世代闸：原子、任意 IRQL
     —— 立即封死旧副本的合法服务路径（[FIX 2026-11-06 视图世代门控] 机制复用）
  2) 排队 PASSIVE 维护作业（RB2 池）：{ flush 范围 → drop 视图 }
     —— 脏数据在异步 flush 前由世代闸保护，不被服务也不被丢弃
  3) 同步前转写（立即落盘）                          // 不变
```

- 脏数据安全：世代闸保证 flush 完成前旧脏块不会被 serve；flush 完成后才 drop——F9「先刷后丢」纪律在异步作业内完整保留。
- 无 WorkItem 前转推迟：B2 满足。
- 依赖项：`rb_stream_bump_view_range`（按范围的世代失效原语，当前只有全流 gen）——需新增，纯原子操作，任意 IRQL 合法。
- 交付纪律：该设计须先在 core 域建模测试（test_wsconc 扩展：DISPATCH 窗写+世代闸+异步维护的全序验证），再上内核。

### 4.2 READ 陈旧读窗——「脏覆盖读」设计

```
PASSIVE 窗内透传读（有脏、flush 被禁）:
  直接读盘 → 交集脏块用缓存内脏数据覆盖（read-your-writes 从缓存取）
```

- 前提：流在窗内仍可读（重建窗的旧流在换装前可读；换装后走世代闸全 MISS）。
- 若缓存路径本身不可用（池耗尽=透传真因）：维持现行为（接受陈旧窗口），登记不扩。

### 4.3 前置门槛（两项设计落地前，两门保持禁改）

1. `rb_stream_bump_view_range` 原语 + core 全序测试绿
2. Verifier（已武装）连续一周无池腐坏/无 stop
3. 重建窗与引导期互斥的运行时保证：`Recreating=1` 时若处于引导期（System 进程 + 无用户登录）→ 推迟重建到登录后（现有 Rb2Tick 机制可承载）

## 5. O-3（RbZombieReap）修复记录（107 批内已落码）

- 病灶：detach 超时路径入队无防重入（另一调用点有 RemoveDone CAS）→ 双入队 → 二次收割 → **IoDeleteDevice 双删** → 池腐坏 → 0xC0000096 野指令（10-24 双 0x7E Failure.Bucket=RAMBlockCache!RbZombieReap 实锤；10-25 Verifier 0xC4_31 OldIrql 花栈同族）。
- 修复：`RB_DEV_EXT.InZombie` 去重闸（QueueExt CAS 入队、Reap 成功归零）+ `Magic` 哨兵卫兵（失活条目纵深防御）。
- 验证：Verifier（已武装）+ 日常 REMOVE/detach 压力；核心套件回归。
