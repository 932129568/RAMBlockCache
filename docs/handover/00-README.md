## 0. 三十秒版本

这是一个 **Windows 卷块上层过滤驱动**（WDM，**不是 minifilter**，且**没有用 WDK**——用 nuget 包补的），
外加 WPF/WebView2 壳 + Web SPA + CLI。名字里的 `V10.4.3-build19` 是**历史遗留目录名**，不是发布版本，
版本号以 `src/common/version.h` 为准（当前 `10.4.1.19`）。

**当前现场状态**：驱动已签名并部署，`dist/` 与 `System32` 同为
`3C696E140F6EF8A0…` / 204,512 B，`Authenticode=Valid`，`Flags=0x0`（缓存特性全关），
`WriteBack=0`（回写关闭），`FilterArmed=0`，`D:` 是唯一加速卷。

**一句话说清现在能干什么、不能干什么**：
驱动**能挂载、能直写、读路径在压测下不崩**；但**缓存层一个字节都没生效**
（`Features\Flags=0`、L2 关闭、`.idx` 仅 4 B 头），所以**没有任何命中收益可宣称**。

## 1. 仓库里有什么（别按名字猜）

| 目录 | 真实内容 |
|---|---|

| `src/ui/` | WPF 壳（现在是 WebView2 容器）+ native-host（D3D/捕获）+ Web SPA |
| `deliverables/` | **256 份编号文档**。这是本项目的知识主体，不是附件 |

| `deliverables/tests/` | bench 判据的回归桩 |
| `docs/` | **面向使用者的手册**（构建/部署/签名/FAQ），与交接文档分开 |

| `archive/` | 历史归档，**不要引用其中的结论** |

### 最容易走错的地方

- **`deliverables/` 里的编号不是顺序读的**。新文档会**更正**旧文档（如 `297` 更正 `296`）。
  读任何一份前，先看它有没有被更晚的文档推翻。
- **`deliverables/FROZEN-BASELINE.md` 是判据与指纹的权威源**。它记载了 5 件冻结件的哈希、
  以及 13 条判据纪律（每一条都是踩坑换来的）。**动代码前先读它的 §六。**
- **`KNOWN_ISSUES.md`（178 KB）是历史清单**，最新有效内容在 `0-I` 节，更早的 `0-A`…`0-H`
  中「当前发布基线」已被取代。

## 4. 当前未闭环的硬阻断（详见 OPEN-ISSUES.md）

一句话：**缓存收益为零**。驱动挂载正常、直写正常、读路径不崩，
但 `Flags=0` 意味着 L1 的「命中」只有 47.78%（次数）/ 42.23%（字节），
且 L2 未启用 ⇒ **读路径的加速收益无法证明**。

`0x7F` 蓝屏**未复现**（2×900 MB 写负载、单机、单形态），
但**这不等于已修复**——Verifier 只覆盖 `RAMBlockCache.sys`，不覆盖全局。

**两个阻断之外，还有三条「文档自身出错」需要先知道**（都在 `OPEN-ISSUES.md`，
它们不影响结论方向，但会让你对着错误的数字做推理）：

| 编号 | 问题 | 一句话 |
|---|---|---|
| `H-4` | `299 §3.2` 的 slack 表三行互相矛盾 | 反解出的入口帧是 1,480 / **320** / **352**，而机器码实测是 **120** |
| `M-2` | `D-02` 这个编号被**两个不同缺陷**占用 | 引用 `D-02` 时必须带文档号，否则无人能判断指哪个 |
| `I-1` | 交接文档称 `Features` 里有 `L2Letter` / `L2SizeGB` | 现场**没有这两个值**，只有 `Flags=0` 和 `ExcludeDirs` |

## 5. 怎么把它跑起来（最短路径）

```powershell
# 1. 构建（唯一入口，别用 build_all.bat，那是归档的失效指令）
build\build.ps1 -Target core      # 编译 core 并跑回归
build\build.ps1 -Target driver    # 编译驱动（未签名）
build\build.ps1 -Target gates     # 跑全部门禁

# 2. 签名（需一次 UAC，由人双击）
deliverables\RB-sign-driver.cmd

# 3. 部署（需一次 UAC）
deliverables\RB-deploy-driver.cmd

# 4. 重启后验收（只读）
deliverables\RB-postreboot-verify.cmd   # 要 PASS=9 FAIL=0
```

**必须用 pwsh 7**（`C:\Program Files\PowerShell\7\pwsh.exe`），用 5.1 会踩编码坑。

## 6. clone 之后的第一个坑（务必先读）

本仓库**没有 `.gitattributes`**，且 `core.autocrlf=true`。
后果：**clone 下来的文件字节与本文档记载的哈希不一致**。

具体说：`RB-write-load.ps1` 在工作区是 87,377 B（CRLF），但 Git 索引里存的是 85,958 B（LF）。
**这不是文件损坏，是仓库的既有特性。**

核哈希时的正确做法：
- 要么用 `FROZEN-BASELINE.md` 里的 **LF 归一化 SHA256** 列
- 要么先按需要转换行尾，再算

**不要拿 CRLF 口径的哈希去核 LF 口径的文件，然后得出「文件被改过」的结论。**

## 7. 需要立刻知道的三条「反直觉」事实

1. **`(7,9)` 这个状态组合在真机上几乎不可观测**，不是因为它不可达，而是因为它的条件是
   **「本引导零成功 attach」**——本机 8 个卷，只要 1 个成功，条件就永久不成立。
   这是**全局条件，不是单点概率**。

2. **`WHY_DIRTY(1)` 有三种完全不同的含义**（刷完有脏页 / 根本没引擎 / 2s 争用超时跳过）。
   看到 `why=1` 就断言「有脏数据没刷」是错的——**`(1,7)` 恰恰是「A4-d 说不出话」的情形**，
   用它当首证等于**用否证当证**。

3. **`ext->Stream` 的写入点是 5 处**（2 建 + 3 置 NULL），不是 2 处。
   报成 2 处后推出的「Stream 非 NULL ⇒ 票为 1」**结论恰好正确**，
   但理由是错的——**「结论对、理由错」比结论错更难发现**。

## 8. 文档维护约定

- 交接文档放 `docs/handover/`，**不要**混进 `docs/`（那是用户手册）。
- 新增技术文档仍放 `deliverables/<编号>-<主题>-<日期>.md`，编号递增，**Gate22 会校验编号连续性**。
- 改了任何判据/阈值，**必须同步 `FROZEN-BASELINE.md` 的对应条款**，否则下一个接手的人会按旧口径判。
- 结论写「未复现 / 未验证 / 已证伪」，**不写「已修复」**，除非有真机证据且能复现验证条件。
