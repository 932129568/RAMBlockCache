## 1. A.1 数据面（`src/driver/rbL2.c`）

### 1.1 新增状态（`rbL2.c:59-63`）

```c
static PVOID   s_Idx; static ULONG s_Slots, s_Stamp;
/* [172/A.1] L2 失效世代：任何 drop 都先 ++s_Gen 再清条目（顺序不可换）。
 * RbL2Store 在拷贝前快照本值，入口/索引赋值前后三次复核——快照后发生过
 * drop 即判定"这份是要被失效的写前内容"并丢弃存储。无锁（见 RbL2DropRange）。 */
static volatile LONG64 s_Gen;
```

### 1.2 两个 drop 例程 + 世代读口（`rbL2.c:126-168`）

三条纪律写进了函数头注释（任务要求）：仅 PASSIVE 且卷已 attach、**不持任何 spinlock**、`off` 是卷内**字节**偏移。

```c
#define RB2_L2HASH_MUL  2654435761ull
static ULONG RbL2Hash(ULONG64 blk) { return (ULONG)((blk * RB2_L2HASH_MUL) % s_Slots); }

VOID RbL2DropRange(ULONG64 off, ULONG64 len)
{
    ULONG64 b, b0, b1, end; ULONG i, slots;
    if (len == 0) return;
    InterlockedIncrement64(&s_Gen);                /* ① 先 bump */
    slots = s_Slots;
    if (!s_Idx || !slots) return;
    end = (off > (ULONG64)-1 - len) ? (ULONG64)-1 : off + len;
    b0 = off >> 16; b1 = (end >> 16) + ((end & 0xFFFF) ? 1 : 0);
    if (b1 > slots) b1 = slots;
    for (b = b0; b < b1; b++) {
        i = (ULONG)((b * RB2_L2HASH_MUL) % slots);
        if (L2Idx()[i].Use && L2Idx()[i].Lba == (b << 16)) L2Idx()[i].Use = 0;
    }
}

VOID RbL2DropAll(VOID)
{
    InterlockedIncrement64(&s_Gen);
    if (s_Idx && s_Slots) RtlZeroMemory(s_Idx, (SIZE_T)s_Slots * sizeof(RB2_L2E));
}

ULONG64 RbL2Gen(VOID) { return (ULONG64)InterlockedOr64(&s_Gen, 0); }
```

### 1.3 与 167 §A.1 骨架的两处**有意**偏差（请重点复核）

1. **槽数一次快照 `slots = s_Slots`，循环里不再读 `s_Slots`。**
   167 骨架直接调 `RbL2Hash(b)`（内部 `% s_Slots`）。但 `RbL2DropRange` 不持
   `s_Ops`，而 `RbL2CloseIntEx` 会在末尾把 `s_Slots` 置 0（`rbL2.c:590`）——
   若并发 Close 恰好落在循环中间，`% 0` = **#DE 除零蓝屏**，比"多留一条陈旧条目"
   严重得多。改成局部快照后窗口消失，语义不变（同一哈希式）。
   为免哈希式子分叉，把乘数抽成 `RB2_L2HASH_MUL`，`RbL2Hash` 与新循环共用。
2. **`b1` 用 `(end>>16)+((end&0xFFFF)?1:0)` 而不是骨架的 `(off+len+0xFFFF)>>16`。**
   两者结果相同，但前者不会在 `off+len` 接近 2^64 时回绕。

**改后（3 行 + 注释）**
```c

    RbL2IdxLoad();                                 /* 重建内存索引（安全校验在探测时） */
```

崩溃/重启同理。只有 `RbL2IdxSave` 会重新写下 Magic。

### 2.3 `RbL2IdxSave` 改为返回 `BOOLEAN` 并导出

改动是 H5 的前置条件，函数体逻辑不变，只加了三处：PASSIVE 守卫、`!s_IdxFile||!s_Idx||!s_Slots`
返回 **TRUE**（见下）、`ok` 汇总两次 `ZwWriteFile` 的返回值。

> 为什么"L2 未开"返回 TRUE：默认 `Features\L2Letter=0` ⇒ L2 永久不开 ⇒ `s_IdxFile==NULL`。
> 若此时返回 FALSE，`rbmsg.c` 的 H5 就永远不会写 `LastCleanShutdown=1`，
> **默认配置的每台机器每次开机都进安全模式**——把 L2 的状态传染给了引擎。
> 语义定为"本会话没有 L2 索引需要证明 = 已证明"。

`rbL2.c:576` 的 `if (s_File && Persist) RbL2IdxSave();` **一字未动**（返回值被忽略），
符合"保持原样"。

## 6. 三锚点：**未同步**（附理由与正确做法）

任务要求"同步三个 sys 锚点"，但核对后**没有改**，理由是可验证的：

1. 三个锚点的语义是**已签名部署件**的哈希，不是编译产物：
   `src/scripts/sync_anchors.ps1` 开头就有 fail-closed 守卫
   `if ($sig.Status -ne "Valid") { throw ... REFUSING to anchor an unsigned/invalid binary }`。
2. 当前锚点值 `75d02eba…`（= `dist/RAMBlockCache.sys`，193352 B 已签名版）与
   `dist` 三处**互相一致**，`check_signature` 也全绿（§7.2）。
   若把锚点改成新的未签名 `9956351f…`，`deploy.ps1` 会拿"已签名 dist"去比"未签名锚点"
   → 部署路径直接 fail-closed，等于把可部署状态改坏。
3. 第三锚点**已经不是 `README.txt`**：仓库根 `README.txt` 不存在（`140 B3` 起改为
   打包期由 `README.payload.template.txt` 的 `{{SYS_SHA256}}` 生成），
   `check_signature.ps1:94-98` 的第三锚点是 `dist\RAMBlockCache.sys.sha256` 边车。

**结论**：锚点同步是**签名之后**的步骤，不能在"未签名构建"阶段做。
用户提权后应运行（按顺序）：

1. `deliverables\RB-sign-deploy-150.cmd` —— 用测试签名证书签 `src\driver\x64\Release\RAMBlockCache.sys`（若沿用旧流程）并落到 `dist\`；
2. `powershell -ExecutionPolicy Bypass -File src\scripts\sync_anchors.ps1` —— 校验签名链 **Valid** 后，把 `75d02eba…` 改成新签名件哈希，同时改 `deploy.ps1` / `verify_deploy_signature.ps1` 两处 `DefaultExpectedSha256`（`dist` 边车由签名步骤写）；
3. `powershell -ExecutionPolicy Bypass -File src\scripts\deploy.ps1` —— 真正部署（内部会再验一次签名 + 锚点）。

## 9. 遗留 / 已知问题（本次明确不处理）

### 9.1 `s_Gen` 是否需要跨 `RbL2Close` / `RbL2LazyOpenInt` 重置？
**不该重置，保持单调递增。** 理由：`s_Gen` 的作用是"discriminate 快照之后是否发生过
drop"。若在 Close/重开时清零，一个在 Close 之前快照的作业（`gen=旧值`）与重开后
新会话的 `gen=0` 可能**偶然相等**，守卫就会放行一份跨会话的写前内容。
单调不回绕（LONG64，实际不可能回绕）是正确语义，因此**不重置**。
唯一需要注意的是：`s_Gen` 是 file-static，跨 attach/detach 也保持——这符合预期
（drop 是全局事实，与容器开合无关）。

### 9.2 `RB2_L2IDX_MAX = 262144` 与默认 32GB 的 `s_Slots` 矛盾（**已知，未修**）
`RB2_L2REC = 24 + 65536 = 65560`，32GB ⇒ `s_Slots = 32GiB / 65560 = 524096`。
而 `RbL2IdxLoad` 有整份拒绝条件 `h.Count > RB2_L2IDX_MAX(262144)`。
即：**索引条目数一旦超过 262144（约容量的 50%），整份索引被拒 ⇒ 冷启动**。
A.2 之后这个行为不再是"偶发"，而是可预期的：索引只在干净关机落盘，
下次开机整份拒绝等价于一次冷启动。本次按任务要求**不处理**，记为已知问题。
风险方向：安全（只丢命中率），不丢数据。

### 9.3 `RbL2DropRange` 与 `RbL2Close` 的 `s_Idx` 生命周期（本次新增的窄窗口）
`DropRange` 不持 `s_Ops`，而 `RbL2CloseIntEx` 会在排空 `s_Ops` 后 free `s_Idx`。
若 `DropRange` 恰好在 `s_Idx` 被摘走前读到非空指针、在被 free 后解引用，就是 UAF。
本次按 167 §A.1 的"不加锁"约束**未处理**（只把 `s_Slots` 归零导致的 **#DE** 用局部
快照消掉了，代价为零）。建议的后续最小修法（**未实现**）：`DropRange` 入口/出口
`InterlockedIncrement/Decrement(&s_Ops)` —— 那是引用计数不是锁，`Close` 已有 5s 有界
排空；但这会改变 167 已评审的形状，需单独评审。
> 现状评估：窗口极窄（Close 只在 REFRESH/flags-off/卸载/降级路径），且
> `s_Idx` 用 `InterlockedExchangePointer` 先摘后 free；`DropRange` 单次循环是纯内存操作。
> 仍需在 Driver Verifier（Special Pool + Pool Tracking）下复验。

### 9.4 `s_IdxDirty` 变成 write-only
删掉周期落盘后，`rbL2.c` 里只有 `RbL2Store` 写它、没有读者。保留是因为
"只做加法"+ 未来诊断可能要用；它不影响任何行为（纯内存写）。

### 9.5 `LastCleanShutdown` 复用（167 §8.4 的建议未实现）
`Clean` 标记仍与引擎的 SafeMode/BootFailCount 共用。167 建议另开 `L2CleanGen` 键，
本次按"不扩大范围"未做。当前语义是保守的：索引保存失败只是**不写** Clean，
不会把引擎的状态判错方向。

### 9.6 失效放大（167 §A.5 的代价，已接受）
4K 随机写 → 丢弃所在 64KB 块 = **16× 失效放大**；NTFS 日志/USN 区常年为空。
H2 对每个写块无条件 drop（含写失败块），进一步放大了这一点——正确性优先。

### 9.7 构建脚本的 PowerShell 5.1 stderr 缺陷（§7.4）
`-Target core` 在 5.1 下无法一次跑完（`NativeCommandError` + `EAP=Stop`）。
建议后续改成 `2>&1 | Out-File` 或 `Start-Process -RedirectStandardError`，本次未动。
